二、论文问题与主张范围

研究问题：
在单 GPU、固定 KV 内存预算的连续批处理推理中，能否利用已知的输出上限和调度器可以兑现的执行进度，更准确地界定未来 KV 峰值，使等待请求更早准入，同时避免把收益转移为 decode 长停顿、额外抢占或长请求饥饿？

默认运行域：原生 vLLM、单 GPU、同步非 speculative decode、无 host offload。先沿用既有 OLMoE/vLLM 版本复核，再选择实际可运行的第二模型。具体版本、GPU、KV 字节数和预算均以现场证据为准。

定义在线可见量：prompt 长度、已计算/已输出 token 数、硬输出上限、请求 phase、物理 KV ownership、native reservations、序列槽和调度 token 预算。真实未来 EOS、未来路由、未来实际输出长度不属于在线信息。

必须区分：
- memory feasibility：块是否装得下；
- progress feasibility：已有请求是否能够按承诺推进；
- service utility：提前准入是否改善完整请求结果。

若机制对 dense/MoE 同样适用，定位为通用 LLM serving，在 MoE 上验证。没有独立因果证据时，不使用“MoE 专属调度”的标题。

三、仅评估三个相关候选，最终选择一个主机制

M0｜FIFO 退休容量包络：当前 Primary
动作：保持队列顺序，利用 resident 的硬 cap 与进度计算全程峰值，放宽总最大占用求和的准入限制。
假说：自然运行中存在显著保守预留损失；可兑现的 decode 推进条件使额外准入安全，并改善请求结果。
首个实验：完成既有 fresh 六格，随后在健康的自然生成任务上对照 native、完整上界 FIFO、M0。
失败边界：额外准入稀少；只在几乎固定长度的退化输出上有效；收益被控制开销/排队/输出变化抵消；或与同信息集强简单规则等价。

M1｜混合 prefill/decode 阶段的容量包络：优先条件扩展
问题：当前要求所有 resident 都是纯 decoder 时才放宽准入，可能在持续到达、混合 prefill/decode 时过于保守。
最小动作：将 resident 分为受保护 decoder 集 D 与仍在 prefill 的集 P。D 使用退休包络；P 及新请求保留完整上界。旧 decoder 获得必要的每步推进额度，余下 token 预算用于 prefill。
示意条件：max_k E_D(k) + Σ(P 的完整上界) + 新准入上界 ≤ 可用物理容量。此式必须按实际 allocator、在途预留和计数边界推导，不能直接当作正确实现。
特别要求：已有准入形成的进度承诺不能因下一步重分 D/P 而丢失；P→D 的转换要有明确边界；protected decode 与最小 prefill 额度须共同可行，避免 prefill 饥饿。
最便宜的探针：先在已有日志/轻量诊断中量化“仅因存在 prefill 而被阻止、但该混合上界仍可行”的状态质量；只计结构机会，不能离线宣布加速。若自然机会存在，再做 M0 vs M1 的相同 FIFO、相同预算原生小实验。
独立贡献条件：解决真实频繁的可执行性障碍，且请求收益超过 M0 和普通 decode-first/chunked-prefill 规则。仅代数紧化或普通优先级规则不自动构成创新。

M2｜保留队头准入机会的有限回填：条件备线
问题：容量条件满足不了队头，但后继小请求可装入；直接 first-fit 已有长请求受损证据。
最小动作：仅在能保留队头的容量与执行进度预约时允许后继回填，不使用真实剩余输出长度。
首先证明：基于硬 cap 的未来可行轮次是有效上界；后继加入后，该预约仍可兑现，且不会消费队头所需的 prefill token 服务。调度轮次保证不等于墙钟 TTFT 保证，后者需要计入 batch 扩大造成的每轮成本。
探针：只读统计 M0 中的实际 HoL 等待和可回填质量，再构造最小状态反例区分普通 first-fit、aging、保守回填与所提动作。只有存在有意义且可执行的差异才实现一个变体。
必须比较经典 EASY/保守 backfilling 的思想，不能把“保留队头再回填”命名为新算法。不再无条件重跑已失败 first-fit；仅在新实验确需机制负控且已预声明时使用它。

候选排序初值：M0 → 有自然证据时 M1；M2 为备线。M1 与 M2 不同时进入控制器实现。事件驱动更新、减少 Python 扫描等属于实现优化，不单独包装成第四个研究 idea。

每个候选给一张短卡：问题/可见状态/动作/保证/最强基线/自然机会/完整成本/最便宜证伪实验。若最终选 M1，M0 必须保留为直接对照，不能只与 native 比。

对 WAIT/Nested WAIT 和 CacheOPT 都做机制级分析。至少实现最直接的可比近邻；如果另一篇覆盖独立的重要动作，也必须补上相应基线。标明官方复现、忠实移植、组件实现的区别。无法完整复现时明确缺口，禁止宣称全面超过原系统。

五、系统设计与正确性

先做最小原生适配：observe state → 计算容量/进度证书 → 选择 FIFO 准入前缀 → native validate/allocate → 执行 → 核对进度/回收 → 更新证书。

必须给出：
1. 块粒度峰值推导，计入触及 cap 的最后一次分配及释放顺序；检查初始点和退休端点是否足够。原生保留空间只扣一次，不混淆逻辑预留与实际分配。
2. 在明确条件下的安全性和推进论证，以及最小反例：token budget 不足、decoder 被排除、prefill 插入、提前 EOS、取消请求。前缀共享/异步/speculative 不支持就写明，不扩张保证。
3. 已借用未来释放容量之后的失效处理。仅“切回 full-bound”不足以偿还已有容量承诺；至少保留已有推进义务、禁止新增风险准入，并给出安全 drain 条件。若只能 abort，定位为受限实验原型，失败请求必须计入评估。
4. 诊断与性能路径分开；基线共享同样的必要记录和正确性修复。保存/加载/重算、决策和同步都按真实暴露成本入账。
5. 决策 p50/p95/p99、CPU 总时长与额外内存。只有它确实占据可测成本后，才做事件端点缓存或增量更新；新旧实现逐状态动作一致、端到端收益分别报告。

规模和时长：先以 128 请求做开发，确认从每 episode 至少 512 请求起评估时间成本；另选一档近容量负载做足够长的持续开放到达，观察队列是否稳定。若达不到尾部估计所需样本，不主张稳定 P99。时长由预热、到达、完整 drain 和稳定性共同决定，不把短 burst 叫稳态。

E5｜消融与机制解释
至少比较：
① 完整上界 FIFO；
② 相同 decoder 服务保护下的完整上界 FIFO；
③ 退休包络 M0；
④ 若选 M1，再加混合阶段包络。
共享队列顺序、计时和日志，排除“只有 proposed 多了 decode-first”这一混淆。取消保护导致不安全的版本只能做 shadow/受控反例，不列为有效性能竞争者。
机制链记录：少预留多少逻辑块 → 额外准入多少真实请求 → 排队/TTFT 改变 → decode 与重算代价 → 完整请求收益。不能把额外准入事件当独立重复或把预留差当 HBM 实际释放。

E6｜敏感性与公平性，采用窄矩阵
以一个模型、两类任务、近容量负载为锚点，分别改变一个因素：
- 可用 KV：原配置的约 0.75/1.0/1.25 倍，先确认物理可容纳；固定权重、dtype 和其它 GPU 使用。它是 KV budget 敏感性，不等于验证不同显卡。
- output cap：例如 256/1024/2048 及异质混合，满足模型上下文限制；同一 cell 各策略 cap 完全一致。不同 cap 的性能不能脱离质量/截断率直接比较。
- prompt：短、长、混合；prefill/decode 占比由真实任务产生，并保留分布。
- arrivals：Poisson 与固定 burst trace；均匀到达仅作对照。
不做全因子笛卡尔积。优先测能击穿主张的边界。每个重要点进行独立重复。
报告长/短请求各自 TTFT、flow、等待、最大生成 gap、被绕过次数及最差退化；均值改善不能掩盖一个长请求被饿死。若 M2 入选，队头预约兑现率与超期代价是必测项。

E7｜部署成本与正确性边界
低负载负控、无内存压力负控、early EOS、取消、跨块增长、预算不足及受保护请求进度中断。小状态穷举检查峰值公式；有针对性的 runtime 事件验证原生语义；不扩展成全面覆盖率项目。
分别测朴素与优化后的决策成本及完整服务差异。新增同步或 logging 税不能只在 proposed 中去掉。单卡结论不外推 EP、A2A、跨实例迁移。

七、指标与统计合同

主指标：冻结阈值下、全部外部到达请求的联合 goodput。
现有 finite episode 沿用 qualified requests / 整个 episode（含 drain）的秒数；持续服务另以固定测量到达窗口定义请求集合和时间分母，等待其结局或按预声明超时计失败，不能与旧 episode 分母混用。

现有 20 s TTFT / 4 s host-return gap 仅是历史实验主点，不冒充业务 SLO。新真实任务可基于独立开发数据和任务需求预先设定阈值，所有策略相同。报告固定主点、阈值附近曲线和宽区间前沿，不能事后选择最有利门槛。

并列指标：TTFT、到达至完成 flow、每请求最大 gap、输出 token/s、完成率、排队长度、抢占/重算、实际 KV 峰值、策略开销、输出长度/EOS 与任务质量。gap 全部不约束时，明确联合 goodput 实际退化成 TTFT 判据，不能夸大双目标改善。

host 一次返回多个 token 时，只能报告可观测返回 gap；没有真实逐 token 时间戳，就不称其为逐 token ITL。失败、未完成、拒绝、无输出和到达后仍排队的请求全部进入口径。不同策略自然输出分叉时，不把 tokens/s 直接称为等工作量加速。

统计单位为独立 episode。使用配对差/比及按 episode 的置信区间，说明小样本限制；不能用 token 数、128 个耦合请求或 20 个阈值冒充独立重复。预声明主要比较，辅助切片不冒充确认性检验。

继续/停止条件需在实际运行前冻结。一个可用的工程预算例子是：goodput 有有意义净增量，同时 tokens/s 损失不超过约 3%、平均 flow 增幅不超过约 5%；如要沿用，说明适用域并以不确定性判断。此预算只是研究选择，绝非 CCF C 录用门槛。安全性、质量不合格时不能用性能补偿；实验无效与有效负结果分开处理。

八、资源、论文组织和投稿目标

先用资格 run 测得单格总成本 t，包括启动、预热、服务和 drain；按 run 数×t 加上约 20% 失败排查余量，估算 GPU 小时。300 格若平均每格 6 分钟，仅主矩阵即约 30 GPU 小时；这只是算例，不是已测预算。加上基线移植、消融与敏感性后再申请/使用实际授权额度。不要把旧 checkpoint 的“100 小时”自动视为新授权。
