# 固定 Q=2048 的准入余量结果

完整六臂均为 COMPLETE，预算与准入 cap 检查全部通过。**cap10 是减少输出停顿的取舍，不是全面 GO**：相对同组 cap16，两次均值的 wall **+0.57%**、mean flow **+2.25%**、实际 token/s **+4.07%**，每次运行最坏 gap 的均值从 **0.9213 降至 0.3351 s**。cap8 的 wall **+10.44%**、mean flow **+8.94%**，未成为更强的完整请求基线。本报告直接摘录[既有完整主分析](results_headroom_r01/metrics.json)，没有另算或选择有利重复。

本轮只改变 native admission cap；测量 Q=2048、expert cap24、GPU KV 1 GiB、engine capacity4096、共同 warmup512/固定32输出均不变。使用已见 source32..47、完整 prompt、同时到达、自然 EOS/max512；六臂同机按 16/10/8/8/10/16 顺序运行。不能与上一自然组的绝对时间拼成跨机器配对。

“最坏 gap”是每次运行所有请求相邻输出间隔的最大值，不是 P95。先为每请求取最大 gap，再取请求间 P95、最后平均两次的结果，cap16/10/8 分别为 **0.6342/0.3351/0.3739 s**；两类指标在 cap10/8 恰好相同不代表定义相同。Mean TTFT 分别为 **3.2732/3.3616/5.6871 s**。cap10 两次配对中的 wall/flow 改善方向并不一致，因此不称稳定的完整请求加速。

cap16 每次有 2 次原生抢占；cap10/8 均无原生抢占。实际 scheduled prefill 超出原始 11,115 prompt tokens 的量分别为 **1,386/0/0**，只代表 observed prompt reprocessing excess，不是所有重算计数。无抢占并未自动产生更低 wall/flow；cap10 的专家搬运还比 cap16 多 **7.30%**，不能仅凭少重处理解释净收益。

每个 cell 都是 **16/16 EOS 完成、0 cap 截断、8/16 正确**。同 cap 的两次输出序列均 16/16 相同；cap16 与 cap10 仅 7/16 完整输出相同。cap10 输出 token 数比 cap16 多 **4.64%**，其实际 token/s 上升不能表述为等工作量加速，完成请求/s 反而下降约 **0.55%**。16 题得分相同不证明质量等价；所有答案、输出分歧和自然长度均留在 metrics。单模型、人工 expert cap24、已见小样本和两次重复仍不足以形成论文级结论。
