# 自然完成确认：2048 暂作为强静态 baseline

六臂完整结果支持将 scheduler token budget **2048** 暂设为当前运行域的强静态 baseline。相对 512，两次重复的平均 episode wall 降低 **12.07%**，平均 flow 降低 **14.77%**，实际输出 token/s 提高 **10.07%**。这是已有 token-budget 动作在当前 MoE 分页引擎中的工程优化候选，不是新算法，也不是等工作量加速。

证据为 [完整 metrics.json](results_natural_r01/metrics.json)、其中列出的六个原始 capture，以及 [分析脚本](analyze_natural.py)。全组状态为 COMPLETE，六臂完成和预算检查均通过；没有使用 partial 结果或选择最快重复。[预声明实验](NATURAL_EXPERIMENT.md)规定顺序为 512/2048/4096/4096/2048/512，每臂 fresh engine；engine capacity 统一 4096，warmup budget 统一 512，使用旧 train16 的固定 32-token warmup。测量使用新 GSM8K source32..47 的完整提示、16 请求同时到达、greedy、EOS 自然停止，输出上限 512；expert cap24、KV 1 GiB、native admission cap16。

|---:|---:|---:|---:|---:|---:|---:|---:|

三组预算两两比较的两次均值变化如下；负的 wall/flow 变化和正的 token/s 变化表示观察指标改善。

| 比较 | Episode wall | Mean flow | 实际 token/s |
|---|---:|---:|---:|
| 2048 相对 512 | −12.07% | −14.77% | +10.07% |
| 4096 相对 512 | −9.01% | −6.16% | +4.54% |
| 4096 相对 2048 | +3.48% | +10.10% | −5.03% |

2048 相对对应的两次 512 对照，wall 分别降低 11.05%/13.09%，mean flow 降低 13.68%/15.85%，方向一致。4096 的第二次 wall 为 20.774 s，不能只用第一次的 18.190 s 代表该预算；第二次 mean flow 相对对应 512 **增加 1.11%**，实际 token/s 降低 2.06%。4096 相对 2048 的两次 mean flow 分别增加 0.23%/20.15%。一组六臂不能确定这次计时变化的原因，也不支持随预算增加就单调改善的结论。

尾延迟有不同口径，必须分开解读。每个 cell 先取全部请求、全部相邻输出 token 间隔中的**单个最大值**，再平均两次结果，512→2048 是 **2.584→0.846 s**；这不是 P95，也不是每请求最大值的均值。表中的“每请求最大 ITL 的 P95”则先为每个请求取最大相邻 token 间隔，再对 16 个最大值取 P95，最后平均两次 cell，结果为 **0.847→0.580 s**。与此同时，全部 token 间隔合并后的 cell ITL P95 为 **0.2018→0.2077 s（+2.93%）**，每请求最大间隔的均值为 **0.383→0.398 s（+3.95%）**。因此不能写成所有间隔指标均改善。所有 ITL 都是 host-observed；以上间隔均不包含 TTFT。

六臂都为 **16 个 EOS stop、0 个 length cap**，固定历史最后数字抽取规则均得到 **8/16**；正确的是同八题：source32、33、34、35、36、40、42、45。512 与 2048 只有 **11/16** 请求的完整输出 token 序列相同，抽取答案 15/16 相同；512 与 4096 完整输出相同 6/16，2048 与 4096 为 8/16。全部输出文本、token IDs、抽取答案和逐请求得分保存在 metrics 中，错误题与输出分歧没有剔除。512→2048 的实际输出量为 **1491→1443（−3.22%）**，所以 episode wall 差不能解释为等工作量加速；同八题正确也不足以证明质量等价，16 题仅能检查明显质量损失。

分页观测与抢占同样保留。原始 prompt 总数是 11,115 tokens；512/2048/4096 的实际 scheduler prefill tokens 分别为 11,841/12,501/12,547，差值分别为 **726/1,386/1,432**，两次重复各自一致。这些差值只称 **observed prompt reprocessing excess**，不是全部重算量。原生抢占次数分别为 1/2/2；raw 中 `total_recomputed_tokens=0` 仅来自负 computed-token 调整的局部计数，不能据此声称没有重算。测量段实际 weight copy 为 733.647/614.675/586.376 GB（十进制），group 数为 6,177/5,510/5,086。2048 较少搬运和较少 group 是实测关联；预算同时改变 batch、自然输出和后续路由，不能把全部请求收益因果归于单一搬运项。

结论止于当前单模型、16 道题、两次重复的 native 请求实验。OLMoE 可以全 resident，当前 cap24 是人工限制出的分页运行域；尚未证明自然超显存场景、其他模型、负载或服务 SLO 下同样成立。Sarathi-Serve 已有按 TBT 约束选择 token budget 的动作，本轮没有建立新的调度方法或论文级泛化证据。现阶段保留全部结果，将 **2048 作为后续比较必须面对的强静态 baseline**，不增加 controller，也不根据本组最快 cell 扩写机制解释。
