# 专家分页下的 KV 恢复成本交叉：可证伪模型

更新：下文为启动实验前的模型。CPU-KV现在已完成r01系统A/B与隔离r02，见`KV_RECOVERY_RESULTS.md`；r02减少重算及平均wall但恶化最长停顿，不能整体GO。后续只读诊断确认了一个data-ready后的尾块容量缺口，最小预留实验见`KV_RESERVE_EXPERIMENT.md`。开启已有swap、通用资源预留本身均不作为独立创新。

**状态与动作。** 固定当前强静态配置 Q=2048、native cap16、expert cap24、GPU KV 1 GiB、完整提示及自然 EOS 契约。A 使用原生丢弃 KV 后重算，B 使用已有 native CPU-KV 保存/加载；两臂各自推进请求、KV、路由和输出，保留所有结果，不构建 controller。B 必须有实际保存、恢复命中及后续输出回执；配置开启但没有恢复动作不算有效 A/B。CPU-KV 当前 **UNRUN**。

**共享扫描与交叉条件。** 对重算臂某层的实际入口驻留集合 R，设重建 token 与同伴 token 的专家集合分别为 H、P，每专家大小 w。固定这一次已观测路由，可定义未被同伴摊销的扫描量：

`δD_expert = w × (|(H∪P)\R| − |P\R|)`。

同伴 prefill 已激活近全专家时，这一增量可能很小；独立重算则可能新增一轮扫描。它只是同一调用内的共享诊断，不能用不同策略的未来路由相减来制造反事实，也不能把整步数 GB 都归给某个恢复请求。后续专家驻留污染可能另加成本。

候选交叉条件是：**重算引起的完整增量暴露成本 > 保存＋恢复的完整增量暴露成本**。左侧含重建计算、未共享专家加载及后续缓存影响；右侧含实际保存、恢复、CPU/元数据开销及与专家传输的资源竞争。若 connector 提前或持续保存，要计入所有请求、包括从未抢占者的保存成本，不能只计受益请求的约 100 MB 恢复。字节量、CUDA copy span 均不能直接代替暴露延迟。

**请求收益与资源约束。** 已有最长 gap 主要发生在重新调度前，因此便宜恢复不自动缩短缺席。逐请求分开记录：抢占→重新调度的缺席、重新调度→新输出的恢复跨度，以及恢复后至下次抢占/完成的新输出数 Y。Y 检查恢复投入是否换来有效 decode 服务，不据此新造 victim 分数。全程只按互斥分账：`T_episode = Σ T_engine + T_outside_engine`；传输事件用于解释，不能再叠加到 engine wall。两臂须满足相同总 GPU 上限，并记录 GPU 峰值、pinned/总 CPU 内存、CPU 开销和双向传输；B 的额外资源不隐去。

**下一轮必测。** 保留每次实际抢占、保存/加载字节及命中、重建的 prompt 与已生成 token 数、实际专家加载和同伴共享量、缺席/恢复跨度/Y；全请求报告完成数、flow、TTFT、每请求最大 gap 分布、episode wall、实际 token/s、答案及输出差异。按已执行轨迹解释共享，不把自然输出不同的 wall 比当等工作量加速。即使恢复跨度下降，若缺席、保存开销或同伴损失抵消，总请求收益仍不成立。

**基线与唯一最弱假设。** 首先比较上述最强已跑静态 recompute 与静态 native swap；已有固定准入/预算结果继续作为简单策略参照。唯一待证假设是：**当前真实抢占恢复中，未被同伴摊销、且落在关键路径上的专家重扫，足以超过 CPU-KV 的完整增量成本。** 如果共享吞掉该项，或实际 B 的保存/加载及竞争抵消它，假设即失败；若仅减少恢复计算而未改善完整请求，系统优化主张也不成立。未发生 swap 或实现失败应记为未验证，不能判成本假设失败。

**贡献边界。** [WiSP §3.3/3.6](https://arxiv.org/html/2606.21868v1)已有专家/KV 联合分配和公共 host-swap；[FlexGen §4](https://arxiv.org/html/2303.06865v1)、[MoE-Lightning §4](https://arxiv.org/html/2411.11217v1)已联合计费权重/KV I/O。开启已有 swap 不构成创新。可能的残差只在实测的、随专家驻留和同伴摊销变化的恢复成本交叉边界，以及该边界能否改变完整请求结果；本页不声称首创或有效。
