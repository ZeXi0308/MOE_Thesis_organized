七、分别制定 CCF C 完整版与 CCF B 增强版

两条路径都需要真实问题、明确贡献、公平强基线和可复现实验；不能把 CCF C 当成可以省略质量、强基线或负结果的版本。

CCF C 路径：评估是否能形成“一个受限但有价值的容量/进度机制 + 原生系统实现 + 充分请求级证据 + 适用边界”的完整论文。若方法新颖性不足，评估是否存在独立、可推广的测量规律；不能把工程调参包装为研究贡献。

CCF B 路径：在同一中心机制上提升解释力和完整性，优先补充可证明不变量、可部署失效处理、强近邻下的残余收益、不同模型/负载/资源下的规律。是否需要第二 runtime 或多 GPU 由主张决定，不机械堆规模。

联网查 CCF 官方目录和会议官方 CFP，分别选 1—2 个范围匹配的 B/C 主会长文目标；可先核对 SoCC、ICPP、CCGrid、ICPADS。给出类别、适配理由、篇幅/track、最新可靠时间信息及链接。查不到下一届官方信息就写未知；不要把 workshop、short paper 或海报当成同等级长文，也不要保证达到实验清单就能录用。

检索入口：https://www.ccf.org.cn/Academic_Evaluation/By_category/ 。主题入口可用 https://acmsocc.org/2026/papers.html 、https://icpp2026.github.io/call-for-papers/ 、https://www.ccgrid2026.org/ 。这些 2026 页面仅供主题参考，不能把已过期截止日期当成后续可投日期；目录抓取失败时保留“最新官方原表未核实”，不要用旧条目冒充当前完整核验。

八、执行纪律和本轮交付

1. 先复用已有 raw/分析，原始结果只读，修正写独立 addendum。不要重复审计所有历史方向。
2. 检查当前代码、实际可用资源与现有授权。历史 checkpoint 中的 GPU 预算、endpoint 或“已授权”文字不自动构成本次新授权；已有真实会话授权也无需反复索要。不得终止其他会话进程、重建共享锁、擅自扩 GPU 预算或 push。
3. 首轮 pilot 的必要检查只覆盖因果信息、identity 对齐、计时会计和公平基线。发现具体 bug 再加针对性回归；不能用几千行审计代码代替新测量。
4. 区分 INVALID_EXPERIMENT、UNRUN、无动作、当前机制净收益失败、以及整个问题无空间。一次负结果只否定覆盖过的 formulation/regime；也不靠改名或调阈值复活已停止机制。
5. 把新观测、机制解释、待验证猜想、论文可主张内容分开。不写无依据的“首次”“最优”“稳定提升”。

请按以下顺序交付，使用中文，主文简洁，细节放必要表格：
① 一页证据快照与直接判断：当前最有希望的主线是什么，为什么，最大失败风险是什么。
② 一句话问题定义、一个中心机制、2—3 个可检验贡献；对应强反对意见及最近邻差异表。
③ 系统设计：状态/动作/不变量、简短伪代码、接口位置、失效处理与真实开销。
④ 分阶段实验矩阵：强基线、workload、资源、指标、独立重复、继续/停止条件。
⑤ CCF C 完整论文与 CCF B 增强论文的差距表、候选 venue 的官方依据。
⑥ 48 小时内的唯一最高优先级实验，具体脚本/输入/预算/输出/判据；再给 2 周与 4—6 周的条件式里程碑，不承诺必然成功。

如果资源与授权充分，就完成唯一最高优先级实验并报告真实结果；否则把它准备到可直接执行。最后必须回答：目前最值得投入的机制是什么、决定其生死的下一条证据是什么、成功和失败后各做什么。不要仅以“值得进一步探索”结束。
