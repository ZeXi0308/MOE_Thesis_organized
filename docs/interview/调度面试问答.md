**1. 你这项论文工作到底在解决什么问题？为什么需要做调度？**

我研究的是 MoE 在线推理中，请求什么时候开始执行，以及有限计算和 KV 容量怎样分配。新请求需要做 prefill，已有请求需要持续 decode；接纳太慢，新请求迟迟看不到首 token，接纳太多，又可能拖慢生成，甚至在 KV 不足时出现长暂停。因此目标是同时看首 token 等待、生成流畅度和完整请求吞吐。

模型已经部署在 GPU 上，我调整的是引擎内部的接纳、每步 token 预算和等待顺序。实验保持模型和执行后端可比，检查这些动作到底减少了等待，还是把等待转移给了另一类请求。Kubernetes 把 Pod 放到哪个节点，是另一层调度问题。

**2. 你之前的调度思路为什么没有继续作为主线？现在有什么变化？**

之前希望利用专家负载和局部执行特征，找到能改善请求结果的调度动作。后来需要先解决两个问题：局部专家执行节省是否真的进入完整请求，以及动作改变 batch 后，后续 route 是否还能沿用原来的观测。不能只看到专家更均衡，就认定端到端更快，也不能固定一条未来 route 来假装运行了不同策略。

当时研究关键路径的 RCBA 候选没有完成依赖和资源约束的定义，正式 Oracle 也没有运行，所以不能说它已经被实验全面否定。现在先把可执行的普通动作做扎实：固定并发、简单反馈、prefill 预算、首次入场排序和 KV 容量对照。已经看到的现象是，新反馈没有稳定超过已测最好静态并发，短 prompt 优先也主要体现为长短请求之间的代价转移。

**3. 队列、KV 和长短请求竞争在 Dense 模型里也有，你的 MoE 特点在哪里？**

这些基础问题确实不是 MoE 独有。MoE 还会把 token 分配给不同专家，同样数量的请求可能形成不同的专家工作量和执行形状；在跨卡专家并行时，还会涉及不同设备的负载和通信。但在 MoE 模型上测到性能差异，本身不能证明专家感知调度有独立贡献。

我会先用输入长度、并发、KV 和近期延迟建立简单基线，再问专家状态是否能解释剩余损害，以及调度动作能否实际减少它。只有预测更准还不够，需要在完整请求结果上稳定超过简单策略。目前还没有证明这项 MoE 独立增量。

**4. 这些能力 vLLM 本来就有，你自己具体实现了什么？**

我实现的是实验侧的调度动作接入和逐请求观测。在原生 scheduler 调用前后，接入新请求并发限制、排空后的实际 token 预算切换，以及从未执行过的等待请求排序；同时关联请求到达、首次调度、每步工作量、KV 状态、抢占和 token 返回时间，能够重算每个请求的等待与完成成本。

Paged KV、Attention 和 MoE 执行核、原生 running 调度及默认抢占重算都复用 vLLM。具体贡献是把动作是否生效、收益由谁获得、代价由谁承担测清楚。原生配置之间的性能差异，不能说成重写了引擎或自研算法的加速。

**5. 你把并发上限从 32 降到 16，为什么可能一点用都没有？**

我的非抢占动作只限制后续接纳，已经运行的请求继续执行。假设当前有 24 条请求，降到 16 后先停止补入新请求，等已有请求完成，运行数才会自然下降；不能直接只取前 16 条执行，把剩下的请求藏起来。

如果触发时没有等待请求，或者主要压力来自已经运行的请求，写入新上限当下就没有改变入场的机会。我的轨迹中出现过触发时 waiting 为零的情况，所以会分别记录决策时刻、第一次实际限制接纳的时刻，以及请求结果。先确认动作来不来得及，再讨论预测模型是否准确。

**6. 你具体怎么测 TTFT、TPOT 和请求完成时间？排队有没有漏算？**

TTFT 是首 token 接收时间减计划到达时间；请求延迟是完成时间减计划到达时间；请求平均 TPOT 是首末 token 的时间差除以输出 token 数减一，只有一个输出 token 时不计算这个平均值。这些时间使用同一 host 时钟，并保存提交、首次调度和每次 token 返回的时刻。

所有到期请求都提交给引擎，等待包括提交滞后、原生队列等待和实际执行。不能在客户端先限制并发，然后从进入引擎才开始计时。当前测量边界是同机进程内请求到返回，若要评价线上接口，还需要计入网络、网关和流式传输。

**7. 你的新反馈比旧反馈最多改善约 61%，为什么不把它当主要成果？**

因为旧反馈不是最强的简单基线。突发到达的四组对照中，新档位相对旧反馈的 goodput 改善约 44% 到 61%，但四组都没有超过同引擎已测的最好静态并发；平稳到达中出现过一次胜出，原样重复没有支持。这个结果只能说明旧规则有改进空间，不能证明动态反馈优于简单静态配置。

已测最好静态点是事后比较参照，用来判断还剩多少研究空间。真正评价部署策略时，要在校准数据上选定静态并发，再在独立到达序列上与动态策略比较；不能看完测试结果再挑一个最有利的静态点，声称自己实现了在线选择。

**8. 平均 TPOT 和 token 间隔的 P99 都很好，用户为什么还能卡住几秒？**

平均值会摊薄停顿；把所有 token 间隔混在一起计算 P99，也可能漏掉少数请求上的长暂停。长上下文的原生并发 32 实验中，混合所有 token 的间隔 P99 约为 28 毫秒，但两条请求仍分别出现约 2 秒和 4.5 秒的暂停。

所以我会同时看请求平均 TPOT、逐 token 间隔和每请求最大间隔，并明确分位数以 token 还是请求为统计单位。如果业务要求生成过程中不能停超过一秒，就应增加对应约束，不能拿平均 TPOT 达标替代这个要求。

**9. 短请求 TTFT 都降低了，为什么你还不认为调度优化成功？**

因为要看完整成本由谁承担。在三个已有完整原始数据的对照块中，短 prompt 优先相对 FCFS 让短请求 TTFT 分别下降约 14%、10%、9%，但长请求 TTFT 增加约 3%、6%、5%，长请求完成延迟的尾部也变差；整体平均完成延迟只改善约 2.52%、0.22%、0.03%。

这证明等待顺序确实改变了请求结果，但还没有形成稳定的整体收益。实验固定并发 8、每步 token 预算 1024、输出长度 128，混合输入长度为 128 和 2048；另外设置全短输入组，此时排序不应改变顺序，用来检查无动作条件下的运行变化。我随后增加了长请求被后来请求越过的次数限制，用真实对照检查能否减少这部分代价。

**10. 连续批处理是怎么做的？Orca 解决了什么问题？**

连续批处理把调度边界从“整批请求全部完成”缩小到“一轮模型执行完成”。每轮结束后，移除已经完成的请求，让未完成请求继续生成，再根据运行名额和 KV 容量加入等待请求。这样，一条长请求不会一直占着固定 batch 的位置，让其他位置空转。

Orca 的关键还包括 selective batching：适合合批的算子一起执行，对请求状态和长度相关的部分分别处理。连续批处理只提供动态调整请求集合的能力，并不自动决定谁先进入、允许多少并发，以及长请求是否会被饿死，这些仍然是调度策略要回答的问题。

**11. 你为什么把安全并发算成 29？这个值怎么得到，又有什么局限？**

我按引擎实际可用的 KV 块和请求声明的最大长度计算。那次可用池是 7677 块，每块容纳 16 个 token；每条请求最多有 3072 个输入 token 和 1024 个输出 token，所以最多需要 `ceil((3072 + 1024) / 16) = 256` 块，保守并发就是 `floor(7677 / 256) = 29`。

这种最大长度预留的思路在 Orca 中已经存在。它的好处是提前考虑后续生成的 KV 增长，代价是实际提前结束的请求会使预留偏保守。这个计算只适用于当次单组 KV 布局和相应配置，不能证明 29 是性能最优值；我的实验中，允许原生恢复的并发 32 吞吐反而更高，但少数请求出现了长暂停。

**12. PagedAttention 已经解决内存碎片了，为什么还会缺 KV？**

PagedAttention 把请求的逻辑 KV 划分成块，通过映射使用不必连续的物理块，减少连续分配带来的浪费，并支持共享 KV。它解决的是内存怎么组织和复用，没有增加物理显存总量。

请求生成时，逻辑长度继续增长，需要不断获得新的物理块。当所有活跃请求的需求超过可用池时，仍然需要限制接纳、回收状态或者暂停部分请求。我的原生 vLLM 实验允许通过抢占和重算恢复，所以要同时观察是否完成、恢复等待和逐请求最长 token 间隔，不能只看内存分配是否成功。

**13. Chunked prefill 具体怎么调度？为什么 Sarathi-Serve 切分 prefill，而你测到小预算反而变慢？**

它把一个长输入的 prefill 拆成多个步骤，每步只处理其中一段，再与已有请求的 decode 合批。这样可以限制长 prefill 占据单步的时间，让正在生成的请求更及时地获得下一次执行机会。Sarathi-Serve 就是围绕这种分块与合批来调节吞吐和 token 间隔。

例如，一个步骤的预算是 512 个 token，已有 6 条请求各生成一个 token，就先占 6 个预算；剩余预算可用于 prefill，但还必须满足请求并发名额和 KV 容量。预算太小会增加分块次数、重复读取与固定开销，也可能让新请求更晚拿到首 token。我的实验测到部分 ITL 改善而 TTFT、整批时间变差，说明预算要根据目标选择，并不是越小越好。

**14. TetriInfer 怎么按长度调度？和你的短 prompt 优先有什么区别？**

TetriInfer 把 prefill 和 decode 分开，并在 prefill 侧支持按到达顺序、短输入优先或长输入优先排序。它先限定本轮参与排序的请求窗口，再在窗口内排序，而不是让后来到达的短请求一直插到已有请求前面。它还利用预测的输出长度和实例资源状态选择 decode 实例。

我的动作更小：只按 prompt 长度重排原生等待队列里从未执行的请求，不打断已经开始的 prefill 和 decode。这能检查排序怎样分配等待成本，但持续流量下若没有窗口、等待时间提升优先级或租户配额，长请求仍可能一直被后来的短请求超过。

**15. FCFS、SJF、SRPT、MLFQ 有什么区别？LLM 服务适合直接用哪一种？**

FCFS 按到达顺序执行，简单但可能让短请求等在长请求后面。SJF 优先处理总服务时间较短的请求；SRPT 优先处理剩余服务时间较短的请求，并允许抢占。MLFQ 不要求提前知道完整执行时长，而是根据请求已经获得的执行时间，在不同优先级队列之间移动。

LLM 通常知道输入长度，却不知道实际输出长度，而且 batch 大小会改变每个 token 的执行成本。因此，按 prompt 排序只是利用已知输入工作量，不等于知道真实最短作业，更不等于知道最短剩余时间。选择策略还要看目标是平均完成时间、流式响应、公平性还是截止时间，以及 KV 暂停和恢复是否足够便宜。

**16. FastServe 的 MLFQ 具体怎么做？为什么不能频繁抢占来照顾短请求？**

FastServe 根据已知输入长度和执行成本估计，把请求放入合适的初始队列；运行中消耗完当前时间片还没结束，就进入更低优先级队列。更高优先级的请求可以在 token 迭代边界获得执行机会，等待过久的请求则可以被提升优先级。这样既利用输入长度信息，也根据实际已执行的工作逐步识别长请求。

真正的代价在于被暂停请求的 KV 还在。只停止计算而不释放 KV，未必能给新请求腾出容量；把 KV 换到主机内存又会增加传输和恢复等待。FastServe 为此配套 KV 换入换出，频繁切换仍可能让复制占据带宽、让生成反复停顿，所以必须把抢占收益和恢复成本一起比较。

**17. 每个租户轮流取一条请求不就公平了吗？VTC 具体怎么记账？**

请求数相同不代表获得的服务相同，例如一个租户每次生成几十个 token，另一个每次生成几千个 token。VTC 为每个客户端维护虚拟服务计数器：请求被选入执行时，按输入 token 数量和输入成本权重增加计数；生成过程中，再按实际输出 token 数量和输出成本权重继续增加。

当 batch 有容量接纳新请求时，优先从服务计数较低的客户端取请求，执行过程中继续更新计数。客户端长时间没有请求、之后重新进入等待队列时，还需要校正它的计数基线，避免它把闲置期间变成无限可用的优先权。带权公平则需要把客户端权重纳入服务量比较，而不是只提高请求的固定优先级。

**18. VTC 每生成一个 token 都更新计数，是不是每个 token 都切换租户？它保证什么？**

不是，记账频率和抢占频率是两回事。基本 VTC 会随着 token 执行更新服务量，但主要在有空间加入新请求时选择客户端，不会因此把已经运行的请求立即调出。

它约束的是持续有请求积压的客户端之间，已经获得的服务量不能相差过大，相关保证依赖成本定义、请求规模和容量等条件。这不意味着每个请求的 TTFT 一样，也不保证所有请求都满足 SLO。已经进入 batch 的长请求继续运行，公平策略的效果需要随着后续接纳逐步体现。

**19. DRF 和 VTC 都讲公平，区别是什么？GPU 和显存怎么一起比较？**

DRF 看的是多种资源的占用份额。比如一个租户占了集群 20% 的 GPU 和 40% 的内存，它的主导份额就是 40%；另一个租户占了 30% 的 GPU 和 10% 的内存，主导份额就是 30%。在需求和可分配条件满足时，DRF 通过优先增加较低主导份额，做多资源的最大最小公平分配。

VTC 看的是随时间已经提供了多少 token 服务，两者的计量对象不同。真实 GPU 集群还要考虑卡型速度、节点拓扑和任务能否拆分，不能把一张不同型号的卡都当成相同服务能力；引擎内的 KV 还会随生成增长，也不能直接把一次资源占用快照当作长期服务公平。

**20. DistServe 的 prefill/decode 分离具体怎么做？分开后为什么不一定更快？**

请求先进入 prefill 实例，计算输入对应的 KV；随后把 KV 交给选定的 decode 实例，后者接着逐 token 生成。DistServe 让两阶段使用不同 GPU，并分别选择资源数量和并行配置，再根据互联带宽安排放置。这样可以减少长 prefill 对 decode 的干扰，也能让两个阶段按各自需求扩展。

新增的成本包括 KV 传输、两阶段之间的排队，以及两边负载不均。prefill 快而 decode 满了，完成的 KV 仍可能需要等待；网络慢时，省下的共置干扰也可能抵不过传输。因此需要保持总资源口径一致，比较 TTFT、生成速度和达标吞吐，不能只对比某一个阶段。

**21. 既然可以预测输出长度，为什么还要按最大长度预留？预测错了怎么办？**

最大长度预留提供保守容量边界，预测长度则用风险换取更高利用率。TetriInfer 把预测的输出长度区间用于调度和放置，但预测值不能当成请求不会超过的硬上限。

如果采用预测接纳，我会同时维护真实 KV 用量和剩余增长余量，并预留误差空间。接近边界时先停止新接纳；已有请求继续增长仍可能触边，所以还必须定义等待、换出或重算的恢复策略。评价时要保留低估导致的抢占和长暂停，不能只展示提高的并发数。

**22. Llumnix 为什么要迁移正在运行的请求？KV 还在增长，怎么搬？**

到达时做一次路由，只能根据当时看到的负载选择实例，后续输出长度和 KV 增长可能让实例重新失衡。Llumnix 除了分发新请求，还把运行中的请求连同 KV 迁移到有余量的实例。

它利用常规自回归生成中历史 KV 不再改写、新 token 继续追加 KV 的特点分阶段迁移：先在源实例继续 decode 时复制已有 KV，再补上期间新生成的部分，最后短暂停止源端推进，复制剩余状态并切换执行端。目的端需要提前具备容量，切换还要避免重复执行和丢失状态。迁移能不能获益，要比较复制与切换成本和留在原实例继续等待的成本。

**23. RadixAttention 怎样复用前缀？缓存命中最多的请求为什么不一定应该先跑？**

RadixAttention 用前缀树组织请求对应的 KV，公共 token 前缀可以引用已经存在的缓存，新请求只需要继续计算未命中的部分。调度时可以优先处理匹配前缀较长的请求，让共享缓存被连续使用，再结合引用状态和回收策略管理容量。

但缓存局部性和请求等待是两个目标。一个长 prompt 如果大部分已缓存，剩余 prefill 可能比短 prompt 还少；反过来，一直优先高命中请求也可能让低命中请求长期等待。因此应综合未缓存的工作量、等待时间和资源状态，不能仅用命中率评价整个调度器。

**24. KV 碎片、副本之间的容量碎片、节点资源碎片，分别是什么？**

KV 碎片是单实例内存组织的问题，例如预留空间没有用满，或者连续分配要求导致部分空间用不上，分页管理能减少这类浪费。副本容量碎片是多个实例加起来有空闲，但某一个请求只能进入其中一个实例，单实例剩余容量又不够，Llumnix 通过请求迁移等动作调整这种分布。

节点资源碎片则发生在集群放置层，例如总共还有 8 张空闲 GPU，却分散在两台各剩 4 张的机器上，放不下一个要求单机 8 卡的 Pod。这几种问题需要不同动作，不能因为总空闲量足够就认为请求或任务一定能开始。

**25. WiSP 怎样协调专家权重和 KV 的显存？和直接调高显存预算有什么区别？**

WiSP 把专家权重视为有访问局部性的工作集：常用专家尽量留在 GPU，不驻留的专家在需要时加载，同时给 KV 保留必要空间。它比较额外一部分显存留给专家、或留给 KV，分别能减少多少延迟，再据此划分两类容量；动态调整还要在排空边界执行，避免正在运行的请求引用被改变的资源。

直接调高 vLLM 的显存预算，是给引擎增加可用资源；在固定预算内回收专家空间给 KV，则必须改变权重驻留和加载方式。后者多出的 KV 容量可能减少等待，也可能引入 PCIe 加载成本，最终仍要看完整请求。我的当前实验测的是前一种配置作用，没有把它写成实现了专家分页。

**26. ELDR 怎样使用专家签名选择 decode worker？为什么不把相似请求都放到同一个实例？**

ELDR 从 prefill 阶段的专家激活构建请求签名，利用这些信息估计生成阶段可能使用的专家。它先把签名空间组织成相对均衡的分组，在线为请求找出局部性合适的一批 decode worker，再从候选中选择负载较低的实例；签名缓存还需要与对应 KV 块一起维护，避免复用前缀时丢失签名信息。

相似请求合在一个 batch，可能增加专家权重的复用，但把热门请求全挤进一个实例又会增加排队。因此局部性只是选择的一部分，必须和容量、当前负载一起使用。还要区分模型把 token 路由到哪个专家，以及服务系统把请求送到哪个实例：ELDR 改的是后者。

**27. 为什么有些场景专家预取没有收益，FluxMoE 却可以通过流水加载提高吞吐？**

预取能不能获益，取决于传输是否能被其他工作覆盖，而不只是专家预测是否准确。在低并发、PCIe 已经繁忙的场景里，额外预取可能和当前必需的专家加载争带宽，预测准确也不代表请求更快。WiSP 就讨论了这种受带宽限制的情况。

FluxMoE 把专家权重与长期 GPU 驻留分开，通过 GPU 压缩存储、主机内存和执行时加载组织流水，试图把更多常驻显存留给 KV。较大的 batch 可以提供不同的计算与加载比例，但仍要付压缩存储访问、传输和调度成本。不能把某个高 batch 场景的总吞吐提升，直接当成低并发流式请求的延迟收益。

**28. Lina 和 Aurora 的专家调度分别在做什么？和请求队列排序有什么区别？**

Lina 的推理部分根据专家热度安排专家复制、打包和设备映射，并结合预测与实际路由的偏差做修正；训练部分还处理 all-to-all 与 allreduce 的通信竞争。Aurora 则结合模型部署、专家共置、GPU 分配和 all-to-all 发送顺序，优化设备与网络上的工作安排。

这些方法改变的是专家工作落在哪些设备、以什么顺序通过链路执行。请求队列排序改变的是谁先进入引擎，两者虽然会相互影响，但动作对象不同。要把它们放在一起评价，需要真实地计入多卡通信、复制和请求等待；单卡没有这条通信路径，不能用单卡排序结果推断多卡收益。

**29. Kueue、kube-scheduler 和推理引擎各负责哪一步？**

Kueue 管作业什么时候获得配额、可以开始，以及是否需要被回收；kube-scheduler 管 Pod 放到哪个节点；推理引擎管实例已经运行后，哪些请求被接纳、每轮执行多少工作。一次请求的等待可能发生在其中不同层，排查时要先确定实际卡在哪里。

例如，服务 Pod 已经 Ready，只能说明实例启动到了相应就绪状态，不能说明引擎有足够 KV 接新请求。反过来，修改引擎 cap 也不能在集群里凭空增加 GPU。两层可以交换容量和负载信息，但不应该让每个 decode 步骤都等待 Kubernetes 调度。

**30. Gang scheduling 到底保证什么？配额够了，为什么一组任务还可能起不来？**

Gang scheduling 面向需要一组成员共同运行才能取得进展的任务，目的是避免部分成员占着资源，却一直等不到剩余成员。整组配额预留只是第一步，随后还要确认每个成员能放到满足容量和拓扑要求的节点上。

Kueue 可以结合配额、拓扑容量检查和等待所有 Pod 就绪的机制。等待就绪超时后回收并重新排队，是对部分启动的补救，不等于所有 Pod 在同一时刻原子启动。整组配额、实际可放置性，以及启动后的运行与故障恢复，需要分别处理。

**31. Filter、Score、Reserve、Permit 分别解决什么？绑定失败怎么回滚？**

Filter 排除不满足条件的节点，Score 给剩余可行节点排序，Reserve 在绑定完成前维护必要的临时资源状态，Permit 决定批准绑定、拒绝或者等待。Reserve 的作用是让需要维护状态的插件在后续绑定过程中正确记账，不能只靠一个分数完成资源预留。

如果 Reserve 或后面的阶段失败，调度框架会触发 Unreserve 清理，按 Reserve 插件执行的相反顺序处理。Unreserve 要幂等且不能失败，避免请求重试后留下错误占用。Permit 等待超时也会走拒绝和清理流程，所以实现组调度时必须同时处理批准、超时、成员失败和资源释放。

**32. GPU 利用率高就用 HPA 扩容，为什么还需要引擎内调度？两个控制怎么避免互相打架？**

HPA 改变副本数量，引擎内调度管理现有副本中的请求，两者生效时间不同。扩容需要经过 Pod 放置、模型加载和就绪检查，不能立即消除当前实例里的 KV 等待；而快速降低准入也不代表长期容量需求已经消失。

如果设计两层联动，我会让引擎处理短时间内的接纳与排队，让扩容根据持续的等待、达标吞吐和容量缺口做较慢调整。还需要限制变化幅度、设置稳定窗口，缩容前停止接收新请求并等待已有请求结束或完成迁移，避免一边缩容、一边又提高剩余实例的接纳压力。

**33. 你怎么证明一个调度策略真的有效？具体怎样做对照？**

先固定一个动作和一个目标，让默认策略、强简单策略和待测策略使用相同模型、资源、请求与到达计划，各自真实推进队列、KV 和生成过程。比如改 prefill 预算时保持其他引擎条件一致；研究排序时检查入场顺序确实改变，并设置同样承担采集开销的对照。

结果要同时报告完整吞吐、TTFT、请求平均 TPOT、每请求最大 ITL，以及失败、未完成和受损请求。不能只报短请求变快，也不能用一条策略的未来 route 去拼另一条策略的结果。出现方向变化时先做受控重复，再判断收益是否稳定，而不是挑最好一次。

**34. 你说的 goodput 怎么算？SLO 阈值换一下，是不是就能让策略赢？**

我这里的请求 goodput，是同时满足预定 TTFT 和平均 TPOT 要求的完整请求数，除以这组请求从开始到结束的实际运行时间。它衡量单位时间内服务了多少达标请求，与输出 token 数除以时间不同。已经到达但失败、超时或没有完成的请求都要保留，不能从达标比例的分母中删掉；中止前还没有到达的计划请求单独统计。

SLO 阈值确实会影响达标数量，所以同一对照提前固定阈值，同时报告连续的 TTFT、TPOT 和完成延迟。比如预算和排序实验用了 5 秒 TTFT、200 毫秒平均 TPOT 的参考要求；如果所有策略都通过，就说明这组阈值没有区分出违约风险。此时可以比较实际延迟和这组请求的 goodput，但还不能推断长期安全容量提高了。要评价承载容量，需要在有业务依据的 SLO 下增加到达负载，观察队列是否持续增长，以及达标率何时下降。

**35. 不同策略的 batch 和输出 token 都可能变化，你的性能比较还成立吗？**

要先说清楚比较的目标。如果比较相同输入和生成配置下，用户实际经历的服务成本，各策略应独立执行后续 KV、路由和生成过程，再比较完整请求。不能把 FCFS 的未来路由拿来给另一种排序策略计时，因为动作已经改变了后续状态。固定输出长度能够控制生成步数，但不能保证 token 内容完全相同。

如果要进一步说“同样的答案算得更快，而且质量保持”，就还需要检查输出和任务质量；只保存耗时不够。我的当前请求级实验主要回答调度成本，不能仅凭性能数据证明质量不变。另外，十几条请求得到的尾部统计只能描述这组输入，尚不足以代表线上大量请求的 P99。

**36. 流量一直超过处理能力，你是让请求排队，还是直接拒绝？**

不能无限排队。扩展到在线服务时，我会同时限制等待请求数和待处理 token 量，再结合已有等待时间、KV 余量和处理速率决定是否接纳。短时突发可以由有界队列吸收；持续过载则需要拒绝新请求，并通过扩容增加后续容量。已经接纳的请求按原有服务约定处理，不能为了让统计变好临时丢掉慢请求。

评价时保留全部到达请求，分别报告接纳、拒绝、超时、完成和达标数量。否则只接很少的短请求也能获得漂亮的平均延迟，却没有真正提高服务能力。当前实验还没有实现这套过载控制；下一阶段如果测持续到达，就需要把这项行为明确下来。

**37. 按截止时间调度怎么实现？快超时的请求是不是一定应该先跑？**

首 token 前，我会计算“到达时间加 TTFT 限额”这个截止时刻，再减去当前时刻和预计剩余 prefill 成本，得到可用余量。首 token 后，只有业务明确约束最大 token 间隔，才用上一次返回时间加间隔限额定义下一次截止时间。平均 TPOT 是整段生成的平均约束，不能直接当成每个 token 的硬截止时间。

余量小的请求需要关注，但不能无条件优先。已经来不及挽救的请求持续占据执行机会，可能让原本能达标的请求也超时；成本估计还有误差。因此需要结合剩余工作量、是否仍可达标和业务优先级选择，并计入已有请求被打断的代价。这是后续策略设计，当前没有把它实现成已验证的调度器。

**38. 你怎样限制短请求插队？具体改了什么，怎么保证规则真的生效？**

我给尚未开始执行的等待请求维护一个计数，记录它被多少条后来到达的请求先入场越过。这次限制最多一次：优先选短 prompt，但如果选择它会让某条更早请求第二次被越过，就先保护那条更早请求。已经开始的 prefill 和 decode 继续按原生路径运行。

计数在实际首次调度成功后更新，仅仅重排队列不算一次。一轮可能接纳多个请求，所以本轮选取过程中也要临时累计，避免连续选几条短请求就突破限制。最后用真实首次入场顺序核验：三个长请求在短 prompt 优先下分别被越过 3、2、1 次，加限制后都变成 1 次，两个执行顺序都一致。

这只能保证首次入场的越过次数。前面一个请求运行很久、KV 不足或者当前没有可用名额，仍可能造成长等待，所以不能把它说成等待秒数保证，也不能代替按租户服务量记账的公平调度。

**39. 限制插队以后，长短请求是不是就都受益了？实验结果到底怎么样？**

没有同时得到稳定收益。相对不限制的短 prompt 优先，长请求完成延迟的 P95 在两次运行中分别下降约 1.8% 和 2.8%，但短请求 TTFT 分别增加约 9.7% 和 7.8%，整体平均完成延迟也分别增加约 1.7% 和 0.5%。相对 FCFS，短请求 TTFT 一次增加约 1.3%，一次下降约 7.1%，没有满足两次都保留收益的预期。

我用同样的 16 条输入、到达时刻、并发 8 和 token 预算 1024，比较 FCFS、短 prompt 优先和一次越过限制；另外放入全短输入组检查没有重排时的变化。两个新启动的引擎反转正式执行顺序，共完成 12 组正式测量和 12 组预热，原始请求与调度记录全部保留。

结论是这条规则能限制越过，也能减少部分长请求的代价，但主要仍在重新分配等待。当前样本不足以证明小幅差异都有统计意义，更不能据此承诺整体加速。我已经停止继续调这个次数阈值。

**40. 你后来为什么限制单个请求的 prefill？它和把总 token 预算调小有什么区别？**

因为等待请求进不去，有时不是并发满了，而是单个长 prefill 用完了本步计算预算。实际轨迹里，一步有 6 条请求各 decode 一个 token，另一条长请求拿走 1018 个 prefill token，正好用完 1024 的总预算。并发上限是 8，此时还有一个名额，但等待的 128-token 短请求没有预算可用。

我比较了三种原生配置：总预算 1024、总预算 512，以及总预算保持 1024 但单请求 prefill 每步最多 512。第三种情况下，同一步可以给已有 decode 6 个 token、长 prefill 512 个、短 prefill 128 个，共 646 个；单纯把总预算降到 512，则全体请求都要分享更小的预算。实验只在引擎排空后切换相应字段，并逐步检查实际分配、已有 decode 是否继续，以及是否发生抢占。

这次动作确实生效：两个混合输入运行块各有 24 次长 prefill 受到单请求限额约束，其中各有 3 次在同一步随后接纳了短请求。但其余时刻可能没有请求等待，或者运行名额已经满了，切小 prefill 并不总能增加接纳。相对默认总预算 1024，短请求 TTFT 一次增加约 0.6%、一次下降约 1.2%；整体平均完成延迟分别增加约 1.6% 和 0.5%。全短负控也有运行波动，所以目前只能说没有观察到稳定整体收益。长请求的最大 token 间隔有所下降，但简单的总预算 512 在这个指标上还更低，不能把它包装成新算法优势。

**41. 你做了这些实验之后，下一步具体要验证什么？怎样避免一直换参数？**

下一步先检查输入长度是否影响了目前观察到的分块开销。我发现，同样是 2048-token 长输入，总预算 1024 时每条需要 3 个 prefill 块，总预算 512 时需要 5 个，单请求限额 512 时需要 4 个。比如已有 decode 每步占一个 token，1024 总预算下就可能分成 1023、1023、2；最后只剩 2 个 token，也还需要再被调度一次。块数能说明执行安排，不能直接换算成节省了多少时间。

我准备先只跑原生 FCFS、总预算 1024 的基线，按固定来源顺序选另一组完整文章，保留各自的自然输入长度；仅按上下文容量排除放不下的文章，不再统一截成 128 或 2048。输出长度和到达设置先保持可比，记录每条请求的实际分块、最后一块大小、等待与完成时间。这样可以判断很小的尾块在自然长度下是否仍然出现，以及是否伴随值得优化的请求成本。这组新输入实验还没有运行。

如果普通分块和排队已经解释了变化，就不急着增加专家预测器。只有这些基线之后还存在可重复的请求损害，才进一步检查专家负载是否提供额外信息、是否有动作能减少这部分损害，并把判断规则放到另一组请求上验证。
