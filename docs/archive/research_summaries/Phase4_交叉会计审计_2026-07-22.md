## 2. Receiver / DDRC

### R-P0-1：正式决策没有强制“两模型完整输入”，可由单模型生成 GO

证据：

- 冻结协议要求 OLMoE 与 LLM-jp 均复现：`docs/archive/receiver_aware/ddrc/DDRC_Phase2_冻结实验协议_2026-07-22.md:224-234`。
- 配置虽写了 `required_models=[olmoe,llmjp]`：`docs/archive/receiver_aware/ddrc/configs/ddrc_v1.json:128-135`，但 `build_decision()` 从现有 accounting rows 推导模型集合，未读取或比较 `required_models`：`docs/archive/receiver_aware/ddrc/experiments/run_ddrc_existence_gpu.py:713-788`。
- 审计用一个 `olmoe` cell、两个相邻 lambda 和全 true capability 调用 `build_decision()`，实际返回：

```text
status=GO_TO_REAL_TRANSPORT_NEXT_ITERATION, go=True,
g0_by_model={olmoe: True}
```

影响：缺失 LLM-jp、缺失某模型 sealed cell 都不会自动阻止 GO，直接违反主门。

关闭条件：正式决策先断言 `observed_models == config.decision.required_models`；每个模型必须具有 calibration、sealed、全部强基线、DDRC、oracle 和完整 quality/bootstrap 产物，不能使用 `all(empty)` 或“仅对出现的模型”判定。

### R-P0-2：bootstrap 单元与冻结协议不一致，P99 block-bootstrap 根本未进入 verdict

证据：

- 冻结协议要求“按 subject/request 分层 paired bootstrap；P99 按 forward/burst block bootstrap”：协议 `:193-220`。
- quality CSV schema 只有 `trace_id/model/arm/harm/cvar/action_signature`，没有 `subject_id`、`request_id` 或 `burst/block_id`：runner `:19-24`、`:504-529`。
- `paired_bootstrap()` 直接对 `trace_id` 有放回抽样：runner `:599-675`。而 trace 本身带 `step/layer`，实现无法证明一个 `trace_id` 就是独立 request；按 layer/step 当独立样本会产生伪重复。
- `summarize_system()` 只算经验 P50/P95/P99：runner `:536-571`；`build_decision()` 不读取 P99 CI，也不读取 `system_summary`。`burst_block_bootstrap=true` 只是配置布尔值，不对应被消费的统计产物：runner `:693-710`。

影响：CI 可被错误缩窄；即使没有 P99 block-bootstrap，配置布尔值为 true 后仍可能进入 GO。

关闭条件：

1. quality 原子行必须含 canonical `subject_id, request_id, question_sha256`；按 subject 分层、request 成对重采样；
2. 系统 trace 必须含 `forward_id, burst_id`，输出独立的 block-bootstrap CI；
3. `decision.json` 必须校验这两个统计产物的 schema、hash、重复数=2000、独立单元和必需 cell，而不是读取 capability 布尔值；
4. 添加“将同一 request 拆成多 layer 行不会改变有效样本数/CI”的反伪重复测试。

### R-P0-3：formal hash 只绑定消费者，未绑定 route/quality producer 与冻结数据身份

证据：

- `source_manifest()` 只包含 `ddrc_policy.py`、runner 与测试：runner `:67-74`、`:111-123`。文档声称 formal review 要把 quality producer 签入 source hash（runner `:23-24`），代码没有对应入口。
- `validate_formal_inputs()` 只检查 trace 文件 hash、quality CSV hash 和 `sealed=true`：runner `:817-829`。
- 它不强制检查：十个 subject、validation/test 数量、canonical question hash、历史 subject registry 不重叠、模型 revision、tokenizer revision、route capture producer、quality producer、balanced workload、一次性 sealed-open 记录。
- action signature 只绑定 `trace_id/model/arm/low/requested/blocked/fallback`：runner `:488-496`；它没有绑定 question/document 身份、模型 revision、logits 或 quality producer。

影响：一个自称 `sealed=true` 的错误/泄漏数据 manifest、或未审查的 quality producer，能通过代码门禁；selection leakage 与 action-mismatch 仍可能污染结论。

关闭条件：新增只写一次的 canonical data manifest builder；formal validator 对冻结 subject 列表、每 subject 数量、split、question SHA、registry exclusion、模型/tokenizer revision、route/quality producer SHA、输入文件 SHA 全部逐字段 hard-fail。source aggregate 必须包含所有 producer、统计与 verdict 代码。

### R-P0-4：G1 不是 sealed quality 之前的停止门；双 codec 判据也未实现

证据：

- 协议要求两模型 oracle ceiling 未达 3pp 时“不启动 sealed quality run”：协议 `:44-48`。
- 当前 formal runner 要求 quality CSV 已存在，随后一次性加载 trace/quality、算 accounting/bootstrap，最后才在 `build_decision()` 中计算 G1：runner `:845-885`、`:728-733`。
- 协议 GO 同时要求 `amortized_once_per_step_proxy` 达门，以及同 action trace 的 `serialized_tiles` 优势仍为正且 CI 不跨负：协议 `:224-234`。正式入口却 hard-code 只允许 `serialized_tiles`：runner `:845-851`，decision 只检查该单一模式：runner `:759-770`。

影响：G1 失败前 sealed quality 已生成/打开，违背预注册停止规则；缺少同 trace 双口径，仍可能错误 GO。

关闭条件：拆成两个不可逆阶段：

1. `existence/oracle` 只读 calibration route trace，产出并签名 G0/G1；
2. 只有签名 G1 PASS hash 才允许 quality producer 打开 sealed；
3. 同一个 `action_signature` 同时重算 serialized 主口径和 amortized sensitivity，decision 同时消费两套 paired CI。

### R-P1-1：credit 字节闭合是“消息总量”，不是冻结协议要求的完整物理 cut 账本

现有正确点：16B header、8B record、alignment、late/duplicate 已收费；`credit_total_us` 还计入 critical credit wire time：`ddrc_policy.py:495-533`、`:728-764`。

缺口：`StepLedger.wire_bytes/critical_wire_bytes` 只含 combine data，credit 只另列一个总 `credit_bytes`：`ddrc_policy.py:854-882`、`:938-997`。没有逐 sender egress、receiver ingress、physical shared-cut 的 data/credit/total closure；formal CSV 也只输出汇总：runner `:931-950`。

关闭条件：每 step 输出 `data_bytes + credit_bytes = total_physical_cut_bytes`，并分别按 sender、receive resource、direction 闭合；明确 `transfer_us` 是固定软件项还是已含 wire，防止与 `credit_wire_us` 双计。

### R-P1-2：hardgate 的 credit tax 分摊规则未预注册，当前等分 lane 偏乐观

`apply_receiver_credit_messages()` 用 `credit_visible_us / len(requested)` 作为每 lane gate 的 credit 成本：`ddrc_policy.py:676-683`。这不按 message bytes、sender 或物理 cut 分摊；lane 大小不同时可能接受本应局部负收益的 lane。最终 step 总时间仍收一次 credit tax，但“positive-net lane gate”的动作集合会改变，进而影响质量。

关闭条件：冻结一种可复算分摊（建议按每 sender 消息固定 header + lane record/alignment 的边际/归因成本，并另做全 plan net gate），补不等 lane 大小时的拒绝/回滚测试。

### R-P1-3：origin 与 causal 顺序、quality key 唯一性不足

- 每个 trace 独立验证 LPT，但不验证同一 request 在跨 layer/step 的 owner 恒定：runner `:217-268`。
- `previous_by_model` 完全依赖 JSONL 输入顺序，没有 step/layer 单调性或 burst 边界校验：runner `:401-499`。
- quality rows 转 dict 时重复 `(trace_id,model,arm)` 会被静默覆盖：runner `:584-598`。
- `causal_prev_step` 出现在协议“强基线”表中，但 `STRONG_BASELINES` 未包含它：runner `:76-81`。协议又称其为历史诊断基线，需在 Phase 2 erratum 明确它是否参与最终 max，不能由代码暗选。

关闭条件：manifest 固定全序和 request-owner 映射；重复 key hard-fail；明确 causal arm 的 gate 身份并在协议/代码保持一致。

### R-P2-1：时间来源未逐字段落盘

协议要求每个时间字段携带 `measured_same_run | measured_other_gpu | analytic | assumed`：协议 `:191`。当前 `StepLedger` 只落 pack/H2D/unpack 数值和总 evidence boundary，不落每字段 source：`ddrc_policy.py:854-882`。配置含 source 不能替代结果行的 provenance，尤其后续合表时容易混口径。

关闭条件：每个时间字段旁写 source、GPU UUID、measurement artifact SHA；formal 决策拒绝缺 provenance 行。

### E-P0-2：formal code/config hash 漏掉能量和 serving 核心实现

配置 hash manifest 只列：policy、surface runner、policy test、config：`route_row_break_even_v1.json:97-106`。它没有绑定：

- `continuous_decode_harness.py`；

- 后续 continuous engine adapter / capture producer / quality producer / verdict 代码。

`verify_formal_signoff()` 只比较这个不完整 aggregate：`route_row_policy.py:682-726`。

### E-P0-3：continuous harness 用 backend 自报布尔 capability 代替可验证事实，而且不实现冻结 batch grid

证据：

- capability 来自 backend 返回的布尔字段：`continuous_decode_harness.py:240-263`。
- 审计把 CPU test backend 的 `real_continuous_engine` 一项改为 true，两个 64/64 请求即可实际得到：

```text
status=COMPLETED, scientific_result_eligible=True,
backend=audit-only-test-backend, max_active=2
```

- harness 没有 `max_num_seqs` 参数或 `{1,4,8,16,32,64}` grid；到达的请求全部 admission：harness `:405-465`。
- prefill 对 admitted request 逐个串行调用，而不是由 engine scheduler 形成受容量约束的 continuous batch：harness `:466-513`。
- formal 路径强制 `max(active_set_sizes)>=2`：harness `:614-621`，这反而使协议必需的 B0/B4 `max_num_seqs=1` 无法作为 formal arm 运行。

影响：`scientific_result_eligible` 不是可信门禁；B0/B4 与 batch-grid 公平性无法实现。

关闭条件：资格来自审查过的具体 engine adapter 类型、commit 与 runtime counters，而非任意 backend 布尔值；runner 显式传入并执行 frozen max-num-seqs grid；B0/B4 允许 cap=1，同时仍验证 engine 是真实 incremental decode。

### E-P0-4：SLO、质量、Pareto 和统计判据没有实现为可执行 verdict

- 当前 ledger 的 violation 只判断 `completion_ns > 一个 request deadline`：harness `:188-236`；冻结协议要求分别由 B0 标定 TTFT/TPOT SLO，并比较 P99 ratio 与 violation-rate CI：协议 `docs/ideas/energy_slo/route_row_fp8/Phase2_RouteRow_FP8_BreakEven_冻结协议_2026-07-22.md:146-173`、`:175-186`。
- `BackendStepResult` 不携带 logits、token KL、route/action census 或 quality manifest：harness `:266-317`，无法执行文档级 paired quality bootstrap。
- 没有 B0–B4/C completeness gate、五 seed 主 CI、预留 seed 停止规则或两模型×两 workload 判定器。

影响：即使能量 surface 正，也不能判断联合 Energy-SLO 主张。

关闭条件：formal runner 必须消费全 arm/cell artifact；分别计算 request-level TTFT/TPOT、token TBT、paired seed/block bootstrap、quality document bootstrap，并在任一 baseline/cell 缺失时拒绝输出 GO/NO_GO。

### E-P0-5：主能量窗口尚未与 serving ledger 原子绑定

`power_accounting.py` 有正确的基础公式和显式边界采样，但没有正式代码把 sampler 的：

```text
t0 = 首个 measured arrival 释放前同步点
t1 = 最后 request 完成 + GPU synchronize
```

与同一 arm 的 event ledger、完整 drain、completed-token denominator 原子绑定。也没有冻结 idle measurement 的 clocks/power-cap/weight-residency/KV 状态。当前 surface 自有另一套 meter，只测 isolated expert repetition：surface `:480-564`、`:608-651`。

影响：存在 window/denominator 串台、warmup/idle 漏计以及将 local expert energy 当整机 J/token 的风险。

关闭条件：单一 context manager 同时产生 power trace、event trace 与 run UUID；开始前 synchronize，结束完整 drain 后 synchronize；校验 arm 间 completed token 数完全相同；idle artifact 与 clock/power-cap/residency manifest hash 绑定。

### E-P0-6：capture/quality 的 SHA 目前只验“长得像 hash”，没有验对应内容

`_load_capture()` 只检查 `capture_producer_sha256/data_manifest_sha256/arrival_config_sha256` 是 64 位十六进制：surface `:219-278`，并未读取和重算对应 producer/manifest/config。capture 也没有 request/document identity，因此无法验证 WikiText 窗口和 calibration/test 隔离。activation 被无条件转成 BF16，未验证 capture 中原 dtype 真是 BF16：surface `:351-393`。

`_load_quality_gate()` 接受 artifact 自报的 `in_loop_decode=true/independent_kv=true/route_replay=false`：surface `:425-468`；这些 producer 又不在 formal hash manifest 中。

影响：selection leakage、route replay 或错误 producer 可伪装成合规 calibration LUT。

关闭条件：formal signoff 直接绑定 producer bytes；读取并验证 canonical data/arrival manifest；capture 写 request/document SHA、policy/run UUID、原 dtype/device；quality artifact 对同一 run UUID、独立 KV 与 logits trace 做可复算检查。

### E-P1-1：未验证实际 NVML 采样间隔，counter 的 t0/t1 也不完全同界

`MonotonicNVMLSampler` 只限制配置的 `interval_s<=20ms`：`power_accounting.py:184-205`，没有对最终样本的最大实际 timestamp gap hard-fail。线程调度延迟可使实际间隔超过 20ms。start 先读 energy counter、后取边界 power sample；stop 先取边界 power sample、后读 counter：`:227-265`，counter 与 sample 的积分窗口并不完全相同。

关闭条件：产物记录 `max_observed_sample_gap_ms` 并在 formal 模式 hard-fail >20ms；定义唯一 t0/t1，并记录 counter-read timestamps；开始端也执行 GPU synchronize，防止前一 arm 污染。

### E-P1-2：unfinished request 的 token 分母与冻结验收语义冲突

`EventLedger.completed_output_tokens` 统计所有已 append token，即使所属 request 最终未完成：harness `:184-186`。测试显式把一个 unfinished request 已产出的 token计入 completed denominator：`test_continuous_decode_harness.py:244-275`。这与协议验收“未完成 request 进入 backlog/右删失但不进入完成分母”不一致：协议 `:203-205`。

正式主运行要求完整 drain，故成功 cell 中暂不触发；但 blocked/partial 路径若被拿去算能耗会偏低。

关闭条件：区分 `produced_token_count` 与 `completed_request_output_token_count`；正式 J/token 只允许后者且要求 zero backlog，blocked/partial 不生成主能耗。

### E-P1-3：surface 的 statistical estimand 需要冻结

surface 先在每个 iteration 内平均该 bin 的 expert events，再等权 bootstrap iteration：`run_route_row_surface.py:802-856`。若不同 iteration 中该 bin 的事件数差异很大，这估计“典型 iteration 的 bin 均值”，不是“典型 expert call 的均值”；而 BF16 energy mass 又使用 event-level sampled mean×population。两个 estimand 不一致。

关闭条件：协议明确目标是 iteration-weighted 还是 event-mass-weighted；建议 cluster bootstrap iteration、但 replicate 内按 event count 聚合 numerator/denominator，保证 CI 与 energy-mass gate 对同一 estimand。

### E-P2-1：LUT 反序列化存在宽松 bool 转换

`RouteRowLUT.from_dict()` 使用 `bool(value["quality_gate_passed"])`：`route_row_policy.py:361-375`；字符串 `"false"` 会变为 true。正式 JSON 通常产生真正布尔值，但该 loader 不应宽松接受错误类型。

关闭条件：要求 `type(value) is bool`，否则 hard-fail；quality artifact SHA 非空且匹配后才允许 true。
