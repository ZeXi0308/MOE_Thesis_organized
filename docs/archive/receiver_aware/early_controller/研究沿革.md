# 名称

Receiver-Aware 通信控制：从拥塞感知降级到质量约束在线自适应必要性检验（Quality-Constrained Adaptivity Existence Test）

状态：**CONDITIONAL / CORRECTED-POLICY RERUN REQUIRED**。结构性拥塞下的静态画像可信；已有 Existence Test 未启用 `require_positive_net_saving`、也未记 H2D tax，与文档声称的纠正后主配置不一致。`SUPERSEDED`：把该跑数当作纠正策略的最终 NO-GO。

## 1. 背景与问题

MoE expert-parallel combine 阶段，不同 receiver（token 来源 GPU）在同一时刻承受的流量并不均衡：有些 receiver 持续过载（结构性拥塞/hotspot），有些只是瞬时随机过载（balanced）。已有系统工作（DeepEP、Comet、UCCL-EP）优化的是通用 EP 通信重叠/调度，没有专门利用"receiver 拥塞状态"这个信号来决定该不该对部分流量降精度。

最初的直觉类似网络里的 ECN 拥塞控制：**能不能感知 receiver 当前是否拥塞，只在拥塞时把低贡献流量降精度，从而比"不管拥塞、随机降精度"更好？** 这条线最早在 2026-07-13 前提出（receiver-aware v1），之后经历了三次系统化重跑（v1→v2→v3）与两次决定性修正（direct-benefit controller 替代 v3；2026-07-21 Quality-Constrained Adaptivity Existence Test），是全项目里方法论演进最曲折、也最能体现"仿真结论在更真实约束下可能反转"这一元教训的候选。

## 2. 核心思想 / 机制主张

主张随版本演进不断收窄：

1. **v1（拥塞感知选择）**：候选池限定为"tail-rank ∩ remote"（排除"偏好远程"这个混淆），用真实 sender/receiver 负载分数选 `hot` 优先降级，稳定跑赢 `random`。
2. **v2（信息陈旧度三级 + 拥塞两种 regime）**：把"信息可用性"拆成 `oracle_same_step`（同时刻先知，不现实）/ `causal_prev_step`（仅用上一步已实现负载，现实可行）/ `calib_static`（纯离线校准画像，零在线信号）；把拥塞拆成 `hotspot`（结构性/持续）和 `balanced`（瞬时/随机）。核心发现：**hotspot 下三种信息可用性几乎重合**（静态画像已够用，不需要在线信号）；**balanced 下现实可行的 `causal_prev_step` 反而比 `random` 更差**（信息陈旧本身是负资产）。
3. **v3（因果合法 regime 检测器，后被推翻）**：用负载 Herfindahl 集中度指数做因果检测，自动切换 `calib_static`/`random`，号称"自适应全面优于三个固定基线"。**该结论存在因果评估错误**（把检测 cutoff 之后才选定的策略回溯应用到 warm-up 期），修正后自适应相对最强固定基线（`always_causal_prev_step`）的优势在 4×2 组合下 95% CI 全部跨 0，已撤回，不得再作为主结果引用。
4. **direct-benefit controller（替代 v3 的系统方案）**：不做场景级 regime 分类，而是逐 lane（每个 (sender_rank, receiver_rank) 对）、逐 global step 独立决策，用 EWMA credit + 双侧滞回（Schmitt trigger）+ 最小驻留时间决定 full↔low 切换，阈值由 calibration 场景上"降级实际净收益 − 真实编解码开销"直接拟合。
5. **Quality-Constrained Adaptivity Existence Test（2026-07-21）**：检验在真实任务质量约束下，是否存在非空 λ 区间使精细在线策略严格优于粗粒度策略。问题定义保留，但 2026-07-21 产物只能视为**乐观 no-hardgate pilot**，不是纠正后策略的最终判据。

## 3. 实验如何设计（模型、指标、基线、预注册门槛、数据隔离）

**模型**：OLMoE-1B-7B-0924（E64K8）+ LLM-jp（E32K16），跨模型强制复现。

**指标演进**：早期（v1-v3）用**通信字节 saving 比例**（analytic bottleneck-wire 模型：跨 rank 取 max 字节 × 固定 inter-node Gbps）；Existence Test 阶段升级为**真实任务质量指标**——MMLU accuracy delta（绝对，相对 BF16 reference）、incremental accuracy harm（相对 `uniform_full`，因为通信收益也是相对 remote-FP8 增量计的）、逐题 lost/gained-correct count、answer-NLL harm、CVaR（worst-case 尾部 harm）、分层 bootstrap CI；saving 侧同时报告 optimistic codec 和 serialized-tile codec 两种敏感性口径。

**基线/策略候选（Existence Test 五臂）**：`uniform_full`（不降级，remote 用 FP8）、`uniform_low`（remote 全部降 INT4）、`calib_static`（纯离线校准画像）、`causal_no_hysteresis`（因果阈值，无滞回）、`controller`（direct-benefit EWMA + 滞回）。

**预注册门槛（2026-07-21 Existence Test）**：
- **GO**：至少一种真实任务 harm 口径下存在非空 λ 区间；该区间内 `controller` 或 `causal_no_hysteresis` 严格优于三个粗粒度策略；优势在两个模型或两个 workload cell（balanced/hotspot）中复现；相对最佳粗粒度策略的预期收益 ≥3%，且在 serialized-tile codec 上界下不消失；bootstrap 后 winner 不是由一两道题翻转造成。
- **NO-GO**：所有可信 λ 区间都被三类粗粒度策略覆盖；精细在线 arm 只在 NLL 代理上获胜但 accuracy/CVaR 不支持；优势只存在于乐观 codec 假设；或增量 <3%。

**Codec 硬门槛（2026-07-21 纠正版）**：目标主配置是 `homo_int4 + codec_tax_mode=once_per_step + require_positive_net_saving + H2D`；`serialized_tiles` 仅作悲观敏感性，拦截时回滚 controller 状态。**2026-07-22 代码核对：旧任务质量入口没有传 `require_positive_net_saving/H2D/measured_rows`，因此已有产物未实现这一口径。**

**数据隔离**：v2 用 WikiText-103（40 篇/模型，offset=0，此前从未被本项目任何实验触碰的干净 sealed 语料）；v3 检测器只用 calibration 场景拟合门槛，test 场景的检测只用因果合法的前 30% global step；Existence Test 阶段 calibration questions 只用于拟合 load scale 和 static profile，test questions 从不用于调阈值。

## 4. 代码怎么组织（入口脚本、关键模块、数据流一句话）

**关键模块**：`receiver_lane_policy.py`（`ReceiverPolicyConfig` + `ReceiverLaneController`，定义 5 个 arm 的逐 lane 精度决策逻辑、EWMA credit、滞回、`require_positive_net_saving` 硬门槛、codec tax 会计）；`test_receiver_lane_policy.py`（对 lane policy 的单元测试，验证 local pair 不被量化、`uniform_full` 只对 remote 用高精度等边界行为）。

**入口脚本演进链**：
- `run_receiver_isolation_experiment.py`：v1 混淆隔离，剥离"偏好远程"confound，验证热点识别本身独立于混淆有效。
- `run_receiver_aware_v2_systematic.py`：v2 系统回放主脚本，构造跨模型/跨文档/时序错位到达的场景，实现"基准+增量修正"的高效字节核算；被 v3 和 v3 因果审计脚本 import 复用核心函数（`build_scenario`/`placement_map`/`remote_loads_by_step`/`select_indices`）。
- `run_receiver_aware_v3_adaptive.py`：v3 检测器 + 自适应控制器（**结论已被推翻，脚本保留作演进记录**）。
- `run_receiver_aware_v3_causal_audit.py`：修正 v3 的因果泄漏 bug（warm-up 固定用 random，检测 cutoff 后才应用检测策略；static profile 统一用 hotspot calibration 构建），产出撤回结论的证据。
- `run_receiver_direct_benefit_controller.py`：替代 v3 的逐 lane EWMA+滞回 controller，阈值用真实 Triton codec 开销（`run_receiver_codec_break_even_gpu.py` 产物）直接拟合。
- `analyze_receiver_aware_bandit_offline_replay.py`：对 direct-benefit 产出的 4-arm 全信息奖励表做离线 UCB1 bandit 回放（regime-aware vs regime-free），诊断方向是否有潜力。
- `analyze_receiver_aware_quality_constrained_reward.py`：把 `saving − λ × low_frac × KL_uniform_low` 线性代理 reward 引入 4 个 low-bit 策略 + `uniform_full`，扫描 λ 找 crossover——这是 Existence Test 的前身（诊断性，非决定性，因为 `low_frac` 是线性近似代理而非真实逐策略 KL）。
- `run_receiver_aware_task_quality_gpu.py`：Existence Test 入口。2026-07-22 已修正为默认开启 positive-net-saving hard gate，传入 H2D tax 和 measured rows；`--no-require-positive-net-saving` 只用于复现旧乐观口径。**修正后尚未 GPU 重跑。**
- `run_homogeneous_lane_codec_gate_gpu.py`：真实 Triton kernel 测量 homogeneous FP8/INT4 的 pack→pinned H2D→unpack 延迟。
- `analyze_receiver_codec_hardgate_replay.py`：把 codec 硬门槛离线应用到已有 `*_steps.csv` 轨迹，重算 `once_per_step`/`serialized_tiles` 两种口径下的净收益与拦截率。
- `run_receiver_aware.py`：早期 FP8+tail-INT4 + receiver_group 综合验证（TBT proxy），产出 max-receiver-bytes/imbalance 等指标。
- `run_receiver_control.py`/`run_receiver_sender_decomposition.py`/`run_receiver_profile.py`：receiver 信号拆解（receiver-side vs sender-side 分量）与稳定性分析支撑脚本。

**数据流一句话**：真实路由 trace（OLMoE/LLM-jp 真实 forward 采集）→ 按 origin_mode（balanced/hotspot）和到达时序构造并发场景 → `ReceiverLaneController` 逐 step 逐 lane 决定 full/low → 分析式字节账本算 saving（+真实 codec tax）；Existence Test 版本额外在真实 expert output 上应用该决策算 MMLU accuracy/NLL/CVaR → bootstrap CI → 按 λ 求逐点 reward winner。

## 5. 演进路径（时间线：提出→实验轮次→正/负结果→当前状态）

| 时间 | 事件 | 结果 |
|---|---|---|
| 2026-07-13 前 | 提出 receiver-aware v1，用"偏好远程"混合"识别热点"的打分函数 | 表面上 `tail_budget_profile_ports`/`scheduler_receiver`/`greedy_ports` 效果相近 |
| 2026-07-11 | 发现 `run_ep_congestion_sim.py` 给所有非 random 策略强制加 remote bonus（confound） | 剥离后：`hot` 仍稳定跑赢 `random`（热点识别本身有独立价值，方向没错），但"三种 selector 效果相近"是假象；receiver-side 信号可离线部署，sender-side 信号跨样本 Spearman 仅 0.39-0.50，非平稳、不可离线 profile |
| 2026-07-20 v2 系统重跑 | 跨模型（OLMoE+LLM-jp）、跨文档（WikiText-103 40篇/模型）、时序动态、信息陈旧度三级分层，24 seeds | **hotspot**：oracle/causal/calib_static 几乎重合（+5.6%~+11.1%），静态画像够用；**balanced**：`oracle_same_step` 正（+2.3%~+6.1%），但现实可行的 `causal_prev_step` 反转为负（-1.1%~-2.8%）；staleness cost 稳定 +4.2%~+8.0%，24 seeds 几乎全部落在 random 95% CI 之外 |
| 2026-07-20 v3 | 因果合法 Herfindahl 集中度检测器 + 自适应切换，号称两模型上全面超过三个固定基线 | 声称正结果（adaptive 0.1706/0.1729 vs 最强固定基线 0.1643/0.1594） |
| 2026-07-20 v3 因果审计 | 发现 `total_saving()` 把检测后才选定的策略回溯应用到 warm-up 期（look-ahead bias） | **结论撤回**：修正后 adaptive 相对 `always_causal_prev_step` 的优势在 4 detect_frac × 2 模型组合下 95% CI 全部跨 0 |
| 2026-07-20 | 转向逐 lane direct-benefit + 滞回 controller，阈值用真实 Triton codec 开销拟合 | **模型依赖**：LLM-jp 上 controller 相对 causal_no_hysteresis 有小但显著增益（+0.91pp，CI[0.23,1.62]pp）；OLMoE 上无显著增益（CI 跨 0）；暴露"hysteresis 价值可能依赖专家数/EP 拓扑规模"这一新变量 |
| 2026-07-20 | expert placement 优化（LPT 贪心均衡分箱）尝试作为 receiver-aware 系统侧的补充杠杆 | **干净负结果**：四格里两格统计显著更差；根因是评测用的瞬时/尾部 max 指标与平均负载均衡目标不匹配（mean-balancing ≠ tail-balancing），不建议继续投入 placement 变体 |
| 2026-07-21 Codec 硬门槛 | 真实 Triton pack/H2D/unpack 测量 + 会计纠错（serialized 缩放、smoke hidden 修正、拦截回滚状态） | 均质微基准 serving 点 0/8 viable（悲观界下仍紧）；但**融合 kernel（once_per_step）主口径下 hotspot 轨迹可正净收益**，此前 `NO_SYSTEM_NET_GAIN` 判决作废，改判 `MIXED_FUSED` |
| 2026-07-21 Existence Test | `run_receiver_aware_task_quality_gpu.py` 任务质量 pilot，两模型×两 workload | 乐观 no-hardgate 设置下仍无稳定 GO 区间，winner probability 最高约 46%，是负向信号。`SUPERSEDED`：把它当作纠正 hard-gated action policy 的最终 NO-GO |

## 6. 当前结论与边界

**当前结论**：结构性 hotspot 下 static profile 几乎覆盖可实现收益、balanced 下滞后在线信号不足的结构结论保留。精细在线 controller 在乐观 pilot 中无稳定优势，但纠正后 hard-gated policy 仍是**未验证**；只允许一次冻结配置重跑，不过即停。

**明确边界**：
- **不要**再引用"HHI v3 自适应全面优于固定基线"这一撤回的结论；
- 结构性拥塞下的静态画像证据仍然有效，可作为受限的正结果写入论文；
- Codec 硬门槛纠正后不能再说"在线降级已彻底无净收益"——融合 kernel 主口径下 hotspot 轨迹仍可正净收益，但均质微基准在悲观界下仍紧；H2D 实测 ≠ 真实 RDMA；
- 不建议继续投入 placement 变体或更复杂 regime 分类器；在纠正后 Existence Test 过门前不进多节点 RDMA；
- 全部证据仍是**带宽/字节分析回放**（除 codec 硬门槛用真实 Triton kernel 测量），没有真实 RDMA 队列/incast/collective 测量。

**定位**：作为「结构证据 + 条件性边界」写入论文，明确交代乐观 pilot 的负向信号和 hard-gate 配置错位；不作系统主贡献，不因「有多 GPU」直接启动 RDMA 系统化。
