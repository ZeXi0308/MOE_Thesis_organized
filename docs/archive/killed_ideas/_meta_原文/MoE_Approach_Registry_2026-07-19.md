## 跨路线元发现（比任何单一候选更重要）

**元模式一：效应量天花板。** 四条独立机制（精度分配、充分统计量压缩、receiver credit、故障域副本分配）中，三条留下了可测的效应量数字，全部落在 5%-10% 量级而不是决定性的量级：RouteFidelity 的 regret 上限 2.5%（门槛 5%）；MassCover 的相对改善 4.7%-6.6%（门槛 10%）；CreditReduce 虽未到"接近但不够"的区间，而是"完全不需要"（uniform FP8 已 dominant）。这不太像三次巧合，更像是在 OLMoE(top-8)/LLM-jp(top-16) 这两个中等规模 MoE 的路由统计结构下，**简单静态信号（gate mass、frequency、uniform FP8）已经吃掉了大部分可挖掘空间**，复杂机制的边际收益系统性地不够跨过论文级别的显著性门槛。

**元模式二：全部发生在同一因果层。** 四条路线的决策对象都是"给定固定的 route/expert-output 之后，如何重新分配精度/统计量/信用/副本"——即 route-level 或 placement-level 的静态重分配。没有一条路线触碰过执行时间线本身：expert compute 与 combine 之间的重叠窗口、多 wave/多 layer 之间的 pipeline bubble、dispatch 与 combine 的相位差、以及这些时间关系如何随 batch/EP 配置变化。**TokenRace-EP 是第一条切到这个因果层的路线，且是首个未被干净判死的候选**——说明切换因果层这个策略方向是对的，但天花板依然存在，只是位置从"是否有效应"移到了"效应能否稳健跨模型泛化"。

**元模式四：即使切换因果层，5%-10% 附近的边界仍在复现。** TokenRace-EP 在 OLMoE 上效应扎实(11%+)，但在 LLM-jp 大 batch 上的真实效应量精确落在 5.4%±0.3%——与 RouteFidelity 的 2.5%(门槛5%)、MassCover 的 4.7%-6.6%(门槛10%)一样，又一次卡在门槛附近。这进一步支持"这两个模型的路由/负载统计结构本身存在一个大约5%-10%量级的可挖掘空间上限"的猜想，且这个上限似乎与具体机制类型无关，可能是更底层的统计性质（K、专家数、负载均衡度）决定的。

**元模式三：novelty 碰撞集中在系统层，不是算法层。** WaveCredit 的死因和前三条不同——不是效应量不够，而是机制本身已被 UCCL-EP、FAST 等 2025-2026 新系统工作用更完整的形式实现。这提示继续在"通信控制/调度"这个大方向里找新点子时，必须先做严格的官方代码/论文碰撞检查，而不是先做 P0 数值实验。

**元模式五：仿真信号在真实硬件上可能发生符号反转，不只是幅度衰减。** TokenRace-EP 是本项目第一条真正跑到 GPU 上验证的路线，结果显示 Mac 仿真严重低估了真实 kernel launch 固定开销（约10倍：真实~57us vs illustrative 6us），且完全没有建模"重批"本身的开销（~26.6-27.1us/层）。这不仅把 OLMoE 的安全边际从 10%-22% 压缩到 6%-8%，还把 LLM-jp 从"卡在5%门槛边缘"直接反转成 -10%~-11% 的净负收益。这提示：**任何仅在 Mac/CPU 仿真上得出的"卡边界"结论，在纳入真实硬件的固定实现开销后，符号都有可能反转，不能假设它只是幅度上的衰减**——这是比"5%-10%天花板"更严重的一类风险，后续任何候选只要涉及"更细粒度的动态操作"（更小的kernel、更频繁的调度决策），都应尽早用真实硬件测一次固定开销，而不是在 Mac 仿真上反复打磨参数敏感性。

**元模式六：简单静态信号在这套 MoE EP 系统里普遍已经逼近 oracle 上限，"改进空间"本身就薄，不是执行细节没做好。** 2026-07-20 对 TokenRace-EP 和 MassCover-EP 做了"能否用 knob/更聪明算法挽回"的复查：(a) TokenRace-EP 尝试用免费的因果信号（确定性负载不均衡，噪声实现前就已知）做自适应触发，结果发现只要阈值超过约0.5×重批开销，触发率直接归零——它的收益几乎全部来自不可预测的噪声/straggler事件，而免费信号对这类事件毫无预测力，这不是调参能解决的，是机制内在矛盾（能救它的信号恰恰不可能免费获得）；(b) MassCover-EP 的 `cvar_greedy` 相对 `oracle_cvar`（事后最优解上限）的差距只有 0.02%-0.7%，几乎已经是完美算法，而上限本身相对 `gate_mass` 简单baseline的天花板只有 2.1%-7.1%，budget 从2%提到10%也没有明显抬升——问题不是算法不够聪明，是 gate_mass 这类简单静态信号已经把可挖掘空间吃掉了大半，连站在上帝视角的 oracle 都摸不到10%门槛。这与 receiver-aware v2 的教训（价值被限定在"静态画像已经够用"的场景）是同一模式的第三次重现：**后续候选如果只是在"给定简单静态baseline"的基础上做更聪明的重分配/调度，天花板可能天生就在5-10%区间，应该优先检验 oracle 上限而不是急于优化算法本身**，详见 `已死路线_knob优化复查_2026-07-20.md`。

**元模式七：函数形式假设本身错误时，任何轻量校正都无法挽救——不是信号不够强，是外推方式本身矛盾。** 2026-07-20 复查了additive-KL MILP的死因，把"不可加"拆解成路由漂移和纯数值误差两个独立来源：用`lock_routing`机制排除跨层路由漂移后，纯数值误差本身依然严重不可加（`locked_additive`相对真实联合效果高估3.77倍，95%CI [3.67,3.87]远离1.0，n=32 sealed test）；进一步用校准集学到的全局漂移比例做最廉价的校正（`locked_additive_plus_global_drift`），误差只从4.63倍降到2.51倍，仍远不可用。说明不可加性的主因不是路由漂移可以被建模修正的那部分，而是量化误差在残差流里存在饱和/部分抵消的非线性交互，是函数形式（加性）本身与真实机制矛盾。**这提醒后续任何"用单点/单层profiling线性外推组合效果"的候选，必须先做类似的联合vs独立对照检验，而不是假设"调一个校正系数就能救"**，详见`experiments/idea_a_mac/outputs/additive_kl_audit_2026-07-20/Additive-KL建模审计_最终结论_2026-07-20.md`。

**元模式八：检验必要条件比检验最终质量指标更省时间——先问"这个前提在真实权重上成立吗"，而不是直接跑端到端质量实验。** 2026-07-20 用免训练截断SVD给 Tiered-Fidelity Shadow Experts 和 Residual-EP 做P0：Residual-EP的核心论证依赖"共享基座之后的残差比原始专家权重更低秩"，这是一个可以独立于任何质量实验、直接用`torch.linalg.svd`在几分钟内检验的必要条件——检验结果是残差有效秩与原始权重几乎相同(甚至略高)，直接证伪了前提，且质量实验（跑完才发现shadow和residual两种模式的KL在全部rank档位统计不可区分）只是再次确认了这个必要条件检验早就能预见的结果。**这提示后续任何"分解/压缩类"候选，应该先用几行代码检验分解结构本身的假设（秩、稀疏度、方差集中度等）是否在真实模型权重上成立，再决定是否值得花GPU时间跑端到端质量/延迟实验**，详见`experiments/idea_a_mac/run_tiered_fidelity_residual_svd_p0.py`与`outputs/2026-07-20_四项后续任务_综合结论.md`。

**元模式九：同一个"训练无关的causal信号"，在这套系统里有时极强（文档难度跨机制迁移，Spearman 0.75-0.98）、有时完全没有区分力（TokenRace-EP的确定性负载不均衡）——不能预先假设"确定性/免费的信号就一定有用"或"一定没用"，必须逐案实测。** Per-request Quality Isolation 的可行性恰恰来自一个免费信号（另一个已经计算过的降级机制的KL）具有极强的跨机制预测力；而 TokenRace-EP 的自适应触发失败恰恰来自另一个免费信号（专家路由的确定性负载差）几乎没有预测力。两者的免费信号的"来源结构"不同：前者预测的是**文档/请求的内在属性**（跨机制稳定），后者预测的是**逐token的瞬时随机噪声**（本质上不可预测）。**这提示评估任何"用免费信号做优化"的候选时，第一步应该先分类这个信号试图预测的对象是"稳定的内在属性"还是"瞬时随机事件"，前者大概率可行，后者大概率不可行**，与receiver-aware v2(结构性拥塞可预测、瞬时拥塞不可预测)是同一分类原则的第三次印证。

**元模式十：用更真实的compute代理替换粗糙代理时，"信号存在"和"信号能转化为端到端收益"是两个独立的问题，后者可能随代理精度提升而反转符号。** 专家预取系统原型v1用逐专家Python循环做compute代理（OLMoE 10ms/层），端到端收益虽小但为正(+2-3%)；换成融合`torch.bmm`compute代理后（543us/层，18.6倍加速，更接近生产级kernel），如果不同时调整预取预算，固定预算=8会让端到端收益**反转为负**(-33%/-26%)——因为原来10ms的compute窗口足够掩盖8次预取的H2D时间，新的543us窗口装不下。修复方式是把预取预算从"统计学最优"(P0-C标准)动态收紧为"当前compute窗口能免费掩盖多少个"，收紧后收益重新转正(+5.32%/+3.07%)。**这提示任何"预取/预计算类"系统设计，budget大小必须与实际执行环境的compute-communication overlap窗口联动，不能只按脱离硬件上下文的统计最优来定**，这是TokenRace-EP"仿真低估真实开销"教训的镜像版本——这次不是开销被低估，而是开销被高估后，一旦纠正过来，原本"看似安全"的固定预算反而变得过度激进。

**元模式十一：系统模拟里最危险的错误不是统计方法，而是"对象身份"定义错误——这类bug会同时污染baseline和treatment，不会被常规的显著性检验发现，只能靠"这个key在物理上唯一标识什么"这个问题揪出来。** 2026-07-20的批判审计发现两个独立的严重bug：①专家预取系统原型的`LRUCache`只用`expert_id`做key，没有`layer_id`，导致16层×64专家的模型里，第4层3号专家和第5层3号专家（完全不同的权重张量）被当成同一个缓存对象，产生大量不存在的"跨层命中"；②receiver-aware v3的`total_saving()`对完整场景（包括warm-up期）打分，把检测cutoff之后才选定的策略，回溯应用到cutoff之前——本质上是让controller"看见了后面才知道该用什么策略，然后假装warm-up期也一直在用这个策略"，是look-ahead bias的一种。这两个bug都**不会在"reactive vs predictive/adaptive哪个更好"的对比里报错**，因为它们同时污染了对比双方的某个组成部分，检验统计量(bootstrap CI、显著性)全部正常运行、结果看起来完全"干净"——**唯一能发现它们的方法是重新审视"这个数据结构的key/这个时间窗口边界，在物理/因果意义上到底代表什么"**，而不是加更多统计检验。同时这次审计还发现一个纯"实验设计"层面的问题：专家预取只测了top-1，但真实combine需要完整top-k，一旦补上full top-k，working set本身就饱和到"几乎所有专家都要用"（LLM-jp 91.2%的layer-batch需要全部32个专家），使"预测该预取谁"这个问题在这个batch size下根本没有意义——**这提示任何"简化到top-1/简化到单一决策变量"的P0设计，在证明信号存在之后，必须补一次"简化是否抹掉了问题本身"的检验，而不能默认简化版本的结论能直接外推到真实系统的完整版本**。
