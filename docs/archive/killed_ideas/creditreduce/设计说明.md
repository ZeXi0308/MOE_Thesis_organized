# 名称

CreditReduce（路由碰撞信用驱动的动态混合精度 Combine）

## 1. 背景与问题

在 EP（Expert Parallel）hierarchical combine 中，本地/远端 partial 常常需要统一 cast 成模型 dtype（如 BF16）才能继续传输或累加，这个转换会引入中间舍入误差。项目观察到：当同一 token 的多个专家贡献在远端发生"碰撞"（即多个专家贡献落在同一目标 domain）时，理论上可以先把这些贡献在本地按更高精度（FP32）累计，省下的字节可以被视为一种"信用"（credit），用来资助部分传输组升级到更高精度（FP32），从而在数值质量敏感处花钱、别处省钱。这是一个动态精度分配思路，试图利用路由碰撞产生的结构性冗余做免费的收益。

## 2. 核心思想 / 机制主张

- 对每个 token t，定义其远端贡献数 `K_{r,t}`（来自非 home domain 的专家贡献数）、非空远端 domains 数 `D_{r,t}`、远端碰撞组数 `C_{r,t}`（同一 domain 内 ≥2 条贡献）。
- 静态强基线 `PD-Full`：碰撞组发 FP32，非碰撞组发 BF16，远端字节上界为 `2H(D_r+C_r)`，且与 `uniform_early_fp32` 数值完全一致（这是必须满足的不变量）。
- `CreditReduce` 动态选择器（P0-2 阶段设计，实际未被执行）：仅对满足数值 eligibility（`C_r>=1` 且存在 home 侧额外 addend）的碰撞组，用一个全局 `residual/frozen_layer_RMS` 阈值 theta 决定是否升级到 FP32，未升级则用 BF16。
- 声称的收益：动态门控相比 `PD-Full` 在保持质量 NONINFERIOR 的同时，进一步节省远端字节（P0-2 门槛要求相对 `PD-Full` payload 至少再省 15%）。
- 核心待检验前提：本地合并再 cast 到 BF16（`clean_early_bf16`）在完整模型质量尺度下是否真的"有病"（即是否违反质量 margin）——这是整套 credit 机制存在的必要条件，如果本来就没有可探测的精度损伤，"资助升级"就无的放矢。

## 3. 实验如何设计

- **P0-1（数值 sealed holdout，唯一被真正执行的阶段）**：在 OLMoE-1B-7B（E64/top-8）和 LLM-jp（E32/top-16）两个真实模型上，用全新未污染的 WikiText-2 train-split 文档（各 64 篇，seq_len=256，teacher-forced、batch=1），冻结 EP8/`ranks_per_domain=4`（两个 source domain）/`contiguous` 主拓扑（`ranks_per_domain=1` 与 `round_robin` 只做 sensitivity），对比六个端点：`late_bf16`（质量 reference）、`stock_early_bf16`、`clean_early_bf16`、`uniform_early_fp32`（数值上界）、`pd_full`（最强静态基线）、`uniform_early_fp8`（低比特强基线）。
- 主质量指标：`delta_NLL_doc = NLL_treatment − NLL_late`，以 document 为统计独立单位，paired bootstrap 10,000 次，单侧 95% CI，非劣 margin 0.005 nats/token，三态判定（`QUALITY_FAIL`/`NONINFERIOR`/`INCONCLUSIVE`）。
- 机会窗口指标：`p_eligible`（碰撞机会占远端贡献的比例）、`rho_credit`（潜在可省字节占比），要求两者 LCB95 分别 ≥20%/≥15%。
- P0-1 生死门要求同时满足：机会窗口达标、`clean_early_bf16` 必须判为 `QUALITY_FAIL`（证明确实存在待修复的精度损伤）、`pd_full` 必须 `NONINFERIOR`、数值不变量 `pd_full == uniform_early_fp32` 全部通过、`uniform_early_fp8` 不能在同等或更优质量下同时提供更低字节（不能构成支配）。
- 预注册明确写死：P0-1 任一门失败则立即停止，P0-2（动态选择器 vs 静态基线的对比）**不得运行**——这不是事后追加的规则。

## 4. 代码怎么组织（scripts/ 下文件角色）

- `creditreduce_reference.py`：纯数值参考实现，定义六个端点（`ENDPOINTS`）的精确算术语义（BF16 contribution 输入契约、canonical 累加顺序、home-domain 特殊处理），只建模逻辑字节，不建模打包、对齐、collective 或实际 kernel/wire。
- `run_creditreduce_p0.py`：P0-1（及为 P0-2 预留）的驱动脚本，负责历史数据排重扫描（递归扫描既往 `data_manifest`，避免复用已用文档）、fresh pool 构建与哈希锁定、跑六端点前向、计算 NLL/KL 指标、执行 paired bootstrap、写出 `decision.json`/`report.md`/`endpoint_summary.csv` 等全部 artifact。
- `test_creditreduce_reference.py`：对参考实现的单元测试（no-op 不变量、碰撞判据、FP32 累加顺序等边界情形）。
- `test_run_creditreduce_p0.py`：对驱动脚本内部工具函数（历史哈希提取、行哈希、bootstrap、gate 阈值判定）的单元测试。

## 5. 演进路径

`CreditReduce_P0_预注册_2026-07-17.md` 一次性冻结了完整的数值语义、topology、统计口径与三态判定规则，并明确列出预注册允许的唯一三种结局：① P0-1 失败即杀死动态核心；② P0-1 通过但 P0-2 失败，则证明 precision dividend 存在但动态 selector 不成立，主方案仍判死；③ 两者都通过才进入单 GPU kernel（且仍不声称通信加速）。该文档冻结当天（2026-07-17）即完成执行，直接命中第一种结局：两个模型 P0-1 均判 `FAIL`，P0-2 未运行。`../errata/判死结论勘误_2026-07-21.md`（2026-07-21 的项目级纠错复核）明确将 CreditReduce 列入"仍可信的判死（本次不改）"，未被后续任何纠错文档翻案。

## 6. 判死结论与不要再怎么救

**KILLED（纠错后维持）**。两个模型的机会窗口 gate 都远超门槛（OLMoE `p_eligible`=99.0%、`rho_credit`=74.7%；LLM-jp 分别 100%/87.5%），说明碰撞机会本身完全充分，不是失败原因；但两个关键质量/支配 gate 双双失败：(1) `clean_early_bf16` 在两模型上都是 `NONINFERIOR`（UCB95 `delta_NLL` 分别 0.00145/0.00112，远低于 0.005 margin）——本地合并引入的 BF16 中间舍入误差在完整模型质量尺度下根本不构成可探测伤害，CreditReduce 想修复的"病"并不存在；(2) `uniform_early_fp8` 同时满足质量合格（`NONINFERIOR`）且字节数远低于 `pd_full`（OLMoE 536.8MB vs 2118.9MB，只省 87.49% vs 50.63%；LLM-jp 135.3MB vs 536.9MB，93.70% vs 74.99%），构成明确支配。**不要再换信用公式，也不要再扫阈值**——没有可探测的误差就没有 credit 机制存在的空间，这是前提层面的失败，不是参数没调好能救回来的问题。
