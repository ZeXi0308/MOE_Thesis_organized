# TokenRace-EP P0 正式结论：CONDITIONAL / EXPLORATORY_SIGNAL（不是干净 PASS）

> 日期：2026-07-19
> 代码：`experiments/idea_a_mac/run_tokenrace_ep_p0.py`
> 数据：真实路由 trace（OLMoE-1B-7B E64/top8、LLM-jp E32/top16 各自的 `*_frozen_confirm_2026-07-14/test_routes.csv`，16 层完整路由，非合成数据）
> 机制：对比"全 batch 同步 combine 屏障"vs"逐 token 提前释放"两种放行策略下的累计跨层 TBT 代理指标
> 证据标签：本节所有数字均为 `[Observed]`（本次仿真直接算出），但底层 compute/variance 模型本身是 `[Hypothesis]`（Mac 上没有真实 GPU 计时，量级为示意性参数）

## 一句话结论

**这是本项目五条路线里第一个没有被干净判死的候选，但也不是无条件 PASS。** OLMoE 在所有 batch size、所有噪声场景下都以很大安全边际通过预注册门槛（moderate 场景 P99 改善 11.6%-15.6%，severe 场景 24%-27%）；LLM-jp 在小 batch（32）稳定通过（P99 改善约 5.7%-7.4%），但在较大 batch（64、128）的 P99 指标上卡在门槛边缘——6 个随机种子重复测量给出 LLM-jp B=128 moderate 场景 P99 改善均值 5.4%±0.3%（范围 4.87%-5.83%），恰好横跨预注册的 5% 门槛，时而通过时而不通过。

## 统计稳健性检查过程

第一次跑（300 decode-step 样本）：gate=FAIL，LLM-jp B=64/128 的 P99 改善分别是 4.94%/4.38%。第二次把样本量提到 2000（种子不变）：gate=PASS，同样两个配置变成 5.91%/5.30%——说明 300 样本对 P99 的估计噪声很大，不能直接采信。为了排除是"换了个种子就变好看"的偶然性，额外用 6 个不同随机种子（1、2、3、4、20260719、777）在 n=2000、B=128、moderate 场景下重复测量 LLM-jp 的 P99 改善，结果为 5.49%、5.83%、5.61%、5.30%、5.30%、4.87%，均值 5.4%、标准差 0.3%。这不是噪声主导的假阳性/假阴性，而是一个真实存在但幅度恰好落在门槛附近的效应——这与本项目 Approach Registry 记录的"效应量天花板往往卡在 5%-10% 区间"的元模式再次吻合。

## 分模型结果（n=2000，seed=20260719）

**OLMoE-1B-7B (E64/top8)**：zero-variance 场景（none）已经因为真实路由的负载不均而有 2%-10% 的改善（不依赖任何硬件抖动假设）；moderate 场景 P50 改善 14.2%-17.0%，P99 改善 11.6%-15.6%；severe 场景 P50 改善 32%-35%，P99 改善 24%-27%。三个 batch size（32/64/128）、三个噪声场景全部远超 5% 门槛，是稳健的正结果。

**LLM-jp E32/top16**：zero-variance 场景改善极小（0.33%-1.14%），说明该模型路由本身相当均衡，效应几乎全部来自硬件抖动/straggler 假设，不是负载不均的副产品；moderate 场景 P50 改善稳定在 5.97%-6.66%，mean 改善 5.86%-6.48%，但 P99 改善只有 5.30%-5.91%（point estimate）/ 真实值约 5.4%±0.3%（6 seed 均值），处于门槛边缘；severe 场景 P50 改善回升到 14.6%-15.0%，P99 改善 9.79%-10.59%，明确高于门槛。

## 为什么不直接判 PASS，也不判 KILL

预注册规则要求"两个模型、所有 batch size 的 moderate 场景 P99 改善必须全部 ≥5%"。严格按字面执行，LLM-jp 在大 batch 上的真实效应量（约 5.4%）统计上无法确定地、稳健地清楚超过 5%——这不是可以四舍五入忽略的问题，而是需要如实记录的边界情况。同时，效应绝对不是零或负值：OLMoE 一侧证据非常扎实，LLM-jp 一侧在 P50/mean 上也稳定为正且明显不是噪声（zero-variance 对照组已经排除了"这只是负载不均artifact"的可能性）。因此最诚实的判决是 **CONDITIONAL / EXPLORATORY_SIGNAL**：机制方向是对的、在至少一个模型上效应扎实，但要作为跨模型通用结论投稿，需要先解决 LLM-jp 大 batch 下 P99 为什么恰好卡在门槔附近这个问题。

## 对"卡边界"现象的初步归因（未验证，[Hypothesis]）

LLM-jp 是 top-16（更大 K）、32 个专家（更少专家数），意味着几乎每个专家在每个 decode step 都会被绝大多数 token 命中（负载天然更均衡，这与其 zero-variance 改善接近 0 一致）；同时更大的 K 意味着每个 token 需要等待更多专家里最慢的那个，token 自己的"最大值 in K"本身就已经比 OLMoE（K=8）更接近全局最大值，压缩了 token-race 相对 barrier 能拉开的差距。这是一个可能成立的结构性解释，但目前只是根据两个模型的对比归纳出的假设，需要用第三个 top-k 配置（比如 top-2 或 top-4 的对照组）来检验"K 越大、token-race 收益越小"这个猜想是否成立。

## 下一步建议（不建议现在投入 GPU）

在把这条线送进单 GPU 验证之前，应该先做一次轻量的 P0-B 来解决这个边界疑点：一是加入 top-4 或 top-2 的第三个对照配置，检验"收益随 K 增大而收缩"这个假设方向是否成立，这能帮助判断 LLM-jp 的边界结果是一般规律还是这个模型的特例；二是把当前的 attn/expert compute 时间模型换成对 backend 更贴近的参数敏感性扫描（当前 BASE_LAUNCH_US、PER_TOKEN_US 是示意性的，需要确认结论不是对这两个参数的具体取值过度敏感）；三是如果上述两项都确认效应稳健，再决定是否把 claim 收窄为"K 较小的 MoE 配置（如 OLMoE 式 top-8 及以下）"，而不是笼统声称对所有 top-k 都成立。这三项都可以在 Mac 上用几十分钟完成，不需要 GPU。
