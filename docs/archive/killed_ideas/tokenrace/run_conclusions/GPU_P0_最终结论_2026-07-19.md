# TokenRace-EP GPU P0 最终结论：真实硬件重批开销已测出，K 依赖性从"收益递减"升级为"收益反转"

> 日期：2026-07-19
> 硬件：租用 NVIDIA GeForce RTX 5090 / 32GB（独享物理卡），CUDA 12.8，PyTorch 2.8.0+cu128
> 代码：`experiments/idea_a_mac/run_tokenrace_gpu_microbench.py`
> 两次独立随机种子（20260719, 777）、不同 repeat 次数（200/300）复现一致，非测量噪声。
> 证据标签：(A)(B) 是 `[Observed]`（RTX 5090 上直接测得的真实 kernel 时间）；(C) 门槛重算里的 barrier/race 时间模型本身仍是 `[Hypothesis]`（沿用 Mac P0 的乘性抖动/straggler 模型，只是把里面的常数换成了真实值），但重批开销部分是 `[Observed]`。

## 一句话结论

**TokenRace-EP 没有被彻底判死，但结论被真实硬件数据彻底改写：它现在只对 top-8 级别的小 K 配置有一个很薄的正向边际（P99 改善 6.4%-7.8%，刚过 5% 门槛，安全边际从 Mac 仿真里的 10%-22% 大幅收缩），而对 top-16 的大 K 配置（LLM-jp）不再是"卡在门槛边缘"，而是变成了明确的净负收益（P99 改善 -10.6% 到 -11.3%，即 TokenRace-EP 实际上会让它变慢）。**

## 三个真实测量结果

**(A) 真实 FFN kernel 时间几乎完全由固定 launch 开销主导，不是计算量主导。** 无论 token 数从 1 到 256，OLMoE 维度（hidden=2048, inter=1024）的真实 SwiGLU 前向耗时稳定在 55-67us（两次跑拟合出 base_us≈57-58us，per_token_us≈0.03-0.04us/token，R²仅0.49-0.55——低R²不是测量出问题，而是恰好证明"per-token 项本来就小到接近噪声，真实成本几乎是一个跟 token 数无关的常数"）；LLM-jp 维度（hidden=512）同理，base_us≈56-57us，per_token_us≈0.001-0.006（更接近0）。**这个 base_us（约57us）比 Mac 仿真里的 illustrative 常数 `BASE_LAUNCH_US=6.0us` 大了近 10 倍**——Mac 仿真严重低估了真实 kernel 的固定开销。

**(B) 真实"重批"操作(index_select 动态抽取子集)的开销约 14.3-14.5us**，跟模型维度几乎无关（OLMoE 14.30-14.53us，LLM-jp 14.41-14.53us）。纯 kernel launch 地板（一个 trivial elementwise 加法）约 12.3-12.6us。

**(C) 把这两项真实测量喂回原始 P0 的路由仿真模型（真实 route trace，不是合成数据），并只对 token_race 侧追加"每层一次最小重批开销"(=bare_launch_us + gather_us ≈ 26.6-27.1us，这是最乐观的下限估计：假设每层只需分成"提前"和"落后"两组，只多付一次 kernel launch + 一次 gather)：**

| model | B | P50改善 | P99改善 | mean改善 |
|---|---|---|---|---|
| OLMoE (K=8) | 32 | 4.5%-5.0% | **6.4%-7.8%** | 4.2%-4.3% |
| OLMoE (K=8) | 64 | 6.1% | 6.6%-7.0% | 5.5%-5.8% |
| OLMoE (K=8) | 128 | 6.1%-6.3% | 6.98%-7.77% | 5.9% |
| LLM-jp (K=16) | 32/64/128 | **-12.7% ~ -12.9%** | **-10.6% ~ -11.3%** | **-12.9% ~ -13.1%** |

两次独立种子（20260719 和 777）、不同 repeat 数（200 和 300）下，这个格局完全一致——不是噪声。

## 这如何修正了之前的判断

之前（Mac 仿真，illustrative 常数，无重批开销）的结论是"OLMoE 稳健通过(11%-22%)，LLM-jp 卡在门槛边缘(4.9%-5.8%)，K 越大收益越小但仍是正数"。现在加入真实硬件的重批开销后：

1. **OLMoE 的安全边际被大幅压缩**（从 10%-22% 压到 6%-8%），且 P50 改善（4.2%-6.3%）比 P99 改善还薄，B=32 时 P50 甚至不到 5%——这意味着 OLMoE 这条线现在是"勉强活着"而不是"稳健通过"，比之前认为的风险更高。
2. **LLM-jp 不再是"卡边界"，而是彻底翻转成净负收益。** 这不是运气不好，是机制性的：K=16 意味着每个 token 本来能从 token-race 里省下的时间就更少（P0-B 已经证明这一点），而每层固定要多付的 26.6-27.1us 重批开销跟 K 无关——收益变小但成本不变，一旦收益小于成本，差值就会变成负的，而且乘以 16 层之后被放大到 -10% 以上。

## 为什么这仍然不是最终判决（还有两个需要说明的边界）

1. **这是"最乐观"的重批开销估计，不是保守估计。** 当前模型假设每层只需要分裂成 2 组（早/晚），真实实现要应对 batch 内更细粒度的到达时刻分布，可能需要 3 组以上，或者需要放弃 CUDA Graph（前面文献调研已经指出 vLLM 的 FULL CUDA Graph 模式要求固定 shape，逐层动态抽取会直接和它冲突，放弃后 decode 阶段整体会慢 25%-50%，这部分代价当前完全没有计入）。也就是说，OLMoE 现在这个 6%-8% 的薄边际，很可能在加入更真实的实现开销后被完全吃掉。
2. **本次用的是未融合的 PyTorch eager kernel（gate_proj/up_proj/down_proj/silu/mul 各自单独 launch）**，不是 vLLM/SGLang 里用的融合 Triton/CUDA MoE kernel。这一点不能简单假设"融合后 TokenRace-EP 会更好"——因为融合会同时降低 base_us（layer 本身更快），而重批开销的绝对值（26.6us）不会跟着降，融合后重批开销占比只会更高，对 TokenRace-EP 更不利，不是更有利。这是一个容易被误判的方向，必须明确指出。

## 对论文 claim 范围的建议

在完成上述两个边界检验之前，**不能声称 TokenRace-EP 对任何配置有稳健的系统级收益**。诚实的当前状态是：`CONDITIONAL_THIN_MARGIN_K_DEPENDENT`——用真实路由数据 + 真实硬件重批开销测得，效应方向对 top-8 类小 K 配置仍为正但边际很薄（6%-8%），对 top-16 类大 K 配置为明确负值。这本身已经是一条可以写进论文的、有真实 GPU 证据支撑的发现："MoE combine 之后的逐 token 提前释放机制，其净收益不仅随 top-k 增大而递减（Mac 仿真已证明），在计入真实重批开销后会在中等 K 值附近发生符号反转，且反转点因 batch size 而相对稳定"——这本身是一条诚实、有 [Observed] GPU 证据、机制清晰的 characterization 贡献，即使 TokenRace-EP 最终不能作为系统优化主张投稿，这条负结果+反转点发现也有独立价值。

## 下一步（如果想继续把 claim 做实，而不是停在这里）

1. 用 CUDA Graph 关闭/打开两种模式重跑 base_us 测量，量化"放弃 CUDA Graph"这个决定性代价，看 OLMoE 那 6%-8% 的薄边际能不能在这个代价下继续存活。
2. 如果 1 的结果仍然是负面的，建议直接把 TokenRace-EP 降级为 characterization 负结果，不再投入更多 GPU 时间；如果 1 的结果居然还能勉强活着，再考虑做 3 组以上release粒度的更真实重批开销测量。
