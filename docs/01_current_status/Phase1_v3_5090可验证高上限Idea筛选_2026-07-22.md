## 0. 选择准则与证据标签

- **[Observed]**：仓库证据或一手文献直接支持。
- **[Inferred]**：由对象身份、系统控制域或已知硬件机制推出，尚未实测。
- **[Hypothesis]**：必须由下一阶段冻结协议验证。
- **L1**：单张 RTX 5090 的真实 kernel / latency / board energy / route / leakage 实验。
- **L2**：单卡上的多 receiver、多 tenant、虚拟链路或 queue 代理，只证明局部机制。
- **L3**：由 L1 实测校准的模拟或 replay。
- **L4**：真实多 GPU、多节点、RDMA、production serving 才能验证的最终 claim。

保留候选必须同时满足：

1. 5090 能做一个便宜而决定性的必要性/上限判死门；
2. 最强简单基线没有显然吃掉核心增量；
3. 成功后的系统 claim 可以自然扩展到真实多租户或分布式 MoE serving；
4. novelty 来自新问题/状态/系统能力，而不是换 predictor、controller、loss 或优化器。

关键碰撞边界：

- [VTC](https://www.usenix.org/conference/osdi24/presentation/sheng) 已允许自定义单租户 cost function，因此 RouteShare 不能只做“route-weighted token”；其唯一增量是 **cost 依赖同批其他租户的 route coalition，无法写成每租户独立函数**。
- [DLPM](https://arxiv.org/abs/2501.14312) 已把 locality 与 fairness 联合；[Sem-MoE](https://openreview.net/pdf?id=MSHPrMpIHZ) 和 [XShare](https://arxiv.org/abs/2602.07265) 已利用 expert affinity/overlap。因此 RouteShare 不把 route-compatible packing 写成首要创新。
- [LLMVisor](https://neurips.cc/virtual/2025/129105) 已做实时 per-request GPU latency attribution；[Fair, Practical, and Efficient Carbon Accounting for LLM Serving](https://dl.acm.org/doi/10.1145/3764944.3764967) 已以 Shapley 为多租户归因的公平基准。因此 Shapley、cost attribution 和 virtual counter 本身都不是 novelty。
- [MoEcho](https://arxiv.org/abs/2508.15036) 与 [Expert Selections Reveal Text](https://arxiv.org/abs/2602.04105) 已给出 route footprint 泄漏证据；[CryptoMoE](https://arxiv.org/abs/2511.01197) 与 [SecMoE](https://ojs.aaai.org/index.php/AAAI/article/view/39721) 已保护 secure two-party inference 中的 routing。RouteCloak 必须限定为 **普通共享 GPU / EP serving 的低开销 execution-metadata 防御**，不能声称通用 private inference。

## 3. R1 RouteShare-VTC（条件主线）

### 3.1 一句话论文主张

> MoE continuous batching 中，租户的真实 expert-stage 服务成本取决于其与同批其他租户的 expert union、row histogram 与共享 weight traffic，不能由 token 数或独立 per-request cost 表示；RouteShare 用 O(rows) 的预算平衡 route-cost share 更新 delayed virtual service，在不修改 router、top-k、权重或精度的前提下抑制 route-amplification noisy neighbor。

### 3.2 新增的系统能力

1. router 后保留 `(tenant, request, layer, token, slot, expert)` 与 per-expert row histogram；
2. expert runtime 对完整 batch 输出统一的 `time/energy cost + route footprint`，而不是伪造可加 per-expert 能耗；
3. cost allocator 把 batch 总成本完整、非负、预算平衡地分给租户；
4. virtual-service ledger 在本轮完成后更新，影响下一轮 ready request admission/order；
5. dense attention/KV 部分仍按已有 cost model 收费，只有 routed expert stage 使用 coalition-aware share；
6. 不读取未来 route，不修改 expert selection，不依赖 route predictor。

关键路径变化是：

> `token completion → token counter += 1`

变为：

> `expert batch completion → observed route coalition → budget-balanced cost share → tenant debt → next scheduling action`

### 3.3 建模形式

- **状态**：当前 ready tenants、已完成 batch 的 route histogram、tenant debt、age/deadline、kernel/board state。
- **动作**：下一轮 admission/order；packing 只能作为普通 tie-break，不是创新主张。
- **集合成本**：`C(B)` 为完整 routed expert batch 的真实 GPU time；energy 只作敏感性指标，不能把旧 JouleQueue LUT 相加。
- **成本份额**：`phi_i(B) >= 0`，且 `sum_i phi_i(B) = C(B)`；exact Shapley 只作小 coalition oracle，正式路径优先 O(rows) 的 per-expert fixed-plus-row share 或 serial share。
- **目标**：在 entitlement 与 starvation 约束下，降低 worst-tenant normalized slowdown / SLO violation，同时维持 total throughput。
- **可观测信息**：只使用已完成当前层/当前 step 的 route 与运行时；禁止未来 token/layer route。
- **关键假设**：expert weight/launch/shared-memory cost 使 `C(A union B)` 对 route overlap 非可加，且 effect 足以影响外部 QoS。

### 3.4 与最强简单机制的本质差异

必须先击败以下简单模型，而不是从 fancy Shapley 起步：

```text
C(H) = alpha * total_rows
     + sum_e beta_e * 1[H_e > 0]
```

其中 row-linear 部分按租户 rows 分，expert fixed/weight-read 部分按使用该 expert 的租户 rows 分，再接普通 VTC。

完整基线至少包括：

- token VTC / weighted-token VTC；
- total routed rows / FLOPs；
- active-expert count；
- 上述 `rows + active experts` 简单模型；
- isolated measured-cost VTC；
- leave-one-out marginal share；
- LLMVisor-like resource attribution；
- exact small-coalition Shapley oracle；
- DLPM / pure overlap greedy 作为 scheduling/locality 对照。

RouteShare 的必要性 witness 不是“拟合误差更低”，而是同时出现：

1. token、total rows、active experts 相同或匹配，真实 cost 次序仍不同；
2. 该错误排序在 token VTC 下造成外部定义的 victim slowdown/SLO 差异；
3. route debt 产生 causal action flip，而不只是 dashboard 数字变化。

### 3.5 5090 最小判死协议

#### Gate 0A：真实非加性成本

- 固定模型权重、BF16、kernel、batch size、clock/thermal 区间；
- 从真实模型采集完整 route identity；
- 构造 matched `total rows / top-k / batch size`、不同 expert overlap 的 executable batches；
- 执行完整 grouped-MoE path，计 sort/permute/FC1/activation/FC2/combine；
- CUDA event 报 latency；如报能耗，用同 trial 的 board-energy window，完整 drain；
- 独立样本是独立 route/input event，inner repeats 只估仪器噪声。

**建议冻结判死门：** route structure 在最强简单模型之外的 cost residual / matched contrast 95% CI 下界小于 expert-stage cost 的 `10%`，或 simple model 已解释至少 `90%` executable-oracle gap，则停止。

#### Gate 0B：外部公平反例

两类 tenant 使用相同 token entitlement，但真实 route cost 不同。主指标必须是：

- worst-tenant isolated-normalized slowdown；
- weighted throughput；
- absolute SLO violation；
- aggregate throughput / J per completed token。

禁止把 RouteShare 自己定义的 `phi` disparity 当唯一主指标，否则结论循环自证。

**建议冻结判死门：** oracle 相对所有强基线对 worst-tenant/SLO 的改善 LCB `<10%`，或 aggregate throughput 损失 UCB `>3%`，则停止。

#### Gate 0C：在线可用性

- 只用已经完成的 post-router histogram 更新 debt；
- 测 histogram、cost share 和 scheduler overhead；
- 验证 `sum(phi) == measured batch cost`、identity closure、无负 share、无未来 route；
- 小 coalition 用 exact oracle 校验近似误差。

若必须依赖 future-route predictor，或 action flip 极少，或控制开销接近 headroom，直接判死；不要用 bandit、学习模型或多节点模拟继续救。

### 3.6 5090 能证明与不能证明什么

**L1 可证明：** route coalition cost 是否真实存在；简单模型是否足够；成本份额是否可在线计算；单 GPU 多租户 replay 是否出现 resource-isolation 增量。

**本轮不能证明：** 多 GPU receiver/rank 的 network externality、RDMA SLO、跨节点 fairness、production tenant 的语义路由可控性。L1 成功后才值得建设 L3/L4。

### 3.7 最大风险与“不要再怎么救”

最大科学风险是：固定 top-k 与现代 fused grouped kernel 已经把 route-dependent variation 压得很小，或 `rows + active experts` 就足够。另一个风险是产品合同本来定义 token fairness，而按语义诱导的 rare-expert route 多收费会被视为 QoS 歧视。

若 Gate 0 不过：

- 不换 Shapley approximation；
- 不加 route predictor；
- 不把 energy、privacy、receiver congestion 拼进来；
- 不用拍定 launch tax 或 Mac 模型制造 headroom；
- 不用 RouteShare 自己的内部公平指标自证。

### 3.8 成功后的完整论文故事

1. route-amplification noisy-neighbor witness；
2. MoE coalition-dependent resource service 的形式化；
3. O(rows) budget-balanced cost share 与 delayed-service fairness bound；
4. causal, predictor-free runtime integration；
5. VTC、DLPM、LLMVisor、simple route cost 和 exact oracle 强对照；
6. 单 GPU真实执行 → continuous serving → 多 GPU EP 的 isolation / SLO / overhead 闭环。

## 4. R2 RouteCloak（高风险候补）

### 4.1 一句话论文主张

> 对只能观察 expert identity/load/timing、但看不到 plaintext activation 的被动观察者，RouteCloak 将真实 MoE route 映射到受 latency/energy SLO 约束的 route-equivalence trace，使多个输入共享同一可观测执行 footprint，在不改变模型 route、权重和输出的情况下显著降低属性推断与文本恢复能力。

### 4.2 新增的系统能力

- **bucket**：把 per-expert row count 向冻结 bucket 上取整；
- **cover execution**：为未选 expert 或不足 rows 执行 dummy rows，但 dummy 结果不进入 combine；
- **mixing**：在 slack 允许时混合多个请求，扩大观测等价类；
- **receiver envelope**：虚拟 EP 下固定 destination/message-size class；
- **fast/slow path**：低风险 route 走低开销 bucket，高泄漏 route 在 SLO budget 内加强 cover；
- **exactness**：真实 token 的 router/top-k/gate weight 与输出保持不变，所有 cover 成本完整入账。

### 4.3 建模形式

- **状态**：真实 route histogram、request slack、queue、observer 可见 channel、GPU/board state。
- **动作**：bucket、padding、dummy expert set、mix window；不能改变真实模型 route。
- **目标**：最小化冻结 attacker 的 attribute/reconstruction advantage 或 maximal leakage proxy。
- **约束**：TTFT/TPOT、board energy、dummy bytes/compute、starvation、exact model output。
- **反馈**：held-out attacker performance、realized latency/J、bucket occupancy；不能用同一 attacker/trace 同时选策略与报结果。

相比纯 heuristic，模型产生具体的 trace equivalence class 和 overhead budget；runtime 反馈再更新可用 bucket，但正式测试集不得用于调 bucket。

### 4.4 Novelty 与威胁模型边界

当前最有利的边界不是“首次发现 routing 泄漏”：这已被 MoEcho 和 2026 route reconstruction 工作覆盖。也不是“首次保护 private MoE inference”：CryptoMoE、SecMoE 已覆盖 2-PC / cryptographic threat model。

潜在创新是：

> 面向普通共享 GPU / expert-parallel serving 的 execution-metadata side channel，设计 exact-output、SLO-bounded、低开销的 route-oblivious runtime。

威胁模型必须冻结：观察者可见 destination/message size/timing、performance-counter 或 TLB footprint，但看不到明文 activation、router logits 和最终 token。若观察者能读 activation，单独隐藏 route 没有意义；若现代隔离使上述 footprint 不可获得，问题也不成立。

### 4.5 最强基线

- no defense；
- only request batching / temporal aggregation；
- static histogram bucket padding；
- fixed top-q cover experts；
- dense/full-expert padding；
- random route noise（只作为非 exact 质量对照）；
- CryptoMoE / SecMoE（不同 threat model 与代价区间，不得省略）；
- privacy-optimal small-trace oracle。

### 4.6 5090 最小判死协议

#### Gate -1：问题存在性

1. 从两个真实 MoE 模型采集 train/calibration/sealed 三分 route trace；
2. 冻结一个明确敏感任务，例如 held-out domain/attribute inference；
3. 用强攻击器和跨模板/跨域 split 测 route-only advantage；
4. instrumentation route trace 只证明信息上限；至少复现一种 5090 上真实 observer channel，才能升级为 systems-security claim。

若攻击只在同模板训练测试、弱攻击器或直接拿 ground-truth route 时成立，而真实 side channel 无法恢复足够 footprint，停止。

#### Gate 0：防御 Pareto

- 保持真实 route/output exact；
- 执行 static bucket、full padding 与 adaptive SLO-budgeted cover；
- 主报 held-out attacker advantage、TTFT/TPOT、board J/completed token、dummy rows/bytes；
- 主口径是完整执行，不能只报 metadata replay。

**建议冻结判死门：** RouteCloak 未消除至少 `80%` 的 attacker advantage，或 latency/energy 开销任一超过 `10%`，或 static bucket padding 达到同一 privacy-overhead Pareto，则停止。

### 4.7 5090 能证明与不能证明什么

**L1 可做：** route leakage existence；held-out attacker；dummy/bucket kernel 的真实 latency/J；数值 exactness；若权限/driver允许，可复现 co-resident performance-counter/TLB channel。

**L2/L3 可做：** destination/message-size/timing 的 virtual EP observer，但只能证明代理机制。

**L4 才能证明：** 真实 EP/RDMA observer、跨节点性能与完整 production threat model。

### 4.8 最大风险与“不要再怎么救”

最大风险是 threat model 不可部署，而不是 attacker 网络不够强。若 observer 能看 activation、observer 根本看不到 route footprint、或 static padding 已到最优 Pareto，立即停。

不要通过弱化攻击器、同分布测试、只报 mutual information proxy、隐藏 dummy energy、允许 route/quality 改变或把 instrumentation trace 冒充 side channel 来救。

### 4.9 成功后的完整论文故事

1. 真实共享 GPU / EP route-footprint leakage reproduction；
2. SLO-bounded route-oblivious problem formulation；
3. route equivalence buckets + cover execution + mixing runtime；
4. exact-output 与完整 energy/latency ledger；
5. adaptive strategy对 static/full padding 和 cryptographic方案的 Pareto；
6. 单 GPU side channel → multi-GPU EP/RDMA 的系统安全验证。

## 5. 最终推荐与下一阶段入口

### 推荐排序

1. **RouteShare-VTC：先做。** 问题价值高，和现有 MoE / multi-tenant serving 主线贴合，且 5090 可用一个很便宜的真实 cost-surface + sealed oracle 实验直接判死。当前只是 `[Hypothesis]`，不是“有搞头”的实测结论。
2. **RouteCloak：高上限候补。** novelty 与潜在 venue 上限更高，但属于明显的 security pivot；先过 threat-model / real-observer Gate -1，再决定是否进入 Phase 2。
3. **FJEC：保留纸面 Gate-0，不进入前二。** 只有在 RouteShare 判死且能证明 contract state 造成 EDF/AMoE/Festina-like 无法复现的 matched-state action flip 时才重排。

### 当前明确不做

- 不写两条候选的正式实验代码；

- 不把 5090 proxy 写成多 GPU/RDMA 结论；
- 不放宽门槛挽救任何候选；
- 不复活归档路线；
- 不引用任何已作废 additive 数字。
