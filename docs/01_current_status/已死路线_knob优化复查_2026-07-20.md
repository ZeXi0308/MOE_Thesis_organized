# 已死路线的"能否用knob/系统化优化改良"复查（2026-07-20）

> 目标：不满足于最终判决，逐条检查是否存在具体旋钮/优化能把已死或卡边界的路线从负变正。方法：优先用现有数据做零成本分析，只有确认有希望时才消耗新的计算/GPU资源。

## 1. TokenRace-EP：自适应触发（结论：knob本身不可行，机制内在矛盾）

**假设**：GPU P0/P1 判死的原因是"每层无条件支付重批开销"（`race_totals[i] += own + rebatch_overhead_us`，不管这一层负载是否均衡都要付）。如果用一个免费的因果信号（专家路由的确定性token计数，在噪声实现之前就已知）做自适应门控——只在预测收益>开销阈值时才触发token-race，否则零成本退化为full_barrier——能否恢复正收益？

**实验**：`run_tokenrace_adaptive_p2.py`，直接复用GPU P0测出的真实常数（`rebatch_overhead_us=26.64us`，`fit_base_us`/`fit_per_token_us`），在真实route trace上扫描阈值倍数(0×~6×开销)，本地Mac运行，不需要新GPU时间。

**结果**：阈值=0（原始无条件版本）复现了P0/P1的负结果（OLMoE moderate P99=+2.15%不过门槛，LLM-jp=-3.18%）。**但阈值只要提高到0.5×开销(13.3us)以上，触发率直接归零，两个模型全部退化为纯full_barrier（0%改善）**。

**根因**：确定性负载不均衡带来的时间差本身很小——`fit_per_token_us`只有0.006-0.035us/token（GPU P0已经测出FFN耗时几乎完全由固定launch开销主导，几乎不随token数变化），远小于13us的重批开销。也就是说，**TokenRace-EP的收益几乎全部来自不可预测的噪声/straggler事件本身，而免费可得的确定性信号对这类事件毫无预测力**。这不是调参能解决的：能救它的信号（真实spread）恰恰不可能免费获得（获得它等于已经付出了噪声实现之后才能观测到的延迟）。

**结论**：自适应触发这个knob从根本上不可行，维持KILLED判决，且这个发现本身比原判决更有解释力（说明了"为什么没有折中方案"）。

## 2. MassCover-EP：混合/更强算法（结论：算法已触及oracle天花板，无空间）

**假设**：CVaR-greedy比最强baseline(gate_mass)只多降4.7%-6.6%，不到10%门槛。是否是算法不够聪明（比如混合CVaR和gate_mass、换更强的组合优化）？

**检查**：直接比较`cvar_greedy`相对`oracle_cvar`（能看到historical test集合的事后最优解，理论上限）的差距。

**结果**：`cvar_greedy_vs_oracle_gap`在全部32个(model×placement×budget)组合下都在**0.02%-0.7%**之间——CVaR-greedy已经逼近oracle上限，几乎没有算法改进空间。而上限本身相对gate_mass的天花板（`oracle_vs_gate_mass_gap`）只有**2.1%-7.1%**，budget从2%提到10%也没有显著往上走。

**结论**：**这不是算法能力问题，是信息天花板问题**——gate_mass这个简单信号本身已经吃掉了几乎所有可挖掘空间，站在上帝视角的oracle都做不到10%改善，任何更复杂的算法（混合策略、更强启发式、甚至精确求解）都不可能突破这个上限。维持KILL_OR_REFORMULATE判决，且不建议在算法层面继续投入。

## 3. QuotaEP-H：语料库问题已解决，Gate C仍需真实kernel（未在本轮处理，见此前进展报告）

已在语料库切换里解决了Gate B的数据复用问题（WikiText-103），但Gate C（真实backend净收益）本质上需要真实GPU kernel实现（不是knob/参数调整能替代的），如果要继续这条线，下一步是实现一个真实的分组混合精度combine kernel，工作量接近TokenRace-EP的GPU验证规模。

## 跨路线的元结论

**两条独立死亡路线（TokenRace-EP、MassCover-EP）在"能否通过优化挽回"这个问题上给出了同一个答案：不能，且原因结构相似**——它们的"改进空间"要么被更简单的免费信号/baseline提前吃掉了(MassCover)，要么依赖的正是无法免费获得的信息(TokenRace)。这跟receiver-aware v2的教训（价值被限定在"静态画像已经够用"的场景）是同一类模式的第三次重现：**这几条候选的"上限"普遍很薄，薄到连算法层面的最优解（oracle）都摸不到门槛，说明门槛本身（5%/10%改善）和这套MoE EP系统里"简单静态信号"的实际能力边界非常接近，不是执行细节没做好**。这个"简单静态信号已经逼近oracle上限"这个模式本身值得写进Approach Registry的元教训。
