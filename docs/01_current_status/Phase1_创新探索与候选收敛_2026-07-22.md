## 1. 旧结论验证结果

### 1.1 Receiver 旧低精度控制

在 RTX 5090 上对 OLMoE 与 LLM-jp 跑了同一 smoke-sized MMLU 单元，启用 positive-net hard gate，并配对 `serialized_tiles` 与 `once_per_step` codec 口径。完整环境、source SHA 和原始表见 [`receiver_old_mechanism_diag_2026-07-22/`](../ideas/receiver_aware/outputs/receiver_old_mechanism_diag_2026-07-22/README.md)。

核心观察：

- **[Observed] balanced**：OLMoE 与 LLM-jp 在 serialized 主复核下所有低精度动作均回滚，三个 arm 都是 `low_pairs=0`、saving=0；OLMoE 即使改用 once-per-step 仍为 0。
- **[Observed] hotspot + once-per-step**：OLMoE 只有约 **0.36%** proxy net saving，且简单 `calib_static` 最好；LLM-jp 仍没有可执行 low action。
- **[Observed] same-action serialized sensitivity**：OLMoE hotspot 的三条 action trace 全部为负净值，旧协议要求的 codec 敏感性存活条件不成立。
- **[Boundary]**：每模型只有 16 道 test question，系统收益仍是解析 wire+codec proxy。因此这是旧机制的负向开发诊断，不是 DDRC 正式 No-Go。

判定：**旧“receiver congestion → dynamic INT4 lane”不再作为候选；不要再加 bandit、HHI、EWMA 或 RDMA 来救。**

### 1.2 DDRC G1 为什么仍未验证

**[Observed: code bug]** `capture_moe.py` 的 `record_routes=True` 被错误地嵌在 `record_diagnostics` 总开关下；`record_routes=True, record_diagnostics=False` 会静默输出空 route。证据：

- route recorder 自身：`experiments/shared/capture_moe.py:118-135`；
- 三个模型 forward 的错误 gate：同文件 `:742-749,852-859,929-936`；
- route-only 入口的绕行方式：`experiments/shared/capture_routes_v2.py:63-69`。

因此旧 GPU runner 不能直接充当 DDRC 合规 native producer。分类是**代码做错 / capability missing**，不是科学结论。遵守 Phase 1 约束，本轮没有写补丁。

### 1.3 Energy-SLO 现状验证

**[Observed]** 远端 vLLM `0.10.2` 的 `Fp8MoEMethod` 在 load 后一次性把 BF16/FP16 expert weights 转成 FP8，执行路径固定 `use_fp8_w8a8=True`；`apply()` 没有 per-invocation BF16/FP8 action。当前 serving stack 因此没有现成的 route-row 动态精度 hot path。

判定：现有 Route-row FP8 实现仍是**工程 BLOCKED**；static FP8 capability 不能证明动态 Energy-SLO。结合近期 mixed-precision 工作密集出现，当前版本不再入选本轮论文主线。

## 4. 主线：Critical-Join Credits（CJC）

### 4.1 一句话论文主张

> 在不改变 routing、top-k、precision、bytes 或质量的前提下，receiver 侧的 sibling-arrival / join-deficit 是 sender-local queue、flow size 和 deadline 无法恢复的增量状态；用它给 combine partial 定价并重排 expert microtile / send order，可提前完成 token/request critical frontier，从而降低尾部闭包时间。

### 4.2 系统创新点

新增运行时能力：

- 为 `(request, layer, token-block)` 维护 `ready/missing sibling bitmap`；
- 将 completion ACK / ready word 汇总成 bounded join credit；
- sender 或 receiver-pull engine 按 credit 重排 ready combine block；
- starvation 超时与 EDF fast path 保证不饿死；
- 不 reroute、不 replicate、不 compress、不 drop，先隔离 receiver information value。

改变的关键路径是 `expert tile ready → combine transfer order → token/layer join completion`，不是总流量预测。

### 4.3 建模创新点

任务 `j=(i,l,b,e,s,r)` 表示 request `i`、层 `l`、token block `b` 经 expert `e` 由 sender `s` 回到 receiver `r` 的 contribution。

- **状态**：missing sibling count `d_{i,l,b}(t)`、ready bitmap、request slack、sender/receiver queue、block bytes、实测 service LUT；
- **决策变量**：各 sender 的下一 compute/pack/send block、tile size及可用 QP/rail service order；
- **目标**：最小化 request/token closure time 的 P99/CVaR 或 deadline miss；
- **约束**：fixed routing/top-k、exactly-once combine、dependency/容量、fairness、starvation bound、严格因果；
- **可观测**：当前层 dispatch、已完成 contribution、当前 queue/slack；
- **禁止信息**：未来 token/layer routing、未来 arrival、test-optimal schedule。

候选在线 score 可写为：

\[
\pi_j(t)=\frac{\Delta \Phi\big(j\mid d(t),\,slack(t)\big)}{bytes_j+\epsilon}-\text{fairness debt}_j,
\]

其中 `ΔΦ` 是发送该 contribution 对当前 closure-risk potential 的边际下降。该式只是 Phase 1 模型草案，不是已冻结算法。

### 4.4 系统—模型结合

模型输出每个 ready block 的 marginal completion credit；runtime 选择下一 block。ACK/ready word 更新 missing bitmap 与 slack，形成闭环。实现可保持 `O(1)` counter/bitmap update；实际协调 bytes、poll/ACK、kernel launch 和 stale state 必须在 Phase 2 计费。

### 4.5 相对最强简单基线的本质差异

必须比较：

- FIFO / static expert order；
- sender-local SRPT；
- sender-local EDF/request slack；
- receiver queue-depth / ECN priority；
- size-desc / largest-flow-first；
- topology-aware join-blind all-to-all scheduler（含 FAST 类能力）；
- global same-layer join oracle。

必要性 witness：sender 看见两个同 bytes、同 deadline 的 ready block `x,y`。世界 A 中 `x` 是某 token 的最后一个 sibling，世界 B 中这个身份交换给 `y`；sender-local observation 完全相同，所以任何 sender-only policy 两个世界做同一选择，至少一个世界非最优。receiver join state 能区分两世界。这个 witness 只证明信息可能有价值；若早闭包不能推进执行，系统收益仍为 0。

### 4.6 必要条件

1. top-k contribution 存在可观测 arrival/service skew；
2. runtime 可在同一层内重排 microtile 或 combine block；
3. 早到的完整 token/block 能释放 buffer、解除 HoL 或推进局部下游，而不是被不可打破的整层 collective barrier吞掉；
4. join state 不能被 sender-local size/EDF 或 generic topology scheduler等价恢复；
5. stale ACK 下仍稳定，协调税小于收益。

### 4.7 最大风险

最危险的不是 predictor 不准，而是**机制没有可控路径**：若 combine 只能整 collective 一次性完成，或者 attention 必须等整层所有 token，最后 sibling 提前没有系统价值。此时直接杀，不转去用 codec/质量损失救。

### 4.8 理论 / oracle headroom

当前为 **[Unverified]**。Phase 2 前的最小判死门建议固定为：

- global causal join oracle 相对最佳 join-blind 强基线，两个模型且至少两个 independent burst/load cell 中，P99 layer/request closure 降低 **≥5%**；
- 或 SLO violation 绝对降低 **≥3 percentage points**，且协调开销计入后仍成立；
- 若不满足，CJC 直接 No-Go，不写 heuristic/controller。

### 4.9 当前 5090 可获得的证据

- L1：修复 route-only recorder 后采两模型真实 `(request,token,layer,expert)` DAG；
- L1：测 expert microtile、pack/unpack、CUDA stream/launch 的 service LUT；
- L1/L2：virtual multi-receiver queue、stale ACK、synthetic straggler 的因果 replay；
- L2：比较 global join oracle、join-blind oracle 与部署近似策略，拆出纯信息增量。

这些最多证明 route-real / transport-calibrated 机制 headroom，不是 RDMA P99。

### 4.10 尚不能验证的 claim

- 多节点 RDMA/NVLink 的真实 receiver-last-fragment 与 end-to-end TTFT/TPOT P99；
- QP/rail contention、NIC polling 与 credit traffic 的实际代价；
- 在真实 serving engine 中早闭包是否能推进 attention / 下一层；
- 大模型、长时间 arrival drift 下的稳定性。

### 4.11 最小判死实验

只做 route DAG + measured LUT 的 exact/relaxed scheduling upper bound；不先写 bandit。若 oracle 不过上述 5%/3pp 门，或加入整层 barrier 后收益归零，停止。

### 4.12 成功后的论文故事

1. sender-only information-value lower-bound witness；
2. join-aware online scheduling model与可解释 marginal credit；
3. route-real calibrated oracle 证明 headroom；
4. causal low-overhead approximation；
5. streaming/persistent EP 原型；
6. 多 GPU/多节点下 receiver-last-fragment、P99、goodput 与开销闭环。

## 5. 高潜候补：JouleQueue-MoE

### 5.1 一句话论文主张

> 在不改数值精度和 routing 的前提下，利用真实 expert row fragmentation、每请求 slack 与实测 marginal joules，延迟并合并安全的 expert invocations，同时让紧急请求走 fast path，可在 TTFT/TPOT P99 硬约束下降低 board joules/completed token。

### 5.2 系统创新点

- router 后按 expert 维护跨 microbatch 的 ready-row queue；
- `launch / defer / urgent-flush` 三动作；
- exact-quality：仅改变独立 rows 的分组/执行时刻，不量化、不 drop、不改 expert；
- 能量 LUT 与实际 queue/slack 位于热路径；
- fast path、max-age 与 starvation hard gate。

### 5.3 建模创新点

- **决策变量**：`u_e(t)∈{launch,defer}`、本次 batch composition、必要时数值等价 kernel mode；
- **状态**：expert queue rows、age、request slack、route fragmentation、`E_e(m)`/`T_e(m)`及置信区间；
- **目标**：最小化 GPU board `J/completed-output-token`；
- **硬约束**：质量等价、full-drain、TTFT/TPOT P99、starvation、KV/request identity；
- **可观测**：当前与历史 ready rows、deadline/slack、实测 LUT；
- **禁止**：未来 arrival、未来 route、test-optimal timeout。

非凸 fixed launch/weight-read cost 使 `E_e(m)` 不必线性。模型可用 deadline shadow cost 将“再等一小段的预计能量收益”和“新增 SLO 风险”比较；shadow price 只是推导机制，不能单独充当 novelty。

### 5.4 系统—模型结合

queue event 更新 `m, age, slack`；LUT 输出合并一批 rows 的 marginal joule saving，风险模型输出等待成本；scheduler 触发 launch 或 defer。所有 lookup/controller 时间与等待期间 board energy 必须收费。

### 5.5 相对最强简单基线的本质差异

必须包括：

- immediate execution；
- best fixed timeout / best static batch；
- EDF / oldest-first；
- max-throughput/tile-occupancy scheduler；
- AMoE-style μ-queue + defrag；
- Festina-like profile-guided energy batching；
- clairvoyant energy/SLO oracle。

只有“marginal joules 让动作顺序显著不同于 throughput/timeout/EDF”才有增量；若最优动作等价于 best fixed timeout，本 idea 失败。

### 5.6 必要条件

1. expert execution 存在可重复的 fixed/underfill energy tax；
2. arrival 与 routing 产生可安全合并的 queue overlap；
3. request slack 足以支付短暂等待；
4. full-drain 后仍降低 J/token，而非少完成请求制造假节能；
5. queue/control overhead 与 idle board energy 不吃掉收益。

### 5.7 最大风险

AMoE 的 throughput defrag、best fixed timeout 或普通 continuous batching可能已隐式最小化 J/token；再等待只会恶化 P99。另一个风险是单次 expert kernel太短，NVML power sampling 无法可靠归因，必须用长重复窗和 total-energy counter。

### 5.8 理论 / oracle headroom

当前为 **[Unverified]**。最小门不放宽：在相同完成集合、质量与 arrival trace 上，clairvoyant energy oracle相对所有 SLO 合格强基线的 `J/completed-token` 改善 95% CI 下界 **≥10%**，同时 TTFT/TPOT P99 ratio 95% CI 上界 **≤1.03**。若 oracle 都不过门，不写 online dual/controller。

### 5.9 当前 5090 可获得的证据

- L1：真实 OLMoE/LLM-jp expert shape与 row-count energy/latency surface；
- L1：native route distribution与真实/冻结 arrival trace；
- L1/L2：clairvoyant launch-time oracle、best fixed timeout、EDF、throughput μ-queue 对比；
- L2：queue replay、full-drain、controller overhead与 NVML gap audit；
- L3（后续）：单 GPU async expert queue 原型与真实 board energy。

### 5.10 尚不能验证的 claim

- 多 GPU EP 下 communication/compute overlap 对 energy headroom 的影响；
- NIC/CPU/集群总能耗；
- 大模型、多 GPU weight residency 与跨节点 queue；
- 长时间 serving drift 与生产 SLO。

### 5.11 最小判死实验

先测 `E_e(m),T_e(m)` 并对真实 route arrival 做 launch-time oracle；若相对 AMoE-style/best-timeout 等强基线不过 10%/3% 门，停止。不要通过加入 FP8、DVFS、offload、replica 或学习 controller 扩大搜索空间来救。

### 5.12 成功后的论文故事

1. MoE expert fragmentation 的能量非凸性测量；
2. deadline-constrained energy launch model与阈值/稳定性解释；
3. exact-quality fast/slow queue runtime；
4. 单 GPU real serving Energy-SLO；
5. 多 GPU EP 扩展及 GPU/NIC/CPU 分账。

## 6. 归档 idea 是否复活

| 路线 | 本轮纠错发现 | 结论 |
|---|---|---|
| MassCover | 文档的 `oracle_cvar` 实为在 test/historical matrix 上重跑同一 CVaR greedy，不是 exact oracle 或理论上界 | 可做 binary CVaR MILP/LP-relaxation 的纠错审计；没有资格挤入前二，默认不复活 |
| popularity-LPT placement | 没有 committed result artifact；所谓 document bootstrap 实际重采样共享同一 document pool 的 scenario seeds；强基线漏 coactivation-aware placement | 旧“placement 普遍无效”表述过度；但重开将是新问题，本轮不复活 |
| QuotaEP | Gate B 质量侧成立、Gate C owner-local grouped backend 未执行；fixed quota 相对 global contribution 有明显 quality tax | 唯一未被科学判死的归档备选，但 prerequisite 与多 GPU backend 未闭合，不挤入前二 |
| Additive / PLTB | 勘误撤回错误会计造成的旧倍率；匹配协议 PLTB 仍败 | Additive 只作可能的建模原语，不自动复活 MILP/PLTB；禁止引用作废数字 |
| CreditReduce / TokenRace / Prefetch / Progressive / RouteFidelity 等 | 纠错后机制仍不过各自门，或简单基线已吃掉空间 | 不复活，不因 GPU 已开而重跑 |

## 7. Phase 1 最终推荐

1. **先做 CJC 的 L1 join-oracle 必要性门。** 它直接回答 receiver information 是否有 sender-only 不可替代增量，且不与 codec/质量混杂。
2. **JouleQueue 作为 Energy-SLO 候补。** 第一刀是 energy-optimal schedule 是否真的不同于 throughput/timeout/AMoE；不是先写 controller。
3. 两轴在各自 oracle 过门前不合并主叙事；不把 5090 proxy 写成 RDMA/P99 或完整 Energy-SLO 结论。

本轮到此停在 Phase 1。下一阶段只能为上述入选候选冻结协议；不得沿用旧 DDRC/Route-row 门槛后验改写成新候选的结果。
