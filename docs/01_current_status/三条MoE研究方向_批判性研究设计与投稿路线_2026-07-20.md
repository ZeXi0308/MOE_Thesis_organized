# 0. 先给结论

## 0.1 三条线当前不能按“三篇独立系统论文”推进

1. **Receiver-aware** 当前是“真实路由 trace + synthetic receiver assignment + 线性带宽回放”。它证明了信息陈旧度会改变策略排序，但没有证明真实 RDMA incast 下省字节能降低 queueing、TPOT 或 P99。v3 还存在因果评估错误：检测器观察前 30% 后，策略却被回溯应用到全场景。
2. **Quality Isolation** 当前是 32 篇文档上的静态 quota 重分配，不是流式 request isolation。Part C 在同一测试集上挑选最相关 proxy，并使用另一种降级策略的测试时 KL 排序，既有 selection leakage，也需要额外完整 forward。
3. **Expert Prefetch** 的离线“跨层信号存在”结果仍有价值；但现有系统模拟的 cache key 只有 `expert_id`，没有 `(layer_id, expert_id)`，把不同层同号 expert 当成同一权重对象，导致 miss rate 和 3–5% 延迟收益无效。更重要的是，ExFlow、Fate、HOBBIT、ProMoE、LayerScope/PreScope、PROBE、ST-MoE 已覆盖跨层关联、预测预取和 hiding-window 约束，当前 novelty 基本被占据。

## 0.2 推荐的研究组织方式

**论文层面：**

- 优先尝试一篇合并的系统论文：  
  **Quality-bounded Congestion Adaptation for MoE Expert-Parallel Inference**  
  Receiver-aware 决定“何时、在哪条通信路径降级”；Quality Isolation 决定“不能总让哪些请求承担降级”。
- Prefetch 不应并入该论文。它面对的是分层内存和专家换入，不是 EP combine 拥塞；合并会形成三套瓶颈、三套控制面、三套评估，论文主线会失焦。
- Prefetch 当前应进入 **暂停/重定位** 状态：保留离线 characterization，先修模拟错误并完成直接 related-work 对照；若找不到不同于现有工作的机制，作为论文中的负结果或毕业论文独立章节，而不是投稿主线。

**毕业论文层面：**

三条线可以由同一方法论统一：

> 在线系统只有在信号满足“决策前可得、跨决策窗口持续、能在真实硬件 slack 内执行”时，预测性控制才有价值；否则离线收益可能衰减，甚至符号反转。

这是统一的研究方法论，不等于把三个机制硬塞进一篇系统论文。

## 0.3 当前证据评级

| 方向 | 可信的已验证结论 | 当前不能声称 | 建议状态 |
|---|---|---|---|
| Receiver-aware | oracle 新鲜负载在回放中优于 random；stale signal 在 balanced 合成场景下反转；static profile 在结构性场景接近 oracle | 可部署控制器、真实拥塞缓解、P99 改善 | 与 Quality Isolation 合并后再做真实原型 |
| Quality Isolation | 文档级降级 KL 在若干机制间相关；oracle 静态 quota 可降低小样本 P95 | 零成本 proxy、长期公平、request isolation、matched bytes | 作为合并系统的质量控制面 |
| Expert Prefetch | top-1 跨层条件信息超过 layer-frequency；信号可延伸多层 | 现有 3–5% 系统收益、完整 top-k、真实 serving 收益、机制 novelty | 暂停；修 bug + 查重后 go/no-go |

# 1. 共同的证据审计：原文结论必须先降级

## 1.1 Receiver-aware v3 的因果错误

`run_receiver_aware_v3_adaptive.py` 在第 125–129 行用前 `detect_frac` 的 receiver 负载做检测；但第 131–139 行的 `total_saving()` 对完整 `cand_rows` 选点并计算整个场景收益。也就是说，控制器在“观察前 30%”之后，回溯修改了前 30% 的动作。

正确评估应为：

1. warm-up 区间 `[0, g_d]` 使用固定 baseline；
2. 只在 `(g_d, G]` 使用检测后的策略；
3. 总收益包含 warm-up 已经发生且不可改变的成本；
4. 固定策略 baseline 同样按同一时间边界评估；
5. 报告 detection delay、post-change regret，而不只报分类准确率。

因此，`adaptive=0.1706/0.1729` **[证据有缺陷]**，不能支撑“因果合法、可部署控制器”。

## 1.2 Quality Isolation Part C 的 leakage 和成本错误

`run_per_request_quality_isolation_p0.py`：

- 第 165–167 行在测试数据上按 Spearman 最大值选择 `best_proxy`；
- 第 110–114 行用同一请求在另一种降级机制下的测试时 `mean_token_kl` 排序；
- 第 46–53 行定义了 bootstrap，但 Part A/Part C 没有实际调用；
- 第 65–76 行按“文档个数”分 quota，并把被保护文档的 KL 直接设成 0，没有按 token/bytes 匹配预算。

所以 Part C 不是“因果合法 proxy”，而是 **同测试集选优的第二次 forward proxy**。当前证据只支持“存在文档级跨机制风险相关性”，不支持在线可实现性。

## 1.3 Expert Prefetch 的 cache identity 错误

`run_expert_prefetch_system_prototype.py` 第 137–153 行的 `LRUCache` 仅存 `expert_id`。但 layer 4 的 expert 3 与 layer 5 的 expert 3 是不同权重，正确 key 至少应为：

```text
(model_id, layer_id, expert_id, precision, version)
```

现有模拟在跨层迭代时复用同一个 cache，因而产生不存在的跨层 cache hit。该错误同时影响 reactive 和 predictive，但不会保证成比例抵消；它会改变 eviction、prefetch pollution、需求 miss 和相对收益。现有 13–16% paging saving、3–5% end-to-end saving 必须视为 **无效系统证据**，修复后重跑。

此外，v2 的 dense `torch.bmm` 让所有 token 通过所有 expert，不是真实 sparse grouped-GEMM。它给出的 overlap window 既不是上界，也不是可信近似。

# 2. 方向 A：Receiver-aware 自适应控制

## 2.1 问题重新定义

### 2.1.1 最有论文价值的问题

**推荐定义：质量约束下的拥塞感知 MoE EP 通信降级。**

系统运行 vLLM/SGLang continuous batching，MoE 层使用 DeepEP/UCCL-EP/NCCL 完成 dispatch/combine。短时间网络压力出现时，系统允许对部分低贡献 combine payload 使用低精度编码，从而减少关键 receiver 的在途字节；控制器必须：

- 只用决策前可得信号；
- 在量化/反量化、metadata 和控制开销后仍减少 P95/P99；
- 满足每请求或每租户质量损失约束；
- 不对同一请求长期重复降级；
- 在信号不可靠时退化到可解释 baseline。

这比“识别 structural/transient 后切换 random/static”更完整，也更有系统论文价值。

### 2.1.2 形式化

令：

- 请求 \(i\in\mathcal R\)，decode step \(t\)，MoE layer \(l\)，routing rank \(k\)；
- 通信单元 \(m=(i,t,l,k,s,r)\)，从 sender \(s\) 到 receiver \(r\)；
- 原始 payload 字节 \(b_m\)，gate weight \(w_m\)；
- 可选动作 \(a_m\in\mathcal A=\{\text{FP8},\text{INT4/NVFP4},\text{drop},\text{reroute}\}\)；
- 动作后的字节 \(b_m(a)\)，量化开销 \(c_m^{q}(a)\)，估计质量损失 \(\hat q_m(a)\)；
- 决策时可观测状态 \(z_t\)：历史 queue、ECN、completion latency、token histogram、QP/NIC counter、GPU stall；
- receiver 队列 \(Q_r(t)\)，通信完成时间 \(C_m(a,z_t)\)；
- 每请求累计质量债务 \(D_i(t)\)；
- 控制器开销 \(T_{\mathrm{ctrl}}\)，切换成本 \(T_{\mathrm{switch}}\)。

一个可实现的在线目标是：

\[
\max_{\{a_m\}}
\sum_{m\in \mathcal M_t}
\widehat{\Delta C}_m(a_m\mid z_t)
-\lambda_q \hat q_m(a_m)
-\lambda_d D_i(t)\hat q_m(a_m)
-\lambda_s \mathbf 1[a_m\neq a_m^{-}]
\]

约束：

\[
\Pr(\mathrm{TPOT}_i>S_i^{\mathrm{TPOT}})\le \epsilon_i,
\quad
\mathrm{CVaR}_{\alpha}(D_i)\le Q_i,
\quad
T_{\mathrm{ctrl}}\le B_{\mathrm{ctrl}},
\quad
\sum_m b_m(a_m)\le B_t.
\]

这里真正应优化的是 **expected queueing/critical-path reduction**，不是 bytes saving 本身。

### 2.1.3 三种问题定义的价值判断

1. **Regime classifier**：HHI 二分类后切策略。实现简单，但 novelty 弱，且当前 synthetic construction 使分类近乎识别生成器参数。
2. **Direct benefit predictor**：直接预测动作对下一决策窗口的 queueing/critical path 减少。更贴近目标，避免“先分类再决策”的信息损失。推荐。
3. **统一动作空间：precision/drop/reroute/replication/admission**：上限高，但范围过大。首篇论文应只保留 precision，加一个 no-op fallback；其他动作作为扩展或 oracle。

### 2.1.4 明确不在范围内

- 不重新训练 router；
- 不改变模型拓扑和 expert 参数；
- 不声称替代 DCQCN/Swift/HPCC 等网络传输层拥塞控制；
- 首版不同时解决 dispatch 与 combine，优先选一个确实可量化且质量可测的路径；
- 不把 synthetic trace replay 当作端到端证明。

## 2.2 核心假设拆解与证伪

### 工作负载假设

1. **真实 serving 存在可持续 receiver skew。**  
   当前只由 `origin_mode` 合成，未验证。  
   证伪：在真实 continuous batching 上记录每 10–100 μs 的 per-receiver byte/queue trace；若自然 workload 中 HHI 接近均匀且 queue 不相关，structural claim 失效。  
   退化：关闭 adaptive，使用 uniform precision 或 FAST 类调度。

2. **skew 的时间尺度长于观测+传播+决策延迟。**  
   当前 balanced 场景已显示 lag-1 可能反转。  
   证伪：比较 hotspot dwell time 与 telemetry age；若 \(T_{\mathrm{dwell}}\le T_{\mathrm{sense}}+T_{\mathrm{prop}}+T_{\mathrm{act}}\)，在线控制无效。  
   退化：只用静态 profile 或作用于下一 microbatch。

3. **synthetic staggered jobs 代表 continuous batching。**  
   未验证。  
   证伪：接入 ShareGPT/Azure-like arrival trace，比较 token/layer concurrency 和 receiver traffic 自相关。

### 模型结构与质量假设

4. **tail-rank combine contribution 低，低精度损失可控。**  
   当前 receiver 实验没有质量测量。  
   证伪：按 rank、gate mass、layer、request 分桶测 task accuracy、token KL 和 worst-request loss。  
   退化：仅对 calibration 中安全的 layer/rank 使用低精度。

5. **不同模型/quant format 下安全集合稳定。**  
   未验证。INT4 fake quant 不能替代 NVFP4/MXFP4/真实 kernel。  
   证伪：OLMoE、Mixtral/Qwen-MoE/DeepSeek-like 至少三种 router/top-k；真实量化 kernel。

### 硬件与性能假设

6. **省字节会减少 receiver queueing。**  
   当前只有 `max(bytes)/BW`。  
   证伪：真实 RDMA incast 下扫描 payload；测 CQ completion、P99 combine、NIC/QP counter。若瓶颈在 packet rate、QP serialization、PCIe、dequant kernel 或 synchronization，字节下降可能不降延迟。

7. **混合精度编码成本小于节省的网络时间。**  
   未验证。  
   证伪：逐消息大小扫描 quant/dequant kernel，含 scale metadata、alignment、launch、receiver unpack。

8. **选择性精度不会破坏融合通信 kernel。**  
   未验证。mixed format 可能导致分支、两次 collective 或额外 buffer。  
   退化：按 contiguous segment/microbatch 统一格式，而非逐 token-rank。

### 可观测性和时间假设

9. **信号能在动作之前到达。**  
   当前 oracle 明显不满足；lag-1 仅是一个假设。  
   必须为每个 signal 画出时间线：采样完成、GPU→CPU/NIC 可见、控制器完成、descriptor 提交。

10. **HHI 表示 congestion persistence。**  
    当前 HHI 主要区分 synthetic receiver assignment。高 HHI 可以没有队列，低 HHI 也可因链路 oversubscription 拥塞。  
    证伪：固定 HHI 改变 link capacity；固定 queue 改变 HHI；检验 HHI 对未来 completion latency 的增量预测价值。

### 部署假设

11. **所有 sender 对 receiver 状态有一致视图。**  
    未验证。分布式控制可能产生相反动作和振荡。  
    退化：receiver 只广播粗粒度 pressure level，sender 使用确定性规则。

12. **切换不会引入 flapping。**  
    当前只检测一次。  
    证伪：热点 receiver 高频切换、突变、周期性流量；报告每秒切换数和额外开销。

## 2.3 最强反方论证

| 审稿质疑 | 当前证据 | 必须补的证据或 claim 调整 |
|---|---|---|
| Novelty：HHI + 阈值切换是标准控制 | 不足 | 核心改为“真实 EP mixed-precision transport + direct queue-benefit control + quality debt”，HHI 只做 baseline |
| Motivation：FAST/UCCL-EP 已可避免 incast，为何要损失质量 | 不足 | 与 FAST、UCCL flow-control、static placement 同台；只在它们仍有 tail queue 时启用 |
| Realism：receiver hotspot 是生成器写进去的 | 明确存在 | 用真实 scheduler 产生 rank assignment 和自然 trace；synthetic 仅做 stress test |
| Causality：v3 回溯修改 warm-up | 失败 | 重写 post-warm-up evaluation；加入 change-point delay/regret |
| Performance：bytes saving 不等于 latency | 失败 | 真实 RDMA + quant/dequant + P99 TPOT |
| Quality：只按 tail rank 假设安全 | 失败 | 请求/任务质量和 CVaR；与 gate mass、entropy、oracle harm 比较 |
| Baseline：random 太弱 | 不足 | uniform tail、queue threshold、ECN threshold、EWMA、FAST、static placement、greedy max-port、oracle |
| Complexity：逐 token precision metadata 破坏 kernel | 未回答 | 报告 kernel path、descriptor 数、buffer、分支和控制开销 |
| Generality：只在 structural 有效，静态策略已够 | v2 支持该反方 | 若 static 在真实 trace 内距 oracle <2%，删除 adaptive claim，只保留 placement/profile 结果 |

## 2.4 替代解释与最小对照

1. **收益来自 placement skew，不是 receiver pressure。**  
   对照：固定 traffic matrix，打乱 expert→rank placement；加入 placement-optimized baseline。

2. **收益来自 max-port objective 与 hot score 同构。**  
   对照：用真实 completion latency 作为目标；对 score 做 receiver-label permutation。

3. **收益来自 remote-only 候选池。**  
   对照：同样预算下比较 `tail-only`、`remote-only`、`tail∩remote`、全局 greedy。

4. **causal 反转来自 synthetic stagger 的 lag-1 反相关。**  
   对照：扫描 lag、EWMA、partial-current-step、NIC queue；报告互信息和未来 completion prediction。

5. **static profile 有效只是 receiver ID 固定。**  
   对照：请求→rank 动态重映射、workload drift、租户迁移。

6. **简单 ECN/queue threshold 已足够。**  
   对照：`if ECN>τ then uniform-tail-low-precision else full`，与复杂 predictor 匹配切换次数和总低精度字节。

## 2.5 机制设计空间

### 静态策略

- 固定 tail-rank 低精度；
- calibration receiver profile；
- static expert placement；
- 每层静态安全 mask。

优点是零在线开销；在 v2 structural 场景中可能已经接近上限。必须作为强 baseline。

### 在线策略

- queue/ECN threshold；
- receiver completion latency EWMA；
- 未来窗口的 \(\widehat{\Delta T}\) 回归；
- contextual bandit 在 `{full, uniform-tail, receiver-ranked}` 三个安全 policy 间选择。

### 混合策略

离线生成质量安全 mask 和静态 receiver prior；在线只根据真实 pressure 调整预算，不在线学习质量。

### Oracle 上限

- 同步知道当前 traffic matrix；
- 知道每个 action 的实际 queue delay reduction；
- 知道每请求真实 KL/accuracy harm；
- 解一次 per-step knapsack/min-cost flow。

Oracle 必须只作为上限，不能与可部署策略混写。

### 最简可部署策略

```text
若 next-microbatch 的 receiver queue EWMA 超过高阈值：
    对 calibration-safe tail segment 使用一个统一低精度格式
若低于低阈值：
    恢复全精度
中间区域保持当前状态，并设置最小 dwell time
```

这比逐 token predictor 更容易进入 DeepEP/UCCL-EP fast path。

### 高复杂度上限策略

对每个候选消息估计：

\[
\mathrm{score}_m =
\frac{
\Pr[m\text{ 位于 critical receiver}] \cdot \widehat{\Delta T}_m
-\lambda_q\hat q_m
-\lambda_e \mathrm{eviction/switch\ cost}
}{
\mathrm{metadata+quant\ cost}_m+\epsilon
}
\]

在每个 microbatch 上做受限 knapsack；控制器必须在几十微秒内完成。

### 失败 fallback

- telemetry stale/缺失：full precision 或静态安全策略；
- flapping：进入 cooldown；
- quality debt 超阈值：禁止该请求继续降级；
- quant kernel 或 metadata overflow：回退原生 DeepEP/NCCL。

## 2.6 从二分类升级为连续控制

### 2.6.1 不只使用 HHI

令 receiver byte share 为 \(p_t\)，队列为 \(Q_t\)：

\[
H_t=\sum_r p_{t,r}^2,\quad
S_t=1-\mathrm{JSD}(p_t,p_{t-1}),\quad
P_t=\mathrm{EWMA}(H_t\cdot S_t)
\]

`H` 表示集中度，`S` 表示热点身份稳定性；只有高集中且高稳定才是 structural。再加入真实 congestion：

\[
C_t=\max_r \mathrm{normalize}(Q_{t,r},\,ECN_{t,r},\,RTT_{t,r})
\]

最终 persistence/pressure score 不应只从 dispatch histogram 得出，而应检验：

\[
\Pr(C_{t+1:t+W}\mid H_t,S_t,Q_t,\mathrm{ECN}_t).
\]

### 2.6.2 更推荐直接预测动作收益

训练/在线校准：

\[
\widehat{\Delta T}_{m,t+1}
=f(Q_t,\Delta Q_t,\mathrm{ECN}_t,\mathrm{completion}_t,
\mathrm{bytes}_{m},\mathrm{receiver}_m,\mathrm{batch}_t).
\]

只在其置信区间下界大于 quant/control cost 时执行低精度：

\[
\mathrm{LCB}(\widehat{\Delta T}) >
T_{\mathrm{quant}}+T_{\mathrm{dequant}}+T_{\mathrm{ctrl}}+\delta.
\]

这提供安全保守性，但不能在没有可观测反事实的情况下声称严格 no-worse guarantee。

### 2.6.3 稳定性和形式保证

- **切换次数上界**：采用高低阈值、最小 dwell time \(D\)，长度 \(T\) 内切换次数至多 \(\lfloor T/D\rfloor\)。
- **安全 fallback**：只有当 adaptive policy 的离线/影子评估 LCB 高于 baseline 时启用；否则 baseline。
- **regret**：可将 `{static, queue-threshold, random}` 视为 experts，使用 delayed-feedback Hedge；但真实线上无法精确得到未执行动作的 tail latency，必须通过 shadow replay 或小流量 exploration 获取，不能空口声称 bounded regret。

## 2.7 真实系统实现

### 推荐栈

优先：**SGLang 或 vLLM + DeepEP/UCCL-EP + Triton/CUDA mixed-precision pack/unpack**。  
若没有多节点 RDMA 环境，先用 PyTorch distributed/NCCL 做功能正确性，但不能作为最终系统结果。

### 数据路径

```text
请求进入 continuous batching
→ router 产生 top-k expert / gate weight / destination rank
→ controller 读取上一决策窗口 telemetry 与 per-request quality debt
→ 为下一层或下一 microbatch 生成 precision bitmap / segment descriptor
→ sender pack+quant kernel
→ DeepEP/UCCL-EP dispatch 或 combine
→ receiver unpack+dequant + grouped GEMM / combine
→ CUDA event、NIC/QP、queue、ECN、per-request quality proxy 回传
→ 更新 pressure model、quality debt、hysteresis state
→ 下一轮决策
```

### 需要修改的组件

1. vLLM/SGLang scheduler：保存 request/tenant ID、优先级、质量 debt。
2. MoE router 输出：携带 token→request、rank、gate mass。
3. DeepEP/UCCL-EP descriptor：增加 format、scale offset、segment length；避免逐 token header。
4. CUDA/Triton kernel：融合 pack+quant，receiver 融合 dequant+combine。
5. Telemetry：GPU event、per-QP completion、NIC counters、ECN/CNP、receiver ring occupancy。
6. Controller：GPU 上并行 top-N/threshold，或 CPU proxy 中执行；不得同步阻塞主流。
7. Trace：每个 decision 记录 signal timestamp、decision timestamp、descriptor submit、DMA/RDMA completion、kernel completion。

### 决策时间点

- **当前 token 当前层**：router 后才知道 destination，但 queue signal 可能已过时；只适合极低延迟 GPU-local signal。
- **下一层**：有一层 compute window，可传 metadata；但路由 destination 尚未知，只能用预测。
- **下一 microbatch**：最现实，receiver histogram 和 queue 已完成，动作可在 descriptor 构造前确定。
- **下一 request batch**：最稳定但反应慢。

首版推荐“下一 microbatch”，并显式测量 signal age。

## 2.8 实验矩阵

### 模型

- OLMoE E64K8；
- LLM-jp E32K16；
- 至少一个更接近现代 serving 的模型：Mixtral/Qwen-MoE/DeepSeek-like；
- top-k：1/2/4/8/16；
- expert size、层数、router entropy 和 load-balance loss 分桶。

### 硬件

- 单 GPU：只做 quant kernel；
- 单机 4/8 GPU：PCIe 与 NVLink；
- 2/4 节点 RDMA：100/200/400 Gbps；
- 不同 GPU HBM、不同 NIC、不同 QP 数；
- 人工 oversubscription 1:1、2:1、4:1。

### workload

- steady、Poisson、bursty、trace-driven；
- continuous batching 1/8/32/64/128；
- prompt/output 长短混合；
- prefill/decode 混跑；
- 负载漂移、tenant 迁移、优先级、多租户；
- structural→transient、transient→structural、周期性热点。

### 指标

- TTFT、TPOT、P50/P95/P99、吞吐；
- dispatch/combine latency 与 queueing；
- NIC bytes/packets、ECN/CNP、completion latency、QP depth；
- quant/dequant/controller 开销；
- 每请求 KL/PPL/任务 accuracy、worst-request、CVaR；
- fairness、切换次数、signal age、fallback 比例。

### 消融

- 无 HHI、无 queue、无 ECN、无 completion；
- 无 predictor，仅阈值；
- 无动态预算；
- 无 hysteresis/cooldown；
- 无 request debt；
- 离线 profile vs 在线更新；
- simulated bytes vs hardware telemetry。

## 2.9 对抗场景与边界

1. **热点 receiver 每步切换**：stale controller 预期比 random 差；检测高 JSD 后回退。
2. **所有 receiver 均匀但链路整体拥塞**：HHI 失效；使用 queue/ECN。
3. **高 HHI 但带宽充足**：不应降精度；direct benefit LCB 应拒绝动作。
4. **packet/QP 限制而非 byte 限制**：低精度不减少 packet 数时无收益；回退到 shaping/FAST。
5. **quant kernel 比网络节省更贵**：关闭动作。
6. **receiver hotspot 与高 gate-mass token 重合**：质量风险升高；quality debt/安全 mask 拦截。
7. **控制器 flapping**：hysteresis、minimum dwell、cooldown。
8. **telemetry 丢失或 age 超阈值**：baseline。

最坏情况“严格不差于 baseline”只有在 full precision fallback 且控制器不产生额外同步时才能近似保证；任何 exploration 或 mixed path 都必须计入额外开销。

## 2.10 最小论文 claim

在完成真实原型前，最小可信 claim 是：

> 信息陈旧度而不是“是否感知热点”本身，决定了 receiver-aware 精度控制是否有效；在 synthetic trace replay 中，结构性偏斜可由静态 profile 捕获，而 stale online load 在瞬时偏斜下会反转。

完成原型后才可升级为：

> 在真实 EP incast 下，一个只对未来 microbatch 生效、由 queue benefit 和 per-request quality debt 共同约束的 mixed-precision controller，在匹配质量预算下改善 P99 combine/TPOT，并在 telemetry 不可靠时回退到原生通信。

# 3. 方向 B：Per-request Quality Isolation

## 3.1 问题重新定义

### 3.1.1 推荐定义

不是“预测哪篇文档脆弱”，而是：

> 在可近似执行的 MoE serving 中，在线分配有限的高精度服务，使每个请求/租户的累计质量风险受限，同时保持系统 throughput/latency SLO。

“脆弱性”不应被假设为固定 request label。更合理的是分层状态：

\[
\rho_{i,t,l,a}
=
\mathbb E[
\mathrm{quality\ loss}
\mid
\text{prompt features},
\text{decode history},
\text{router state},
\text{layer},
\text{action }a].
\]

它可以同时包含：

- prompt-level prior；
- token/decoding-step 动态状态；
- layer/rank/action 特异性；
- tenant SLO 和历史 debt。

### 3.1.2 形式化

每个时隙 \(t\) 有活跃请求 \(\mathcal R_t\)。对请求 \(i\) 的通信/计算单元选择动作 \(a_{i,t,l}\)。

- 性能收益：\(\Delta T_{i,t,l}(a)\)；
- 估计边际质量损失：\(\hat q_{i,t,l}(a)\)；
- tenant 权重：\(w_i\)；
- 累积质量 debt：

\[
D_i(t+1)
=
\gamma D_i(t)
+
\sum_l \hat q_{i,t,l}(a_{i,t,l})
-
\eta\cdot \mathbf 1[a_{i,t,l}=\mathrm{full}].
\]

优化目标可选：

1. **bounded degradation**：\(\Pr(D_i>Q_i)\le\epsilon_i\)；
2. **max-min fairness**：最小化 \(\max_i D_i/w_i\)；
3. **proportional fairness**：最大化 \(\sum_i w_i\log U_i\)；
4. **tail quality**：最小化 \(\mathrm{CVaR}_{0.95}(D_i)\)。

最适合论文的是 **bounded degradation + CVaR**，因为它直接回答“平均质量掩盖少数请求”的问题。

## 3.2 当前实验究竟证明了什么

### 已证明

- 在 OLMoE/LLM-jp、WikiText-2、32 个文档、固定 fake-quant `fixed_tail` host 上，文档级 `mean_token_kl` 在若干降级布局之间有较高 Spearman 相关。
- 如果事后知道每个文档的 base-policy KL，把 full-precision quota 给最高风险文档，P95 指标会优于随机。
- 路由 top-1 predictability/entropy 与该 KL 在 45 个 OLMoE 文档上不显著相关，说明两个信号不能直接合并。

### 没有证明

- request 脆弱性跨模型、任务、decode step、quant format 稳定；
- proxy 在当前动作前可得；
- proxy 零额外 forward；
- quota 按 bytes/token 匹配；
- 流式长期 credit/debt；
- 多租户公平和未知输出长度；
- 真实任务 accuracy 改善；
- host degradation 机制本身值得部署。

### 小样本 P95 的问题

当 \(n=32\) 时，P95 主要由第二或第三大样本决定。oracle 把最高的 3–16 个值直接设为 0，P95 大幅下降在数学上接近必然。需要：

- 至少数百到数千请求；
- bootstrap 请求流而不是只 bootstrap 单个 P95 数组；
- 同时报 P90/P95/P99/max/CVaR；
- 对保护后的请求真实重跑，而不是 KL 置零。

## 3.3 核心假设拆解与证伪

### 工作负载

1. **请求风险分布有长尾。**  
   当前 n=32 暗示但不足。  
   证伪：在 ≥1000 请求上测；若风险近似同质，isolation 无收益。

2. **请求会经历多次降级，长期 debt 有意义。**  
   当前静态一次性。  
   证伪：短请求或低负载下每个请求只被降级 0–1 次，credit 机制没有作用。

3. **不同租户可共享质量预算。**  
   多租户通常不能共享。  
   退化：per-tenant 独立 debt 与 quota。

### 模型/质量

4. **proxy 对 marginal harm 而不是绝对难度有预测力。**  
   当前相关性可能只是文档本身难。  
   证伪目标应为：

\[
\Delta q_i(a)=q_i(a)-q_i(\mathrm{full}),
\]

而不是只预测 \(q_i(a)\)。

5. **prefill 风险可预测 decode 风险。**  
   未验证。  
   证伪：按 decode step 分段测 rank correlation、worst-decile recall。

6. **KL 与真实任务质量一致。**  
   未验证。  
   证伪：GSM8K/Math、HumanEval、MMLU/ARC、LongBench、对话 judge；报告 per-request failure。

### 信号可观测性

7. **proxy 在第一次降级前可得。**  
   当前不满足。另一个降级机制的 KL 需要 reference logits 和完整 forward。

8. **zero-forward 特征足够强。**  
   尚未做。必须在 calibration-only 选择特征和模型。

### 时间和部署

9. **risk 在请求生命周期内稳定。**  
   未验证，且可能在 reasoning 后期反转。  
   退化：token-window 在线更新，而不是一次性 request score。

10. **controller 不导致高风险请求占满全精度资源。**  
    当前没有 starvation 机制。  
    需要 per-request cap、aging 和 tenant weight。

## 3.4 最强反方论证

| 审稿质疑 | 当前回答 | 必须补的实验 |
|---|---|---|
| Novelty：这只是 risk-based priority queue | 不足 | MoE-specific marginal harm proxy + quality-debt bound + real approximate communication host |
| Causality：proxy 需要第二次 forward | 失败 | 单次正常 forward 的 router/hidden/logit 特征，且只用决策前特征 |
| Leakage：测试集选最佳 proxy | 失败 | train/calib/validation/test 四段；nested selection |
| Fairness：没有长期请求流 | 失败 | continuous batching + tenant 流 + debt/aging |
| Budget：文档数不是 bytes | 失败 | token/layer/action 的实际 wire bytes 和 kernel 时间 |
| Quality：P95 KL 不等于用户质量 | 不足 | task accuracy、CVaR、worst-tenant、human/judge 指标 |
| Baseline：random 太弱 | 不足 | length、PPL、entropy、gate mass、FIFO、DRR/VTC、oracle marginal harm |
| Host：fixed_tail 本身未证明值得部署 | 不足 | 绑定真实 receiver-aware 或其他明确有效的 degradation host |
| Complexity：请求级状态破坏 batching | 未回答 | scheduler overhead、batch fragmentation、GPU metadata |

## 3.5 替代解释与最小对照

1. **收益来自请求长度。**  
   对照：长度匹配随机；回归掉 token_count；按实际 bytes 配 quota。

2. **收益来自 perplexity/语义难度。**  
   对照：PPL、token entropy、prompt embedding cluster；比较增量 AUROC。

3. **收益来自高 baseline KL 的 tautological 排序。**  
   对照：预测真实边际 harm \(\Delta q\)，不是另一策略的绝对 KL。

4. **gate-mass proxy 只是长请求统计更稳定。**  
   对照：固定长度、分层 bootstrap、每 token 标准化。

5. **静态 quota 已足够，不需要 debt。**  
   对照：同一请求身份反复出现的流；比较 static risk、LRU-protection、VTC-like debt。

6. **简单“连续降级 K 次后强制 full”足够。**  
   必须作为最简 baseline，并扫描 \(K\)。

## 3.6 零额外 forward proxy 设计

### 候选特征与可用时点

| 特征 | 可用时间 | 额外成本 | 风险 |
|---|---|---:|---|
| prompt length / tenant / sampling params | 到达时 | 近零 | 可能只是 workload proxy |
| router entropy、top-k margin、gate mass | 每层 router 后 | 低 | 对当前层通信可能太晚，对下一层/下一 microbatch可用 |
| expert disagreement / output norm | expert compute 后 | 中 | 当前动作后才可得 |
| hidden-state norm、residual change | 每层 | 低到中 | 需避免额外同步 |
| final logit margin、token entropy | 每 token 输出后 | 低 | 只能更新后续 token 风险 |
| prefill PPL / prompt NLL | prefill 后 | 低 | 未必预测 decode 后期 |
| KV cache statistics | decode 时 | 低 | 与 approximation harm 的因果关系不明 |

### 正确评估协议

1. 按文档/会话/租户拆分，禁止同源 prompt 跨 split；
2. calibration 只用于特征和阈值选择；
3. validation 选择 predictor/hyperparameter；
4. sealed test 只做一次；
5. 目标是 worst-risk decile recall、AUROC、Spearman 和最终 allocation utility；
6. 与 length、PPL、entropy 单特征 baseline 比；
7. 报告 predictor latency、GPU→CPU 同步、每 token bytes；
8. workload drift 下在线 calibration 不能读取 reference full logits，除非明确抽样 shadow traffic 并计入成本。

## 3.7 长期 credit/debt 机制

### 最简可部署版本

对每个请求/tenant 维护：

\[
D_i\leftarrow \gamma D_i+\hat q_i(a),
\]

在需要选择被降级请求时，优先选择：

\[
\arg\min_i \frac{D_i+\hat q_i(a)}{w_i},
\]

也就是让当前加权 quality debt 最低的请求先承担近似；高 debt 或高 predicted harm 请求得到 full precision。

配套规则：

- 每个请求连续降级不超过 \(K\) 次；
- 每个窗口 full-precision 占用有上限，避免高风险请求永久垄断；
- 请求提前结束时 debt 记入 tenant，而不是丢失；
- 输出长度未知时按已生成 token 归一化，不依赖长度预测；
- 新请求通过 counter lift 避免利用“新身份”逃避 debt；
- tenant 付费等级映射到 \(w_i\) 和 \(Q_i\)，不共享不可共享的质量预算。

### 三层预算

1. **request/tenant 层**：长期 fairness 和 SLO；
2. **token/microbatch 层**：当前拥塞下 quota；
3. **layer/rank 层**：根据 calibration 安全 mask 决定具体降级单元。

静态 request quota 不足以处理请求长度未知和 decode 风险变化。

### 可证明性质

若每次降级的估计 harm 有上界 \(0\le\hat q_i\le q_{\max}\)，且每次选择最小 normalized debt 的 backlogged tenant，则可仿照 VTC/DRR 证明任意两 backlogged tenant 的估计 debt 差受 \(O(q_{\max})\) 约束。  
但这只是对 **估计 harm** 的公平，不代表真实质量公平；predictor calibration error 必须单独给出 bound 或 empirical coverage。

## 3.8 机制设计空间

- 静态：prompt/PPL risk bucket + 固定 quota；
- 在线：token-window risk update；
- 混合：静态 prior + router/logit 动态修正；
- oracle：真实 per-action marginal task harm；
- 最简：连续降级 K 次后强制 full；
- 高复杂：risk+debt+latency benefit 的 per-microbatch knapsack；
- fallback：risk 置信度低时使用 round-robin/VTC-like fairness，不使用 predictor。

必须报告 predictor、debt、动态预算、fallback、hysteresis 各自的独立贡献。

## 3.9 真实系统实现

```text
请求进入
→ scheduler 创建 request/tenant quality-debt state
→ prefill 提取 prompt/PPL/router prior
→ 每层 router 输出 token→request、entropy、gate margin、gate mass
→ Quality Controller 结合 risk、debt、tenant weight 和网络预算
→ 生成 per-segment precision/quota
→ mixed-precision EP / expert kernel 执行
→ 输出 token entropy、任务 proxy、性能 telemetry
→ 更新后续 token risk 与 debt
→ 请求结束后 debt 汇总到 tenant 长期状态
```

控制器不能对 continuous batch 做逐请求 CPU 循环。推荐 GPU tensor state：

- `request_id[token]`；
- `risk[request]`；
- `debt[request]`；
- `precision_segment[]`。

用 segmented reduction/top-k 生成保护集合；CPU 只做低频 policy 更新。

## 3.10 实验矩阵

### 模型与降级机制

- OLMoE、LLM-jp、现代开源 MoE；
- INT4/NVFP4/MXFP4、rank drop、expert miss/CPU fallback 至少两类 host；
- 检验 proxy 跨机制迁移，不默认稳定。

### 任务

- WikiText/PPL 仅用于 language modeling；
- MMLU/ARC：知识与分类；
- GSM8K/Math：推理；
- HumanEval/MBPP：代码；
- LongBench：长上下文；
- 对话/摘要：judge + factuality；
- 每项都报告 per-request success，而不只 aggregate。

### workload

- 真实 continuous batching；
- 短/长请求混合，未知输出长度；
- bursty/steady/drift；
- 多租户、不同 SLO/付费等级；
- 请求身份重复与新身份 churn；
- 高风险请求集中到单 tenant。

### 指标

- quality：KL、PPL、accuracy、pass@1、judge、worst-request、P95/P99/CVaR；
- fairness：max debt gap、Jain、max-min utility、per-tenant SLO violation；
- performance：TTFT、TPOT、throughput、P99、controller overhead、batch fragmentation；
- resource：full-precision bytes、低精度 bytes、quota utilization、switch frequency。

### 强 baseline

- random、FIFO、round-robin；
- request length、PPL、token entropy、routing entropy、gate mass；
- static risk profile；
- consecutive-K protection；
- DRR/VTC-like token fairness；
- oracle marginal KL/task harm。

## 3.11 对抗场景与边界

1. **所有请求同样脆弱**：predictor 无排序价值；回退 round-robin debt。
2. **prefill 与 decode 风险反转**：在线 token-window 更新；限制 prior 权重。
3. **大量短请求**：历史不足；tenant-level prior + 最简公平。
4. **一个 tenant 全是高风险请求**：tenant quota/cap，禁止侵占其他 tenant。
5. **请求通过重新建 ID 逃 debt**：tenant/account 级 counter。
6. **质量 predictor drift**：coverage monitor；失配时禁用 risk，只保留 fairness。
7. **host action 对质量产生重尾 cliff**：安全 mask 和 hard SLO，不用均值优化。
8. **高风险保护导致 P99 爆炸**：性能 SLO 优先级与 admission control。

## 3.12 最小论文 claim

当前只能声称：

> 在两个小规模 fake-quant 数据集中，文档级降级风险在若干策略间相关，事后 oracle quota 显示了降低 tail KL 的潜在空间。

独立成篇所需的最小升级：

> 单次正常推理中可得的 MoE 信号能预测 action-specific marginal harm；一个 VTC-like quality-debt scheduler 在真实 continuous batching 和 matched bytes 下，降低 worst-request/tenant CVaR，同时保持 TPOT SLO。

若没有真实 degradation host，该方向更适合作为 Receiver-aware 系统的第二贡献，而非独立论文。

# 4. 方向 C：跨层路由可预测性驱动 Expert Prefetch

## 4.1 问题重新定义

### 4.1.1 正确的系统问题

这不应被定义为单纯“预测下一层 expert”，而应是：

> 在分层内存、有限 cache 和传输/计算争用下，做带 deadline、成本、污染和 eviction 的 expert block prefetch scheduling。

cache object 必须为：

\[
o=(model,layer,expert,weight\ block,precision,version),
\]

而不是只有 `expert_id`。

### 4.1.2 形式化

- GPU cache \(C_t\)，容量 \(M\) bytes；
- 下一层/未来层对象需求 \(R_{t+h}\)；
- 对象大小 \(s_o\)，传输时间 \(\tau_o\)；
- 命中概率 \(\hat p_o(h)\)；
- 可用 overlap deadline \(d_o\)；
- 预取带宽 \(B_t\)；
- eviction cost \(E_o\)，pollution cost \(P_o\)；
- 与 compute/HBM/PCIe 争用成本 \(I_o\)。

逐对象 expected benefit：

\[
\mathrm{EB}(o)=
\hat p_o\cdot L_o^{\mathrm{demand}}
-
L_o^{\mathrm{prefetch,exposed}}
-
E_o-P_o-I_o.
\]

选择：

\[
\max_{x_o\in\{0,1\}}\sum_o x_o\mathrm{EB}(o)
\]

约束：

\[
\sum_o x_os_o\le M_{\mathrm{free}},\quad
\sum_o x_o\tau_o\le W_{\mathrm{overlap}},\quad
\mathrm{deadline}_o\ge \mathrm{completion}_o.
\]

对于不同 expert 大小，这是带 deadline 的 knapsack/scheduling，而不是固定 `budget=N`。

### 4.1.3 三种 framing 的判断

1. **预测问题**：已被大量工作覆盖，单独不够。
2. **缓存问题**：需要比 LRU/LFU/Belady/pinning 明确更强，当前没有。
3. **deadline-aware prefetch scheduling**：系统 framing 最合理，但 LayerScope/PreScope 与 PROBE 已直接覆盖 hiding-window/cost-aware scheduling。

因此当前最合理决策不是继续包装，而是先确认是否还有未被占据的机制差异。

## 4.2 当前实验证明与未证明

### 仍可信的离线结果

- calibration/test 分离下，top-1 transition 比 layer-wise frequency baseline 高约 13–19pp；
- lookahead 到 8 层仍有增量信息；
- top-N transition hit rate 比 top-N layer-frequency 高；
- 这些结果支持“跨层条件信息存在”。

### 现有 prototype 不能作为证据

- cache key 跨层错误；
- 只有 top-1，真实是 top-8/top-16；
- cache/miss/prefetch 是离散模拟，不是真正异步 data path；
- v1 Python expert loop 严重放大 compute window；
- v2 dense all-expert BMM 不是真 sparse grouped-GEMM；
- 只测孤立 H2D，不含 compute、HBM、PCIe、多个 stream/tenant 争用；
- prototype 只与 reactive LRU 比，没有 freq-prefetch、LFU、pinning、Belady；
- “n_docs” 实际是 chunk 数；
- 模型未证明真实超过 HBM，可能只是人为限制 cache。

所以当前系统结论应回退到：

> 离线存在条件路由信息，但其可转化系统收益尚未被有效测量。

## 4.3 Novelty 冲突

投稿前必须逐项精读并做 feature matrix：

- **ExFlow (2024)**：跨层 expert affinity/conditional routing，用于 placement 和通信；
- **ProMoE (2024)**：learned multi-layer predictor、GoodPred、chunked prefetch、preemption、reordered inference；
- **HOBBIT (2024)**：mixed-precision expert offload、adaptive prefetch、multi-dimensional cache；
- **Fate (2025)**：cross-layer gate 预测下一层 expert 和 prefetch；
- **LayerScope/PreScope (2025)**：跨层 predictor、全局 cost model、按 compute bubble 校准 prefetch count；
- **PROBE (2026)**：lookahead predictor、replication、strict hiding-window planner、phase-locked co-scheduling；
- **ST-MoE (2026)**：跨层与跨 token 的时空 expert prefetch。

目前“transition table + overlap cap”不能作为主要 novelty。只有以下情况才值得继续：

1. 找到上述工作没有解决、且你的数据已显示明显空间的新对象或新约束；
2. 机制区别不是换一个 predictor，而是新的系统抽象；
3. 修正模拟后仍有显著端到端收益；
4. 直接 baseline 下仍领先。

## 4.4 核心假设拆解与证伪

### 信号假设

1. **transition 增量不是 popularity 重编码。**  
   当前只对 layer-frequency。  
   证伪：within-layer token permutation、conditional entropy、document-holdout、Markov order baseline。

2. **per-token 信息在 batch union 后仍有增量。**  
   未验证。batch 大时 union 可能覆盖大量 expert，频率已足够。  
   证伪：batch 1–256 下比较 per-token、batch histogram、global LFU。

3. **top-1 可代表完整 top-k working set。**  
   明显未验证。  
   证伪：以 full top-k recall、all-required-ready、weighted gate mass 命中为指标。

4. **OOD/漂移后 transition table 稳定。**  
   仅 WikiText 家族。  
   证伪：代码、数学、对话、多语言和时间漂移。

### 硬件假设

5. **存在至少一个 expert-copy 的可用 slack。**  
   当前 proxy 不可信。  
   证伪：真实 sparse grouped-GEMM 下逐层测 overlap；若多数层 \(W<\min_o\tau_o\)，预取不可行。

6. **H2D 可与 expert compute 重叠。**  
   未做并发实验。  
   证伪：同时跑 memcpy + grouped GEMM，测双方 slowdown、HBM controller 和 copy engine。

7. **系统确实 memory constrained。**  
   当前人工 cache。  
   证伪：使用总 expert 权重大于 HBM 的模型或多模型共置。

### 缓存和部署

8. **prefetch 不污染 cache。**  
   未单独测。  
   证伪：wasted bytes、prefetch-before-use eviction、demand hit displacement。

9. **CPU-offload 是合适场景。**  
   需要与 GPU replication、CXL、NVMe 层级比较；不同场景 prior art 不同。

10. **控制器和 predictor 不在关键路径。**  
    未实现真实 pipeline。

## 4.5 最强反方论证

| 审稿质疑 | 当前证据 | 必须回答 |
|---|---|---|
| Novelty 已被 ProMoE/Fate/LayerScope/PROBE/ST-MoE 覆盖 | 严重 | 明确 feature-level 差异；否则停止 |
| Prototype cache identity 错误 | 失败 | 修 key 后全部重跑 |
| 只 top-1，不是模型真实执行 | 失败 | full top-k working set |
| dense BMM 不是 grouped-GEMM | 失败 | 真实 sparse kernel |
| reactive LRU 是弱 baseline | 失败 | freq-prefetch、LFU、pinning、Belady、existing system |
| 人为 cache 限制不代表真实部署 | 不足 | 真正超过 HBM 或多模型共置 |
| 5% 可能在修正后消失 | 高风险 | 跨硬件、batch、模型的 P99 和 CI |
| H2D/compute 独立相加忽略争用 | 失败 | concurrent microbenchmark + Nsight |
| prediction hit rate 不等于 deadline hit | 不足 | timely hit、wasted bytes、exposed latency |

## 4.6 替代解释与最小对照

1. **transition 只是下一层热门 expert 的条件重排。**  
   对照：frequency top-N prefetch 在同一 cache simulator 和真实系统中运行。

2. **收益来自 LRU 太弱。**  
   对照：LFU、ARC、static pinning、layer-wise cache partition、Belady。

3. **收益来自人工小 cache。**  
   对照：容量从 5% 到 100%，用真实 HBM pressure。

4. **收益来自长 Python compute window。**  
   对照：真实 grouped-GEMM；逐层而非 median cap。

5. **多层可预测性来自 global semantic continuity。**  
   对照：token shuffle、document shuffle、同层邻居、last-token history、router weight similarity。

6. **简单 hot-expert pinning 已拿走全部收益。**  
   对照：先 pin hot set，再在剩余容量上测试 transition 的增量。

## 4.7 机制设计空间

### 静态

- layer-wise expert pinning；
- LFU/hot-set；
- static cache partition；
- ExFlow-like placement。

### 在线

- LRU/LFU/ARC；
- batch histogram；
- transition predictor；
- routing drift update；
- deadline-aware prefetch queue。

### 混合

固定 pin 热 expert，剩余 cache 给预测 prefetch；当 predictor entropy 高时只 demand fetch。

### Oracle

- Belady：知道未来完整 top-k；
- deadline oracle：知道 copy completion 和 compute timeline；
- global knapsack：知道 eviction/pollution。

### 最简可部署

逐层 frequency top-N + per-layer measured slack cap。若 transition 不能显著超过它，复杂 predictor 不值得部署。

### 高复杂度上限

对未来多层对象做 cost-aware deadline knapsack，考虑：

- full top-k probability/gate mass；
- expert block size；
- current cache 和 eviction；
- transfer queue；
- compute/copy contention；
- request deadline。

但该空间与 LayerScope/PROBE 高度重叠。

### fallback

- predictor entropy/漂移过高：frequency/LFU；
- 无 overlap：不预取；
- cache pressure 高：demand-only；
- copy contention：取消低 benefit prefetch。

## 4.8 如果仍继续，正确的真实系统实现

### 推荐场景

必须选一个真实需要分层内存的模型：

- expert 权重总量超过 HBM；
- 或多个 MoE 模型共置导致 HBM 不足；
- CPU pinned memory 为第二层；
- 可扩展到 NVMe/CXL，但首版不要同时做。

### 数据路径

```text
请求进入
→ router/轻量 predictor 产生未来 full top-k expert-block 概率
→ cache manager 查询 (model, layer, expert, block, precision)
→ scheduler 计算 expected benefit、deadline、eviction cost
→ copy stream 发起 cudaMemcpyAsync / GPUDirect Storage
→ CUDA event 标记每个 object ready
→ grouped-GEMM 只等待真正需要且未 ready 的对象
→ 更新 hit/timely-hit/waste/eviction/contention telemetry
→ 下一层/下一 token 决策
```

### 同步原则

- 不可在主 stream 上全局 synchronize；
- 每个 object 使用 event；
- demand kernel 只等待其依赖对象；
- copy stream 有优先级和取消策略；
- 逐层使用真实 slack，不用全模型 median；
- Nsight 验证 copy/compute overlap 和 HBM 争用。

## 4.9 实验矩阵

### 模型/路由

- E=8/32/64/128/256；
- top-k=1/2/4/8/16；
- 不同层数、expert size、router entropy；
- OLMoE、Mixtral/Qwen-MoE/DeepSeek-like；
- full top-k 与 gate-mass weighted working set。

### 硬件/层级

- PCIe 3/4/5；
- NVLink/NVSwitch GPU-to-GPU migration；
- HBM 容量不同；
- pinned/non-pinned CPU；
- 可选 NVMe→CPU→GPU；
- 多 stream、多 tenant、copy engine 饱和。

### workload

- prefill/decode；
- batch 1–256；
- prompt/output 长短混合；
- burst/drift/OOD；
- 多模型共置；
- cache working set 小于/接近/远大于 HBM。

### 指标

- demand hit、timely prefetch hit；
- precision/recall；
- wasted bytes、prefetch-before-use eviction；
- pollution-induced misses；
- exposed copy latency；
- TTFT/TPOT/P95/P99/throughput；
- GPU util、HBM occupancy、PCIe/NVLink bytes；
- predictor/scheduler 开销；
- compute 与 memcpy slowdown。

### baseline

- demand-only LRU；
- LRU/LFU/ARC；
- static hot pinning；
- frequency top-N prefetch；
- layer-wise cache partition；
- Belady；
- cost-aware greedy；
- 直接对比 ProMoE/HOBBIT/Fate/LayerScope 可复现实现或等价机制。

### 消融

- 去掉 transition；
- 去掉 multi-layer；
- 去掉 cost；
- 去掉 eviction；
- 去掉 deadline cap；
- per-layer vs median slack；
- top-1 vs top-k；
- 无 contention model；
- 静态 vs 在线更新。

## 4.10 对抗场景与边界

1. 路由随机：transition 退化为 frequency；
2. domain 突变：drift detector 后 fallback；
3. cache 小于下一层 working set：prefetch thrash；
4. batch 很大：几乎所有 expert 都被需要，预测无意义；
5. batch 很小且 sparse kernel 极快：无 copy slack；
6. PCIe 极快：demand miss 不重要；
7. PCIe 极慢：任何单 expert 都无法按 deadline 完成；
8. compute/memcpy 争用：表面 overlap 实际让两者都变慢；
9. expert 大小不同：固定 N 预算错误；
10. 错误预取驱逐即将 demand 的对象：收益反转。

## 4.11 最小 claim 与 go/no-go

当前可保留的 claim：

> 两个模型的 WikiText route trace 中，当前层 top-1 expert 对未来层 expert 含有超过 layer-frequency 的条件信息。

当前不能保留系统 claim。

继续条件：

1. 修复 `(layer, expert)` cache key；
2. full top-k；
3. frequency/LFU/pinning/Belady；
4. 真实 sparse grouped-GEMM；
5. 真正 memory-overcommitted 模型；
6. 明确不同于现有工作的机制；
7. 在以上条件下仍有 ≥5% P99/throughput 改善。

任一关键条件失败，应停止独立投稿。

# 5. 合并论文：Receiver-aware + Quality Isolation

## 5.1 为什么这两条可以形成一条主线

Receiver-aware 单独回答“哪里拥塞”，却没有回答“降级谁”；Quality Isolation 单独回答“保护谁”，却没有一个值得部署的 host。两者合并后形成完整控制回路：

```text
网络 pressure 决定是否需要 approximation 以及需要省多少资源
→ per-message expected latency benefit 决定在哪里省
→ per-request risk/debt 决定不能反复伤害谁
→ mixed-precision EP kernel 执行动作
→ 网络与质量 telemetry 更新下一轮
```

这不是把两个弱点拼接，而是补齐彼此缺失的两个约束；前提是 mixed-precision EP kernel 在真实硬件上确实有效。

## 5.2 推荐论文问题

> 如何在动态 MoE expert-parallel 拥塞下，用只在决策前可得的信号选择性压缩通信，同时保证每请求/租户的累计质量退化有界？

## 5.3 可能的核心贡献

1. **Causal mixed-precision EP data path**：真实 DeepEP/UCCL-EP 路径，量化与 metadata 开销可测。
2. **Direct-benefit congestion controller**：不用 synthetic regime label，直接预测下一 microbatch 的 queueing reduction。
3. **Quality-debt isolation**：VTC-like debt，在未知输出长度下限制 repeated degradation。
4. **真实评估与负结果**：说明 stale telemetry、静态 profile、简单 threshold 各自的适用边界。

## 5.4 必须避免的过度扩张

- 不同时加入 drop、reroute、replication、admission 五种动作；
- 不把 prefetch 加进论文；
- 不声称替代底层 congestion control；
- 不以平均 KL 和平均 latency 为主要结果；
- 不用 synthetic hotspot 作为唯一 workload。

# 6. 完整 go/no-go 与执行顺序

## 6.1 Receiver + Quality 的 kill criteria

1. 原生 mixed-precision combine 相比 optimized uniform FP8：
   - combine latency 改善不到 10%，或
   - 端到端 P99 TPOT 改善不到 5%，  
   则停止系统主线。
2. static placement / FAST-like schedule / queue threshold 与复杂控制器差距小于 2%，删除 adaptive predictor claim。
3. bytes 减少与真实 queueing/P99 无显著关系，停止 receiver-aware precision。
4. 决策前 quality proxy：
   - worst-decile AUROC < 0.7，或
   - recall 不到 random 的 2 倍，或
   - 在线开销 >1%，  
   则只保留 round-robin debt，不声称 risk-aware。
5. quality debt 相比 consecutive-K/VTC baseline：
   - worst-request/CVaR 改善不到 20%，或
   - throughput 代价超过 3%，  
   则删除复杂 isolation。
6. controller warm-up 超过 workload phase 的 10%，或错误切换造成 >5% regret，改用静态策略。

## 6.2 Prefetch 的 kill criteria

1. 无法写出与 ProMoE/Fate/LayerScope/PROBE/ST-MoE 明确不同的一句话贡献；
2. 修复 cache identity 和 full top-k 后收益 <5%；
3. 真实 grouped-GEMM 下多数层 slack 小于一个 expert copy；
4. frequency+pinning 与 transition 差距 <2%；
5. 模型并不真实超过 HBM；
6. contention 后收益反转。

满足任一项即可停止独立投稿，不应继续用更多离线 predictor 掩盖系统不可行动性。

## 6.3 八周执行计划

### 第 1 周：修复效度

- 修 v3 post-warm-up 因果评估；
- Quality 做严格 calibration/validation/test；
- Prefetch 修 `(layer, expert)` key、top-k 和 baseline；
- 完成 related-work feature matrix。

### 第 2 周：最小硬件可行性

- mixed-precision pack/transport/unpack microbenchmark；
- RDMA incast bytes→queueing 曲线；
- sparse grouped-GEMM + concurrent memcpy；
- 决定 Prefetch 是否终止。

### 第 3–4 周：合并原型

- vLLM/SGLang request state；
- DeepEP/UCCL-EP precision segment；
- telemetry timestamp；
- 最简 queue threshold + consecutive-K debt。

### 第 5 周：复杂机制只在简单机制有空间时加入

- direct benefit model；
- risk proxy；
- VTC-like debt；
- hysteresis/cooldown。

### 第 6 周：强 baseline

- FAST/UCCL/native；
- static placement/profile；
- random/uniform/queue threshold；
- length/PPL/gate mass；
- round-robin/DRR/VTC；
- oracle。

### 第 7 周：完整矩阵与失败场景

- 跨模型、跨 workload、跨硬件；
- drift、短请求、热点切换、oversubscription；
- task quality 和 tail fairness。

### 第 8 周：硬性 go/no-go

- 按 kill criteria 删除无效机制；
- 冻结 claim；
- 只为通过门槛的主线写论文。

# 7. 投稿定位

- **MLSys**：若重点是 MoE serving 中的 mixed-precision data path + online controller + quality fairness，最匹配。
- **NSDI**：只有在真实多节点网络、incast/flow control 和 FAST/UCCL 对比成为主贡献时才匹配。
- **ASPLOS**：若核心创新落在 mixed-format通信/融合量化 kernel、GPU/NIC 协同和硬件瓶颈。
- **EuroSys**：若形成完整 serving runtime、可部署控制面和多租户隔离。
- **OSDI**：需要跨平台、生产级 trace、广泛适用性和明显端到端收益；当前距离较远。
- **Prefetch**：在 novelty 和有效性问题解决前，不建议选顶会目标。

# 8. 最终决策

1. **不要把原文三条都标为 PASS。**
2. **Receiver-aware：Conditional，保留为合并系统的性能控制面。**
3. **Quality Isolation：Promising P0，但当前 proxy claim 无效；保留为合并系统的公平/质量控制面。**
4. **Expert Prefetch：当前系统结果无效且 novelty 高度冲突；暂停，先修复和查重。**
5. **唯一值得优先投入的论文路径：真实硬件上的 Quality-bounded Congestion Adaptation。**

论文最小可信主张应当窄而硬：

> 我们实现了一个因果、硬件可测的 MoE EP 近似通信路径。系统只在下一 microbatch 的真实 receiver pressure 足以覆盖量化开销时降级，并用 per-request quality debt 限制重复伤害；在 telemetry 过时、质量风险不确定或收益不足时自动回退到原生通信。

如果这句话不能被真实系统实验支持，应接受负结果，而不是继续增加模拟层。
