# PartialGuard：层级 MoE Combine Partial 的晚绑定完整块固定基数编码

> 严格研究报告｜2026-07-14  
> 研究对象：分布式 MoE 推理中的 hierarchical/high-throughput combine  
> 当前阶段：研究假设与前置验证方案，不是已完成系统

## 一页判决

**[Inferred] 唯一主方案：PartialGuard（Late-Bound Full-Tile Fixed-Cardinality Coding of Hierarchical MoE Partials）。**

[Hypothesis] 一句话定义：在 hierarchical/high-throughput MoE combine 的 backend-native source-domain 归并已产出 BF16 partial、尚未发起跨节点 RDMA 的窗口，对真实 destination-token partial 做 reduction-fused partial-norm 评分；每个完整 B-item wire tile 恰好保护 q 个 partial 为 FP8，其余编码为 MXFP4，并装入两个同质、固定容量 lane；非完整块回退同 fork 的 uniform FP8。

[Observed] 当前实验只在“按 expert owner 分组”的 Mac/CPU fake-quant surrogate 上证明：post-output 信号比 rank、gate、random 更会选择固定数量的 FP8 向量；它没有实例化 source domain、destination peer、native FP8/FP4、真实 lane、NIC bytes、GPU kernel 或延迟。

[Inferred] 该方向仍是三条候选中最适合继续的主线，因为它复用真实 HT backend 已存在的 reduction-before-RDMA 数据流，机制无跨步状态，且可以依次用 Mac、单 GPU、两节点小集群快速证伪。

[Hypothesis] 它能否成为论文贡献，取决于三个尚未通过的门：真实 wire-unit 上的质量优势、计入全部物理开销后相对 uniform FP8 至少约 20% 的 actual-byte 空间、以及 fused codec 的净 receiver-completion/TTFT 收益。

**[Inferred] 硬结论：当前不具备 CCF B/C 系统论文结论。**  
[Inferred] 若完成真实 source-domain P0、单 GPU fused codec 与至少 `2 nodes × 4 GPUs/node` 的 RDMA operator，可形成高质量 ML Systems workshop / operator-characterization 候选；CCF C system claim还必须有端到端serving结果，CCF B只能是完整多模型、多拓扑结果后的冲刺上限。  
[Inferred] 若完全没有多 GPU，本课题仍可形成合格硕士论文，但必须收缩为“数值机制 + codec break-even characterization”，不得声称 EP 系统加速。

# A. 当前 Idea 的真实技术核心，以及最大的新颖性缺口

## A.1 已成立的 observation

[Observed] patched-full 与原模型bitwise equal；EP=1 grouped combine与patched-full bitwise equal，最大logit difference为0。这只验证软件patch和EP1变换没有改语义，不验证EP8 owner grouping、真实wire unit或低精度codec。

[Observed] 两个模型、两种 placement 的 EP8 owner-group replay 均存在合并机会：OLMoE E64 top-8 的 routed-pair/grouped-vector 为 1.455–1.475、pair collision 为 31%–32%；LLM-jp E32 top-16 分别为 2.106–2.118 和 52%–53%。

[Observed] 在约 50% FP8 / 50% MXFP4、tile=64 的相同 simulated quota 下，`mixed_contribution` 相对 rank 的 grouped-reference KL 下降 12.9%–19.2%，相对 gate 下降 11.2%–22.4%，并在每个目录内的六项比较经 document bootstrap 与 Holm 调整后保持方向。

[Observed] `mixed_contribution` 与 `mixed_qerr` 无稳定显著差异；grouped contribution 相对 pre-group pair contribution 也没有稳定优势。因此成立的是“expert output 已知后的信号族有用”，不是某个 norm 公式或 cancellation 理论已成立。

[Observed] 固定 owner/tile quota 相对 global allocation 的 grouped-reference KL tax 为 4.2%–22.3%，其中 3/4 setting 显著；这说明 deterministic rate 不是免费的。

[Observed] 当前记账下 mixed 相对 grouped BF16 的 logical saving 为约 61.5%–61.7%，相对 uniform FP8 的增量 logical payload saving 约 23.6%。该记账没有真实 header、mask、alignment、padding、buffer reservation、message startup、pack/unpack 或 overlap。

[Observed] mixed 的质量在四个 setting 都差于 uniform FP8：相对 grouped-BF16 的 KL 增幅约为 +63.7%、+74.7%、+28.7%、+44.6%。因此当前 trade-off 是“多约 23.6% logical-byte saving，换取更高 KL”，不是对 uniform FP8 的质量支配。

[Observed] LLM-jp round-robin 中 contribution 虽在 KL 上优于 gate，但 PPL 相对 gate 变差约 0.055，95% bootstrap CI 为 [0.020, 0.095]。不能写“所有质量指标一致改善”。

## A.2 当前最强 inference

[Inferred] 正确的研究对象不是 expert rank，也不应默认是当前代码中的 owner vector，而应是目标 backend 真正在跨域链路上传输的最小可独立编码向量。

[Observed] NCCL EP HT 文档要求 caller 对 expert outputs 应用权重并预归并成 `[N(r), hidden]` combine input；其 Hybrid kernel 在节点内以 FP32 累加、转 BF16，随后以 `batch_count × H × sizeof(uint16_t)` 发起跨节点 RDMA。参见 [NCCL EP README](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/README.md#L349-L360)、[BF16 partial store](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/device/hybrid_ep.cuh#L1969-L2021) 与 [RDMA byte count](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/device/hybrid_ep.cuh#L2198-L2224)。

[Inferred] 因而，“在 backend-native local reduction 产生BF16 partial之后、跨节点 RDMA 之前，按真实 domain partial 晚绑定编码”是一个真实且窄的插入窗；但它只适用于存在该数据流的 HT/hierarchical path。

[Observed] NCCL EP LL 是面向小 batch 的直接 P2P 路径，receive/combine layout 可为 expert-major/rank-major 展开形式；它与 HT 的 flat pre-reduced unit 不同。[NCCL EP mode split](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/README.md#L34-L42) [LL layout semantics](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/README.md#L358-L364)

[Inferred] 主方案应先限定为 prefill/高并发 HT；decode/LL 默认 fallback 到 native BF16 或 uniform FP8，除非独立实验证明 tile fill 和 break-even 成立。

## A.3 尚未验证的 system claims

- [Hypothesis] real source-domain partial 上仍存在足够的 score separation。
- [Hypothesis] full-tile exact-q mixed lanes 计入所有物理开销和短组回退后，整体仍比 uniform FP8 少至少约 20% actual bytes。
- [Hypothesis] reduce、score、top-q、quant、pack 可以融合，新增 GPU 时间不超过 uniform-FP8 combine 的 10%，且小于 RDMA 暴露时间节省。
- [Hypothesis] receiver completion、quality-constrained goodput 或 TTFT 能获得稳定净收益。
- [Hypothesis] 多层量化不会造成不可接受的 routing drift、长尾请求伤害或任务准确率回退。
- [Hypothesis] fixed cardinality 对 CUDA graph、静态 buffer 与双 lane 的工程价值大于其 4.2%–22.3% quality tax。

## A.4 已失败或降级的旧叙事

- [Observed] PLTB：降为 format-dependent historical baseline。
- [Observed] fixed-rank R-layout：降为低开销/布局规整 baseline。
- [Observed] receiver-aware：仅有 proxy 信号，无真实 receiver queue、NIC、completion 或 P99。
- [Observed] Graceful/ignore-late：receiver 忽略不等于 sender 少发，不能记 wire saving。
- [Observed] QTree/topology-aware accumulation：hierarchical reduction 已是 backend 基础机制。
- [Observed] additive-KL MILP：端到端可加性假设失败。
- [Observed] “Gate B 已通过”：不成立；只观察到 quality-side trigger。

## A.5 最大的新颖性缺口

[Observed] local reduction、hierarchical EP、uniform FP8/FP4、mixed-precision activation、gate×activation importance、fixed buffer 和 progressive transmission 均已有公开先例。

[Inferred] 因此不能把“FP8/FP4 mixed combine”或“先 local reduction”写成创新。唯一可能的新颖交集是：**以真实 post-reduction domain partial 为 late-bound 决策对象，并用full-tile exact-cardinality homogeneous lanes生成长度与lane offset可静态计算的HT codec frame。** 这不是backend buffer安全的必要条件。

[Hypothesis] 该交集尚未被逐篇全文/代码穷尽证明为首创；它是待保护的 novelty claim，不是已确认的 novelty fact。

# C. 选出唯一主方案

## C.1 选择

[Inferred] 选择 **PartialGuard**，但其论文表述必须是“待验证的 HT wire-contract mechanism”，而非“已经证明的 QuotaEP-H 系统”。

## C.2 为什么优于另外两个

[Inferred] 相对 DPCM，PartialGuard 无跨 request/token 状态、无 cache coherence、无 rollback/migration protocol，且已有一条虽有污染但方向一致的 quality-side signal。它最符合硕士论文“少量高信息实验可杀、机制简洁”的约束。

[Inferred] 相对 CodecMap，PartialGuard 提供了可实现的新 wire contract，而不只是测量框架。CodecMap 应内化为 PartialGuard 的 phase gate、cost model 和 negative-result safety net，不计作并列主贡献。

[Inferred] DPCM 不与 PartialGuard 融合。把 temporal cache 塞进当前主线会改变语义对象并制造复杂状态机；只有 PartialGuard P0 失败且 decode trace 显示强 residual redundancy 时才另案切换。

## C.3 为什么不是已有工作的简单组合

[Observed] NCCL EP/Hybrid-EP 已提供 hierarchical/local reduction 和 BF16 HT combine；MoRI 当前源码已支持 inter-node uniform FP8 combine，且将 blockwise FP4 combine 限在 intra-node 路径；Practical FP4 把 FP4 用于 forward dispatch、combine 保持 BF16；FGMP 的细粒度混合精度对象是权重/激活计算块，不是 EP post-reduction wire partial。

[Inferred] PartialGuard 不能认领这些组件。它只认领一个待验证的contract：**必须等real partial形成后才能观察其局部量化风险；在RDMA前对full tile做exact-cardinality分流，可生成长度和lane offset静态可计算的mixed frame。** exact-q不是backend预分配的必要条件，因此必须击败variable tagged/bounded frame强基线。

[Hypothesis] 这个 contract 是否足以构成论文贡献，仍需 prior-art 全文与实现结果共同确认；如果最终只是两个独立 buffer 加 top-q，则 novelty 不足。

## C.4 其他方案的去留

- [Inferred] DPCM：条件备份，仅做一次低成本 trace P0；未通过前不投入通信 kernel。
- [Inferred] CodecMap：强制评价骨架；即使主方案失败，也保留为诚实的 negative characterization。
- [Inferred] bounded borrowing：只作为 dev-only optional enhancement；除非它以固定上界、单次局部操作显著追回 quota tax，否则不进入主机制。
- [Observed] receiver-aware、PLTB、rank、Graceful、QTree、MILP：分别作为历史 baseline、消融或被否定路线，不与主方案并列。

## C.5 为什么不把 bounded borrowing 升为核心

| setting | strict→global 可追回KL | 占 strict→uniform-FP8 KL差距 |
|---|---:|---:|
| OLMoE contiguous | [Observed] 0.000219 | [Observed] 10.32% |
| OLMoE round-robin | [Observed] 0.000578 | [Observed] 25.02% |
| LLM-jp contiguous | [Observed] 0.001516 | [Observed] 81.74% |
| LLM-jp round-robin | [Observed] 0.000411 | [Observed] 18.72% |

[Observed] 即使达到global-contribution upper bound，其KL仍比uniform FP8高约57.10%、56.00%、5.25%、36.29%；三组setting中，borrowing解决的不是mixed-vs-FP8主差距。

[Inferred] 算法本体只是partition lower/upper bound下的capacity-constrained top-k；跨K个tile还会等待更多partial，破坏NCCL Hybrid当前8-token streaming。因此它只保留为 `K≤4,r/B≤1/8` 的development ablation，不计论文核心贡献。

# D. 主方案的完整设计

## D.1 系统模型与适用范围

[Hypothesis] 目标是有层级拓扑的 MoE inference EP group：`G=N×g` 个 GPU 分布在 `N` 个 source domain（第一版即节点），节点内为 NVLink/NVSwitch，节点间为 RDMA。

[Hypothesis] 第一版只覆盖 high-throughput/prefill 或高并发 chunked-prefill combine。LL/decode、小 batch、单节点、通信完全被 expert compute 隐藏的区间不启用。

[Observed] NCCL EP 将 LL 定义为小 batch direct P2P，将 HT 定义为节点内聚合后跨节点 RDMA；其公开 HT combine 当前只接受 BF16。[NCCL EP README](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/README.md#L34-L42) [NCCL EP datatype assertion](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/nccl_ep.cc#L3170-L3185)

## D.2 真实 backend 数据流

对 destination/origin token `t`，source domain `d` 上的本地专家集合记为 `E(d,t)`。

$$
v_{d,t}
=
\operatorname{cast}_{BF16}
\left(
\sum_{e\in E(d,t)}
g_{t,e}\,o_{t,e}
\right)
$$

[Observed] NCCL Hybrid-EP 源码在节点内以 FP32 accumulator 累加，随后转为 BF16 destination-token partial，再复制到 per-destination global buffer；RDMA warp 发送 BF16 partial。[local reduction/store](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/device/hybrid_ep.cuh#L1969-L2021) [RDMA put](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/device/hybrid_ep.cuh#L2198-L2224)

[Hypothesis] PartialGuard 的插入点就在 `v_{d,t}` 写入 RDMA source buffer 之前：

`expert outputs → weighted local reduce → real BF16 domain partial → score/select/encode → RDMA → decode → destination BF16 accumulation`。

[Observed] 这不是现有 Python reference 的实际语义。当前 `grouped_owner_combine.py` 只有 owner dimension，没有 token-origin rank、source domain、destination peer 或 peer pair；其“peer”标签超出了实现。

## D.4 Wire unit 与决策窗口

[Hypothesis] wire unit 是 `(layer, source-domain, destination-peer, token-origin)` 对应的非零 BF16 partial，而不是 `(token, expert)`、expert owner 或 rank。

[Observed] 当前NCCL commit的 `HYBRIDEP_COMBINE_RDMA_STREAMING_BATCH=8` 是最大flush阈值，不是固定8项batch；hole、stream末尾或达到阈值都会提前flush，因此原生group大小为1–8。[NCCL Hybrid streaming configuration](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/device/hybridep_configs.cuh#L42-L48) [early-flush condition](https://github.com/NVIDIA/nccl/blob/5067397c2676d5aed50042fc39e5c8ee96eb0027/contrib/nccl_ep/device/hybrid_ep.cuh#L2198-L2211)

[Hypothesis] 主系统点严格冻结 `B=8,q=4`：只有连续凑满8项的native group使用mixed frame，1–7项early-flush group均回退same-fork uniform FP8。`B∈{16,32,64}` 只作exploratory sensitivity，不可从中重选confirmation赢家。

[Observed] 当前正向质量证据只覆盖tile=64；[Hypothesis] B=8信号与目标workload的full-tile fraction是新生死门。短group不跨request等待、不跨iteration carry；整体只有buffer上界，只有full tile具备exact-cardinality frame。

[Observed] NCCL Hybrid-EP 已用 max-token fixed-stride buffer 承载可变 `batch_count` RDMA writes；因此“backend 必须 exact-q 才能静态分配”不是事实。exact-q 的必要性只能来自本文双-codec lane offset 可预测性与选择开销上界，必须用实验而非措辞证明价值。

## D.5 可观测信号与决策变量

[Hypothesis] 主评分使用 reduction 时可顺手累积的

$$
s_i=\lVert v_i\rVert_2^2.
$$

[Observed] 当前 surrogate 中 contribution 与 qerr 无稳定差异；[Inferred] qerr 需要先计算或近似两种 codec error，可能多读写整条向量，因此不应默认优于 norm。qerr 只作为强诊断 baseline。

[Hypothesis] 每个 full tile 的二元变量 `z_i∈{0,1}` 表示 FP8（1）或 MXFP4（0），且：

$$
\sum_{i=1}^{B}z_i=q.
$$

[Hypothesis] 理想目标是最小化量化引起的端到端质量损失：

$$
\min_{\mathbf z}\sum_i
\big[z_iD_8(v_i)+(1-z_i)D_4(v_i)\big],
\quad \sum_i z_i=q,
$$

[Inferred] 真实 `D` 在线不可得；第一版用frozen norm score做局部top-q。qerr只近似边际收益：

$$
\Delta_i=\lVert v_i-Q_4(v_i)\rVert_2^2
-\lVert v_i-Q_8(v_i)\rVert_2^2
$$

[Inferred] 该qerr只用于诊断norm proxy是否损失过大，不作为已证明廉价的online score。

1. [Hypothesis] 冻结 target backend commit、model/tokenizer/dataset revision、target-format codec、accumulation order和 source-domain mapping。
2. [Hypothesis] target system point预先固定 `B=8,q=4`；calibration split只校准scale，development split只冻结phase-enable threshold；confirmation split一次性运行。更大B只进exploratory appendix。
3. [Hypothesis] 建立 CodecMap：对 `(phase,batch,H,top-k,domain width,link)` 测 native BF16、同 fork 优化的 uniform FP8、matched-byte uniform FP6（若目标 codec可得）、uniform MXFP4 和 PartialGuard 的 `pack + transfer + unpack`。
4. [Hypothesis] 只在预测 actual-byte saving≥20%、codec overhead≤uniform-FP8 combine 的 10%、且通信未完全 overlap 的 bucket 启用。
5. [Hypothesis] 不训练 controller，不拟合跨 GPU 全局 oracle，不用 test/confirmation 数据选超参。

## D.7 Online 算法

```text
Input: backend-ordered BF16 partial stream V, tile B, protected count q
Frozen: phase_enable[stage,batch_bucket,link], codec layouts

for each (layer, source_domain, destination_peer) stream:
    for tile T in V:
        if not phase_enable or len(T) < B:
            encode_uniform_fp8(T); continue

        # fused with final local-reduction store
        for partial v_i in T:
            score_i = sum_j float(v_i[j])^2

        H = stable_block_topq(score, q)   # B-bit high mask
        parallel for i in [0, B):
            if H[i]: encode_fp8(v_i, high_lane[rank_H(i)])
            else:    encode_mxfp4(v_i, low_lane[rank_notH(i)])

        write(header, high_mask, high_lane, low_lane)
        rdma_put(one_contiguous_region)

receiver:
    verify codec/version/tile header
    for original slot i in deterministic order:
        decode from high/low lane using mask popcount
        accumulate into destination token in backend-defined precision/order
```

[Hypothesis] `stable_block_topq` 可用 warp/block bitonic selection、radix/histogram threshold 或小 `B` selection network；第一版不使用跨 tile/global borrow。

## D.8 Buffer layout

```text
| fixed header |
| high mask:  B bits |
| alignment padding |
| FP8 lane: q × aligned_S8(H) |
| MXFP4 lane: (B-q) × aligned_S4(H) |
| end padding / completion flag |
```

[Hypothesis] header 至少冻结 `{codec_version, layer/stream epoch, B, q, valid_count, scale format, lane offsets, byte_length}`；token routing metadata应尽量复用 backend 现有 map。

[Hypothesis] 对 full tile，物理 bytes 为

$$
M_{PG}
=H_{hdr}+\lceil B/8\rceil+P_{align}
+qS_8(H)+(B-q)S_4(H).
$$

[Inferred] 主路径不需要额外valid mask，因为只编码full tile且收发双方复用已有canonical route/token map；若目标backend强制padded slot/validity metadata，必须对PartialGuard和所有baseline同样计入。

[Hypothesis] `S_8,S_4` 必须取 native packed size，包括 block scale、对齐和 codec-specific metadata；不得继续使用软件 proxy 的 `H+4` 或 `H/2+H/32` 冒充实际 backend wire。

[Hypothesis] baseline bytes 同样按相同 header、routing map、alignment、message count 记账：

$$
M_{U8}=H_{hdr}+P_{align,8}+B S_8(H).
$$

## D.9 Kernel/collective integration

[Inferred] NCCL EP 当前 API/HT kernel硬编码 BF16 combine，因此 PartialGuard 不是一个配置开关；需要 fork/extension：在 intra-node reduction store 与 GIN RDMA warp之间加入 score/select/pack stage，并在 remote reduction前加入 decode。

[Inferred] 最小可行 prototype 不应先改完整 vLLM/SGLang，而应先复刻 Hybrid-EP 的“reduced buffer → RDMA → remote accumulate”operator，确认 codec break-even 后再接 serving runtime。

[Observed] DeepEP 的新 elastic path 支持非 expanded layout与 local/scale-up reduction语义，但公开 combine input仍以 BF16 为主；reference 也显式区分 `reduce_in_local` 与 `reduce_in_scaleup`。[DeepEP reduction reference](https://github.com/deepseek-ai/DeepEP/blob/dd758caf451848bd150e1046af3d0a73e5fff38d/deep_ep/utils/refs.py#L177-L243)

[Observed] MoRI 当前 inter-node combine源码支持 homogeneous `Fp8DirectCast`，而 `Fp4BlockwiseQuant` 被显式限制到 IntraNode combine。[MoRI inter-node combine](https://github.com/ROCm/mori/blob/4890fd9d4a4c0e2776f5c3768c5b35d7185fdb78/src/ops/dispatch_combine/internode_v1.cpp#L1215-L1247) [MoRI FP4 restriction](https://github.com/ROCm/mori/blob/4890fd9d4a4c0e2776f5c3768c5b35d7185fdb78/src/ops/dispatch_combine/launch.cpp#L522-L527)

## D.10 复杂度

- [Hypothesis] 时间：local reduce 原有 `O(BHk_d)`；新增 score/quant/pack 为 `O(BH)`，top-q 为 `O(B log B)` 或小固定 B 的 `O(B)` selection。
- [Hypothesis] 临时空间：`O(BH)` 双缓冲；score/mask 为 `O(B)`；生产实现可复用 RDMA source window。
- [Hypothesis] 通信：每 full tile 从 `O(BS_8)` 降为 `O(qS_8+(B-q)S_4+metadata)`；这只是编码复杂度，actual NIC bytes 必须实测。
- [Hypothesis] 控制：完全 peer-local，无全局同步、MILP、跨 peer top-k 或在线反馈。

## D.11 Break-even condition

[Hypothesis] 对一个 full tile：

$$
T_{\text{wire-save}}
=\frac{M_{U8}-M_{PG}}{BW_{\text{eff}}}.
$$

$$
T_{\text{added}}
=T_{\text{score}}+T_{\text{topq}}+T_{\text{pack-PG}}
-T_{\text{pack-U8}}+\Delta T_{\text{decode}}
+\Delta T_{\text{signal/sync}}.
$$

[Hypothesis] 只有同时满足以下条件才启用：

$$
T_{\text{wire-save}}>T_{\text{added}}
$$

且

$$
\Delta T_{\text{exposed}}
=
\max(0,T_{\text{combine,base}}-T_{\text{overlap}})
-
\max(0,T_{\text{combine,PG}}-T_{\text{overlap}})
>0.
$$

[Inferred] 23.6% logical payload saving 是绝对上界的一部分；即使 codec 零开销，端到端上界也约为“未被覆盖的跨节点 combine 时间占比 × 23.6%”，不能外推成 23.6% TTFT/TPOT。

[Hypothesis] 目标workload中至少80%的transmitted partial必须进入full B=8 frame；否则短group fallback使整体saving不足，关闭PartialGuard。该阈值与native group-size histogram必须在真实trace上报告。

## D.12 Fallback 与稳定性

- [Hypothesis] LL/decode、1–7项early-flush group、unsupported shape/format、single-node、低 predicted saving：same-fork optimized uniform FP8；该扩展不可用时回退native BF16。
- [Hypothesis] codec/version/layout 在 communicator 初始化时协商；不支持者整组关闭，禁止 per-message 隐式猜测。
- [Hypothesis] stable tie-break 以 backend slot index 为准，保证可重复。
- [Hypothesis] 参数只在 deployment profile 更新；运行中无反馈振荡。
- [Hypothesis] 若 quality canary、routing drift 或 codec parity 超阈值，按 layer/stage 静态禁用，而不是临时训练策略。
- [Hypothesis] bounded borrowing 不是主路径。若未来加入，只允许固定窗口、固定 spill cap，并必须证明不会引入额外 barrier 或可变 buffer 风险。

# E. 三条明确、可独立成立的论文贡献

> 以下是“计划形成的贡献”，不是当前已经完成的贡献。

## E.1 Contribution 1：post-reduction partial 的候选决策窗口

- Observation：[Observed] routing-only rank/gate 在 owner surrogate 中弱于 post-output signal；真实 HT backend又确实在 RDMA 前形成 local-reduced partial。
- Mechanism：[Hypothesis] 把 precision decision 从 routing 后或 per-expert output 移到 backend-native reduction产生BF16 partial后、RDMA前，并只观察real partial。
- Evidence：[Hypothesis] untouched real-domain replay需证明 PartialGuard在两个模型上同时优于 random与 strongest origin-only selector；backend capture需证明该 partial与 native BF16 combine等价。

## E.2 Contribution 2：full-tile 固定基数的同质双 lane wire contract

- Observation：[Observed] content-adaptive mixed precision与当前 homogeneous backend buffer/codec不直接兼容；[Observed] exact quota存在4.2%–22.3% quality tax。
- Mechanism：[Hypothesis] full tile内 exact q/B，mask映射到单连续region中的FP8/MXFP4同质lane，短tile走uniform FP8。
- Evidence：[Hypothesis] native operator需证明actual bytes减少≥20%、新增codec时间≤uniform-FP8 combine的10%，并对比variable layout、uniform codec与global upper bound。

[Inferred] 该贡献的风险最高：现有HT backend在fixed-stride buffer中已能发送variable token count，因此exact-q不能靠“静态buffer必须如此”自证；它只让full-tile output length和lane offset可静态计算，且必须在相同质量下击败variable tagged/bounded frame。

{KL_{\text{random}}-KL_{\text{global}}}.

[Hypothesis] 仅当 `KL_random > KL_global` 时使用该比例；若分母不为正，则H2直接失败，禁止用不稳定比例包装结果。

# J. 推荐论文标题、摘要与完整叙事

## J.1 推荐标题

**PartialGuard: Late-Bound Full-Tile Fixed-Cardinality Coding of Hierarchical MoE Combine Partials**

中文：**PartialGuard：层级 MoE Combine Partial 的晚绑定完整块固定基数编码**

[Inferred] 标题刻意不写receiver-aware、output-aware、first、static-buffer-preserving或end-to-end acceleration，因为这些词要么未证明，要么边界过宽。

## J.2 拟摘要（150–250字）

[Hypothesis] 层级MoE节点内归并后仍须跨节点发送combine partial。PartialGuard在归并产出BF16 partial后、RDMA前融合计算范数；仅对完整8项flush group固定选q个FP8，其余用MXFP4，写入含位图与固定偏移的单frame，短group回退uniform FP8。未见数据、H100软件codec和两节点RDMA依次检验质量非劣、物理字节、codec开销与暴露完成时间，并报告uniform FP8更优边界。

## J.3 完整叙事

### Problem

[Observed] HT MoE combine可在source domain内把多个expert contribution预归并，但跨节点仍以BF16或uniform低精度发送destination-token partial；单纯降bits不保证降低exposed latency。

### Observation

[Observed] surrogate显示post-output signal比routing-only signal更会分配固定数量FP8，但现有owner proxy和seen-data不能验证真实system。  
[Observed] backend source表明real post-reduction partial在RDMA前存在，同时native streaming只给出很短的决策窗口。

### Mechanism

[Hypothesis] 仅在完整8项native flush group内，用reduction-fused partial norm做stable exact top-q；q个FP8、B-q个MXFP4；1–7项group回退uniform FP8。

### Implementation contract

[Hypothesis] 一个连续frame、一个precision mask、两个固定offset homogeneous payload region；无全局排序、无receiver feedback、无跨步cache、无MILP；unsupported/不盈利bucket回退uniform FP8。

### Evaluation

[Hypothesis] 先用untouched real-domain replay杀质量假设，再用单GPU杀codec overhead，随后用两节点operator测actual NIC bytes、first-byte与completion，最后才测TTFT/goodput。每层证据都报告不能支持的claim。

### Limitation

[Inferred] 方法只面向有reduce-before-RDMA的hierarchical HT path；B必须适配backend streaming；fixed quota有质量税；收益上限受uniform FP8、已有overlap和codec开销约束；当前没有任何真实GPU加速证据。
