# 名称

TokenRace-EP（打破 MoE Combine 全有或全无同步屏障的逐 Token 提前释放）

## 1. 背景与问题

本项目此前四条已死路线（CreditReduce、RouteFidelity-EP、WaveCredit、MassCover）全部是"给定固定的 route/expert-output，重新分配精度/统计量/信用/副本"，决策对象都是数据本身，不改变同步结构。TokenRace-EP 主动切换到一个此前完全没被检验过的自由度：**同步粒度**。当前系统（无论是本项目自己的仿真脚本，还是真实 backend）几乎总是把 MoE decode 阶段的 combine 实现/建模为全 batch/全 layer 粒度的同步屏障——下一层计算必须等最慢的 receiver 收完所有专家贡献才能开始。而专家执行时间存在真实的差异（ViBE 实测硬件抖动约 7% variance，RepetitionCurse 报告极端路由不均可致吞吐降至 10%-20%），这些差异如何转化为 combine 同步等待，此前从未被当作研究问题正面检验。

## 2. 核心思想 / 机制主张

- 标准做法：等所有 rank 的所有 token 的所有专家贡献到齐 → 统一释放整个 batch 进入下一层（"全有或全无"屏障）。
- TokenRace-EP：为每个 token 维护一个 completion counter（其 top-k 专家中已到达的数量），一旦某 token 的 counter 达到 k，立即把该 token 标记为 ready，可以先行进入下一层计算（continuous batching 本身就是 per-token 独立的），同 batch 中因专家 straggler 未到齐的 token 继续等待，但不再拖慢已经到齐的 token。
- 因果链：专家执行时间差异/硬件抖动 → 同一 batch 内不同 token 的 top-k 贡献到达时刻不同 → [现状] 全有或全无屏障：全部等最慢者 → [TokenRace] per-token 提前释放：每个 token 的下一层开始时刻=该 token 自己的到达时刻。收益来源 = `E[max(到达时刻)] − E[到达时刻]`，即 straggler 拖慢的"其他健康 token"的等待时间。
- 实现思路：不需要发明新的 collective，continuous batching 框架（vLLM/SGLang）已经按 token/request 维度管理调度状态；NCCL EP 的 LL kernel 本身已是 counter-based signal，只是当前上层调度没有把它接到"是否放行进入下一层"这个决策上。TokenRace-EP 的 ABI 改动是：暴露一个 per-token/per-slot ready bitmap 或 completion counter 给上层调度器。

## 3. 实验如何设计

- **P0（Mac 仿真，真实路由 trace）**：复用 `run_tbt_congestion_bridge.py` 已有的 decode-step 采样管线，对 OLMoE（top-8）与 LLM-jp（top-16）真实 16 层完整路由（非合成数据），给每个 (expert, decode-step) 赋一个执行时间模型（`BASE_LAUNCH_US + PER_TOKEN_US*cnt` + 乘性抖动），对比 `full_barrier`（下一层=max(全 batch 到达时刻)）与 `token_race`（下一层=各 token 自己到达时刻）两种放行策略的 TBT P99/P50/mean。预注册门槛：两个模型、所有 batch size 的 moderate 场景 P99 改善均需 ≥5%。
- **P0-B（top-K 截断消融）**：用真实 gate_weight 排序截断到 K∈{2,4,8,16}，检验"K 越大收益越小"假设，发现干净的单调曲线，解释了 P0 中 LLM-jp（原生 top-16）卡边界的现象。
- **严格性审查**（`TokenRace-EP_严格性审查与后续方向_2026-07-19.md`）：外部调研发现 P0 完全没有建模"重批"（re-batching）开销这一负成本项——真实 GPU kernel launch overhead 量级 5-10us，与 P0 试图节省的量级同阶；且 vLLM/SGLang/TensorRT-LLM 均不支持 layer-wise 异步推进，CUDA Graph 要求固定 batch size，逐 token 提前释放会与之冲突。
- **GPU P0（RTX 5090 微基准）**：实测真实 FFN kernel 时间（发现几乎完全由约 57-58us 固定 launch 开销主导，比 Mac illustrative 常数 6us 高近 10 倍）、真实 index_select 重批开销（约 14.3-14.5us），把两者喂回原始路由仿真重算门槛。
- **GPU P1（补齐两个此前承认没算的开销源）**：CUDA Graph replay vs eager 模式的真实代价差（约 30-44us/层）；更真实的 3/4 组释放粒度开销（47.9-127.2us，随组数近线性增长）。
- **P2（自适应触发）**：用"确定性负载不均衡"这一免费、因果合法的信号，尝试只在预测收益 > 阈值时才触发 token_race，扫描 absolute/percentile 阈值网格。
- **纠正重算**（2026-07-21）：修正会计错误（graph advantage 应记入 barrier 侧而非叠加进 race overhead；重批开销不应无条件对每个 request 收取，只有"提前"的 request 才付）后离线重算。

## 4. 代码怎么组织（scripts/ 下文件角色）

- `run_tokenrace_ep_p0.py`：P0 主驱动，Mac-only 仿真，真实路由 trace 驱动的 per-layer expert finish-time 模型与两种放行策略对比，预注册 5% P99 改善门槛判定。
- `run_tokenrace_ep_topk_sweep.py`：P0-B，复用同一批真实 token 的真实专家偏好排序，截断到 top-K 子集，验证"K 越大收益越小"的因果解释。
- `run_tokenrace_gpu_microbench.py`：GPU P0，RTX 5090 上实测 (A) 真实 FFN kernel wall-clock 时间 vs token 数、(B) index_select 动态重批开销，并用真实常数替换 illustrative 参数重算门槛。
- `run_tokenrace_gpu_p1_overhead.py`：GPU P1，实测 (D) CUDA Graph replay vs eager 差、(E) 更真实的 3/4 组释放开销，再次重算门槛。
- `run_tokenrace_adaptive_p2.py`：P2，用"deterministic load-imbalance"这一零延迟因果信号做逐请求逐层的自适应触发规则，扫描阈值，检验能否只在划算时才付重批开销。
- `analyze_tokenrace_p1_corrected_recompute.py`：离线（无 GPU/无 torch）纠正重算脚本，修正 graph credit 记账位置与重批开销的无条件收取问题，复用已有 GPU P0/P1 的 JSON 常数与真实路由 CSV。

## 5. 演进路径

TokenRace-EP 是本项目第一条从"route/placement 静态重分配"范式主动切换到"执行时间线/同步粒度"因果层的候选，提出时被认为可能是四条已死路线之外的真正未被触碰的空间。P0/P0-B 在 Mac 仿真上拿到跨模型一致、单调、可解释的正效应曲线，是本项目第一个没有被干净判死的候选（`CONDITIONAL / EXPLORATORY_SIGNAL`）。严格性审查指出"重批开销零成本"是最大风险假设后，GPU P0 微基准测出真实开销显著高于仿真假设，判决收缩为 `CONDITIONAL_THIN_MARGIN_K_DEPENDENT`（仅 top-8 级 K 值薄边际存活，top-16 已净负）。GPU P1 补齐 CUDA Graph 代价与更真实释放粒度后，两模型全部 batch size 深度净负收益，判决升级为 `KILLED`。2026-07-21 的纠正重算（修正记账错误）与 P2 自适应触发复查确认：修正会计问题不会复活该方向，自适应触发在有信息量的阈值下也无法恢复跨模型 5% 门槛。

## 6. 判死结论与不要再怎么救

**KILLED（GPU P1 追加验证 + 2026-07-21 纠正重算维持）**。死因是本项目第一次不是"文献碰撞"或"效应量不够"，而是"仿真模型系统性低估了真实硬件的固定开销"：Mac illustrative `BASE_LAUNCH_US=6us` 比真实测得的 ~57us 低近 10 倍；P0 最乐观的重批开销估计 26.6us 比真实测得的 2 组开销（47.9us）还低近一半，4 组真实开销（87.4-87.65us）是 P0 估计的 3 倍多。任一被 P0 忽略的真实开销源（CUDA Graph 代价或更真实的多组释放粒度）单独代入，都足以让两模型全部 batch size 变成深度净负收益（-30%~-62%）。2026-07-21 纠正会计错误后重算，没有任何纠正场景能让 P99 改善跨模型全部 batch size 通过 5% 门；P2 自适应触发扫描显示，能救它的信号（确定性负载不均衡）恰恰对真正造成收益的不可预测噪声/straggler 事件毫无预测力。**不要再调阈值网格，也不要指望修复会计问题能救回来**——死因是真实固定开销相对负载差过大，这是硬件层面的结构性问题，不是参数或统计口径问题。
