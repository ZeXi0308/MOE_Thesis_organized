# 名称

Popularity-Balanced Expert Placement（基于专家流行度均值均衡的通信感知放置）

## 1. 背景与问题

在此之前的全部 Receiver-aware 通信线实验（v1、v2 systematic、v3 adaptive、direct-benefit controller）中，专家 placement 始终被当作固定输入——`contiguous`（`expert_id // ep_size`）或 `round_robin`（`expert_id % ep_size`），两者都完全不看任何真实数据，只在给定这个固定 placement 的前提下优化"在线精度降级决策"。但 receiver 侧拥塞有一个更经典、更结构性的成因：如果"热"专家（真实调用频率高的专家）恰好因为数据无关的 placement 规则聚集在同一物理节点上，该节点的出口就会成为瓶颈，无论运行时控制器多聪明都无法绕开——这正是一个经典的多路数字分区/负载均衡装箱问题，可以用 LPT（Longest-Processing-Time-first）贪心按真实专家调用频率做流行度均衡放置来缓解。这条候选试图检验：这个此前从未被触碰过的"放置"杠杆，能否比在线控制杠杆更直接地缓解瞬时/尾部拥塞。

## 2. 核心思想 / 机制主张

- 用真实路由 trace 里每个专家的选中频率作为 LPT 贪心装箱的物品权重（按权重降序排列，每次把下一个专家放进当前负载最轻的 bin/节点），产出一个数据驱动的流行度均衡 placement，与两个数据无关的静态基线（`contiguous`、`round_robin`）比较。
- 复用 `run_receiver_aware_v2_systematic.py` 已经验证过的场景构造与瓶颈指标（`build_scenario`/`fp8_total`：每个全局时间步取跨 rank 的 max（瞬时瓶颈/尾部驱动）流量代理，转换为微秒），保证结果与该系统化重跑的已有数字直接可比，不引入新的评测口径。
- 核心区分：**均值负载均衡（mean-balancing）** 与 **尾部/瞬时突发均衡（tail-balancing）** 是排队论里两个不同的目标。第一版验证的 `fp8_total` 是整个场景内逐步瓶颈值的**总和（sum）**，容易被瞬时并发噪声主导；而系统真正关心 P99 TPOT 的是逐步瓶颈值的**分布尾部（P95/P99）**，二者不等价——一个只削平中位数步骤但不动最差步骤的 placement 毫无价值；一个能削平尾部但不改变总和（因为大多数步骤本来就便宜）的 placement 才是真正有价值的，且这种价值在原始 `fp8_total`（求和）指标下完全不可见。

## 3. 实验如何设计

- **零新 GPU 时间**：两个实验都是对已收集的真实路由 CSV（`outputs/receiver_aware_v2/olmoe_routes.csv`/`llmjp_routes.csv`，与当时 direct-benefit-controller 实验共用同一批数据）的纯 pandas/numpy 离线分析，`build_scenario`/`placement_map` 等核心函数直接照抄自 `run_receiver_aware_v2_systematic.py`（不重新实现），确保结果与该脚本已报告的全部数字直接可比。
- **第一版（均值/求和指标）**：假设 H：真实专家 popularity（真实 per-token top-k 选中频率）足够倾斜、且与 `expert_id` 足够不相关，使得数据驱动的流行度均衡 placement 相对两个数据无关基线中最好的一个，能降低全 FP8 baseline 的瓶颈字节-时间总和（`fp8_total`）。预冻结的 GO 判据：对给定 (model, origin_mode) cell，≥20 个 held-out 场景种子上，`(best_existing_baseline_fp8_total − popularity_balanced_fp8_total)` 的 scenario-level paired bootstrap 95% CI 严格 >0，且平均降幅超过 10%。
- **第二版（尾部指标重审）**：复用完全相同的路由 CSV 与场景构造，把目标指标从"整场景瓶颈值求和"换成"逐步瓶颈值的分布尾部（P95/P99）"，这是根据第一版报告自己指出的根因（"求和容易被瞬时并发噪声主导"）而做的预先指定（非事后调参）的正确后续检验。冻结的 GO 判据：对给定 (model, origin_mode) cell，`(best_existing_baseline_P95_step_us − popularity_balanced_P95_step_us)` 的 scenario-level paired bootstrap 95% CI 严格 >0，且平均 P95 降幅超过 10%；同时报告 P99 和 max-step 作为次要诊断（不参与 GO 判定，避免多重比较下的挑选）。
- 若尾部指标依然无效，这将把原始发现从"求和这个目标指标选错了"升级为"底层假设（并发驱动的瞬时瓶颈支配任何逐步统计量，不只是求和）本身正确"，使原始 NO-GO 更难被归因为指标选择的假象——这正是这个后续检验被设计用来揭示的。

## 4. 代码怎么组织（scripts/ 下文件角色）

- `analyze_expert_placement_optimization.py`：第一版驱动，实现真实专家选中频率驱动的 LPT 贪心均衡 placement，与 `contiguous`/`round_robin` 两个数据无关基线在 `fp8_total`（瓶颈字节-时间总和）指标上做 held-out 场景的 paired bootstrap 比较，冻结 GO/NO-GO 判据（≥10% 降幅且 95% CI 严格 >0）。
- `analyze_expert_placement_tail_metric_reaudit.py`：第二版驱动，零新 GPU 时间地复用同一批真实路由 CSV 和场景构造，把目标指标从"求和"换成"逐步瓶颈值的分布尾部（P95/P99）"，用相同的冻结纪律（预先指定判据、不事后调参）重新检验放置杠杆是否对系统真正关心的尾部延迟有效。

## 5. 演进路径

这条候选是 Receiver-aware 通信线的一次范式转换尝试：从"给定固定 placement，优化在线控制"转向"放置本身是否是被忽视的结构性杠杆"。第一版用总量指标（`fp8_total`）检验后判定 NO-GO，且该报告自己在根因分析中已经明确指出"这次评测复用的 `fp8_total` 指标在每个全局时间步取的是跨 rank 的 max（瓶颈/尾部驱动），不是跨 rank 的总和或均值……平均负载均衡和尾部/瞬时突发均衡是排队论里两个不同的目标"。第二版据此设计了预先指定（非事后 p-hacking）的尾部重审检验，用完全相同的数据和场景构造，只换目标指标为 P95/P99。

## 6. 判死结论与不要再怎么救

**NO-GO**。偏斜确实存在（真实专家调用频率确实不均衡），但均衡"均值负载"不等于均衡"瞬时/尾部突发负载"——系统的真实瓶颈是**瞬时 max**（某个时间步跨 rank 的最大流量），而不是整个场景的负载总和或均值。第一版在总量指标下已判 NO-GO；第二版换成系统真正关心的尾部指标（P95/P99）后仍未能证明数据驱动的流行度均衡 placement 能带来 ≥10% 且统计显著的改善——这确认了原始 NO-GO 不是"指标选错了"这个可挽救的方法论问题，而是"并发驱动的瞬时瓶颈支配任何逐步统计量"这个更根本的结构性事实：即使找到一个更懂真实数据的 placement，只要瓶颈由瞬时并发噪声决定而不是由哪个专家在哪个节点决定，单纯调整专家的物理分布就无法系统性地压低尾部延迟。**不要再尝试更复杂的均衡算法（如更精细的多目标装箱、动态重平衡）去挽救这条线**——问题不在于 LPT 贪心不够聪明，而在于"放置类"杠杆本身作用在错误的变量（长期平均分布）上，而真正的瓶颈由另一个变量（瞬时并发噪声）决定，这是不同维度的问题，静态放置无法触及。
