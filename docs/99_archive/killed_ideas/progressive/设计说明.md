# 名称

Progressive Residual Transport（渐进式 base+residual EP 通信）

## 1. 背景与问题

在低比特 EP 通信场景中，一个直觉上有吸引力的想法是：先传一个便宜的低比特 base 表示，再按需（比如 gate 权重较高、更关键的 pair）补传一个 residual 来提升精度，这样理论上比"直接对不同 pair 混合使用两种固定精度"（direct mixed）更节省字节，因为大多数 pair 只需要 base 精度就够了。这是 Receiver-aware 通信线的一个子方向：receiver credit + progressive transport，试图用渐进式传输替代粗粒度的混合精度分配。

## 2. 核心思想 / 机制主张

- 表示方式：所有 routed pair 先发送一条 INT4/MXFP4 base 向量；gate 较高的 50% pair 再补发一条同格式的 residual 向量，接收端做 base+residual 的组合重建。等 wire（即总字节数固定）对照是 `direct_equal_wire`：部分 pair 直接发送 FP8，其余发送一条 INT4/MXFP4，低比特比例按 scale metadata 精确匹配 progressive 的总 wire bytes。
- 待检验的两个独立假设：① 表示质量假设——在相同 wire bytes 下，progressive（base+residual）表示能否比 direct mixed 更准确地重建原始信号；② 系统必要条件假设——即使表示质量打平或更差，真实 codec（pack/unpack）的额外依赖和 kernel launch 开销是否能在合理链路速率下 break-even。
- 备选（selector 上界）：用发送端输出量化误差（sender-output-aware quantization-error，qerr/reserr）作为"该不该升级到 residual"的昂贵上界 selector，检验失败是否仅来自选择器太弱，而非表示方式本身的问题。

## 3. 实验如何设计

- **表示质量 gate**：在 OLMoE-1B-7B（E64K8）和 LLM-jp（E32K16）上，用 WikiText-103 train 新文档（各 24 篇、128 token/篇），比较 `progressive_50`（50% refinement，平均 6 bits/element）与 `direct_equal_wire`（wire bytes 精确匹配）在 INT4 和 MXFP4 两种低比特格式下的 mean token KL，document paired bootstrap 给 95% CI。同时用 `qerr/reserr` 昂贵上界 selector 重跑一遍，排除"失败只是因为 gate selector 太弱"这个解释。
- **Codec gate**：用真实 Triton kernel 实现 symmetric INT8/INT4 pack/unpack、INT4 base pack/unpack、residual pack 与接收端 in-place add，扫描 hidden size（512/2048）、routed vectors/tile（32/128/512）、50% refinement，测量真实 pack+unpack 延迟，结合 100/200/400/800 Gbps 理论 wire time 和 pinned H2D 实测延迟，计算 break-even link rate（progressive 比 uniform INT8 快所需的最低链路速率）。实验刻意排除 selection compaction、RDMA descriptor 和 credit feedback 开销，因而是对 progressive 有利的乐观下界。

## 4. 代码怎么组织（scripts/ 下文件角色）

- `run_receiver_progressive_quality_gate.py`：表示质量 gate，实现 progressive（base+50%残差）与 direct_equal_wire 两种表示在精确匹配 wire bytes 下的端到端 KL 对比，支持部署可行的 gate-weight selector 与 sender-output-aware quantization-error 上界 selector 两种选择方式，document paired bootstrap。
- `run_receiver_codec_break_even_gpu.py`：Codec gate，用真实 Triton kernel 实现打包/解包与接收端加法，测量 sender pack、receiver unpack/add、pinned host-to-GPU 传输延迟，在多个理论链路速率下计算 progressive 相对 uniform INT8 的 break-even link rate。

## 5. 演进路径

该方向源于 Receiver-aware 通信线在 2026-07-20 的第三轮 GPU 有效性验证——在投入多节点 RDMA 原型前，先验证 progressive transport 的表示质量和单卡 codec 必要条件。两个独立的必要条件检验（表示质量、codec break-even）都在这一轮被同时证伪，因此没有进入更贵的多节点系统原型阶段。项目随后把 Receiver-aware 通信线的保留方向收缩为"receiver credit + topology-domain price + homogeneous one-shot codec lane"——即在整条 peer/lane 上一次性选择 FP8 或低比特格式，不再在小 tile 内逐 vector 混合两种 codec，也不再先发 base 再发 residual。

## 6. 判死结论与不要再怎么救

**NO-GO**，且是两个相互独立的失败叠加：① **表示质量劣势**：在相同 metadata-aware wire bytes 下，progressive representation 在两个模型上都没有优于 direct FP8/4-bit 混合，多数配置显著更差——OLMoE INT4 上 progressive KL 是 direct 的约 3.53 倍（0.076739 vs 0.021753，95% CI [-0.060798,-0.049753]，progressive 更优概率为 0）；LLM-jp INT4/MXFP4 同样方向一致地更差；即使用昂贵的 output-aware selector 上界也没有挽救（residual upper bound 比 direct upper bound 多 0.008-0.005 KL，CI 严格小于 0），说明失败不能归因于 gate selector 太弱，而是 base+residual 这种"渐进式细化"表示方式本身在等 wire 下就不如直接混合精度。② **Codec 不划算**：真实 Triton codec 显示 progressive 比统一 INT8 codec 多约 35-37us pack+unpack 开销（第二次量化、依赖 base 的 residual kernel、接收端 add 三者叠加），使 break-even 链路速率被压到约 0.9-59.2 Gbps 区间，而现代 100-800 Gbps EP 网络远高于这个区间，即使质量打平也回不了本。**不要再加渐进式细化变体，也不要试图靠更聪明的 selector 挽救**——两个独立失败原因中的任一个已经足够判死，保留的方向应改为"整条 lane 一次性选择精度格式"（homogeneous one-shot codec lane），这已不是 progressive 本身的救法，而是完全不同的设计。
