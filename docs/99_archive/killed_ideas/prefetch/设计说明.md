# 名称

Expert Prefetch / Routing-Predictability-Driven Speculative Decoding（路由跨层可预测性驱动的专家预取/投机解码）

## 1. 背景与问题

2026-07-20 的调研报告识别出"利用 MoE 路由的跨层可预测性设计专家预取/投机解码 draft 机制"是少数同时满足"文献确认空白"和"现有资源可零成本验证"的方向：既有工作（MoESD、SP-MoE）把投机解码用到了 MoE 上，但没有利用跨层路由结构来设计 draft/预取信号本身。核心问题：给定当前层 token 的路由结果（top-1 专家），能否比"下一层专家的全局频率"这个零信号 baseline 更准确地预测该 token 在下一层（甚至未来若干层）的路由选择？如果能，这个信号能否转化为真实系统收益（HBM 专家预取或投机解码 draft）？

## 2. 核心思想 / 机制主张

- 离线统计信号：学习一个 `P(expert_{L+1} | 当前层 top-1 专家)` 的转移表（`top1_transition`），在 sealed test split 上与"下一层全局频率 baseline"（`freq_baseline`，零信号地板）对比。
- 系统机制：GPU 常驻专家 LRU 缓存（容量 C 个/层），当层 L 计算进行时，用 calibration 学到的转移表异步预取层 L+1 的候选专家权重（真实 `cudaMemcpyAsync`，在 side CUDA stream 上与 L 的真实计算 overlap），对比纯需求驱动的 reactive LRU（无 lookahead）。
- 关键前提：预测目标（下一层路由选择）本身是确定性的、由模型权重决定，不是随机噪声，因此信号有效性不依赖"猜中随机事件"这种不可能的任务——这是它与 TokenRace-EP 自适应触发（预测对象是不可预测噪声）的本质区别。

## 3. 实验如何设计

- **P0（门槛检验）**：在 calibration split 学习转移表，sealed test split 评估准确率，与 `freq_baseline`、`topk_transition`（用完整 top-k 集合做状态，验证是否过拟合稀疏状态空间）、`neighbor_same_layer`（同层相邻 token 局部可预测性）对比。预注册门槛：改善幅度 ≥5pp 且 95% bootstrap CI 不含 0 且 Holm 校正后 p<0.05，与 CreditReduce/RouteFidelity/MassCover 使用完全一致的门槛标准。
- **P0-B（lookahead 衰减曲线）**：把预测距离从 1 层扩展到 2/3/4/6/8 层，检验信号能维持多远，判断是否有足够提前量支撑真实预取调度。
- **P0-C（预取预算命中率曲线）**：把"预测单一专家"换成"预取器只能预取 N 个候选专家（N 远小于专家总数），真实下一层专家是否落在候选集里"，与同预算的频率 baseline 对比命中率。
- **系统原型 v1**：真实 GPU（RTX 5090）实现 reactive vs predictive LRU 缓存，用真实测量的 H2D 带宽和 MoE 层真实 compute 时间。
- **系统原型 v2（fused）**：把逐专家 Python 循环 compute 代理（O(64) kernel launch/层）替换为融合 `torch.bmm` 代理（O(3) kernel launch/层），检验更真实的 kernel 实现对端到端收益的影响方向。
- **GPU 有效性审计**（决定性阶段）：修复此前审计发现的两个关键错误：① cache key 从只用 `expert_id` 改为 `(layer_id, expert_id)`（原实现把不同层同号专家错误当成同一缓存对象，产生不存在的跨层 cache hit）；② 同时评估 top-1 和真实完整 top-k 的工作集大小（原实现只测了 top-1，但真实 combine 需要完整 top-k）；③ 加入 reactive LRU、静态频率 pinning、频率预取、随机、one-layer oracle 作对照；④ 用 GPU 实测 sparse padded batched compute 代理测 safe overlap budget（允许为 0，不强制至少预取一个）。

## 4. 代码怎么组织（scripts/ 下文件角色）

- `run_routing_predictability_p0.py`：P0 门槛检验，`top1_transition`/`topk_transition`/`neighbor_same_layer` 三类 predictor vs `freq_baseline`，calibration/test 严格分离，paired bootstrap + Holm 校正。
- `run_routing_predictability_p0b_lookahead.py`：P0-B lookahead 衰减曲线，训练 k∈{1,2,3,4}（结论文档中扩展到 8）的转移表并评估衰减速度。
- `run_routing_predictability_p0c_prefetch_budget.py`：P0-C 预取预算命中率曲线，把单一预测问题转化为"N 个候选专家覆盖真实下一层专家"的系统相关问题。
- `run_expert_prefetch_system_prototype.py`：系统原型 v1，真实 GPU LRU 缓存 + 异步预取（真实 `cudaMemcpyAsync`）+ reactive/predictive 对比，逐专家 Python 循环 compute 代理。
- `run_expert_prefetch_system_prototype_v2_fused.py`：系统原型 v2，把 compute 代理替换为融合 `torch.bmm`（更接近生产级 grouped-GEMM kernel），隔离出"更真实 kernel 实现"对端到端收益的影响。
- `run_expert_prefetch_gpu_validity_audit.py`：决定性的 GPU 有效性审计脚本，修复 cache key bug、补齐 full top-k 工作集评估、加入多个强对照策略、用 GPU 实测的 sparse padded compute 代理算 safe overlap budget。

## 5. 演进路径

P0/P0-B/P0-C 三个离线统计实验全部以显著优势通过预注册门槛（改善幅度 13-35 个百分点，比本项目此前所有路线的 5%-10% 效应量天花板高出一个数量级），是本项目第一次在如此严格的门槛检验下产出如此大幅度、跨模型一致、机制可解释的正结果，被判定为 `PROMISING_STRONG_SIGNAL`，进入系统机制设计与 GPU 真实验证阶段。系统原型 v1 用真实硬件常数测出正的换页延迟节省（13-16%）但端到端节省仅 2-3%（受限于逐专家 Python 循环 compute 代理开销过大）；v2 换成融合 compute 代理后，如果不同时调整预取预算，固定预算会让端到端收益反转为负，收紧预算后重新转正——这是本项目"仿真开销被高估、纠正后原本安全的固定预算反而过度激进"的一个反向案例。真正的转折点出现在 2026-07-20 的 GPU 有效性审计：cache key bug 修复后此前的正收益被推翻；补齐真实完整 top-k 工作集后发现系统性饱和问题。

## 6. 判死结论与不要再怎么救

**系统 NO-GO（独立论文层面）；离线信号存在这一结论保留**。P0/P0-B/P0-C 的离线统计结论不受影响：`top1_transition` 比 `freq_baseline` 领先 13-35 个百分点，lookahead 8 层仍有效，信号本身是真实、强、可解释的。但系统实现层面被两个决定性问题推翻：① **工作集饱和**——用正确 `(layer, expert)` cache key 与真实完整 top-k 后，OLMoE full-top-8 覆盖 77.9% 专家池，LLM-jp full-top-16 在 91.2% 的 layer-batch 上需要全部专家；一旦几乎所有专家都要用，"预测该预取谁"这个问题本身就失去意义，transition/frequency/random/oracle 的 prefetch precision 全部趋近 100%，复杂 predictor 没有实际选择空间。② **正确 cache key 下 safe-budget oracle 上限接近 0**——OLMoE safe budget=1 时 transition 比 reactive LRU 更差（-0.24%~-0.49%），理论 oracle 上限仅 +0.256%；LLM-jp 不存在满足"并发时间不超过 compute 5%"的安全预取预算（safe budget=0）。③ 相比简单 frequency baseline 的增量不足 0.1 个百分点。④ Prior art（ExFlow/ProMoE/HOBBIT/Fate/LayerScope/PROBE/ST-MoE 等 2024-2026 工作）已从预测器、缓存策略、deadline-aware 调度多个角度覆盖同一机制空间。**不要在同一 batch 设定下继续堆更聪明的 predictor**——死因不是路由信号不存在，而是系统模拟本身有身份识别 bug、predictor 相对简单 baseline 的增量几乎为零、且真实 serving batch 下工作集饱和使"预测该预取谁"这个问题失去意义。可保留的新问题是：当 full top-k 使工作集饱和时，是否应完全放弃 prediction，改为 deterministic load pipeline、expert block splitting、降低 top-k 或 GPU-side replication——但这已是另一个问题，不是当前 transition-table 预取论文。
