# 名称

MassCover-EP（贡献风险感知的跨故障域专家副本放置）

## 1. 背景与问题

在 EP 部署中，若某个故障域（如一个节点/机架）整体不可用，该域内的专家就会全部丢失，导致 combine 输出丢失部分本应贡献的 gate mass（"missing mass"）。一个直觉合理的缓解方式是：用有限的 shadow（备份）预算，把一部分专家在正常路径上"闲置"的副本预先放到别的故障域，从而在故障发生时能部分恢复缺失的贡献。MassCover-EP 试图用 gate/contribution 或 CVaR（Conditional Value at Risk，尾部风险度量）证据来决定"哪些专家的副本最值得放在哪里"，从而在固定的 shadow HBM 预算下，压低故障发生时质量爆炸的尾部风险（用 missing mass 的 CVaR95/P99 衡量），比简单的静态基线（按流行度/gate mass 放置副本）做得更好。

## 2. 核心思想 / 机制主张

- 用 `gate_weight / sum(top-k gate_weight)`（在线可观测的贡献代理）近似真实的专家贡献，并用一个独立的小型 intervention artifact 单独审计这个代理与真实贡献之间的相关性（Spearman），确保代理本身可信。
- 在固定的 shadow HBM 预算（如 10% 的 layer-expert 副本）下，用 calibration-only 的 CVaR-greedy 算法选择哪些专家副本应该跨故障域放置，目标是最小化 historical test 上的 missing-mass CVaR95（故障时质量爆炸半径的尾部风险）。
- 对比对象：frequency（按调用频率放副本）、gate-mass（按 gate 权重质量放副本）、random（随机放）三个静态基线，以及 `oracle_cvar`（事后已知测试结果的最优解，仅作上限参考，不可部署）。
- 检验门槛：相对最强静态基线（`gate_mass`）的 CVaR 改善是否 ≥10%，同时 gate 代理对真实贡献的 pair-level Spearman 相关性在两模型均不低于 0.50（确保代理本身可靠，不是拿一个失真的信号在做优化）。

## 3. 实验如何设计

- 这是一个 **route-level historical retrospective screen**，不是新的 sealed confirmatory experiment：`C1`、gate share 和 missing-mass 都是逻辑/语义代理，没有测真实 wire、恢复时延、TTFT、TPOT 或 P99；shadow expert 在正常路径上假定 inactive，这里只计专家副本数量，不计真实 HBM、加载和路由表更新成本；`oracle_cvar` 只表示理论上限，不能部署。
- **Gate → contribution proxy 审计**：在两个模型（`olmoe_e64k8`：131,072 pairs、8 requests；`llmjp_e32k16`：262,144 pairs、8 requests）上分别计算 gate 代理与真实 contribution 的 pair-level 和 layer-expert mass Spearman 相关性。
- **正常通信与故障风险的 placement tradeoff**：在四个冻结的 primary placement（`calibration_coactivation_balanced`、`calibration_frequency_lpt`、`contiguous`、`round_robin`）上，分别测量无 shadow 时的 C1 cross-domain fraction、mean missing mass、CVaR95、P99。
- **10% shadow 预算生死比较**：在同样四个 placement 上，对比 MassCover（`cvar_greedy`）与三个静态基线（frequency、gate-mass、random）在相同 10% shadow HBM 预算下的 historical-test CVaR95，取相对最强基线的改善幅度作为门槛判据。
- 预注册要求：CVaR-greedy 必须在每个模型至少 75% 的冻结 primary placements 上，相对三个基线中最佳者再降低至少 10% 的 CVaR95；且 gate 代理的 pair-level Spearman 相关性两模型均需 ≥0.50。

## 4. 代码怎么组织（scripts/ 下文件角色）

- `run_masscover_ep_p0.py`：历史 P0 唯一驱动脚本，实现整套流程——gate 代理构造与审计（Spearman 相关性）、四个 primary placement 上的正常通信/故障风险 tradeoff、10% shadow 预算下 `cvar_greedy` 与三个静态基线以及 `oracle_cvar` 的生死比较，输出 `risk_results.csv`、`placement_tradeoff.csv`、`proxy_fidelity.csv`、`verdict.json`、`manifest.json` 等全部 artifact，并给出机器自动判决。
- `test_masscover_ep_p0.py`：对上述驱动脚本核心逻辑（贡献代理计算、CVaR 估计、placement 构造等）的单元测试。

## 5. 演进路径

MassCover-EP 是本项目 route-level 静态重分配范式（给定固定的 route/expert-output 之后重新分配精度/统计量/信用/副本）中的第四条独立机制。P0 一次性同时检验了"代理是否可信"（proxy gate）和"算法是否有效"（route-risk gate）两层问题：proxy gate 顺利通过（两模型 pair-level Spearman 均 >0.50），说明用在线可观测的 gate 代理近似真实贡献是合理的；但 route-risk gate 在两个模型、四个 placement 组成的全部 8 个 cell 上全部失败。2026-07-20 的 knob 复查进一步检验了"是否只是算法不够聪明"这个假设：`cvar_greedy` 相对 `oracle_cvar`（事后最优解上限）的差距仅 0.02%-0.7%，几乎已经是完美算法；而 `oracle_cvar` 相对 `gate_mass` 简单基线的天花板本身只有 2.1%-7.1%，把 shadow 预算从 2% 提到 10% 也没有明显抬升——这确认了问题不是算法能力不够，而是 `gate_mass` 这类简单静态信号已经把可挖掘空间吃掉了大半，是本项目"元模式六"（简单静态信号普遍已逼近 oracle 上限）的第二次独立复现。

## 6. 判死结论与不要再怎么救

**KILLED / 无 knob 空间（`KILL_OR_REFORMULATE_MASSCOVER`）**。Proxy gate 通过（PASS），但 route-risk gate 在两个模型、四个 primary placement 的全部 8 个 cell 上全部 `FAIL`：MassCover 相对最强静态基线 `gate_mass` 的 CVaR95 改善幅度仅约 4.7%-6.6%（LLM-jp 四个 placement 分别为 6.2%/6.5%/5.4%/5.7%；OLMoE 四个 placement 分别为 6.0%/5.1%/4.7%/6.6%），全部低于 10% 门槛。2026-07-20 的 knob 复查进一步排除了"算法不够聪明"这个救命稻草：`cvar_greedy` 已经逼近 `oracle_cvar` 上限（差距仅 0.02%-0.7%），而 `oracle_cvar` 自己相对 `gate_mass` 的天花板只有 2.1%-7.1%，扩大预算（2%→10%）也没有明显抬升这个天花板。**不要再尝试更复杂的 CVaR 算法或混合策略去挽回效应量**——这不是算法能力问题，静态 `gate_mass` 副本策略本身就已经把大部分风险吃掉了，复杂算法的边际空间根本不够跨过论文级别的显著性门槛。即便本 P0 通过，下一步原本也仍需要直接 mask 整个失败域的专家输出，在相同 shadow HBM 预算下比较各策略与 test oracle 的 KL/PPL/任务质量，随后才轮到 2-4 GPU 的 failure detection、mutable routing 和恢复时延验证——但由于 route-risk gate 已经失败，这些更贵的后续步骤都不再需要投入。
