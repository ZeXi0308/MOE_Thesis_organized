# Idea A 后续验证记录（2026-07-11）

## 结论先行

这轮验证支持继续做，但改变了“创新点应该落在哪里”的判断：

1. **tail 比 head 安全已经较稳**：同为 62.5% 理论 payload saving，head4 INT4 的 mean per-token KL 是 fixed rank-tail4 的约 9.24 倍。
2. **固定 rank 不是当前最佳质量 selector**：gate threshold 和 cumulative tail-mass 在相近或更高 saving 下，KL 分别比 fixed rank-tail 低约 39.4% 和 29.7%。
3. **rank 的剩余价值必须由系统实现证明**：只有定长 two-lane layout 的真实开销优势能补偿质量差距，rank 才适合作为论文主方法。
4. **多 MoE 拥塞产生了一个值得验证的新扩展**：在质量安全集合内优先压缩跨节点关键 flow，解析回放中可用更少的全局 INT4 预算达到与全部 tail INT4 相同的 bottleneck-byte proxy。
5. **仍没有端到端加速证据**：所有 saving 均为 fake-quant payload 或 bandwidth-only trace proxy，不是 GPU collective、TPOT 或 P99 实测。

## 1. Held-Out 信号对比

### 1.1 设置

- model：`allenai/OLMoE-1B-7B-0924`，16 layers，top-8；
- dataset：WikiText-2 validation；
- calibration：offset 0，16 条文本；
- test：offset 128，32 条文本，与 calibration 文本无重叠；
- max sequence length：128；
- test next-token positions：1,925；
- 质量指标：有效 token 上的 per-token KL；累计 token NLL 后统一计算 corpus PPL；
- uncertainty：1,000 次 sample-level bootstrap；
- 量化：Mac fake quant；不包含真实 pack、scale metadata 或通信 kernel。

校准结果：

- target INT4 pair fraction：0.5；
- gate threshold：0.045898；
- calibration gate-threshold INT4 fraction：0.50245；
- cumulative tail-mass budget：0.159424；
- calibration tail-mass INT4 fraction：0.50008。

### 1.2 结果

| strategy | theoretical payload saving vs BF16 | corpus PPL | PPL delta vs full | mean per-token KL | KL 95% CI |
|---|---:|---:|---:|---:|---:|
| full | 0.00% | 18.7915 | 0.0000 | 0.00000 | [0, 0] |
| uniform FP8 | 50.00% | 18.7832 | -0.0083 | 0.00472 | [0.00377, 0.00589] |
| fixed rank-tail4 INT4 | 62.50% | 19.2381 | +0.4466 | 0.03032 | [0.02583, 0.03616] |
| gate threshold INT4 | 63.13% | 18.9738 | +0.1823 | 0.01836 | [0.01566, 0.02211] |
| cumulative tail-mass INT4 | 62.74% | 18.9142 | +0.1227 | 0.02130 | [0.01903, 0.02421] |
| contribution-tail oracle | 62.50% | 18.9473 | +0.1558 | 0.01813 | [0.01649, 0.02007] |
| head4 INT4 control | 62.50% | 24.6168 | +5.8253 | 0.28016 | [0.24957, 0.32610] |

### 1.3 解读

- fixed rank-tail 的 KL CI 与 head-control 完全分离，支持 rank-dependent sensitivity；
- gate threshold、tail-mass 的 KL CI 均低于 fixed rank-tail，说明它们的优势不是单个样本造成的表面均值波动；
- gate threshold 的 test payload saving 为 63.13%，意味着固定 calibration threshold 在 test 上选择 INT4 的比例略高于目标 50%，但仍同时取得更低 KL；
- contribution oracle 依赖 expert output norm，只能作为质量上界；gate threshold 已非常接近该上界；
- 各近似策略的 PPL CI 大量重叠，不应宣称小幅 PPL 下降代表模型变好；当前更可靠的是 KL 排序与 head-control 的大效应。

直接决策：同时实现 R-layout 与 G-layout microbenchmark。R-layout 是固定 rank 两条 lane；G-layout 是 gate/tail-mass 动态 mask。比较必须包含 mask/prefix-sum、metadata、variable-size collective、pack/unpack 和 reduction，而不只比较 payload。

## 2. 多 MoE/多请求 EP 拥塞回放

### 2.1 语义和设置

本轮不再使用 expert-id group 充当 receiver。combine 流定义为：

```text
sender   = expert_owner_rank
receiver = token_origin_rank
```

- route：来自上述 OLMoE held-out selected-expert trace；
- expert placement：64 experts contiguous 映射到 EP=8 ranks；
- topology：2 nodes × 4 GPUs；跨节点名义带宽 200 Gbps；
- layers：16 个真实 route layers；
- concurrency：1、2、4、8、16 requests/replicas；
- origin：balanced 与 50% requests 聚集到 rank 0 的 hotspot；
- metric：逐层 max sender/receiver remote bytes 的和，再除以名义带宽；
- selective budget：只对已属于 fixed safe-tail 的 pair 使用 50% INT4 预算。

### 2.2 16 并发结果

| origin | policy | total payload saving vs BF16 | remote-wire saving vs BF16 | bottleneck proxy saving vs uniform FP8 |
|---|---|---:|---:|---:|
| balanced | all rank-tail INT4 | 62.50% | 62.44% | 23.02% |
| balanced | random half-tail budget | 56.25% | 56.20% | 11.66% |
| balanced | profile critical-port half-tail | 56.25% | 62.30% | 23.02% |
| balanced | scheduler receiver half-tail | 56.25% | 62.30% | 22.90% |
| balanced | greedy critical-port half-tail | 56.25% | 62.30% | 23.02% |
| hotspot | all rank-tail INT4 | 62.50% | 62.48% | 24.20% |
| hotspot | random half-tail budget | 56.25% | 56.23% | 11.99% |
| hotspot | profile/scheduler/greedy half-tail | 56.25% | 62.21% | 24.20% |

### 2.3 可优化 idea

候选方法可写成两个相互正交的约束：

```text
quality-safe selector: rank / gate / cumulative tail mass
              ∩
system-critical selector: remote flow / hot sender / hot receiver
              ↓
bounded INT4 budget
```

建议优先级：

1. **先做 selector kernel 对决**：fixed-rank two-lane vs gate/tail-mass dynamic layout；
2. **再做 coarse topology-aware 模板**：离线生成少量 `(layer, topology class, concurrency class)` 模板，避免在线逐 pair greedy；
3. **加入 drift-safe fallback**：当实际 sender/receiver distribution 偏离 profile 时回退到保守 uniform FP8 或 fixed tail count；
4. **优化目标用双侧 critical port**：不要只优化 receiver，collective completion 也可能受 sender egress 限制；
5. **预算约束必须来自端到端质量**：不能恢复旧 additive-KL MILP；只在少量冻结策略上做端到端复测。

### 2.4 不能越过的边界

当前模拟没有：

- NCCL/DeepEP collective schedule；
- queueing、head-of-line blocking 和真实 request arrival；
- quant/pack、metadata、padding、alignment、unpack/dequant；
- compute/communication overlap；
- NVLink/IB contention 与有效带宽变化；
- 真实 token-level sequence-parallel ownership；
- GPU operator、TPOT、TBT 或 P99 实测。

所以它只能证明“critical-flow budgeting 值得做真实实验”，不能证明已有加速。

## 3. 下一轮最小实验

1. 在至少一个更大 MoE、三个 workload 域上复测 gate vs rank，冻结 calibration 后只跑一次 test；
2. 生成逐 flow `Traffic[layer, sender, receiver, rank, bytes]` 文件，并用真实 serving arrival trace 驱动 replay；
3. 在 8×A100/H100 上先完成 uniform FP8 combine，再实现 R-layout 与 G-layout microbenchmark；
4. 对 critical-flow 扩展只实现离线模板，不先做在线 greedy；
5. 只有 mixed operator 相对 uniform FP8 稳定快约 10%～15%，才进入 serving integration；只有 TPOT 约 +3% 或 P99 约 +5%，才写端到端加速 claim。
