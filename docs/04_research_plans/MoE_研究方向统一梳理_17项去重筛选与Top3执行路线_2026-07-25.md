## 0. 统一结论

### 0.1 最终组合

严格合并后，**没有任何方向达到 A. 立即验证**。当前组合为：

| 角色 | 统一编号 | 方向 | 结论 | 当前只允许做什么 |
|---|---:|---|---|---|
| 首选主线 | U01 | RankLane-Combine | **B. 先做 Profiling** | 5090 必要条件 + 8 卡 combine 删除式 Oracle；不先改完整 serving backend |
| 次选备线 | U03 | ResumeSet | **C. 有条件保留** | pause-specific expert cold-start Oracle；不先写联合 cache manager |
| 高风险旁线 | U02 | RouteCloak | **B. 先做 Profiling** | 只验证低权限真实 observer 与攻击优势；不先写防御 runtime |
| 公共测量工具 | U04 | ScaleBridge / ScaleTail | **D. 子机制** | 统一 trace、Amdahl、配置 regret 和 8 卡校准 |
| 可选子机制 | U07/U14/U15/U16 | JouleBatch、fused quantize、route clocking、DriftGuard | **D. 子机制** | 仅在主机制通过硬门后作为实现或消融 |
| 淘汰 | 其余 9 项 | 见第 6 节 | **E. 淘汰** | 不再新增系统代码 |

“科学潜力排名”和“执行顺序”不同：RouteCloak 若威胁模型成立，论文上限高于 ResumeSet；但其失败概率也最高。因此执行上把 ResumeSet 放作性能方向备线，把 RouteCloak 放作高风险旁线。

### 0.2 下一步只有一个

未来 1～3 天只做 U01 RankLane 的三重硬门：

1. combine 删除式 Oracle 是否至少 10%，且至少一个常见 bucket 达到 15%；
2. producer/consumer fused codec 税是否低于毛收益 30%；
3. uniform INT8/static cutoff 是否已经捕获 80% 以上 headroom。

任一失败即停止 U01。Oracle 低于 5% 时永久淘汰；5%～10% 时最多降为工程优化，不作为论文主线。

## 1. 三份文档的关系与裁决顺序

三份文档记录的是筛选过程的不同阶段，不能把其中的“Top 3”并列看待：

| 阶段 | 文档作用 | 当时输出 | 现在如何使用 |
|---|---|---|---|
| 方向生成 | 10 Idea 探索文档 | 提出 RankLane、RouteCloak、ResumeSet 等 10 项，初步保留 5 项 | 保留问题背景、机制草图和最初实验想法；不继承偏乐观结论 |
| 补漏与交叉复审 | 12 Ideas 文档 | 加入 speculative、layered prefill、KV/expert HBM、clocking、drift 等候选 | 用于证明搜索空间覆盖度，并提供直接 prior-art 淘汰证据 |
| 最终 Red-Team | 10 Idea 严格评审 | 2 个 B、1 个 C、2 个 D、5 个 E | 对重叠方向采用这里的更保守结论和硬阈值 |

统一裁决规则：

1. **新证据优先于旧判断。** 例如 ELDR 出现后，ResumeSet 从“新状态抽象”下调为 pause/resume workload 上的增量组合。
2. **严格评审优先于探索性评价。** 初稿中的“保留”不等于可以实现；B/C 只授权做判死实验。
3. **直接覆盖优先于主观新颖性。** 即使物理 headroom 很大，只要最近工作已提出同一信息、动作和目标，仍然淘汰。
4. **真实关键路径优先于代理指标。** bytes、hit rate、route predictability、occupancy、R² 都不能替代 E2E wall-clock、P99、goodput 或攻击优势。
5. **资源匹配是硬约束。** 只有跨节点 InfiniBand、真实生产故障域或多 topology 才能成立的方向，不因“未来可能有机器”而保留。

## 2. 选题目标与不可妥协约束

选题不是寻找听起来最新的名词，而是寻找同时满足以下条件的研究对象：

1. 问题在目标 MoE serving workload 中真实出现，不是通过人为缩小 HBM、降低带宽或注入极端 skew 才出现。
2. 删除式 Oracle 对用户可见指标通常至少有 5%，最好超过 15%；否则复杂系统没有 Amdahl 空间。
3. 最强简单 baseline 捕获不到 70%～80% 以上 Oracle headroom。
4. 机制直接作用于瓶颈，并计入决策、同步、迁移、codec、内存、质量和尾延迟税。
5. 5090 能在 1～3 天验证关键必要条件；8×A100 能增加真实因果证据，而非只把实验跑大。
6. 最近 3～6 篇工作没有覆盖相同的“信息集—决策变量—系统动作—目标指标”。
7. 最终可形成问题、观察、机制、Oracle、强 baseline、多模型、多 workload、消融、开销和 failure case 完整闭环。

硬件事实也限制了选题：

- 单 5090 没有真实 expert-parallel all-to-all，不能证明多卡通信或 receiver 因果。
- 单节点 8×A100 只证明 scale-up，不等于跨节点 scale-out。
- [A100 数据表](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet-nvidia-us-2188504-web.pdf)不包含原生 FP8。fake quant、逻辑 bytes 下降和 H2D proxy 不能写成 A100 Tensor Core 或 NCCL 实际加速。
- A100 是 40 GB/80 GB、PCIe/SXM、是否有 NVLink/NVSwitch 会直接改变 U01/U03 的可优化空间，正式实验前必须确认。

候选生成不是纯文献脑暴，而是从仓库已有信号出发：

- [Rank-tail 质量证据](../ideas/A_rank_tail_fp8/设计说明.md)：OLMoE top-8 与 LLM-jp top-16 的 matched-byte 实验显示高/低 gate rank 存在质量敏感度差异，由此产生 RankLane。

- [FJRC corrected 结果](../ideas/receiver_aware/FJRC_Corrected_Level1_Result_2026-07-23.md)：join information 虽改变动作，但未稳定跨过 deadline/action boundary；由此限制 receiver-rescue 类方向。

## 5. 实际采用的筛选漏斗

### Gate -1：研究对象是否清晰

先把每项写成：

> 当条件 X 成立时，机制 Y 相对 baseline Z 改善指标 M，同时满足约束 C。

无法明确条件、动作、基线、最终指标的想法，不进入实验。只优化 hit rate、预测准确率、逻辑 bytes 或 occupancy 的候选，必须补上到 E2E 的因果链。

### Gate 0：现象与 bottleneck 是否真实存在

分别检查 prefill/decode、batch 1/continuous batching、低/高并发、单卡/8 卡、compute/communication-bound。先问“目标开销占多少”，再问如何优化。

直接判死例：U06 的 matched-route 残差只有 2.35%～3.06%；即使模型能预测它，也不代表有足够调度价值。

### Gate 1：删除式 Oracle 与 Amdahl 上界

统一使用：

\[
S(p,s)=\frac{1}{(1-p)+p/s},\qquad S_{oracle}=\frac{1}{1-p}.
\]

Oracle 优先用 trace replay、删除目标时间、future-known 离线优化或 full-padding 等方式实现。一般规则：E2E Oracle <5% 直接淘汰；5%～15% 只在 P99、隐私、显存上限等特殊目标下保留；>15% 才说明物理空间充足。

### Gate 2：最强简单 baseline 与 Captured Headroom

\[
CH=\frac{M_{simple}-M_{current}}{M_{oracle}-M_{current}}
\]

对越低越好的指标按改善方向取差。`CH≥70%～80%` 时，复杂 predictor/controller 原则上停止。每个方向还必须做“配置消失测试”：增加 HBM、调整 batch/EP/TP、启用新 collective、增加静态副本或隔离权限，是否能直接消除问题。

### Gate 3：净收益而非毛收益

净收益必须扣除：decision、profiling、codec、migration、synchronization、memory、quality、kernel launch、batch fragmentation 和 tail 税。局部 10% 毛收益若作用段只占 E2E 10%，理论贡献只有约 1%，很容易被一个额外 kernel 吃掉。

### Gate 4：当前资源能否产生有效证据

- 5090 可以做：质量 Pareto、codec tax、cache/offload replay、能耗积分、attack observer 必要条件。
- 5090 不能证明：真实 EP all-to-all、rank fork-join、receiver congestion、多卡配置迁移准确度。
- 8×A100 可以做：单节点 EP、NCCL/NVLink、真实 rank tail 和队列耦合。
- 8×A100 仍不能自动证明：跨节点 InfiniBand、多故障域、多 topology 泛化。

### Gate 5：论文贡献是否仍存在

逐项比较最近 3～6 篇工作，不只比较标题。若信息集、动作和目标已相同，换 workload、增加动态更新、增加一个目标项或换求解器不构成新论文。最终还要检查是否能形成“问题—新观察—机制—Oracle—强 baseline—E2E—泛化—failure case”的闭环。

## 7. 按去留原因梳理所有方向

## 7.1 为什么只有三个方向进入下一道门

### U01 RankLane-Combine：首选，但不是已成立方向

核心假设是：当 EP combine 位于关键路径且低 gate-rank contribution 稳定更不敏感时，固定单消息双 lane 编码相对 BF16 和 uniform INT8 可降低 TPOT/P99，同时守住质量边界。

它能留下，不是因为“通信压缩听起来重要”，而是因为：

1. 本地 OLMoE/LLM-jp 已出现跨模型 rank-quality 结构，至少观察不是纯假设。
2. 最近邻 Lina、ScMoE、Comet、FlashMoE、SwiftEP、MixServe 覆盖通信、fusion 和 overlap，但尚未直接覆盖 combine-only 的 gate-rank 质量结构与固定规整双 lane。
3. 5090 能在 1～3 天否定质量 Pareto、codec tax 和 shape/bandwidth break-even；8 卡能验证真实 all-to-all。
4. 若通过，它有一条可讲清的因果链：`rank-quality结构 → 固定wire表示 → combine时间下降 → E2E收益`。

但当前因果链只有第一环有证据：

`rank质量不对称（有） → combine是critical path（缺） → dual-lane减少真实wire time（缺） → fusion不破坏packing/P99（缺） → E2E（缺）`。

本地未融合 FP8→INT4 codec 在 rows 128/512、200～400 Gbps 等效链路上 0/8 可行，codec tax 约 58～61 μs。这不是小问题，而是 U01 必须先面对的物理反证。若只能在 ≤50 Gbps 慢链路为正，而目标服务器是 NVLink/NVSwitch，直接按资源不匹配淘汰。

最强 baseline 不是 BF16，而是 **single-message、producer/consumer fused uniform INT8 + static rank cutoff + 最新 overlap**。双 lane 只有在同消息数、同 fusion、公平质量约束下仍留下至少 20% Oracle headroom，才有研究价值。

### U02 RouteCloak：科学上限高，证据风险最高

核心假设是：低权限共租观察者可从 MoE route 执行足迹恢复 token/属性，而 static bucket/dummy routing 能在 exact output 下移除大部分攻击优势，P99/throughput 代价受控。

它能留下，因为问题本身新颖且重要：[MoEcho](https://arxiv.org/abs/2508.15036)、[Expert Selections Reveal Text](https://arxiv.org/abs/2602.04105)、[CryptoMoE](https://arxiv.org/abs/2511.01197)、[SecMoE](https://arxiv.org/abs/2601.06790)分别证明了 route/side-channel/secure-compute 邻域的重要性，但普通共享 serving 中 exact-output、SLO-bounded traffic defense 仍有可能形成独立问题。

它不能成为首选，因为最关键的桥梁尚不存在：

`route与文本相关（已有） → 普通tenant可看到route proxy（缺） → 攻击跨run/模板迁移（缺） → padding降低信息（缺） → ≤10%性能代价（缺）`。

full padding 是隐私 Oracle，但 top-8/64 若执行全部专家，最坏约增加 8× expert work。它证明“信息可以隐藏”，不证明可部署。最强 baseline 还包括自然 continuous batching、固定窗口混洗、static traffic bucket、MIG/权限隔离；如果隔离能低成本阻断 observer，就没有必要造复杂 cloak。

因此 U02 的第一步只能是攻击存在性：真实低权限 observer 的攻击优势若低于 20 个百分点、AUC<0.70～0.75、只在管理员权限成立或无法跨 run 迁移，立即停止。

### U03 ResumeSet：可验证，但创新边界和容量 regime 都脆弱

核心假设是：tool/human pause 后 KV 仍被保留，但 expert 工作集被驱逐，恢复前 N token 出现独立 cold-start；联合保留相对 KV-only、LRU/LFU 和 last-W 可改善 resume SLO。

留下它的理由是：pause/resume 是明确请求生命周期，5090 可以通过真实 offload 与受控 HBM budget 测删除式 Oracle；它失败时也能得到明确的 cold-start characterization。

保留条件很苛刻：

- 模型权重全驻留时 expert miss=0，headroom严格为0。
- [InferCept](https://arxiv.org/abs/2402.01869) 已覆盖 API interruption/KV，[ELDR](https://arxiv.org/abs/2607.00466) 已使用 KV-indexed expert signature，[HOBBIT](https://arxiv.org/abs/2411.01433) 和 [FluxMoE](https://arxiv.org/abs/2604.02715) 覆盖 expert residency。创新性只能来自 **pause-induced eviction/cold-start 这个独立 phase**。
- 最强简单 baseline 是 KV TTL 同步的 `last-W expert union + static quota`。若它捕获 ≥70%，学习型联合策略没有论文价值。
- 为暂停请求保留 expert 会污染活跃请求。必须以全局 goodput/SLO 评价，不能只看 resume hit rate。

只有两个模型、两类真实/公开 pause trace 上，KV-only 后 expert 独立 Oracle≥15%、last-W CH<70%、全局 goodput下降≤2%，它才从 C 进入实现。

## 7.2 为什么五个方向只能降级为子机制

### U04 ScaleBridge / ScaleTail

它预测 8 卡性能与 P99，但不直接改善 serving。完整 8 卡 sweep 是 regret=0 的 Oracle；最强 baseline 是 roofline+NCCL LUT+3～5 个校准点+max rows/rank。若 baseline 的 best-config regret≤5%，复杂模型只是 curve fitting。它最合理的价值是给 U01/U02/U03 提供统一 trace schema、删除式 Oracle 和配置选择，不是单独包装论文。

### U07 JouleBatch

perfect expert packing 对 E2E energy/token 的粗上界只有约 3%～12%，fixed slack threshold + per-expert FIFO 或 persistent kernel 很可能捕获大部分收益。等待还可能恶化 P99。它应作为最终系统的 energy 指标、threshold baseline 或消融；只有 Oracle≥10%、threshold CH<80% 才能重新讨论独立性。

### U14 Fused Quantize-at-Dispatch

fusion 能决定 U01 是否物理可行，但 fusion 本身是 kernel/backend 实现细节。SwiftEP、Comet、FlashMoE/MixServe 已把 buffer、overlap 和 producer/consumer 路径抬到很强的 baseline。U01 未通过 combine Oracle 前，不实现 U14；通过后它是单消息双 lane backend，不单独立题。

### U15 Route-Intensity Clocking

PALS、Festina、GreenLLM 等已覆盖 phase/batch/power/SLO 联动，route 只可能是额外 feature。必须先做 matched phase×batch 下 route feature 的增量价值；若 route residual energy<5% 或 static clock table CH≥80%，结束。它适合一天 profiling 或能耗消融，不适合主线。

### U16 DriftGuard-MoE

动态 expert quantization 已非常拥挤，且仓库已有三重负先验：sensitivity persistence 弱、quality proxy 不免费、动态低精度完整路径不比 BF16 快。没有真实 executor 快区时，完美 precision assignment 的系统收益仍为0。它最多用于检查 U01 的 rank-quality 结构是否跨时间漂移。

## 7.3 为什么九个方向直接淘汰

### 第一类：物理上界或现象已经偏低

- **U06 RouteShare：** matched-route effect 仅2.35%～3.06%，简单模型 held-out `R²=0.9971～0.9986`。即使 route feature 可预测，也很难转化成≥5% E2E；继续写 coalition scheduler 只会优化代理指标。
- **U05 QualityDebt：** 没有真实 slow-rank census。若慢事件只影响10% step、每次多50%延迟，整体可删部分约4.8%；P99或许更高，但 Capacity-Aware Inference/ReaLB 已覆盖 drop/reroute/precision 动作。新“quality debt”目标不足以救活机制。

### 第二类：物理空间可能存在，但论文空白已被覆盖

- **U11 Expert-Set Speculative Verification：** EcoSpec、MoE-Spec、EVICT、MoESD 已联合 acceptance、expert activation/union cost 与 verification budget。资源更大不能创造 novelty。
- **U12 Layered Prefill：** From Tokens to Layers 已提出 layer-wise prefill 减少权重读取；Sarathi-Serve、MoE-Lightning 等构成强执行 baseline。换成 MoE/offload workload 不构成新机制。
- **U13 KV/Expert HBM Exchange：** FluxMoE 已联合处理 expert paging 与 KV pressure；HOBBIT、MoE-Lightning、KV-cache work 进一步覆盖。generic 版本淘汰，只把 pause 特例归入 U03。
- **U08 Cancellable Spec-MoE：** SP-MoE、MoE-Spec、MoE-SpAc、SpecMoE 已密集覆盖。更重要的是可回收量不是 rejected work，而是 `reject×判决后尚未完成×可取消×critical`，通常远小于直觉。
- **U09 Shadow-Price Placement：** Aurora、Gimbal、MoEless、Mixture-of-Experts Serving 已覆盖 placement、dynamic allocation 与 reconfiguration cost。单卡无法验证，8卡单 topology 也不足以支撑 scale-out；换成 shadow-price 求解器不是新 insight。
- **U10 Sensitivity Cache/Quant：** HOBBIT、DynaExq、ProMoE、MODE 等覆盖 sensitivity/hotness/precision/cache/prefetch。仓库又已有 cache working-set 饱和和 quant path 负结果。把三个失败组件联合起来只会增加归因困难。

### 第三类：与本地已审对象重复，且资源不能验证核心

- **U17 Critical-Sibling Receiver Rescue：** 与旧 FJRC/keyed sibling deficit 是同一 scientific object。单卡注入不能证明自然 receiver straggler，既有 corrected 结果又显示 join 信息没有稳定跨过 deadline/action boundary。只有真实8卡同时出现 join wait≥15%、aggregate queue解释不了、receiver信息 action flip≥10% 才重开。

| 时间点 | 当时判断 | 新证据/更严格问题 | 调整后判断 |

## 10. Top 3 的统一执行路线

## 10.1 首选 U01 RankLane：1～3 天预注册实验

### 目标

只回答三个必要问题：

1. combine 在目标 workload 中占多少不可 overlap 的 critical path？
2. fixed dual-lane 在完整 `producer→pack/quant→transfer→unpack/dequant→combine` 路径中是否存在正区？
3. 简单 uniform/static baseline 是否已经足够？

### 模型、框架与数据

- 模型：OLMoE top-8 主实验；LLM-jp top-16 独立复现。
- 框架：复用 `docs/ideas/A_rank_tail_fp8` 的 route/quality runner，以及 `docs/ideas/receiver_aware/experiments/run_homogeneous_lane_codec_gate_gpu.py`；只增加 shape 导出、统一 metadata 计费、once-per-step fused lower bound 和 timeline。
- 数据：已有 matched-quality 文档集；至少补一组 serving-like prompt。性能按 prefill/decode、batch/concurrency 和真实 token-per-destination bucket 分层。
- 规模：每模型至少 200 文档；每性能 bucket≥1,000 warm iterations、5 个独立 run、bootstrap 95% CI。
- 显存：沿用现有可运行模型配置；额外 activation/codec buffer≤2 GB。

### Baseline 与 Oracle

- B0：BF16 单消息、无 codec。
- B1/B2：single-message uniform INT8/INT4，使用与新机制相同的 fusion 假设。
- B3：最佳 static global/per-layer rank cutoff。
- B4：activation-magnitude cutoff，防止“任意 signal 都能分组”。
- Oracle-P：从真实/等价 timeline 中删除全部 combine critical-path 时间。
- Oracle-C：codec cost=0，但保留消息启动与不可压缩 metadata。
- Oracle-Q：离线逐层/逐样本选择满足质量边界的最低精度，只作为质量上界。

### 自变量和控制

- payload：BF16、uniform INT8/INT4、固定 dual-lane。
- rank cutoff：0%、25%、50%、75%、100%。
- rows：真实 trace 的 P10/P50/P90，至少覆盖32/64/128/256/512。
- 等效链路：25/50/100/200/400 Gbps；若8卡可用，以实测 BF16 combine 有效带宽替换 proxy。
- mode：unfused负对照、serialized tile、once-per-step fused lower bound。

固定 router output、token/expert assignment、随机种子、scale规则、metadata、消息数、warm-up、功率状态和质量样本。不能只给新机制 fusion/overlap，也不能用两个 collective 对比一个 collective。

### 指标

记录 dispatch/expert/combine/overlap residual，codec P50/P95/P99、真实 bytes、临时 buffer、message count、break-even bandwidth、prefill latency、TPOT、P99、tokens/s、energy/token、质量差与配对 CI、Captured Headroom、`codec tax / gross saving`。

### Go / No-Go

全部满足才进入 8 卡 backend 原型：

1. 两个模型代表性 decode/continuous-batching bucket 中 Oracle-P≥10%，至少一个常见 bucket≥15%；
2. once-fused dual-lane 净收益≥5%，95% CI 下界>0；
3. codec tax≤毛 byte-time saving 30%；
4. 最佳 simple baseline CH<80%；
5. 消息数不增加，P99恶化≤2%，跨两模型质量约束通过。

任一触发 No-Go：Oracle-P<5%；只有≤50 Gbps慢链路为正；simple CH≥80%；codec税>毛收益30%；正区只在不常见大 rows；必须拆成两个 collective；只在单模型/合成 workload成立。

### 三天安排

- Day 1：导出真实 shape，完成 B0/B1/B2 与 Oracle-P；所有常见 bucket <5% 当天结束。
- Day 2：once-fused lower bound、dual-lane/B3/B4、质量配对；CH或codec门失败即结束。
- Day 3：只有前两天通过才做真实8卡一层/多层 BF16 profiling/replay；zero-combine E2E<5% 最终淘汰。

## 10.2 次选 U03 ResumeSet：1～2 天独立 cold-start Oracle

### 目标与设计

只验证 pause 后 KV 已保留时，expert fetch 是否仍独立决定 resume 前 N token 的关键路径。

- 模型：OLMoE 与 LLM-jp；必须至少有两个容量/模型比例。
- trace：tool call、human pause 或公开/真实 agent lifecycle；不能只有固定合成 pause。
- HBM budget：8/12/16/24/32 GB 或按模型权重比例分层；自然 32 GB 配置必须报告。
- N：恢复后32/64 token。
- Baseline：KV-only、LRU、LFU、global hot set、last-W union+static quota。
- Oracle：知道 resume time 和 future N-token expert set，在相同总 HBM 下最优保留；分别删除 KV restore 与 expert fetch，计算独立份额。
- 指标：resume TTFT/P95、前N token TPOT、fetch critical time、expert hit、HBM opportunity cost、active-request P99、全局 goodput。

### 判据

全部满足才实现 event-driven TTL/quota：expert 独立 E2E Oracle≥15%；last-W CH<70%；两个模型、两类 pause trace成立；全局 goodput下降≤2%；结果不只存在于≤25%权重 cache 的极端 regime。

任一失败即淘汰，不用 learned predictor、复杂联合优化或换更小 cache 救活。

## 10.3 高风险 U02 RouteCloak：先攻击、后防御

### 第一阶段只验证威胁模型

- 攻击者：明确普通低权限、不同进程/tenant；记录权限、counter/API、时间分辨率和隔离设置。
- 目标：从真实可达 timing/cache/TLB/traffic proxy 预测 ground-truth route、token 或敏感属性；不能直接把 route trace 喂给攻击器冒充端到端攻击。
- 变量：batch1/continuous batching、prefill/decode、并发、模板、语言、checkpoint、MIG/权限隔离。
- Baseline：随机、频率先验、自然 batching、fixed-window mixing、权限隔离。
- 指标：token top-k、属性 AUC、mutual information、跨run/模板/模型迁移。

No-Go：攻击优势<20个百分点、AUC<0.70～0.75、无法跨run/模板迁移、只在管理员权限成立、MIG/禁counter低成本阻断。任一出现均不写防御。

### 第二阶段才画 privacy–SLO frontier

攻击通过后，比较无防御、自然 batching、static buckets、full-padding Oracle；报告攻击优势、P50/P99、throughput、J/token 和额外 A2A。只有≤10%性能代价内可移除≥80%攻击优势，才设计 RouteCloak runtime。

## 11. 公共实验底座：把 U04 变成方法，而不是第四条主线

所有后续方向共享同一套证据格式：

1. **Trace schema：** model/checkpoint、phase、batch/concurrency、layer、expert/rank、rows、bytes、queue、kernel、collective、overlap、P50/P99、power/energy。
2. **删除式 Oracle：** 每个目标瓶颈必须能在 trace replay 中删除，得到 E2E 上界。
3. **配置消失测试：** batch、EP/TP、HBM、static replica、collective、隔离设置。
4. **Captured Headroom：** 所有 simple baseline 与 Oracle 在相同质量、SLO、HBM、arrival trace、message count 下比较。
5. **配置 regret：** 预测模型不只报 MAPE，必须报 best-config regret 和节省的 GPU-hours。
6. **证据标签：** `[本地实测]`、`[论文作者报告]`、`[离线模拟]`、`[推断/待测]` 分开，禁止 proxy 升格。

U04 只有在 roofline+NCCL LUT+3～5 个校准点的 config regret>5%，而复杂模型能把 regret 显著降下并节省≥80% profiling 时，才可能独立讨论。否则它就是高质量实验方法。

## 13. 建议的一周执行顺序

### 第 0 步：当天确认环境

确认 8×A100 的 40/80 GB、PCIe/SXM、NVLink/NVSwitch、可用 NCCL/DeepEP/vLLM 版本。该信息不清楚时，不预设 U01 通信收益或 U03 容量压力。

### 第 1～3 天：U01 三重硬门

按第10.1节执行。每日结束都允许永久 No-Go，不为凑满三天继续跑。

### 第 4 天以后只走一个分支

- U01 通过：先做一次无侵入8卡 BF16 profile；combine Oracle继续通过才实现 U14 fused backend。
- U01 失败：转 U03 cold-start Oracle；不修补 codec、不换慢链路救活。
- U03 也失败：转 U02 observer existence；不并行写防御。
- U02 失败：停止在这17项中继续包装，重新基于新的系统 measurement 或新文献事实生成候选。

执行流程：

```text
U01 quality/codec necessary gate
        │
        ├─ pass → 8×A100 zero-combine Amdahl gate
        │              ├─ pass → fused single-collective prototype
        │              └─ fail → stop U01
        │
        └─ fail → U03 pause-specific cold-start oracle
                       ├─ pass → TTL/quota prototype
                       └─ fail → U02 low-privilege observer gate
                                      ├─ pass → privacy–SLO frontier
                                      └─ fail → stop current portfolio
```

## 14. 最终研究判断

这轮筛选没有证明 RankLane、ResumeSet 或 RouteCloak 会成功；它只证明它们是 17 个独立研究对象中，**仍值得支付一次廉价反证成本**的三个方向。

最终选择 U01 RankLane 作为首选，是四个条件共同决定的：本地已有跨模型质量观察；直接 novelty 尚存；5090 可先验证必要条件；8×A100 能验证核心 all-to-all 因果。U03 留作备线，是因为实验可快速判定，但容量 regime 和 ELDR 重叠使论文上限下降。U02 留作高风险方向，是因为问题潜力最大，但观察者可能不存在。

最重要的路线纪律是：**先测可优化部分占比，再测简单 baseline，最后才写机制。** 没有 Oracle、没有真实 critical path、没有胜过 simple baseline 的剩余 headroom，就没有理由继续实现。
