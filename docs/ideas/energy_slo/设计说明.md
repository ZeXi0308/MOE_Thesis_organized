# 名称

Energy-SLO Precision EP：真实 GPU 能耗测量下的 batch × 精度联合控制

状态：**HARDWARE CHARACTERIZATION / SYSTEM UNVERIFIED**。已观测固定 full-sequence shape 下的 batch 利用率效应和预量化 FP8 GEMM-core 效应；未验证 KV-cache decode、arrival/queueing/P99 或含动态 quantize/scale/cast 的端到端 Energy-SLO controller。

## 1. 背景与问题

Energy-SLO Precision EP 最初在选题地图（2026-07-13）里被定位为"精度/放置/副本/能耗联合控制"，复用 Idea B 的精度轴，但被要求不与主线同时推进，此后长期未被拾起（选题时间线 #9）。2026-07-20 重新拾起时，首先要面对一个诚实的方法论问题：**本项目现有的精度降级机制（`fake_quant.py`）全部是下游质量代理**——它们在同一个 bf16 计算路径里做 quant-dequant，不改变真实 GEMM 的 FLOPs 或 dtype，因此在单卡上无法体现任何真实能耗差异（单卡也没有真实网络/EP mesh，因此原方案里"placement/副本"这个维度在这里完全无法测量）。

与其在现有基础设施测不出真实能耗差异的情况下硬造一个数字，本 idea 选择只测量单张租用 GPU 上**真实可测**的两个轴：(1) batch size 与 energy-per-token 的真实吞吐/功耗权衡曲线；(2) 真实（非代理）的低精度计算路径——把 expert FFN 的权重真正 cast 成 `torch.float8_e4m3fn` 并用 `torch._scaled_mm` 做真实 FP8 tensor core GEMM，与 bf16 做真实能耗对比。

## 2. 核心思想 / 机制主张

**已验证的受限主张**：在单卡 RTX 5090 的两个不同微基准中，存在两个方向一致的硬件效应：
1. **Fixed full-sequence batch 效应**：batch 1→64，OLMoE 上 measured energy-per-counted-token 改善约 **17.4×**（235.9 → 13.6 mJ/token）。该 token 来自每轮重复的 `batch×seq_len` full forward，不是 decode arrival 服务 token。
2. **GEMM-core 精度效应**：预先 cast 好的 FP8 tensor-core GEMM 相对 bf16，吞吐约 **2.03×**，单 matmul 能耗降低约 **34.3%**。计时不含每次调用所需的 activation amax/scale/cast，不是端到端 FP8 路径数字。

**`SUPERSEDED`：「batch=64 在延迟和能耗两维严格支配更小 batch」。** 文档自身给出的代理 iteration latency 是 142.2ms → 209.5ms，后者延迟更高；SLO>210ms 只能说 batch=64 在该代理门槛下可行且已测 J/token 最低，不是延迟支配。又因无 arrival/queueing，不能把该 iteration latency 称为 serving TPOT/P99。

**待检验的系统问题**是 `arrival- and communication-aware precision-batching co-control`：在真实 Poisson/bursty arrival、P99 SLO 和 EP 通信能耗约束下，联合选择 batch accumulation 与计算精度。当前两个微基准效应不能相乘，也不能代替相对最佳单轴 controller 的增量检验。

## 3. 实验如何设计（模型、指标、基线、预注册门槛、数据隔离）

**模型**：OLMoE-1B-7B-0924、LLM-jp（E32K16），两模型均跑齐 FP8 质量门槛；batch-power 曲线目前以 OLMoE 为主证据。

**硬件测量方法**：`pynvml` 以 ~50ms 间隔采样真实 GPU 功耗，在 ≥3s 的持续推理循环上积分求能耗（`energy = ∫power dt`），`J/token = energy / tokens_processed`——这是真实硬件测量（`[Observed]` 标签），不是仿真估计。

**指标**：
- batch-size sweep：`throughput_tokens_per_s`、`mean_power_w`、`energy_per_token_mj`（batch ∈ {1,4,16,64}，seq_len=64）；
- 精度对比：matched-shape 的 expert `gate_proj` 尺寸真实矩乘，`matmuls_per_s`、`mean_power_w`、`energy_per_matmul_mj`（bf16 vs 真实 FP8 E4M3 tensor core）；
- **质量 confound 门槛（此前缺失、后补齐的关键环节）**：真实端到端模型跑 FP8-compute 候选路径 vs bf16 参照路径，token-level KL(reference‖candidate) + corpus PPL。

**FP8 计算质量门槛的具体协议**：每篇文档跑一次 bf16 参照前向；再跑一次候选前向——把每个 expert 的 `gate_proj/up_proj/down_proj`（OLMoE/Qwen2-MoE 风格 SwiGLU MLP）monkey-patch 成真实 `torch._scaled_mm` FP8 E4M3 tensor core GEMM（权重按 per-tensor absmax/448 静态 scale 一次性 cast，激活值按 per-tensor absmax/448 动态 scale 逐次 cast），router 本身不动，因此更深层的路由分歧是该 patch 的真实下游效应，不是 patch 本身的 artifact，正确地被计入 KL 数字。

**预注册门槛（质量门槛，非项目已有预注册常量，是本脚本显式做出的判断调用）**：
- **GO**："FP8 计算是免费午餐"——95% CI 上界 < `--acceptable-kl`（默认 0.05，约比已知"通信 INT4 降级"的 KL 锚点 0.257 低一个数量级）；
- **NO-GO**：95% CI 下界 > 0.05；
- **INCONCLUSIVE**：CI 跨越阈值，需要更多文档。

注意：通信 INT4 的 0.257 KL **只作定性锚点**，不是可直接统计对比的基线——本项目此前反复发现"通信量化"和"计算量化"在同一 KL 数值下的实际伤害并不等价。

**数据隔离**：WikiText-103（`wikitext103_docs`，offset=0），OLMoE/LLM-jp 各 24 篇文档；两模型独立跑质量门槛，无 calibration/test 划分需求（本实验不含任何需要拟合的超参数）。

## 4. 代码怎么组织（入口脚本、关键模块、数据流一句话）

**入口脚本**：
- `run_energy_slo_power_probe.py`：P0 真实硬件测量主脚本，内含 `PowerSampler` 类（`pynvml` 后台线程采样，`nvmlDeviceGetPowerUsage` 每 ~50ms 一次），先跑 batch-size sweep（真实 OLMoE/LLM-jp 模型推理循环），再跑 matched-shape 的 FP8 vs bf16 真实 GEMM 能耗对比（`torch.float8_e4m3fn` + `torch._scaled_mm`）。
- `run_energy_slo_fp8_compute_quality_gate.py`：**质量 confound 门槛脚本**，补齐"FP8 计算是否伤质量"这个此前缺失的环节——真实模型端到端跑 bf16 参照与 FP8-compute 候选各一次前向，用 `metrics.py` 统一的 KL/PPL 口径判定 GO/NO-GO；修复了三个真实实现 bug（见第 5 节）。

**数据流一句话**：真实模型加载 → (a) batch-size sweep：固定 seq_len，扫描 batch，`pynvml` 后台采样功耗，算真实 energy/token；(b) matched-shape micro-benchmark：抽取真实 expert `gate_proj` 尺寸，做 bf16 vs FP8 tensor core 矩乘吞吐/能耗对比；(c) 质量门槛：真实文档语料前向，monkey-patch expert FFN 为 FP8 tensor core kernel，token-level KL vs bf16 参照 → 写 `report.md`/CSV。

## 6. 当前结论与边界

**当前结论**：Energy-SLO 目前是两个硬件 characterization，不是已证系统机制。质量脚本证明其自己的端到端 FP8 expert patch KL 小，但能耗脚本只测预量化 GEMM core；两条证据未在同一实际执行路径闭环。

**明确边界（尚未做的事）**：
- 联合 Pareto 目前是"用已有独立数据推导出的规则"，不是"真实测量的联合 arrival×batch×precision 空间"——真正的下一步是在真实 Poisson/bursty arrival 下同时选择 batch accumulation 与计算精度，检验两个杠杆联合后是否仍有相对最佳单轴 controller 的增量（不能假设乘性效应成立）；
- batch 曲线是 seq_len=64 整段 full forward，不是 KV-cache decode；当前没有 queueing/accumulation/P99 SLO 证据；
- 34.3% 数字不含每次 activation 的 float/amax/scale/cast，只能标为 GEMM-core 能耗差；
- 原方案里"placement/副本"维度需要多 GPU EP mesh，单卡完全未覆盖；多 GPU 阶段需要计入 GPU、NIC、CPU 和通信等待能耗；
- FP8 质量门槛只 patch 了 expert FFN 的三个矩乘（`gate_proj/up_proj/down_proj` 或 `w1/w2/w3`），attention 投影、router 自身的 gate 矩乘、embedding/LM head 仍是 bf16——生产系统若把更多部分转 FP8，质量 delta 可能比这里测到的更大；
- 用的是 per-tensor（非 per-channel/block）absmax scaling，是最简单的真实 FP8 recipe，也是在 outlier 密集激活上最可能失真的 recipe——当前 GO 不排除 per-channel/MXFP8 下可能 NO-GO；
- 质量门槛脚本里"通信 INT4 KL=0.257"只是定性锚点，不能被当作可直接统计对比的基线。

**GO 门槛（下一步，`research_report_moe_next_direction_2026-07-21.md`）**：单卡先做真实 arrival 的 batch×precision 联合 Pareto，Go 门槛是相同 P99 SLO violation 下，能耗/token 相对最佳单轴 controller 下降至少 10%，TPOT/P99 不恶化超过 3%；多 GPU 阶段再计入 GPU/NIC/CPU/通信等待能耗，要求节能仍至少 8%。如果只能复现独立 microbenchmark，只能作为第二贡献。
