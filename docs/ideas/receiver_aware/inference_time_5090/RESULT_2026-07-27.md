# Receiver 多 MoE 层 inference-time 5090 实测结论（2026-07-27）

## 1. 直接裁决

1. **此前缺失的完整 inference-time 已补齐。** 本次不再使用 single-forward、codec
   或 replay 代理，而是在 RTX 5090 上真实执行 prefill 和带 KV cache 的逐步 decode。
2. **“多个 MoE 层会累计影响 inference time”得到单卡正证据。** 16 层 LLM-jp
   中，本地 MoE block 时间约占 profiled decode 的 82.8%–90.2%，且不是由某一层
   独占，而是 16 层近似均匀累积。
3. **“多 MoE 层已经导致 Receiver 拥塞”仍未验证。** 该机器只有一张 GPU，没有
   EP ranks、NCCL/NVLink return all-to-all、receiver ingress queue 或 join wait。
4. fixed RankLane 现有 NO-GO 不变；真实 Receiver 存在性仍需 8×A100 EP Gate。

## 2. 冻结实验

### 硬件与软件

- GPU：NVIDIA GeForce RTX 5090 32607 MiB
- Driver：580.95.05
- PyTorch：2.8.0+cu128
- Transformers：4.57.6
- dtype：BF16
- 主模型：`llm-jp/optimal-sparsity-math-d512-E32-k16-920M-A520M`
- revision：`1d5983076dfc67aee4a77ec06a27027f5bab6055`
- 模型结构：16 个 MoE 层，32 experts，top-k=16

### 矩阵

- batch：1、4、8、16、32
- prompt length：128
- decode steps：32
- repeats：5
- 每个 decode cell 的主计时样本：160
- `unprofiled`：只记完整 forward CUDA Event，作为 inference-time 主口径
- `profiled`：增加每层 MoE CUDA Event，只用于时间分解
- 两条 arm 按 repeat 交替 AB/BA，以降低单调热状态与顺序偏差
- route census 独立 untimed 运行，不污染主 inference-time

## 3. 主要结果

### 3.1 完整 KV-decode inference time

| Batch | Decode median | Decode P95 | Goodput | Profile observer tax |
|---:|---:|---:|---:|---:|
| 1 | 43.009 ms | 45.514 ms | 23.25 token/s | 4.04% |
| 4 | 72.671 ms | 79.022 ms | 55.04 token/s | 2.34% |
| 8 | 79.014 ms | 87.437 ms | 101.25 token/s | 2.46% |
| 16 | 82.162 ms | 89.709 ms | 194.74 token/s | 2.15% |
| 32 | 83.098 ms | 92.758 ms | 385.09 token/s | 2.38% |

batch 1 到 batch 32 时，每个 decode step 的 latency 增加约 1.93×，而同时生成的 token
数增加 32×，所以 goodput 增加约 16.6×。这是本地 batch/expert execution 表征，
不是 continuous-arrival serving TPOT/P99。

### 3.2 多层 MoE 累计占比

| Batch | 16 层 MoE 累计 median | MoE / profiled decode median |
|---:|---:|---:|
| 1 | 37.054 ms | 82.84% |
| 4 | 66.031 ms | 88.83% |
| 8 | 72.699 ms | 89.82% |
| 16 | 75.655 ms | 90.18% |
| 32 | 76.733 ms | 90.21% |

这个比例包含每层 MoE block 中的 router、expert compute、本地 dispatch/combine 及 HF eager
实现开销；其中没有多卡 return all-to-all，不能把 82.8%–90.2% 当作
`p_return`。

### 3.3 不是单个慢层，而是 16 层均匀累积

在所有 decode batch cell 中：

- 最慢单层只占各层 median 之和的 6.36%–6.58%；
- 最慢 4 层合计只占 25.20%–26.11%；
- 16 层 median latency 的层间 CV 为 0.59%–3.65%。

因此，“多 MoE 层需要进入完整 inference denominator”得到支持。只 profile 一个层或
只选最慢层都会丢失大部分累计成本。

### 3.4 Route imbalance 未呈现一致正相关

top-k=16/32 使用 `max(max/mean)` 时该指标在各个 batch 均饱和为 2，因此主分析改用
逐层平均 `max/mean` 与平均 load CV。在仅 16 个确定性 decode steps 的描述性样本中：

- 没有看到“路由越不均衡、decode 越慢”的稳定正相关；
- batch 4/8/32 的 load-CV 与 latency 甚至是负相关；
- 一个合理但未验证的解释是：路由更集中时，少数 expert 得到更大的局部 GEMM，
  反而提高单卡执行效率。

这些 step 并非独立 serving request，p-value 也只是诊断字段。该结果不允许宣称
“不存在 Receiver 拥塞”，但它明确反对将 logical route imbalance 直接当作 congestion。

## 4. 交叉检查

2 层 `jamesdborin/tiny-mixtral` 使用同一脚本得到：

- batch 1 decode median 2.265 ms，batch 16 为 3.895 ms；
- 本地 MoE 累计占比从 43.2% 增至 64.2%；
- observer tax 为 5.2%–7.5%。

该模型只有 2 层，不作 Receiver 主证据；它只证明脚本能够在另一个架构上闭合
KV decode、MoE 层 census 和 observer-tax 计算。

### 4.1 本地 MoE component breakdown

随后在同一 5090 和同一 LLM-jp 模型上，将本地 Mixtral MoE block 粗分为 gate、
routing setup、expert loop 和未归因尾部。该分解的最大 decode observer tax 为 6.55%，
低于预先设置的 10% 有效性门：

| Batch | Expert loop / profiled decode | Routing setup | Gate | 未归因尾部 |
|---:|---:|---:|---:|---:|
| 1 | 74.90% | 5.69% | 0.80% | 1.29% |
| 4 | 84.00% | 3.56% | 0.52% | 0.81% |
| 8 | 85.22% | 3.30% | 0.49% | 0.75% |
| 16 | 85.63% | 3.22% | 0.47% | 0.73% |
| 32 | 85.67% | 3.21% | 0.47% | 0.72% |

`expert_loop` 仍包含 gather、expert compute、routing-weight multiplication 和本地
`index_add`，不是纯 expert GEMM。但这个结果说明 82.8%–90.2% 的高 MoE 占比主要来自
本地 expert execution，而不是已经观察到的 return traffic。完整结果见
[`receiver_moe_breakdown_coarse_llmjp_formal_20260728/`](outputs/receiver_moe_breakdown_coarse_llmjp_formal_20260728/)。

### 4.2 自然文本与 context-length 稳健性

为排除冻结合成 token 序列造成的单一输入伪影，又补跑了来自 Project Gutenberg
`Alice's Adventures in Wonderland` 的连续自然文本 span。prompt=128、batch=1/4/8 时，
MoE 累计占比分别约为 82.86%、89.14% 和 89.98%，与主结果接近。该 workload 仍不是
continuous serving arrival，但说明“全层本地 MoE 成本很高”并非只由 token 重排输入产生。

另在 prompt length 128/512/2048、batch=1/4/8 上复核后，decode MoE 累计占比保持在
约 82.7%–89.9%。这些稳健性结果仍只适用于当前 LLM-jp + Transformers eager 单卡实现，
不能外推 OLMoE、vLLM/DeepEP 或多卡 EP。

## 5. 对 Receiver 课题的影响

### 新增的正证据

- Receiver 未来的端到端会计必须覆盖全部 MoE 层，不能只使用一个 selected layer。
- 多个 MoE block 的本地累计成本是完整 decode 的主要部分，所以值得在多卡上继续
  分解 expert compute 与 return path。
- component breakdown 表明主要成本位于本地 expert loop；这会提高 Receiver 方向的
  反证压力：真实 return path 必须在强 backend 上单独留下足够 exposed headroom。

### 仍然缺失的证据

- 每层 `expert-ready → return A2A → receiver-visible → unpack/combine-complete`。
- 请求/token completion 与通信事件的同时钟 precedence DAG。
- 真实 sender/receiver fan-in、busy period、join wait 与 transport identity。
- strongest overlap/fusion/zero-copy backend 之后的 exposed return fraction。

### 下一步

8×A100 Gate 应将“每个 MoE 层的 return-path event”接入同一 token/request DAG，然后统一
删除 return service 重算完整 completion。不能直接将 16 层 profiler span 相加，因为这会忽略
overlap 和不同请求的依赖关系。
