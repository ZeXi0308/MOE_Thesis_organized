## 0. 直接裁决

本轮不再把 `receiver-aware`、combine codec、动态量化、expert cache 或普通 placement 当作默认主线。它们要么已有本地 NO-GO/资源阻塞，要么被 2025–2026 年的新工作正面覆盖。

`[Observed]` [审计期间新增的 RankLane 代数上界](../receiver_aware/cpr_ranklane/CPR_MoE_RankLane_5090快验协议与裁决_2026-07-25.md)给出了更强停止证据：在 `raw BF16 exposed return fraction≤20%`，并把 codec、launch、queueing 与 metadata 税全部设为零时，OLMoE 与 LLM-jp 相对 uniform FP8 的最乐观 E2E 改善都只有 **4.1667%**；达到 5% 至少需要 `p_return=23.5294%`。因此固定 RankLane actuator 在该冻结域内 `NO_GO_RANKLANE_ACTUATOR_UNDER_P_RETURN_MAX_0_20`。这不测也不否定真实 8×A100 return-path existence，但足以让它退出当前唯一主攻。

最终唯一值得先投入的研究问题是：

> **[Hypothesis] 在存在 exact-weight expert replicas 的 MoE serving 中，传统 least-load / hash 分派为了平衡队列而分裂同一 expert 的 token rows，导致更多小 GEMM、launch、weight-read 与 fork-join tail；若在 deadline 与通信约束下联合决定 replica assignment 和短 coalescing window，可以在不改变模型输出的前提下提高 SLO-satisfied throughput。**

它不是“再做一次 expert placement”。最小版本固定 replica placement，只控制每个已路由 contribution 去哪个**等价权重副本**以及何时封批。核心结构是：

```text
least-load 分散流量
→ 队列更均衡，但每个副本 rows 更小、GEMM/launch/weight-read 更多

consolidate 合并流量
→ GEMM 更高效，但队列、远端通信和 deadline 风险更大

BCRD
→ 用实测的非线性 service curve，在两者之间做 deadline-bounded assignment
```

当前没有正结果。最可能收益先验为 **8%–15% E2E/SLO-capacity**，但只有三个快速实验全部通过后才保留；若自然 trace 中 replica fragmentation 的 E2E 占比不足 10%，立即淘汰。

## 1. 证据纪律、假设和比较口径

全文使用四种标签：

- `[Observed]`：本仓库已有真实运行或正式分析结果；严格受原协议限制。
- `[Literature]`：论文作者报告；不能当作本机或本模型结果。
- `[Inferred]`：从架构、公开 profiling 与当前资产推导的有界判断。
- `[Hypothesis]`：本轮新提出、尚待实验否定的判断。

### 1.1 四个部署 regime

| Regime | 说明 | 主要限制 |
|---|---|---|
| R1 | 1×5090，1–7B active、权重全驻留 | 小 GEMM、launch、weight bandwidth、batch fragmentation |
| R2 | 1×5090，大总参数 MoE、CPU/NVMe offload | weight movement、cache miss、HBM 容量 |
| R3 | 8×A100，模型全驻留、EP/TP serving | expert compute、A2A、load imbalance、fork-join tail |
| R4 | 8×A100，长上下文/高并发/接近 HBM 上限 | KV–weight–workspace 竞争、admission、paging、P99 |

8×A100 的 40/80GB、PCIe/SXM、NVLink/NVSwitch 和实际 serving backend 尚未确认。任何依赖这些条件的收益都保持条件化。

### 1.2 Amdahl 与净收益

若被优化的**暴露关键路径**占比为 `p`，该段局部加速为 `s`：

\[
S=\frac{1}{(1-p)+p/s},\qquad
G_{gross}=1-\frac{1}{S}.
\]

本文把近似净收益写为：

\[
G_{net}=G_{gross}-O_{decision}-O_{execution}-C_{error/stability}.
\]

所有百分比都是筛选假设；不是测量值。`p` 只算未被 overlap 隐藏且位于 request/token completion DAG 上的部分，不把逻辑 bytes、GPU busy time 或多个重叠阶段重复相加。

统一硬门：

- deletion/oracle E2E <5%：淘汰；
- 5%–10%：最多保留工程/测量价值；
- 典型自然 workload 的 oracle ≥15%，且预期净收益 ≥10%：才允许进入系统实现；
- 最强简单策略捕获 oracle 的 90%–95%：停止复杂算法；
- 预测可用但不改变合法动作，或动作不改变 completion DAG：actionability=0，停止；
- 只在 synthetic skew、关闭 overlap、人工 barrier 或不常见容量压力下成立：淘汰论文主张。

## 2. 最新 prior-art 边界

以下是一手来源直接压缩掉的空间：

- [ExpertPlex](https://arxiv.org/abs/2607.18002) 已用 adaptive persistent kernel 在 tile 粒度调度动态 expert compute，并联合 prefill/decode sharing；普通“deadline-aware tile scheduler”不再新。
- [Gimbal / Coordinated Scheduling](https://arxiv.org/abs/2606.15177) 已联合 frontend request pressure、KV、prefill、expert pressure 与 expert placement；普通“expert-congestion-aware admission”不再新。
- [SwiftEP, NSDI 2026](https://www.usenix.org/conference/nsdi26/presentation/li-xingyi) 已用 buffer fusion/TMA/zero-copy 强化 EP 路径；[FAST, NSDI 2026](https://www.usenix.org/conference/nsdi26/presentation/lei-yiran) 已处理 skew/incast 下的 A2A scheduling；不能靠弱 collective baseline 制造通信空间。
- [XShare](https://arxiv.org/abs/2602.07265)、[Lynx](https://arxiv.org/abs/2411.08982) 和 [Alloc-MoE](https://arxiv.org/abs/2604.08133) 已覆盖 batch-aware expert selection、动态减少 active experts 与 activation budget；普通 adaptive top-k 不再新。
- [PagedWeight](https://arxiv.org/abs/2607.16184)、[FluxMoE](https://arxiv.org/abs/2604.02715) 和 [CrossPool](https://arxiv.org/abs/2606.24506) 已直接处理 KV 与 expert weights 的显存冲突、expert paging/quantization 和 cold-MoE pooling；generic KV–expert allocator 不再新。
- [Mixture-of-Experts Serving](https://arxiv.org/abs/2607.17880)、[Director](https://arxiv.org/abs/2607.08782)、[Fast MoE Inference via Predictive Prefetching and Expert Replication](https://arxiv.org/abs/2605.11537) 与 [HCRMap](https://arxiv.org/abs/2607.11586) 已覆盖 expert 资源分配、迁移、在线 placement 和 pressure-aware replica mapping；“预测热点再复制”不是新问题。
- [RaMP](https://arxiv.org/abs/2604.26039) 已按 runtime expert histogram 选择 MoE megakernel 配置；[FEPLB](https://arxiv.org/abs/2604.19654) 已在分布式 MoE 训练中做细粒度 per-microbatch load rebalancing。BCRD 若继续，必须证明自己的动作是 **固定 replica set 内的 contribution-to-replica assignment + deadline-bounded consolidation**，并在全文/代码级查重中排除同构调度。
- [Capacity-Aware Inference](https://arxiv.org/abs/2503.05066) 已做 overload token drop/reroute；质量预算式 straggler rescue 必须证明不同动作和更强语义。

`[Inferred]` 从这些论文的公开问题定义看，仍可能存在的窄空白是：**给定 replica set 后，token-to-replica dispatch 是否应显式建模 GPU batch service curve、通信位置、fork-join deadline 和 consolidation benefit。** 这不是完整查重结论；若实验 Gate 通过，还必须下载全文和代码做逐动作 collision audit。

## 5. 十四个候选的逐项审计

每个候选均比较 `current / random / threshold / greedy / oracle / proposed`。三场景分别为保守 C、典型 T、高压力 H；`gross/net` 是 `[Hypothesis]` latency reduction 或 SLO-capacity equivalent improvement。

### I1. Batch-Conscious Replica Dispatch（BCRD）

1. **核心矛盾与当前浪费。** least-load/hash 把同一 logical expert 的 rows 分散到多个 exact replicas，降低单队列长度，却制造更多小 GEMM、weight reads、launch 和 top-k fork-join；强 consolidation 相反，会制造 queue/remote-link tail。当前 placement 与 dispatch 通常分别优化，未显式使用非线性 GPU service curve。
2. **核心 insight。** `[Hypothesis]` expert GEMM 总 service time 对 rows 呈次可加/分段凹的 batching economy；因此“最空闲副本”不等于“最早完成请求的副本”。在中高并发自然 route 上，deadline-bounded consolidation 能同时降低总 work 与 P99。
3. **决策变量。** 当前 routed contribution 到 replica `r` 的 assignment `x_{i,r}`；每个 replica/expert 的封批时间 `h_{e,r}`；完整版本才低频决定 replica 数量，最小版固定 placement。
4. **目标与约束。** `max Σ_j 1[C_j≤d_j] - λE - μB_remote`，约束 exact-weight semantics、每 contribution 只执行一次、HBM replica budget、hold≤request slack、queue stability、message conservation。
5. **系统机制。** 观测 rows/queue/deadline/src/dst；查实测 `(expert,rows,dtype)→service` LUT；以“deadline risk + remote cost − marginal batching credit”给候选 replicas 排序；短窗口封批；反馈实际完成时间并只更新 LUT/阈值，异常回 least-load。
6. **Amdahl/净收益。** C：`p=.20,s=1.25`，gross≈4.0%，扣 decision 0.4、extra execution/comm 1.0、误差 0.6，net≈2.0%；T：`.35,1.6`，gross≈13.1%，net≈10.0%；H：`.50,2.2`，gross≈27.3%，net≈22.8%。Oracle 上限先验 15%–30%，最可能净收益 8%–15%。
7. **瓶颈迁移。** `replica fragmentation/launch → consolidated queue/remote A2A → hot-replica HBM/weight bandwidth → attention`；第二层空间是 replica budget，第三层才是 drift adaptation。
8. **5090 快速验证。** 用 OLMoE top-8、LLM-jp top-16 真实 route trace；实测 grouped-GEMM rows 曲线；用 2/4/8 个 virtual replicas 做 trace replay，并以多 CUDA streams 复核代表性 assignment 的局部 service。能验证 batching economy 和 oracle gap，不能声称真实 A2A/P99。
9. **8×A100 价值。** exact replicas、真实 src/dst A2A、并发 GPU queues、top-k join、NVLink/PCIe 与 replica HBM 成本进入同一时间轴；测 SLO capacity、TPOT P99 和 placement×dispatch 交互。
10. **最大风险。** 8 卡根本放不下足够 replicas；真实 rows 已够大，service curve 近线性；remote bytes 抵消 consolidation；least-load 或简单阈值已捕获 oracle。
11. **已有工作区分。** Director/Gimbal/动态 replication 主要决定复制/placement 或 request pressure；HCRMap 已是最接近的 pressure-aware replica mapping。BCRD 只有在以下边界确实未被 HCRMap 等覆盖时才有创新：最小版固定 replica set，研究 per-wave exact replica assignment 的**非线性 batch service、deadline 与 fork-join completion**。若全文查重发现已有同一 action/state/objective，则淘汰。贡献类型：**新模型 + 新在线分派算法 + runtime 闭环**。
12. **强制 baseline。** current=runtime 原生 hash/least-load；random=合法 replica 均匀采样；threshold=`rows<r0` consolidate，否则 least-load；greedy=最小预测完成时间；oracle=未来 arrivals 已知的 MILP/DP；proposed=deadline-bucketed marginal batching credit。若 threshold/greedy 捕获 ≥90% oracle，不做复杂算法。
13. **Reviewer attack 与结论。** 攻击点：只是 placement 的小变体、单卡 replay、复制内存未计、收益只在人工 skew。可修复条件是两模型自然 trace + 8卡 exact accounting + 强 baseline residual。**结论：Top 1，仅获准三重 Gate。**

### I2. BufferLease-MoE：EP workspace 的 deadline-safe 显存借贷

1. **核心矛盾与浪费。** EP backend 为 peak dispatch/combine 预留 staging/workspace，KV、expert cache/replicas 和临时 activation 又各自按峰值预留；生命周期不重叠时仍不能相互使用，降低可承载 batch/KV pages。
2. **核心 insight。** `[Hypothesis]` communication workspace 需求是 layer/phase-bursty 且 reclaim deadline 可预测；把闲置 pages 临时借给 KV 或 expert cache，可在不改变质量的情况下提高 SLO capacity，但必须保证下次 collective 前可无阻塞收回。
3. **变量。** 每 epoch 给 KV、expert/replica、comm workspace、activation 的 page quota；lease expiry；reclaim priority；fallback reserve。
4. **目标。** `max SLO-satisfied throughput`，约束 `M_total≤M`、collective 不因 reclaim stall、KV 不错误驱逐、OOM 概率为 0、P99≤L。
5. **机制。** 采集 buffer lifetime/next-use；page-granular VMM/pool；只借出有确定 reclaim slack 的 pages；低频 marginal-capacity allocator；miss 或 reclaim risk 时保留静态 reserve。
6. **Amdahl/净收益。** C：`p=.15,s=1.3` gross≈3.5%，扣 remap/reclaim/fragmentation 1.5，net≈2%；T：`.30,2` gross≈15%，net≈11%；H：`.50,4` gross≈37.5%，net≈29.5%。Oracle 上限以 extra admitted tokens/KV hit 表示，预计 10%–35%；最可能净 capacity 5%–15%。
7. **迁移。** `HBM reserve waste → reclaim/remap stalls → KV/weight movement → compute/network saturation`；第二层是 quota choice，第三层是 drift-safe control。
8. **5090。** 复用真实模型 KV/activation allocations，注入按真实 EP shape 推导的 workspace lifetime trace，测 page remap/reclaim、fragmentation 和 admission frontier；核心 EP reclaim deadline 仍需多卡确认。
9. **8卡。** 接入真实 DeepEP/可用 backend，观测 collective buffer lifetime、stream ordering、KV capacity 与 SLO；验证不会因 allocator lock/CUDA graph invalidation伤 P99。
10. **风险。** backend 已复用/按需分配 buffer；workspace 占 HBM <5%；VMM/remap 太慢；PagedWeight/FluxMoE 的 weight–KV 管理已吸收大部分收益。
11. **区别。** SwiftEP 优化 buffer 数据路径；PagedWeight/FluxMoE 优化 weight–KV；这里把**通信 workspace 的时间所有权和 reclaim deadline**作为资源。若实际 backend 无静态 reserve，问题消失。贡献：**新资源抽象 + 内存机制 + 在线闭环**。
12. **baseline。** current 静态 peak reserve；random page lending；threshold 低水位 reclaim；greedy largest-idle-pool；offline future-known lease oracle；proposed deadline-safe marginal-capacity lease。simple≥90% oracle则只保留机制。
13. **Red Team。** “只是 allocator 工程”“空间由人为 overprovision 产生”“5090 无法验证”。只有真实 8卡 workspace≥10% HBM且 capacity oracle≥15%可修复。**结论：Top 3，条件保留。**

### I3. Guarded Expert Reuse：带审计回退的 expert 输出复用

1. **矛盾与浪费。** 同一 expert 在 batch/相邻 token 上处理大量相似 hidden states，但每行都完整读取权重并执行 MLP；直接复用可省 compute/HBM/energy，却可能累积质量错误。
2. **insight。** `[Hypothesis]` 在部分 `(layer,expert,phase)` 中，hidden-state 局部簇足够紧，使一个 representative output 加廉价 residual/correction 的误差低于冻结质量预算；机会率应由真实执行分布而不是 prediction accuracy 决定。
3. **变量。** representative/cluster assignment；reuse、residual 或 exact action；审计采样率；cache TTL。
4. **目标。** `max SLO goodput - λE`，约束 document/task quality CI、per-request error budget、cache HBM、audit overhead、fallback rate。
5. **机制。** expert-local embedding/sketch；近邻命中后走 reuse/residual；随机或风险分层 exact audit；误差越界立即清 cache、回 exact；不修改 router/训练。
6. **Amdahl/净收益。** C：`p=.25,s=1.15` gross≈3.3%，审计/lookup/error tax≥3.5，net≤0；T：`.45,1.6` gross≈16.9%，net≈9.9%；H：`.60,2.5` gross≈36%，net≈25%。Oracle 上限 15%–40%，最可能净 0%–12%。
7. **迁移。** `expert GEMM/weight bandwidth → lookup/cache/residual → attention/A2A → quality audit`。
8. **5090。** 两模型真实 hidden/output capture；先算 exact nearest-neighbor/reuse oracle，再实现 GPU hash/lookup 与真实 residual；完整 quality evaluation 可在单卡完成核心证伪。
9. **8卡。** 验证 cache locality、replica consistency、A2A bytes 是否可随 representative 合并、并发 P99 与跨 rank audit。
10. **风险。** 近邻机会率低；误差跨层放大；audit 必须做完整计算而吞掉收益；类似输入的 output 仍差异大；cache 内存和索引比省下的 work 更贵。
11. **区别。** XShare/Alloc-MoE/Lynx 改变 active expert/activation budget；本方案保持 routed expert 身份，复用 expert function evaluation。仍需查重 activation memoization/approximate computing。贡献：**新 observation + 近似机制 + 质量闭环**。
12. **baseline。** exact current；random reuse；distance threshold；greedy nearest representative；future-known error oracle；proposed risk-UCB + audit。threshold≥90% oracle则不用复杂风险模型。
13. **Red Team。** “只是 activation cache”“质量不可恢复”“训练分布特化”。需要两模型、真实任务、long decode 和全开销才能修复。**结论：Top 2，高风险。**

### I4. Critical-Path-Budgeted Expert Return

1. **矛盾/insight。** return bytes 与 codec 税、quality budget 冲突；只有强 overlap 后仍暴露的 return span 有价值。`[Observed]` rank-quality 不对称存在，但 optimized return criticality 未测。
2. **变量/模型。** contribution bit/lane；producer fusion；固定 backend order。目标最小 TPOT CVaR + J/token，约束 quality、one-message、codec tax。
3. **机制。** deletion-DAG oracle → offline lane catalog → fused producer/consumer → fallback BF16。
4. **Amdahl。** C `.05,1.5` gross≈1.7%、net≈0；T `.10,2` gross≈5%、net≈3%；H `.20,3` gross≈13.3%、net≈9%。
5. **迁移。** return A2A → codec/layout → receiver queue/expert compute。
6. **5090/8卡。** 5090只能测 quality/codec，不能测核心 EP criticality；8卡可做 deletion oracle 与真实 collective。
7. **风险/已有工作。** SwiftEP、Comet、CoCoQuant、tile overlap 已压缩 residual；当前 `P1` 文档已判定 `BLOCKED_RESOURCE_NOT_TESTABLE_HERE`。贡献若成立是新测量+执行原语，否则为局部 codec。
8. **baseline/攻击/结论。** current BF16、random lane、static/uniform INT8、greedy per-layer、zero-return oracle、proposed fixed lane。最大攻击是违反 5090 快速验证硬约束且典型净收益<10%。**淘汰本轮主攻；保留为未来 8卡 measurement。**

### I5. Deadline-Aware Expert Coalescing

1. **矛盾/浪费/insight。** 立即执行满足低延迟但产生小 GEMM；等待聚合提高效率却消耗 slack。`[Hypothesis]` deadline 分布异质时可用富余请求的 slack 给同 expert 聚行，同时保护紧急请求。
2. **变量/模型。** per-expert hold time、封批阈值、tile priority；`max SLO throughput`，约束 wait≤slack、starvation=0、memory limit。
3. **机制。** expert μ-queue、deadline buckets、service LUT、超时立即 flush；低开销 catalog lookup。
4. **Amdahl/净收益。** C `.15,1.2` gross≈2.5%、net≈1%；T `.30,1.5` gross≈10%、net≈7%；H `.45,2` gross≈22.5%、net≈17.5%。
5. **迁移。** small GEMM → queue wait → weight bandwidth/A2A。
6. **5090/8卡。** 5090 可跑真实 expert queue/GEMM；8卡增加 A2A 与 join tail。
7. **风险/区别。** ExpertPlex 已做 tile-granular adaptive persistent scheduling，MoE-Gen/EPS-MoE 也覆盖 module batching/kernel choice；剩余只是 deadline feature。
8. **baseline/攻击/结论。** current immediate、random wait、fixed timeout、EDF-greedy、future oracle、proposed deadline bucket。若 fixed timeout≥90% oracle即结束；prior-art collision 已很强。**降级为 I1 的封批子机制，不独立。**

### I6. Route-Set Batch Shaping

1. **矛盾/insight。** 普通 continuous batching按到达/长度组批，可能激活更大的 expert union并分散 rows；route-compatible requests 合批可减少 active experts/提高 locality，但等待与预测错误伤 SLO。
2. **变量/模型。** next-iteration request subset、route-set similarity、max wait；目标 goodput/TPOT，约束 fairness、质量不变、causal signal。
3. **机制。** previous-token/prefill signature 估计；route-set bins；短 horizon composer；错误时 FCFS。
4. **Amdahl。** C `.15,1.2` gross≈2.5%、net≈0.5%；T `.30,1.4` gross≈8.6%、net≈5.6%；H `.45,1.8` gross≈20%、net≈15%。
5. **迁移。** expert union/fragmentation → wait/fairness → attention/KV。
6. **5090/8卡。** 单卡可用真实 route trace重放组批；8卡验证 locality/A2A/DP engine balance。
7. **风险/已有工作。** ExpertFlow 已重排不同 batch 的 tokens，XShare做 in-batch expert sharing，2026 activation-pattern work已做 workload-aware micro-batch grouping；预测准确不等于 E2E action value。
8. **baseline/攻击/结论。** FCFS、random bins、similarity threshold、greedy union、future route oracle、proposed risk-aware composer。simple threshold很可能捕获大部空间，且 novelty 碰撞。**淘汰独立主线。**

### I7. Request-SLO Expert Activation Budget

1. **矛盾/insight。** 固定 top-k 给所有请求同 compute/quality；困难请求需要更多 experts，宽松/紧急请求可少算。把一个请求的 quality/slack budget转为另一个请求的 capacity。
2. **变量/模型。** per-request/token/layer `k`、reroute/drop；目标 SLO goodput，约束 task quality、minimum k、per-class fairness。
3. **机制。** 离线 sensitivity catalog + runtime slack bucket；任何不确定请求回原 top-k。
4. **Amdahl。** C `.20,1.2` gross≈3.3%、error/quality tax后≈0；T `.40,1.5` gross≈13.3%、net≈8.3%；H `.60,2` gross≈30%、net≈20%。
5. **迁移。** expert compute → attention/A2A → quality audit。
6. **5090/8卡。** 单卡能做真实 quality/perf；8卡测 P99/capacity/imbalance。
7. **风险/已有工作。** Alloc-MoE、XShare、Lynx、Capacity-Aware Inference 已直接覆盖 activation budget、batch expert selection 和 drop/reroute；SLO 标签不构成新动作。
8. **baseline/结论。** fixed top-k、random drop、gate threshold、greedy sensitivity、quality oracle、proposed slack catalog。即使有空间，创新性不足。**淘汰。**

### I8. Expert-Congestion Admission and Doomed-Work Shedding

1. **矛盾/insight。** 过载时继续接纳已不可能满足 deadline 的请求，会占用 expert/communication/KV资源并拖累可满足请求；早拒绝提高 SLO capacity但损失完成率。
2. **变量/模型。** admit/defer/reject、request priority、per-engine destination；最大化 weighted completed-under-SLO，约束 fairness/rejection budget。
3. **机制。** queue/KV/expert pressure estimator；deadline feasibility test；safe reservation；错误时保守 admission。
4. **Amdahl。** C `.10,1.2` gross≈1.7%、net≈0.7%；T `.25,1.5` gross≈8.3%、net≈6.3%；H `.40,2` gross≈20%、net≈15%。
5. **迁移。** doomed work → admission queue → underutilization/model routing。
6. **5090/8卡。** 单卡 arrival replay可测 overload；8卡测 engine/expert pressure和实际 capacity。
7. **风险/已有工作。** Gimbal 已把 request/KV/prefill/expert pressure联合，QLM/P/D-Serve 已做 SLO queue/admission/timeout；只在过载丢请求容易虚增指标。
8. **baseline/结论。** accept-all、random reject、queue threshold、EDF feasibility greedy、clairvoyant oracle、proposed expert-aware feasibility。强近邻且典型净<10%。**淘汰。**

### I9. KV–Expert HBM Portfolio

1. **矛盾/insight。** KV pages、expert weights/precision/replicas争同一 HBM；固定 split不能适应 context、并发与route热度。联合边际价值可能提高 SLO capacity。
2. **变量/模型。** KV quota、expert residency/bitwidth、replicas、eviction；最大化 SLO throughput，约束 quality、paging bandwidth、migration stability。
3. **机制。** 秒级 allocator、service/paging LUT、双阈值 hysteresis、fail-safe static split。
4. **Amdahl。** C `.15,1.3` gross≈3.5%、net≈1.5%；T `.35,2` gross≈17.5%、net≈12.5%；H `.60,4` gross≈45%、net≈35%。
5. **迁移。** HBM/OOM → weight/KV movement → compute/network。
6. **5090/8卡。** 单卡 offload+long-context可测真实 capacity；8卡测 distributed KV、replicas和migration。
7. **风险/已有工作。** PagedWeight、FluxMoE、CrossPool已直接处理这一母问题；容量压力可能人为制造。
8. **baseline/结论。** static split、random pages、low-watermark、marginal greedy、future oracle、proposed portfolio control。物理空间大但问题/动作已被覆盖。**淘汰 generic 版；I2 只保留未被覆盖的 workspace lifetime 子问题。**

### I10. Cancellable Speculative MoE

1. **矛盾/insight。** speculative branches并行提高接受吞吐，但 rejected/late-discovered branches的expert工作无价值；应尽早延迟、合并或取消。
2. **变量/模型。** branch admit、expert budget、cancel point、verification order；最大化 accepted tokens/s，约束 exact sampling semantics。
3. **机制。** verifier progress signal、cancelable queues、提交 collective 后不可取消的会计、fallback普通 speculation。
4. **Amdahl。** C `.10,1.3` gross≈2.3%、net≈0.8%；T `.25,1.6` gross≈9.4%、net≈6.4%；H `.40,2` gross≈20%、net≈14%。真实可回收量还需乘 `reject×late×cancellable×critical`。
5. **迁移。** wasted expert work → cancellation/control → verifier/attention。
6. **5090/8卡。** 单卡可测 timeline/cancelability；8卡测 collective提交点和网络浪费。
7. **风险/已有工作。** MoE-Spec、SpecMoE、SP-MoE、MoE-SpAc/EVICT 等近期工作已覆盖 expert budget、prefetch、verification；可取消窗口可能极短。
8. **baseline/结论。** no-cancel、random cancel、acceptance threshold、greedy budget、future acceptance oracle、proposed staged cancel。novelty与净空间均不足。**淘汰。**

### I11. Online Expert Placement and Replication

1. **矛盾/insight。** popularity/skew随 domain 与时间漂移；静态 placement制造hot rank，频繁migration又占网络/HBM并打断graph。
2. **变量/模型。** replica count、placement、migration epoch、reroute；目标 P99/goodput，约束 HBM、migration bytes、稳定性。
3. **机制。** popularity/drift estimator、低频 optimizer、background migration、rollback。
4. **Amdahl。** C `.15,1.3` gross≈3.5%、net≈0.5%；T `.30,1.7` gross≈12.4%、net≈6.4%；H `.50,2.5` gross≈30%、net≈18%。
5. **迁移。** hot rank → migration/replica fragmentation → KV/weight HBM → A2A。
6. **5090/8卡。** 单卡只能 trace replay；8卡可测 migration/graph/A2A，但单 topology泛化弱。
7. **风险/已有工作。** Director、Gimbal、Mixture-of-Experts Serving、动态 replication、HCRMap 等直接覆盖；periodic greedy可能接近oracle。
8. **baseline/结论。** static、random、threshold replication、greedy placement、future zero-migration oracle、proposed online optimizer。即使物理空间大，创新与资源匹配均差。**淘汰；固定 replica 后的 dispatch gap归 I1。**

### I12. Pause-Specific ResumeSet

1. **矛盾/insight。** tool/human pause时保留KV避免重算，但expert working set可能被其他租户驱逐；保留expert减少resume cold-start却占HBM并伤active requests。
2. **变量/模型。** paused request的KV/expert set、TTL/quota、swap/preserve/discard；最小化resume P99并最大化global goodput。
3. **机制。** pause event、last-W route signature、TTL、active-pressure eviction、future audit。
4. **Amdahl。** C `.20,1.5` gross≈6.7%、net≈4.7%；T `.40,2` gross≈20%、net≈15%；H `.60,4` gross≈45%、net≈35%。仅在自然offload/cold regime成立。
5. **迁移。** resume weight fetch → HBM污染/active P99 → KV swap/compute。
6. **5090/8卡。** 5090可人为限制cache并做oracle，但需真实pause trace避免造regime；8卡看模型是否全驻留与租户干扰。
7. **风险/已有工作。** InferCept已做pause KV策略，ELDR/ExpertFlow做expert signature/cache，CrossPool做cold MoE；last-W/static TTL可能接近oracle。
8. **baseline/结论。** discard/preserve、random expert、TTL/last-W、Belady greedy、future oracle、proposed joint retention。若expert独立deletion oracle<15%或last-W≥90% oracle即停。**Rank 4 条件备线，不进Top3。**

### I13. Route-Intensity Power Control

1. **矛盾/insight。** static clock/power为峰值配置；memory-bound/route-light wave可降功耗而不伤SLO，compute-heavy wave需要boost。route可能提供低成本phase signal。
2. **变量/模型。** GPU clock/power cap/stream priority；最小 J/completed-token，约束TPOT P99与thermal stability。
3. **机制。** phase×batch×rows lookup、低频功率档切换、温度反馈、fallback default clock。
4. **上限/净值。** C energy gross≈3%、switch/latency tax后net≈1%；T gross≈10%、net≈6%；H gross≈20%、net≈12%。对应latency Amdahl通常仅<1%/≈6%/≈15%。
5. **迁移。** power waste → DVFS switch/thermal → latency tail。
6. **5090/8卡。** 5090可真实测J/token；A100正式验证多卡同步与board power。
7. **风险/已有工作。** route可能只是phase/batch代理；切频周期慢于wave；能耗收益不改变capacity；本地Energy-SLO只是microbenchmark。
8. **baseline/结论。** max clock、random cap、util threshold、phase×batch greedy、future energy oracle、proposed route residual。若route在phase×batch后增量<5%则停。**降为评价/子机制。**

### I14. Safe Expert Prefetch and Cache

1. **矛盾/insight。** offload下按需加载stall大，提前加载可能错取、挤掉有用expert并浪费PCIe；causal route signal若有足够lead time可隐藏movement。
2. **变量/模型。** prefetch expert、horizon、cache eviction、bandwidth budget；目标TPOT/P99，约束miss、wasted bytes、HBM。
3. **机制。** prefill/early-layer signature或previous-token统计、deadline-awareDMA、miss fallback。
4. **Amdahl。** C `.20,1.5` gross≈6.7%、net≈3%；T `.50,3` gross≈33.3%、net≈22%；H `.80,8` gross≈70%、net≈50%。仅R2/offload有效。
5. **迁移。** weight movement → predictor/wasted DMA → compute/KV capacity。
6. **5090/8卡。** 单卡offload可真实测；8卡增加distributed cache/link contention。
7. **风险/已有工作。** 本地正确cache key/full top-k后working set很快饱和、safe oracle近0；ProMoE、HOBBIT、DuoServe-MoE、ExpertFlow等已覆盖prediction/prefetch。
8. **baseline/结论。** demand、random、LFU/last-W、Belady greedy、future oracle、proposed predictor。当前本地oracle和prior art均不支持重开。**淘汰。**

## 10. Top 3 深入展开

### Top 1：BCRD

#### A. 论文级问题定义

> 在具有 replicated experts 的 continuous-batching MoE serving 中，联合优化 routed contributions 的 replica assignment 与 bounded coalescing，以最大化 SLO-satisfied throughput，同时满足 exact model semantics、deadline、HBM、communication 和 queue-stability 约束。

#### B. 数学模型

集合：请求 `j∈J`，logical experts `e∈E`，其合法 replicas `r∈R_e`，contribution `i=(j,l,k,e)`。

状态变量：

- `a_i`：ready time；`d_j`：request/token deadline；
- `src_i`、`dst_r`：源与副本位置；
- `q_r`：replica queue state；`n_{e,r}`：待封批 rows；
- `T_e(n,h,dtype)`：5090/目标GPU实测service curve；
- `C(src_i,r,b)`：通信/packing cost；
- `m_r`：replica memory；`z_t`：load/drift regime。

决策变量：

- `x_{i,r}∈{0,1}`：contribution分配；
- `h_{e,r}∈[0,Hmax]`：封批/hold；
- 完整版才加入 `y_{e,r}∈{0,1}` replica residency。

请求完成时间由 top-k 与层依赖 DAG 决定：

\[
C_j(x,h)=\operatorname{longestPath}_j
\left(a_i+C(src_i,r)+Q_r+T_e(n_{e,r})\right).
\]

目标：

\[
\max_{x,h}\sum_j w_j\mathbf 1[C_j\le d_j]
-\lambda_E E(x,h)-\lambda_C B_{remote}(x)
-\lambda_O T_{decision}.
\]

约束：

\[
\sum_{r\in R_e}x_{i,r}=1,
\quad h_{e,r}\le \min_{i\in batch} slack_i,
\]

\[
\sum_{e,r}m_e y_{e,r}+M_{KV}+M_{temp}\le M,
\quad \rho_r<1,
\quad semantics=exact.
\]

不确定性来自 future arrivals、service jitter 和route drift。即使 placement固定，该问题也含 unrelated-machine assignment、batching 和 deadline，离线一般是NP-hard；在线不求MILP。

候选算法：

1. 离线把service curve离散为rows buckets；
2. runtime为每个合法replica计算
   `score = predicted_deadline_risk + remote_cost - marginal_batching_credit`；
3. 先按deadline bucket保护紧急contributions，再将有slack的contributions合并；
4. 决策预算超时或LUT失配立即回least-load。

只有实验3证明threshold/greedy未接近oracle，才需要更复杂的primal-dual/rolling-horizon版本。

#### C. 系统闭环

```text
Profiling
  → grouped-GEMM / link / queue service curves
Observation
  → route identity, replica queues, rows, src/dst, deadline
Prediction
  → 只预测当前候选动作的completion；不预测未来route
Decision
  → exact replica assignment + bounded seal time
Execution
  → existing grouped GEMM / EP backend
Feedback
  → actual batch rows, service, TPOT/P99, remote bytes
Correction
  → LUT update / threshold hysteresis / least-load fallback
```

#### D. 三层优化路径

1. **第一层：** 固定replicas，只消除assignment-induced fragmentation；这是最小科学对象。
2. **第二层：** 把remote A2A、top-k sibling completion和封批共同纳入，解决consolidation后的queue/communication迁移。
3. **第三层：** 秒/分钟级调整replica budget与placement，处理drift；只有在I1前两层通过且与Director/Gimbal有清晰增量时加入。

#### E. 最小可发表版本

- 两个不同top-k MoE + 一个serving-scale模型；
- 1×5090证明自然route上的service-curve/assignment oracle；
- 8×A100 exact-weight replicas和真实EP backend；
- current/random/threshold/greedy/oracle/proposed全套；
- exact semantics、TPOT P50/P95/P99、SLO capacity、GPU/HBM/network/decision全会计；
- 明确配置消失区：低并发、无replicas、rows已大时不生效。

#### F. 完整版本

加入replica placement慢控制、load drift、多个SLO class、failure fallback和多topology；但不把scale-out RDMA作为当前必需贡献。

### Top 2：Guarded Expert Reuse

#### A. 论文级问题定义

> 在不修改预训练MoE router的在线推理中，联合决定哪些expert evaluations可被representative/residual近似以及何时审计回退，以最大化SLO goodput/Joule效率，同时满足请求级质量风险和显存约束。

#### B. 数学模型

状态 `s_i=(l,e,h_i,g_i,phase,cluster_state,quality_debt)`；动作 `a_i∈{exact,reuse,residual,audit}`；决策变量为representative、distance threshold、audit rate、TTL。目标：

\[
\max \text{SLO-goodput}-\lambda E-\mu T_{audit}
\]

subject to `Pr(ΔQ_j>ε)≤δ`、cache≤M、fallback bounded。误差分布未知且跨层相关；在线近似为带置信上界的contextual decision，理论保证只有在校准误差UCB有效时成立。

#### C. 闭环

`exact capture → locality/error profiling → UCB risk → reuse/residual → random exact audit → drift test → cache flush/fallback`。

#### D. 三层

1. exact duplicates/identical hidden state（几乎零风险但机会可能为零）；
2. local residual approximation；
3. request-level quality debt与online recalibration。

#### E. 最小可发表版

先证明两模型自然execution中≥20% expert rows存在可用reuse oracle，真实GPU lookup+residual后net≥10%，并在NLL/KL及两个任务上通过paired quality gate。

#### F. 完整版

跨replicas共享representatives、通信去重、per-request audit budget与故障恢复。最大风险是第一层opportunity就为零。

### Top 3：BufferLease-MoE

#### A. 论文级问题定义

> 在显存饱和的MoE serving中，联合管理KV、expert/replica与EP communication workspace的时间化所有权，以最大化SLO-satisfied throughput，同时满足collective reclaim deadline、zero-OOM和P99非退化约束。

#### B. 数学模型

状态 `M_KV(t),M_E(t),M_C(t),M_A(t)`、buffer next-use、arrival/KV growth、expert heat；决策为page allocation `m_k(t)`、lease expiry和reclaim order：

\[
\max \sum_j\mathbf1[C_j\le d_j]
-\lambda P_{reclaim-stall}-\mu Bytes_{paging}
\]

subject to `Σ_k m_k(t)≤M`、`M_C(t_next)≥demand_C`、zero-OOM、quality exact。future buffer/KV demand未知，是online caching + deadline resource allocation；用safe reserve和marginal-value greedy，不用RL。

#### C. 闭环

`lifetime profiling → next-use observation → conservative demand forecast → lease allocation → VMM/pool execution → reclaim/stall feedback → reserve correction`。

#### D. 三层

1. reclaim确定空闲的comm/temp pages；
2.在KV与expert cache/replicas间按marginal SLO capacity分配；
3.在drift下更新reserve与hysteresis。

#### E. 最小可发表版

真实8卡backend中workspace≥10% HBM、静态split造成≥15% capacity oracle；实现page lease且collective P99不退化>2%；胜static/low-watermark/greedy。

#### F. 完整版

加入多模型池、CUDA graph兼容、failure-safe reclaim和不同backend/topology。若backend workspace原本按需且<5% HBM，方向立即死亡。

## 11. 唯一主攻方向：为什么只能选 BCRD

最终唯一主攻 **Batch-Conscious Replica Dispatch（BCRD）**；不是 Top 3 并行推进。当前只授权三个串行 Gate，不授权实现完整 online controller。

1. **优化空间最大且最接近可测。** `[Hypothesis]` 目标 penalty 是 replica assignment 造成的小 GEMM/launch/weight-read/queue fragmentation，典型 `p≈35%`、`s≈1.6` 时 gross≈13.1%、净≈10%；5090 能用真实 MoE route 与真实 grouped-GEMM service curve先行证伪。
2. **不是局部 kernel 优化。** 控制的是 exact-weight replicas 间的 contribution assignment 与 bounded seal time；目标落在 request completion DAG、SLO capacity 与 P99，而不是单个 GEMM 吞吐。
3. **具有明确建模结构。** 状态、合法副本、非线性 service curve、remote cost、deadline、top-k fork-join 与 queue stability 均可显式写入；offline Oracle 和 simple-policy Captured Headroom 可直接判死复杂算法。
4. **质量风险最低。** 最小版只在 identical expert replicas 间选择执行位置，不改 router、不丢 token、不降 precision，保持 exact model semantics；这比 Guarded Reuse 的跨层近似风险更可控。
5. **5090 快速验证价值高。** 单卡不能证明真实 A2A/P99，但能真实测 batching economy、用自然 route 构造 virtual-replica action space，并计算 current→Oracle gap。只要任一前件失败即可停止，信息增益高。
6. **8×A100 能形成新增系统问题。** 多卡首次引入 replica HBM、真实 src/dst、A2A、并发队列、top-k sibling completion 与 remote-vs-local consolidation；这正是单卡 Oracle 需要正式验证的因果链。
7. **最可能收益范围。** `[Hypothesis]` 常见中高并发 cell 为 8%–15% E2E/SLO-capacity；保守 0%–3%，高压 15%–23%。不把文献最大值或单卡 local service reduction当作本机收益。
8. **最大失败风险。** 自然部署没有足够 exact replicas；原生 least-load 已产生大 rows；remote communication抵消 batching；fixed threshold/greedy 捕获≥90% Oracle；或者全文查重发现同一 action/state/objective。

为什么不选另外两项：

- Guarded Expert Reuse 的 compute 上限高，但自然 reuse opportunity 可能为零，且 quality audit 可能等价于重算；失败面比 BCRD 更大。
- BufferLease 的 capacity 上限可能高，但核心 `workspace≥10% HBM` 必须由真实 8卡 backend 验证，5090无法快速决定，且容易退化为 allocator engineering。
- RankLane 已在 `p_return≤20%` 冻结域内被最乐观代数上界淘汰为 actuator 主线；return-path existence 仍可等待 8卡 measurement，但不再占用单卡优先级。

## 12. BCRD 三个 RTX 5090 快速证伪实验

三项严格串行：实验 1 失败不进实验 2；实验 2 失败不进实验 3。所有 5090 正结果只授予 `8×A100 Candidate`，不能声称真实 EP/NCCL/P99 收益。

> 2026-07-29 simulator-correctness 约束：以下是代码/协议修复，不是科学结果。formal 输入必须使用 `route-v3`，显式记录 `document_id`、request/layer/route/dispatch/expert/combine 时间和 legal replica set；同一 request 的 step `t+1` 必须等待 step `t` 最后 combine。assignment、transport-ready、seal、launch、finish 由同一个事件引擎处理；singleton 必须支付完整 hold，deadline cap 必须预留 seal/launch/service 成本。Gate 1 对每个 model/phase/layer 只连续回放一次，hash salt 全 run 固定；actionable mass 只计有共同合法 replica 的 expert work，exposure denominator 必须唯一覆盖完整预注册矩阵。calibration/evaluation 按 document（缺失时 request）全局一次切分，任何交叉均 `INVALID`。

### 实验 1：瓶颈占比验证 — Natural Replica-Fragmentation Census

#### 假设

`[Hypothesis B1]` 在两个真实 MoE 模型的自然 route trace 上，hash/least-load 将同一 logical expert 的 rows 分配到 2/4/8 个合法 replicas 后，相对同 deadline bucket 内的 consolidated execution，额外 expert service、launch 与 weight-read 的 E2E-equivalent exposed penalty 在共同常见 cell 中≥10%，且至少一个 common cell≥15%。

#### 自变量

- virtual replica 数 `R∈{2,4,8}`；
- policy：hash、least-load；
- concurrency/batch proxy：1/4/16/64 requests；
- phase：prefill/decode；
- route regime：自然 trace 主结果，uniform 与 synthetic skew 只作 sensitivity。

#### 控制变量

checkpoint、document split、route seed、top-k、hidden/intermediate、dtype、sequence length、kernel/backend、GPU clock、warmup、rows bucket。所有 assignment 保持每个 contribution 只执行一次、exact expert identity 不变。

#### Workload

- `allenai/OLMoE-1B-7B-0924` top-8；
- `llm-jp/optimal-sparsity-math-d512-E32-k16-920M-A520M` top-16；
- 每模型至少 128 fresh documents；decode-heavy input 128/output 128 与 mixed input 1024/output 128；
- route capture 使用真实 forward；formal service curve 对每个 `(model, layer, expert, rows bucket, dtype)` 做 20 warmups + 200 measured iterations，不得用单个 expert 的 layer-level proxy 代替。

#### 指标

- `T_e(n)` 的次可加收益：`Σ_r T_e(n_r)-T_e(Σ_r n_r)`；
- extra launch count、weight bytes proxy、rows distribution；
- 占完整 model/layer service 的 fragmentation penalty；
- P50/P95/P99、跨 document/seed paired bootstrap CI；
- virtual actionability：至少两个合法 replicas 且 assignment 会改变 rows partition 的 expert-work mass 占比；wave-count rate 只作诊断。

#### 成功阈值

- 两模型共同的自然、常见 `R/concurrency/phase` cell，fragmentation penalty point estimate≥10%、95% LCB>5%；
- 至少一个 common cell 两模型均≥15%；
- actionable natural expert-work mass≥20%；
- 不能只在 `R=8`、synthetic skew 或极小 rows 成立。

#### 淘汰阈值

- 所有 common natural cells `<5%`：永久淘汰 BCRD；
- 5%–10%：最多保留 kernel/measurement，不进入系统算法；
- 只有单模型、单层、synthetic skew 或极端 replica 数正：淘汰论文主张；
- service curve 近线性、合并不降低总 service：淘汰。

#### RTX 5090 实现方式与最小代码

```text
docs/ideas/bcrd/experiments/
  capture_native_routes.py          # 单设备 route-v3 identity 兼容性，非 formal 时序 producer
  benchmark_expert_service_curve.py # 真实 grouped-GEMM rows curve
  census_fragmentation.py           # hash/least-load virtual replicas
  test_identity_conservation.py     # contribution/expert/rows conservation
```

不需要实现多流 controller；代表性 partition 可用多 CUDA streams 复核 local service，但不把 stream timing冒充多 GPU。

#### 结果判定树

```text
route/identity/rows conservation !=100%
  → INVALID，只修测量
all common natural penalty <5% 或 actionable mass<20%
  → KILL BCRD
penalty 5%–10%
  → 降级 measurement/kernel，不进实验2
common ≥10% 且一个 common ≥15%
  → 冻结 trace/service LUT，进入实验2
```

### 实验 2：Oracle 空间验证 — Fixed-Replica Assignment/Batch Oracle

#### 假设

`[Hypothesis B2]` 在实验 1 冻结的自然 trace 与 fixed replica set 上，future-known offline Oracle 联合选择 contribution-to-replica assignment 与 bounded seal time，相对 current hash/least-load 的 E2E-equivalent gross gain在两模型 common cells≥15%，且扣除 calibrated local execution与保守 remote-cost sweep 后仍≥10%。

#### 自变量

- action：replica assignment `x_i,r` 与 seal/hold `h_e,r∈{0,5,10,20,50,100µs}`；
- remote cost：0（乐观）、NVLink-like、PCIe-like 三档，仅作 sensitivity；
- deadline/slack bucket：tight/medium/loose；
- replica count只取实验1通过的冻结 cells。

#### 控制变量

使用实验1原始 trace、service curve、arrival与expert identity；不重新挑 workload。所有 policy 同一 batching/communication cost model；Oracle 可看未来 arrival，只作上界，proposed 不可看未来。

#### Workload

实验1通过的两模型、两 phase、常见 R/concurrency cells；每 cell 5 arrival seeds。正式统计不包含容量校准 seed。

#### 指标

- current→Oracle completion-time/SLO-goodput gap；
- action-flip rate、rows consolidation、remote assignments、queue stability；
- gross saving、decision-free net upper bound；
- request/seed clustered paired bootstrap 5,000 次；
- 配置消失：低并发、rows 已大、remote cost 高时 Oracle 是否归零。

#### 成功阈值

- 两模型 common natural cells Oracle point≥15%、95% LCB>10%；
- 保守计入目标 remote-cost 档后仍≥10%；
- assignment action-flip≥20%，且不是所有最优动作等价；
- 至少一个非 synthetic/high-skew cell通过。

#### 淘汰阈值

- Oracle `<10%`：淘汰 BCRD；
- 只有 zero-remote-cost 或未来无限 hold 才通过：淘汰；
- actionability=0/等价动作：淘汰；
- 只在极端 replica overprovision 成立：淘汰。

#### RTX 5090 实现方式与最小代码

```text
docs/ideas/bcrd/experiments/
  build_fixed_replica_instances.py # frozen trace→assignment instances
  solve_assignment_oracle.py       # 小规模 MILP/DP/枚举 upper bound
  replay_completion_dag.py         # top-k/layer/deadline completion
  test_oracle_legality.py          # future-info只允许 Oracle 使用
```

实现中只对可证明 exchangeable 的 singleton-expert jobs 做 symmetry reduction，repeated experts 保持显式动作，并对每个 active `(replica, expert)` 独立枚举 hold。只有结构化状态空间全部访问才写 `exact=true`；超出预注册上限必须 `UNSOLVED_EXACT_STATE_LIMIT`。大实例可用分窗 exact solve + 可验证 bound；不要用 proposed heuristic 充当 Oracle。

> 当前实现只能 exact replay `single_layer_window`，尚未把 assignment/hold 改变的完成时间传播到后续 layer/decode step。因此 formal Gate 2 无条件返回 `INVALID_REQUEST_DAG_REPLAY_NOT_IMPLEMENTED`。Gate 1 通过后仍必须先实现 full counterfactual request-DAG，不得用单层 finish 冒充 request SLO。

  → KILL BCRD

### 实验 3：简单策略差距验证 — Threshold/Greedy vs BCRD vs Oracle

#### 假设

`[Hypothesis B3]` deadline-bucketed marginal batching credit 相对 current hash/least-load 达到≥10% E2E-equivalent净收益，同时最强 fixed-threshold/greedy 未捕获 Oracle 的90%；若简单策略达到90%–95% Oracle，则复杂 BCRD 算法没有研究价值。

#### 自变量

策略固定为：

1. current hash/least-load；
2. random legal replica；
3. threshold：`rows<r0` consolidate，否则 least-load；
4. greedy：最小预测完成时间；
5. proposed：`deadline risk + remote cost - marginal batching credit`；
6. offline Oracle。

只允许 threshold、deadline bucket 与 decision budget 在 calibration split 上选择；evaluation split冻结。

#### 控制变量

相同 trace、service/link LUT、deadline、replica set、消息/row conservation、decision implementation、warmup与统计。所有策略均使用 exact-weight semantics；不得给 proposed 更强 executor或更多 replicas。

#### Workload

实验2通过的 common cells，另加一个低并发与一个高 remote-cost disappearance cell；两模型各 5 evaluation seeds。自然 route 为主，uniform/skew只作外推边界。

#### 指标

- E2E-equivalent net gain、SLO-goodput、completion P50/P95/P99；
- decision P50/P99、extra remote bytes、queue instability/starvation；
- Captured Headroom：

\[
CH=\frac{M_{simple}-M_{current}}{M_{oracle}-M_{current}};
\]

- proposed 的 Oracle regret 与相对 strongest-simple 增量。

#### 成功阈值

- proposed 相对 current 两模型 common cells净收益≥10%，95% LCB>0；
- proposed 捕获≥70% Oracle；strongest simple `CH<90%`；
- proposed 相对 strongest simple 仍有≥3% E2E-equivalent增量；
- decision+execution tax≤20% gross、P99不恶化>2%、无 starvation/queue instability。

#### 淘汰阈值

- strongest simple `CH≥95%`：采用 simple，淘汰算法与 novelty；
- `90%≤CH<95%`：只保留简单 threshold/greedy 机制，不做 controller；
- proposed 总净收益<10%或相对 simple增量<3%：不作为独立论文；
- 只在 calibration、单模型或高 skew 正：淘汰。

```text

  compare_policies.py            # frozen evaluation replay
  compute_captured_headroom.py   # paired CI/CH/regret/net accounting

```

若实验 3 通过，才实现代表性 multi-stream executor做局部 regression；正式系统贡献仍需 8×A100。

#### 结果判定树

```text
simple CH ≥95%
  → SIMPLE_WINS；停止复杂算法
90%≤simple CH<95%
  → 固定 simple mechanism；取消 BCRD controller
proposed net<10% 或 incremental<3%
  → KILL paper line
CH<90% 且 proposed net≥10%、跨模型
  → 8×A100 CANDIDATE；进入全文/代码 prior-art collision audit
```

### 8×A100 正式转换门

三个 5090 Gate 通过仍不等于 GO。正式实验必须：

- 先确认 A100 型号/拓扑/backend，以及模型在 KV/temp 后仍能容纳至少两份目标 exact experts；
- 使用真实 EP backend、src/dst、replica HBM、queue、top-k join 与 continuous arrivals；
- current/random/threshold/greedy/proposed/oracle 使用相同 replicas 与 executor；
- 报告 TPOT P50/P95/P99、SLO capacity、actual bytes、HBM、decision、energy 与 failure regimes；
- 两个既有模型之外增加一个 serving-scale open MoE；
- 若 8卡 current→Oracle `<10%`、simple `CH≥90%`、replica HBM 不可接受或 remote cost吞掉收益，正式淘汰。

## 13. 最终研究判断

本轮最大的结论不是“又找到一个联合优化器”，而是先清掉三个伪空间：固定 RankLane 在 `p_return≤20%` 的最乐观 actuator 上界仍不足 5%；generic KV–expert allocator 已被 PagedWeight/FluxMoE 等正面覆盖；ordinary deadline-aware tile/defrag 已被 ExpertPlex、AMoE 和 RaMP 等显著压缩。

剩下最值得用一张 5090 快速证伪的结构性问题是：**exact expert replicas 是否把 load balance 与 GPU batch efficiency变成互相冲突的目标，而现有 hash/least-load 是否因此制造可观的 completion-DAG penalty。**

顺序固定：自然 fragmentation 占比 → offline Oracle → simple-policy gap → prior-art collision → 8×A100 formal。任何一步失败都停止，不通过扩大 skew、replica 数、deadline 或更换指标救活。

## 14. 最终停止规则

- 不因实验1失败而换更大replica数、极端skew或synthetic deadline救活；
- 不因实验2失败而设计predictor、RL或online MILP；
- 不因实验3 simple胜出而把算法复杂度包装成创新；
- 不把5090 route replay写成多卡P99结果；
- 不把8卡单节点写成跨节点RDMA或生产结论；
- 不把论文作者报告的up-to收益当作本方向的本机先验；
- 若BCRD淘汰，下一顺序是Guarded Expert Reuse的opportunity/error oracle；它也失败后才测BufferLease workspace share，不并行推进三条线。

## 15. 最终一句话

> 当前唯一值得立即做的不是新的receiver/precision/cache controller，而是先验证：**exact expert replicas上的least-load是否因打碎rows而浪费了足够多的GPU批效率与SLO容量。** 若5090上的真实route + 真实service-curve oracle不给出至少10%–15%的共同自然空间，BCRD当天死亡；若给出，再用simple-gap Gate决定它是一篇系统论文、一个简单工程策略，还是仍应停止。
