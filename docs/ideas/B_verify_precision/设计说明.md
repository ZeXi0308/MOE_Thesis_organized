# 名称

Idea B：Verify, Don't Predict —— MoE 解码期专家精度充分性的闭环影子验证控制器

状态：**CONDITIONAL GO**。固定周期（period≈4）影子验证在 OLMoE 上过全部预注册门槛，是当前唯一"设计动机被真实 GPU 数据直接验证"的正结果，推荐作为论文主线核心机制。

## 1. 背景与问题

MoE 权重/计算精度轴此前的思路是"预测未来脆弱性"：用 prefill 阶段的 router/NLL 特征预测一个请求未来会不会被降级伤得很惨（Quality Isolation 的早期尝试、"Idea F"路线）。这个思路在两轮严格实验中被系统性证伪：

- **Round 2/4 判死**：`run_decode_fragility_strict_gpu.py` 严格协议（prompt 用 full-precision 生成真实 KV cache，decode 阶段才施加近似，标签为逐 step 未来 decode KL，feature group/ridge α 只在 validation 上选）在 LLM-jp 上测试——第二轮曾经冻结的正结果（same-prompt proxy ρ=0.517, CI[0.315,0.673]）迁移到"预测未来 decode harm"任务后，sealed test 上 ρ 全部跨 0（fixed-tail INT4: ρ=-0.103, CI[-0.518,0.373]；drop 50%: ρ=0.044, CI[-0.545,0.583]），validation 上 0.595 的"发现"在 test 上完全消失，是典型 selection noise。判定 **NO-GO**：prefill-only 特征不能预测未来 decode 风险，且不同降级动作（通信量化 vs expert drop）的 fragility 排序本身不一致（Spearman 仅 0.13-0.87），说明"一个请求有一个固定 fragility 标签"这个前提本身不成立。

这次判死直接催生了 Idea B 的核心问题转向：**不再问"能否从早期信号预测未来风险"（已被证伪的更强假设），而是问一个更弱、更可能成立的假设——"decode 内，短 horizon 的已实现（realized）量化风险是否存在自相关持续性？如果存在，一个只依赖自身近期已实现信号的因果反应式控制器，能不能在不预测未来、不跨请求泛化的前提下，用较小的高精度开销把风险控制住？"**

## 2. 核心思想 / 机制主张

核心主张分两层假设（H1 决定性，H2 操作性）：

- **H1（主判据）**：同一文档内，decode 的 lag=1..8 步的已实现 KL 存在自相关持续性（Spearman correlation, document-level block bootstrap）。
- **H2（次判据）**：一个纯因果的"固定周期影子验证 + 阈值升级"控制器——每隔 `period` 步用 BF16/高精度"影子验证"一次当前风险，若验证到的 KL 超过 calibration 标定的分位数阈值 τ，则接下来的窗口升级为高精度，否则继续服务低精度（INT4 weight-only）——能否用较少的高精度步数占比拿到大部分质量保护。

关键设计哲学（与已判死的预测路线的本质区别）：**验证 "精度是否够用"（precision sufficiency），而不是预测 "未来会不会脆弱"**。检索确认 QuantSpec/EAGLE/Medusa 等投机解码验证系列全部验证"draft token 是否会被接受"（token 正确性），从未做"验证一个已生成 token 的精度是否够用"（精度充分性）——这是差异化定位的关键，未发现直接文献碰撞。这个设计还带来一个优雅退化性质：即使 H1 的持续性信号很弱，只要配合周期性重新验证和保守阈值，反应式控制器依然能拿到大部分质量保护（H2 GO），不会像预测器一样在假设失效时直接崩溃——这正是选择"验证"而非"预测"路线的理论期望，并且被真实数据直接验证。

INT4 weight-only（而非 FP8）被选为受测精度，因为 FP8 计算对 expert FFN 的质量伤害已经被 `run_energy_slo_fp8_compute_quality_gate.py` 证实极小（两模型 KL 0.0068-0.009），FP8 档没有值得保护的风险，INT4（对齐 GPTQ/AWQ 式 W4A16 serving）才有足够的真实质量风险和方差使"该不该升级精度"成为一个非空的问题。

## 3. 实验如何设计（模型、指标、基线、预注册门槛、数据隔离）

**模型**：OLMoE-1B-7B-0924、LLM-jp（E32K16），各 32 篇文档（calib=12/test=20），48 decode steps，教师强制（teacher-forced）真实语料续写。

**精度轴与代理**：INT4 weight-only fake-quant（`fake_quant.symmetric_quant_dequant`，逐输出通道对称 RTN，与项目其它实验完全同一套代理，零改动），只 patch `gate_proj/up_proj/down_proj`（OLMoE/Qwen2-MoE 风格）或 `w1/w2/w3`（Mixtral 风格），router 本身不 patch。

**指标**：逐 decode step 的 logit KL（vs 全精度参照）；lag-k Spearman 持续性（document-level block bootstrap 95% CI）；控制器仿真的累计 KL、相对 `always_low` 的降幅、高精度步占比、相对 non-causal oracle 的倍数。

**基线**：`always_low`（全程 INT4）、`no_escalate`（仅周期验证但从不升级）、`oracle`（非因果，已知真实每步风险的上界）、`reactive`（本文因果控制器）。

**预注册门槛（冻结于运行前）**：
- **H1 GO**：任一 lag 的 document-level bootstrap 95% CI 下界 > 0.2。
- **H2 GO**（每个 period 独立判定）：(a) 相对 `always_low` 累计 KL 降幅 ≥50%；(b) 高精度步占比 ≤50%；(c) 相对 non-causal oracle 倍数 ≤2×。

**因果纪律（最容易出静默 bug 的地方）**：记录的 router/gate 特征来自 INT4 权重路径自身（不是 BF16 参照路径）——真实系统只能看到自己的内部状态；同步（same-step）路由特征相关性只作探索性诊断，**明确不参与任何 GO/NO-GO 判定**（因为决定"整个 decode step 用高/低精度"不能引用该 step 自己还没算完的路由输出）；H1/H2 只使用滞后（严格过去）信息。

**数据隔离**：escalate 阈值 τ 只在 calibration 文档（32 篇中前 12 篇）上标定一次（0.75 分位数），直接用于 test（20 篇），不反向调参；OLMoE τ=0.067，LLM-jp τ=0.079（彼此接近但不同，符合"模型有自己的风险尺度"的预期）。

## 4. 代码怎么组织（入口脚本、关键模块、数据流一句话）

**核心入口**：`run_expert_precision_persistence_shadow_verify_p0.py` —— Day-1 决定性实验，一次运行内完成 H1（lag persistence 计算）和 H2（controller 仿真：`always_low`/`no_escalate`/`reactive`/`oracle` 四策略对比），产出 `per_step_samples.csv`（逐 document×step 的原始 KL 轨迹，是后续所有零 GPU 时间深化分析的唯一数据源）、`lag_persistence_results.csv`、`controller_simulation_results.csv`、`same_step_diagnostic_correlations.csv`、`report.md`。

**零新 GPU 时间的深化分析脚本**（全部纯 pandas/numpy 重分析 `per_step_samples.csv`，不重新调用模型）：
- `analyze_idea_b_finegrid_and_threshold_sensitivity.py`：把 period 网格从 {4,8,16} 加细到 {1,2,3,4,6,8,16}，escalate-quantile 从固定 0.75 扫描到 {0.6,0.7,0.75,0.8,0.9}，并对 45%/50%/55% 三档降幅门槛做敏感性分析——显式报告完整网格而非只报最优格，避免多重比较 p-hacking。
- `analyze_adaptive_shadow_verify_controller.py`：AIMD 风格自适应验证周期（安全时窗口加法增长、危险时窗口乘法收缩），在 calibration 上网格搜索超参数（用"均值−标准差"鲁棒评分，非原始均值，避免小样本过拟合），held-out test 上评估——**负结果**：未能改善固定 period=4 的结果。
- `analyze_dual_axis_joint_controller_poc.py`：概念验证——combine 轴（`run_receiver_direct_benefit_controller.py`）和 compute 轴（本 idea）能否共享一个质量-debt 预算联合调度。明确标注为 POC 而非系统结论，因为两轴当前用的是**不可通约的单位**（combine 轴无 KL、compute 轴无排队延迟），构造合成流本身尺度差异达 10-30×——**负结果**：两版贪心分配器（固定时间顺序 / 每轮内代价升序）在两模型 5 个预算档位上全部显著劣于独立分帽。

**辅助/前序脚本**（诊断 prefill→decode 预测路线为何被判死，是本 idea 转向的直接动机）：`run_decode_fragility_strict_gpu.py`（严格 prefill-to-decode 迁移协议）、`analyze_frozen_prefill_proxy_to_decode.py`（把 round 2 冻结的 same-prompt proxy 原样迁移到未来 decode 任务并验证失败）。

**数据流一句话**：真实语料 prompt → 全精度 prefill 建立 KV cache → decode 阶段按策略（`always_low`/INT4 全程 或 影子验证控制器）逐 step 施加 INT4 fake-quant → 记录逐 step KL 轨迹 → 计算 lag 自相关（H1）与控制器仿真累计 KL/高精度占比（H2）→ 后续所有深化分析脚本复用同一份 `per_step_samples.csv` 做零成本重分析。

## 6. 当前结论与边界

**当前结论**：固定 period=4 的影子验证控制器是**当前整个项目里为数不多"设计动机被真实 GPU 数据直接验证"的正结果**——OLMoE 干净 GO（降幅 50.1%，效率优良 oracle 比 1.66×），LLM-jp 技术上 NO-GO 但非常接近（点估计 47.0%，CI 上界 53.4% 已过线）。三个后续深化尝试（自适应周期、真实运行时、双轴联合）都没有改善这个结果，但都提供了诚实、有信息量的边界确认，巩固了"固定周期"作为主机制的地位——**更复杂的机制没有换来真正的提升**。

**明确边界**：
- H1（持续性假设本身）严格判 NO-GO（lag-1 rho 仅 0.18-0.20，未达 0.2 门槛）；但这不等于机制失败——H2（真正回答"信号对系统有没有用"的问题）在 OLMoE 上干净 GO，这正是"验证而非预测"设计哲学的优雅退化：弱持续性对预测器判死刑，对配备安全网的反应式控制器只是效率打折，不是崩溃；
- INT4 weight-only 是 quant-dequant 代理，不含真实低位 tensor core 内核，因此当前只是**质量信号**，不含 wall-clock 证据；42.5%/44.8% 的字节收益是分析性估算，待真实打包内核（如 `torchao`）验证；
- 教师强制（teacher-forced）续写，不是模型自由生成；
- 双轴联合控制器仅是 POC，不建议在没有真实跨轴可通约代价单位之前继续投入；
- **不能**再引用 round 2 的"prefill 预测未来 decode 风险"结论——该路线已被 round 4 严格证伪，是 Idea B 存在的直接前提（先证伪更强假设，再退到更弱、更可能成立的假设）。

**下一步**（`research_report_moe_next_direction_2026-07-21.md` 给出的 GO 门槛）：真实 in-loop 双算/切换开销 + wall-clock，Go 门槛为两模型真实 decode 下 harm reduction 至少 40-50%、端到端 TPOT 或能耗改善至少 8%、验证总开销低于 5%；这条路径**不依赖多 GPU**即可推进，是当前 5 条活候选里除 Energy-SLO 外最值得投入的单卡候选。
