# 名称

Idea A：Rank 长尾结构 + FP8-first Tail-INT4 Pareto（MoE Combine 通信精度分配）

状态：**GO（结构性证据）**。作为论文的 motivation / 基础章证据，不作为系统主贡献。

## 1. 背景与问题

MoE 推理中 expert-parallel（EP）场景下，combine 阶段需要把每个 token 的 top-k 个 expert output 按 gate 权重加权求和后传回：

$$y_t = \sum_{e \in S(t)} g_{t,e} \cdot o_{t,e}$$

已有系统工作（Lina/USENIX ATC'23、DeepEP、MixServe）证明 dispatch/combine 的 all-to-all 通信是 MoE serving 延迟的主要瓶颈之一，但这些工作把 combine 通信当作不可再分的整体来优化调度/重叠，没有利用一个"免费"的结构信号：gate 权重在路由结束、combine 之前就已知，且不同 expert 的 output 是完全独立的传输单元。

Idea A 最初的问题是：**能否按 gate/rank 给不同 (token, expert) 的 combine output 分配不同的通信精度，以省字节而不明显伤质量？** 这是全项目里最早提出的方向之一（选题地图 2026-07-13 前），也是后续 R-layout、PLTB、QuotaEP-H、receiver-aware 等一整条"combine 精度/字节分配"谱系的共同技术根基。

## 2. 核心思想 / 机制主张

核心主张分两层，随实验演进不断收窄：

1. **Rank 长尾结构（C1，最终稳固的核心）**：同一个 token 选中的 top-k 个 expert 里，`contribution = gate × ‖expert_output‖` 按 rank（gate 从大到小排序的位次）呈明显长尾——tail rank（最低 gate）贡献份额远小于 head rank（rank-1）。在三个模型上验证：OLMoE top-8 tail share 4.91%（rank1/tail 比 5.43×），Mixtral-TinyMistral top-2（14656×，因接近 one-hot 不作主证据），LLM-jp top-16（2.05%，9.39×）。
2. **FP8-first, tail-INT4 second（最终的部署主张）**：uniform FP8 本身已经是极强的默认基线——50% byte saving 且 KL/PPL 几乎无损，因此论文**不与 FP8 竞争**，而是问"FP8 之后还能不能继续省"。答案：把 tail rank 从 FP8 继续降到 INT4 可以把 saving 推到 62.5%，PPL 几乎不崩（+0.30，相对 1.4%）；但同样的 saving 如果压在 head rank 或随机 rank 上会导致 PPL 崩溃（+5~7）。因此 rank 不是精调 FP8 的信号，而是"INT4 能不能安全落地"的**必要性判据**：高 gate 的 output 不许动，低 gate 的 output 才可以继续降到 INT4。

机制演进中出现过的两个更复杂的候选（R-layout 固定按 rank 分层、PLTB 按 layer sensitivity 动态调整 rank 预算、gate-threshold/tail-mass 动态 selector）目前的定位是：**gate-threshold/tail-mass 在质量上优于固定 rank（held-out 结果），但 rank 的价值在于运行时零成本（路由结束立即可得，不需要等 expert 算完就知道 ‖o‖）与规整的定长 two-lane kernel 布局**——最终是否保留固定 rank 取决于真实 kernel 的系统收益，而不是纯质量对比。

## 3. 实验如何设计（模型、指标、基线、预注册门槛、数据隔离）

**模型**：主模型 OLMoE-1B-7B-0924（E64K8）；跨模型验证 LLM-jp（`llm-jp/optimal-sparsity-math-d512-E32-k16-920M-A520M`，E32K16）；早期 smoke 用 `jamesdborin/tiny-mixtral`（top-2，仅作补充，不作主证据因近似 one-hot 路由）。

**指标**：
- combine 输出 KL(full-precision softmax‖approx softmax)（主指标，per-token/per-document 聚合）；
- corpus PPL delta；
- 下游任务：MMLU 200 题 zero-shot log-likelihood 准确率；
- byte saving（理论字节，含 scale metadata 的 FP8/MXFP4/NVFP4 wire bytes 计算）；
- （GPU 复核轮）文档级 paired bootstrap 95% CI，5000 次重采样。

**基线/对照策略**：`full`（BF16）、`uniform_fp8`（50% saving 强基线）、`uniform_int4`（75% saving 上界参照）、`rank1_int4` vs `rankk_int4`（matched-byte-budget 头尾对照）、`fp8top{n}_rest_int4`（FP8-first tail-INT4 sweep）、rank 选择对照组（tail / head / odd-random，同 saving 下比较）。

**预注册门槛（2026-07-20 GPU 严格复核）**：
- **Claim 1**（头尾不对称，"决定性证据"）：`rank1_int4` vs `rankk_int4` 改变字节量完全相同，文档级 paired bootstrap 95% CI 下界 > 0 且比值 > 5×才判 GO。
- **Claim 2**（FP8-first tail-INT4 Pareto）：KL 随 saving 单调不降，且在扫描网格最差点相对 `uniform_int4` 的安全边际 ≥5×。

**数据隔离**：早期实验用 WikiText-2 单一 split，后续修正版严格区分 calibration（validation split，offset 0）与 formal test（test split，从未被任何 pilot 触碰的 offset，如 45 篇 `[16:61]`）；GPU 复核轮进一步用**全新 offset=600 的 128 篇文档**，确保与此前 Mac 实验完全不重叠；bootstrap 全部在文档级做 paired 重采样，不做 token 级重采样（避免同文档内 token 相关性夸大显著性）。

## 4. 代码怎么组织（入口脚本、关键模块、数据流一句话）

**共享底层库**（`experiments/shared/`，各脚本头部有 `_ensure_shared_on_path()` bootstrap 自动定位）：`capture_moe.py`（hook 住 Mixtral-style MoE 层的 combine 路径，实现 `patch_mixtral_moe`，支持按 rank/layer/receiver_group 施加不同精度策略或 LUT）、`fake_quant.py`（FP8/INT4/MXFP4/NVFP4 fake quant-dequant 代理）、`policies.py`（把字符串策略名映射成每个 rank 的精度列表）、`modeling.py`/`prompts.py`/`paths.py`（模型加载、语料、输出路径解析）。

**关键入口脚本**（`experiments/`）：
- `run_approx.py` / `run_fp8_tail_int4.py` / `run_fp8_tail_int4_general.py`：核心近似策略扫描（rank/FP8/INT4 组合），产出 `approx_results.csv` / `fp8_tail_int4_results.csv`；`_general` 版本把策略构造参数化为任意 `top_k`，用于跨模型（LLM-jp）复用同一套代码。
- `run_fp8_rank_control.py` / `run_rank_mix.py`：固定 62.5% saving 下的 rank 选择对照（tail/head/odd）与 BF16/FP8/INT4/drop 三档混合。
- `run_layer_sensitivity.py`：逐层敏感度扫描，支撑 PLTB 的"哪些层该保护"决策。
- `run_signal_comparison.py`：held-out 严格版，calibration/test 分离 + bootstrap，比较 rank vs gate-threshold vs tail-mass vs contribution-oracle 四种 selector。
- `run_fp4_format_comparison.py`：把 INT4 fake-quant 代理换成对齐真实硬件的 MXFP4/NVFP4 block-scaled 格式，检验相对排序是否格式无关。
- `lut_optimizer.py`：给定 `delta_profile`（(layer, rank, precision)→KL）和路由频率表，求解 `LUT[layer, receiver_group, rank]→precision` 的 MILP / rank-only / greedy 三种方法。
- `run_lut_evaluation.py`：把求得的 LUT 端到端应用并测真实 KL，检验"单层 delta 可加性假设"（发现 94× 的级联放大，即该假设不成立，此后不再作为主方法）。
- `run_idea_a_rank_lut_gpu_rigorous_verify.py`：**2026-07-20 GPU 严格复核入口**，唯一带真实统计推断（bootstrap CI）的验证脚本，复用与 Mac 阶段完全相同的 `policies.py` 策略，只换硬件（RTX 5090）、换全新文档 offset、加 CI。
- `run_inference_time.py`：本地 wall-clock 计时（仅供 sanity check，非真实多卡通信基准）。
- `run_mmlu_eval.py`：下游任务准确率验证 PPL/KL 退化是否转化为真实任务损失。
- `plot_*.py` / `make_fig1.py`：论文图生成脚本（fig1 rank 长尾对比、fig11/12 FP8 vs INT4 Pareto 等）。

**数据流一句话**：加载模型 → `patch_mixtral_moe` hook 住 combine 前的 expert output → 按策略/LUT 对每个 (layer, rank) 施加 fake-quant → 前向拿到 logits → 与 full-precision baseline 对比算 KL/PPL/MMLU acc → 写 CSV/report.md/figures。

## 6. 当前结论与边界

**当前结论**：Idea A 的根基性主张（rank 长尾结构 + FP8-first tail-INT4 Pareto）在真实 RTX 5090 GPU、全新文档、文档级 bootstrap CI 的严格条件下**完全站得住**，是全项目效应量最大、复现最干净的静态结构性发现（跨 3 模型、跨 INT4/MXFP4/NVFP4 格式一致）。约 62.5% 低比特饱和点可以写进论文基础章。

**明确边界（不做的事）**：
- 不包装成多卡 RDMA P99 系统贡献——现有证据只是单次前向 combine 输出的 KL，不含真实通信延迟、all-to-all kernel、TBT/P99；
- 不做在线自适应——那是 receiver_aware idea 的范畴，Idea A 只提供静态结构证据；
- 不再主张"receiver_group 离线 profile 有效"——该结论已被 confound 剥离撤回，只保留 receiver-side（非 sender-side）信号在 hotspot 场景下有效这一条更窄的结论；
- 不再把 additive-KL MILP 当主方法——单层 delta 到多层组合存在 94× 的级联放大，可加性假设被证伪；
- Mixtral-TinyMistral top-2 的极端倍数（14656×）不作为主证据引用，因其路由接近 one-hot，是特例而非代表性证据。

**在当前 5 条活候选里的定位**：作为 motivation / 基础章证据，优先级低于 Energy-SLO 和 Idea B 的进一步验证；不因"有多 GPU"重启在线自适应或 RDMA 系统化尝试。
