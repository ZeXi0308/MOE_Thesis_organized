# 名称

Quality Debt / Per-request Quality Isolation：跨请求质量公平的 predictor-free 债务调度

状态：**WEAK**。predictor-free debt 调度约 11-12% 改善，方向真实显著但未过预注册 20% 强门槛；定位为第二贡献候选，非主线、非主杀。

## 1. 背景与问题

这条候选最初（2026-07-13）被设计成 Graceful-EP（criticality-aware graceful degradation/QTree-EP）的"第二贡献"：当系统整体做质量降级时，平均质量可能很好，但少数请求可能持续多层受损，需要类似网络公平队列（VTC/DRR）的"降级 credit"机制保护 worst-case。但它的宿主机制 Graceful-EP 已被严格复核判死（温和降级多耗 0.0098 KL 只多省 1.68 个百分点字节；two-lane 字节数反而多耗 15.85%-45.47%），所以 Quality Isolation 原本"没有独立存在的基础"，选题地图里未被独立推进。

2026-07-20 的重新设计把这个逻辑摘出来独立验证：**Quality Isolation 的核心逻辑（"给配额，优先保护最脆弱的请求"）本身不依赖 Graceful-EP 具体是什么机制，只需要任何一个"对不同请求做不均匀质量分配"的宿主策略。** 项目里早已有一个活的、已验证的宿主——`fixed_tail4`/`fixed_tail8` 均匀降级基线（来自 layer_budget 实验）。把 Quality Isolation 挂载在这个基线上，逻辑完全成立，不需要发明新机制。

## 2. 核心思想 / 机制主张

主张分三层，随审计不断收窄：

1. **Oracle 上限（Part A，未受质疑）**：给定固定的全精度配额 M（占文档数 10%-50%），把配额给"KL 最差的 M 个文档"（用测试标签直接选，oracle）相对"随机给 M 个"，在匹配总字节预算下能让 P95 KL 多降 20.7-38.6 个百分点。这证明"有针对性地保护最脆弱请求"这个方向在数学上确有空间。
2. **信号可迁移性（Part B，未受质疑）**：文档级"降级脆弱性"是否是跨降级机制稳定的**内在属性**（与具体用什么降级机制无关，更多取决于文档本身的内容复杂度）？检验发现：任何一个已经跑过的降级机制的 KL，都与其他机制的 KL 高度 Spearman 相关（OLMoE 0.75-0.85，LLM-jp 0.98 左右，全部 p<0.0001）——**这是一种"用已有计算的副产品做决策"的系统思维**：可以把一个已算过的机制的 KL 当作另一个机制的免费诊断信号。
3. **Part C 现实可实现版本（原本声称有效，后被判定当前实现无效）**：用 Part B 里相关性最强的另一个机制的 KL 作为"因果合法"的优先级信号重新分配配额，声称能几乎复现 oracle 效果。**这一 claim 已被 2026-07-20 批判审计判定当前证据无效**（见第 5 节），因为该信号本身需要额外一次完整 forward，且原始实验存在测试集选择泄漏。

**当前唯一可信的、经过重新设计后仍站得住的主张**：不用任何预测/proxy 信号，只用**已实现（realized）的过去降级历史**做跨请求公平调度——`quality_debt` 策略（VTC 风格）：每轮给"累计已实现 harm 最低"的 K 个租户降级（而不是随机或轮转），主动拉平累计 harm，而不是拉平累计次数。这个策略不预测任何东西，只读自己的过去，因此不会继承此前被证伪的预测类假设（见下）。

## 3. 实验如何设计（模型、指标、基线、预注册门槛、数据隔离）

**模型**：OLMoE-1B-7B-0924（top-8, `fixed_tail4`）、LLM-jp（top-16, `fixed_tail8`）；quality-debt fairness 实验用 LLM-jp 的 4 种真实降级动作（`fp8top8_rest_int4`/`rankk_drop_renorm`/`keep12_drop_renorm`/`keep8_drop_renorm`，来自 `decode_fragility_samples.csv`）。

**Part A/B/C 指标**：给定文档数配额 M，token/字节预算匹配下的 P95 KL 降幅（相对 baseline 和 random）；proxy 信号与真实标签的 Spearman 相关系数 + p 值。

**GPU 严格 proxy 验证（第二轮）指标**：Spearman ρ + bootstrap 95% CI（document-level）、双侧 permutation p 值、worst-decile AUROC、recall@10%（能否找回真正最脆弱的请求）、token-quota 匹配下的 P95 KL 降幅。

**quality-debt fairness 预注册门槛（冻结于运行前）**：对每个降级动作，`quality_debt` 判 GO 的条件是——bootstrap 试验中相对 `random` 的 worst-tenant 累计 harm 相对降幅均值 ≥20%，且该降幅的 95% CI 排除 0，且总系统 harm（全部租户求和）相对变化在 `random` 的 ±3% 以内（防止"用少做总降级来买公平性"这种调度 artifact 而非真实公平性收益）。

**基线（quality-debt fairness 四策略对比，每轮相同降级预算 K，谁都不能靠少做降级"赢"）**：`random`（每轮均匀随机选 K 个租户）、`round_robin`（固定轮转窗口，只匹配次数不匹配已实现 harm 幅度）、`static_once`（第 0 轮固定选 K 个租户全程降级，即早期 Part A/C 风格的静态一次性配额）、`quality_debt`（每轮选累计已实现 harm 最低的 K 个租户）。

**GPU 严格 proxy 验证的数据隔离（关键修正）**：原 P0 有三个会夸大结果的问题——①在测试集上选相关性最高的 proxy（selection leakage）；②proxy 使用另一种降级机制的**测试时** KL，需要额外完整 forward，不可部署；③用文档数而非实际 token/byte 成本匹配全精度配额。修正版：每个模型先采 96 篇 WikiText-103 train 文档（此前从未被 Quality Isolation 触碰），严格顺序划分 48 train/16 validation/32 sealed test；所有 feature group 和 ridge α 只按 validation Spearman 选择；选择完成后用 train+validation 64 篇重新拟合再打开 test；LLM-jp 出现弱正结果后，**冻结** `post_prefill_all + α=1`，在全新采集的 offset 96-159 共 64 篇未接触文档上做纯 test-only replication，不重新选特征或超参数。

**quality-debt fairness 数据隔离/合成边界**：多轮到达过程是**合成的**（对 48 篇文档池做带放回的 bootstrap 重采样模拟多轮流），必须明确标注为"这些是真实测量的 harm 值，但多轮到达过程本身是合成的"；同一动作内部独立跑，不跨动作平均（呼应"fragility 是 action-specific"的既有发现）。

## 4. 代码怎么组织（入口脚本、关键模块、数据流一句话）

- `run_per_request_quality_isolation_p0.py`：最早的 P0（Part A oracle 上限 + Part B 信号可迁移性），纯本地 Mac 分析，复用已有 `layer_budget` 实验的 `sample_metrics.csv`，零新 GPU 时间。
- `run_quality_isolation_proxy_gpu_strict.py`：**GPU 严格 proxy 验证主脚本**（第二轮），真实模型采集 arrival-time lexical 特征、早期/完整 prefill router 统计、NLL，加一次 `fixed_tail` 降级 forward 拿标签；`lexical_features`/`route_stats` 等函数被后续 ablation/replication 脚本 import 复用。
- `analyze_quality_isolation_proxy_strict.py`：给严格 GPU 结果加 proxy ablation（`feature_groups`：`arrival_lexical`/`full_router_plus_lexical`/`prefill_nll_only`/`prefill_nll_plus_lexical`/`post_prefill_all` 五组特征）与跨模型迁移检验（`cross_model_transfer`）。
- `evaluate_quality_isolation_frozen_replication.py`：把 exploratory 阶段冻结的 `post_prefill_all` proxy + ridge α，在全新采集、完全未接触的 replication 文档集上做一次性 sealed 验证（不重新选特征/超参数）。
- `run_quality_debt_fairness_p0.py`：**当前唯一被重新设计为独立、predictor-free 的主脚本**，实现 VTC 风格的 `quality_debt` 调度器，与 `random`/`round_robin`/`static_once` 对比，复用已有 `decode_fragility_samples.csv`，零新 GPU 时间；显式声明"不预测任何东西，只读自己的已实现历史"，与已被证伪的预测类假设完全脱钩。
- `run_quality_routing_synergy_check.py`：检验 Quality Isolation 需要的"文档难度"信号能否与 MoE 路由预取需要的"路由可预测性"信号共享——用与 Routing-Predictability P0 完全相同的 45 篇文档，复用其 calibration/test 路由划分，补跑一次 `fixed_tail4` 的 KL。

**数据流一句话**：Part A/B/C 与 fairness 脚本均复用**已有实验的历史输出**（`sample_metrics.csv`/`decode_fragility_samples.csv`）做纯 pandas/numpy 重分析，零新 GPU 时间；只有 GPU 严格 proxy 验证（`run_quality_isolation_proxy_gpu_strict.py`）真正跑新的模型前向——采集特征 → 严格 train/validation/test 划分 → validation 选 feature group/ridge α → train+validation 重新拟合 → sealed test 算 Spearman/AUROC/recall → 冻结后在全新文档上做一次性 replication。

## 6. 当前结论与边界

**当前结论**：Quality Isolation/debt 是一个**真实但效应量不够大**的候选。debt 调度让 worst-tenant 累积 harm 比 random 降低约 11%-12.5%，四个动作全部方向一致、CI 不跨 0，且总系统 harm 几乎不变（代价为零）——这是一个真实的、predictor-free 就能拿到的公平性增益，但没有达到预注册的 20% 门槛，按冻结标准应判 **NO-GO**。这个结果说明 debt 调度机制本身有效，但当前 16 篇 sealed-test 文档 + 12 租户（原始设计）+ 200 轮的规模下，harm 分布本身的长尾程度还不足以让 debt 调度显著超车 `round_robin` 这类强基线。

**明确边界**：
- **不能**再引用"proxy 信号（另一个机制的 KL）可用于现实部署"这一 Part C 原始 claim——存在 selection leakage 与非零成本问题，当前判定无效；
- **不能**把 GPU 第二轮的 ρ=0.517 结论当作"可预测未来 decode 风险"的证据——Round 4 严格协议证明这只是同一输入内的同时相关，不能迁移到预测未来；这也是 Idea B 转向"验证而非预测"的直接动机之一；
- 跨模型 fragility 标签不存在（OLMoE↔LLM-jp 迁移 CI 均跨 0，两模型同批文档的真实 harm 相关性仅 ρ=0.331）——风险更接近 `request × model × action` 的联合函数，不是请求的固定属性；
- 与路由预取信号（"容易预测的路由"）正交，不能共享同一个诊断信号；
- 多轮到达过程目前是合成的（bootstrap 重采样 48 篇文档池），真实请求流的时间相关性/长尾程度可能使 debt 调度器的优势变大或变小。

**在 5 条活候选里的定位**：作为**第二贡献/附属章节**候选（例如作为 receiver-aware 系统的"质量公平控制面"组件引用），不单独立项，不作为主线也不作为主杀。仅在主机制（Idea B 或 Energy-SLO）需要"租户公平"附属证据时引用一句。
