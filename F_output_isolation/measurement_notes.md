# 测量边界与停止审计

正式回放只回答 CPU 输出阶段的筛选问题。没有实际模型生成、input rendering、engine msgpack IPC 或真实网卡路径；不得把本结果改写为完整 GPU LLM 服务论文收益。

一次 profile 的用途是选择修改位置：原生 LogprobsProcessor 的候选 token 解码/对象构造明显重于 JSON 编码，chat logprobs 对象也有成本。profile 带有计时扰动，且最初适配器 GC startup 不完整，所以不引用其延迟数值证明问题或收益。正式测量不启用 profile。

正式计时之前修正两个会产生伪结论的接线问题，完整保留旧输出：

1. 原生 API lifespan 调用 `freeze_gc_heap()`；缺失该行为会把导入/预建对象的 GC 扫描算成原生输出瓶颈。所有正式臂执行相同原生调用。
2. 客户端保存嵌套解析对象以便离线校验，会制造不必要的长期存活对象。正式客户端仍真实解析，但只保留完整原始 SSE 字节，计时后才重解析并哈希。旧组已有时间戳显示 collector→client P99 约82–114 ms，engine→collector约17–18 ms；不能把该旧组尾延迟归因于服务器隔离。

重请求 logprobs 不是 GPU 记录，而是固定 rank-one 的合法合成概率数组。数组为 sampled 项 + top-20，sampled重复项的值相同；原生字典输出20个唯一候选。真实生成 token与prompt来自未缩放GPU轨迹。它们满足API成本形状，但不能代表全部logprob排名/字符串分布，更不能证明GPU生成这些metadata的成本。原GPU轨迹没有请求top-20，所以其速率只证明文本引擎曾达到这一进度，并不是已观测的top-20混合服务速率。它可用于本轮有界CPU筛选；不能据此宣称真实混合服务瓶颈已经成立。

全量语义核验包括每请求文本与逐token logprobs的规范化SHA256、token总数、DONE、finish_reason=length、usage；原生 collector 的合并可能改变 SSE事件个数和重复信封字节数，未改变内容或格式。各方法使用同一规则，不能把事件数相同假设强塞进真实前端。空文本token仍以其原生SSE事件完整解析为可见时间，指标不是屏幕字符首次渲染时间。

时序用同机 perf_counter_ns，对原始批次时间加公共epoch。producer独立进程/物理核，报告实际发送前时间与计划迟到；主指标从实际发布时间计算，planned-ready指标用于发现生产漂移。每条batch按冻结顺序一次供应，不时间压缩、不重复批次、不随机重排。服务器只接收批号，完整EngineCoreOutputs在计时前准备；峰RSS因此包含本不属于生产frontend的回放存储，不可直接作为部署内存需求。

CPU固定为前端1核、client1核、producer1核。整个主机不是独占，其他研究可在其他核/GPU运行；没有终止其他进程或占GPU锁。两个反序重复仅用于快速筛选，不能排除所有host噪声或提供统计显著性。client峰RSS是同一负载driver的累计高水位；server每臂新进程。微小内存差异不解读为方法收益。

C1仅在原生EngineCoreOutput边界恢复，实际CPU配额100µs，不是严格的抢占上界：一个同步单元、原生serializer或GC都可以跨过配额。它不追踪整个HTTP/serializer的每请求CPU债务，也未实现严格字节积压界限。这个最小候选失败后，不以未经验证的更复杂状态机继续包装论文贡献；若成功，才有理由进入真正可恢复对象/序列化与积压控制，而本轮正向主张仍须通过全部门槛。

正式组另有一个必须保留的外部时序失败：formal_medium/03_cost 的producer迟到P99=52.45ms，原始批间隔中位数12.17ms。独立producer被延迟后会改变实际批次突发，故这一次C与B不是公平的时序匹配比较。其完整输出和原始性能数值仍保留、表中加†；不将该次50.13ms主指标解读成候选的因果退化。中压只有第二次C的有效配对，不能支持稳定收益；不再补跑。高压两次候选与基线的时钟P99迟到都小于0.33ms，主结论来自该组未过门槛。

主时钟文字与实现曾有偏差，详细见research_contract最后一节。最终同时审阅原始计划ready→可见和实际producer发布→可见两种口径；高压按计划时钟，B1主指标中位数28.59ms、C为30.17ms，仍退化约5.5%，与实际发布口径结论一致。不能以实际发送时间重设起点掩盖中压的产出时序污染。
