# 研究判决：停止本轮 F 论文探索

**结论（2026-10-08）：停止；不进入第二轮候选，不使用 GPU。** 本轮完成普通文本与 top-20 logprobs 的原生 CPU 输出回放、一个成本配额候选、两种简单配额和正反序重复。候选没有建立超过强简单方案的稳定收益，也未形成足以支持论文的独立方法增量。此结论限于冻结的两条单卡产出轨迹和当前响应类型，不否定其他场景存在输出隔离问题。

**核心证据。** 高压轨迹有160请求、77,824个真实生成token，原速约2,235 token/s；各方法固定单个frontend核，另有独立client/producer核。最强简单基线B1使用上游支持的单条输出配额，轻请求客户端交付P99为 **26.85 / 30.04 ms**；C1按实际输出处理CPU每100µs让出，为 **33.34 / 26.67 ms**。中位数从28.45升至30.01 ms，**退化5.48%**；配对改善为−24.16% / +11.22%，不满足稳定改善20%的立项门槛。按原协议的计划产出时钟并列核算，B1/C为28.59/30.17ms，结论相同。全部响应完成，吞吐差异小于0.01%；候选重请求交付P99中位数增加约4.2%，server CPU从31.65%升至33.61%，峰RSS约1.24GiB，未见饥饿。

中压轨迹36请求、8,448 token，约1,105 token/s。一个候选重复的producer迟到P99达52.45ms，超过原批间隔中位数12.17ms，改变了实际突发结构；完整保留并标记为时序污染，不将其50.13ms尾延迟归罪于候选。另一有效候选重复为8.29ms，对应B1为9.70ms，仅改善14.54%。中压不能作为完整有效配对结论，也不能补救高压未过门槛。未通过追加重复或换负载寻找正收益。

**问题解释与方法判断。** 一次定向剖析把主要工作定位为logprobs token解码/对象构造，JSON序列化不是主要成本。每个真实批次每请求仅产出1 token；C1在已有自然边界保存batch cursor并按CPU时间让出，仍无法抢占单个同步对象处理或GC，也未实现完整路径CPU计费和严格积压界限。当前证据不足以支持继续增加对象/serializer状态机：收益未超过固定配额，额外计时和调度反而增加成本。没有把普通合作式调度包装成论文创新。

**最近邻差异。** [vLLM RFC #57479](https://github.com/vllm-project/vllm/issues/57479) 已讨论无中间对象渲染、分块和有界通道；当前vLLM 0.26.0 (`gffd46bfab`)已自带输出chunk/yield及API startup的GC冻结。F原拟主张应是混合响应中的成本隔离改善完整交付，但本轮没有证明这一独立增量。不能用仅战胜不完整默认接线的结果立项。

**可信范围与成果。** 使用真实OutputProcessor、tokenizer、chat streaming generator、Pydantic serializer与HTTP SSE客户端；所有正式臂的逐请求完整文本/logprobs哈希一致，DONE/usage/token总数通过。原GPU轨迹未请求logprobs，故尚不能证明top-20混合服务的可达产出速率；合成logprobs数值、固定输出长度、缺失原批内返回顺序、共享主机噪声、预开连接和省略engine IPC均已披露。旧诊断暴露的原生GC startup遗漏和客户端校验堆积已统一修正，旧数值不纳入判决。回放吞吐不是完整GPU推理吞吐；CPU阶段未过关，因此按规则保留GPU资源。

交付：`main_results.md`（全臂及副作用）、`README.md`（最小复现）、原型、冻结输入、全部原始记录和源码哈希。**不提供正向论文摘要或“三项贡献”。** 重新立项需要新的真实瓶颈证据、超越固定配额的独立方法，以及随后一次真实GPU闭环；本轮不继续扩展验证。
