# 冻结端点诊断：服务成本与服务顺序

冻结于任何新运行前。目的：旧C1未改变FIFO顺序，且原基线遗漏可实现的有界解码缓存；用同一高压点的两个合法动作分辨“工作成本”与“前驱次序”，不从负候选推断问题不存在。四个端点属于一个最小2×2因果设计，不是寻找参数的扫描。

A=fixed1 FIFO，P=fixed1+当前批稳定light-first；D=fixed1+4096项在线LRU；DP=同缓存+稳定light-first。缓存是RFC已有思想的独立组件适配，**不是#54050或RFC整栈复现，更非新方法**；P为已有静态类别优先原则的实现。所有端点复用同一原生fixed1 handler、tokenizer、GC freeze、API生成器和serializer，不使用C1成本阈值。排序在定时处理路径内完成；缓存从空状态开始，只缓存原生helper的单token不可变字符串，随后原生context correction保持，每次返回新list，不预取后续token。

预算修订（在读任何新结果前）：初稿仅P的ABBA四运行；近邻源码核验发现D为必须有的强简单对照，冻结为 A,P,D,DP,DP,D,P,A 共8运行，唯一high trace。约10分钟CPU运行、整个阶段45–60分钟主动工作，0GPU；不加负载、不调缓存容量/配额/优先级，不因数值不利追加重复。旧16run已见过，均标开发证据；本8run也是动作诊断/探索，非独立论文确认。

模型先验预测：P减少轻流前方重工作，轻server receive→collector等待及交付下降，重流等待增加；D减少重复解码CPU，轻/重批内等待均可能下降；若D后P收益基本消失，说明单位成本优化足够；若仍有清晰P效应，则有残余顺序取舍，但需新证据才能说明比已知分类优先更复杂的在线状态必要。总吞吐受固定source限制可能变化很小，不能据此声称提高可承载容量。post/client与producer只用于排除竞争解释，不把阶段P99相加。

开放环产出：直接使用inputs/high.json现有文件，SHA cb813b551ed43b8aafbfedda87d7f3bba57fbd9cb4e6d993d17d5a63a728a32b；不改变batch时间/大小、arrival、prompt/output IDs、重请求集合或metadata。全部HTTP连接先打开，窗口从逻辑epoch至所有DONE并排空；内容/结束/usage/hash必须一致。所有请求纳入；timeout、失败必须留记录并中止组而不是删去。无有效工作预热，与旧口径一致；首次处理冷成本保留，不能事后剔除。

主指标仍为轻token实际source emit→parsed SSE P99，同时并列原计划ready口径；无产品SLO，不设成功百分比。必要约束为前端1核+client1核+producer1核（2/4/6），不启GPU。报告独立run重复值、light/heavy delivery与gap、完成P99、CPU/RSS、全量吞吐、source误差及尾事件条件分解。前端之外可能重叠，不直接把CPU时间换算成延迟。

完整性与有效性规则：同一source记录batch数、token数和源SHA；top20所有语义跨arm一致。P99 source迟到超过原高压batch间隔中位数53.27ms时，预先标时序失配，保留原数值、不作公平因果结论、不重跑；同时报告max误差避免只看P99。主机非独占，其他研究进程不修改。2次run不足以断言统计显著，方向与物理归因仍必须在两次独立运行中审阅。

当前数据对D有利：合成alternatives来自固定短词表，可能得到近乎全命中；D阳性只支持当前回放可被简单优化，不外推真实top-k命中率。混合GPU速率未知，任何端点收益均仅为CPU输出回放证据。若简单端点已经给出主要取舍且无增量状态依据，收束当前新方法投入；若可控残余大且简单端点无法解释，再另行声明下一阶段，不自动扩展。

执行后措辞澄清（不改变上述冻结实验）：批内处理完成只保证本批所有OutputProcessor调用结束后再取下一批，consumer/HTTP交付可以跨批交错；不表示每一批已在客户端排空。完整响应排空只在全run结束时检查。
