# D10 Fixed-C8 Continuous-Decode 最小成本 Gate

> 冻结时间：2026-08-10 18:39:31 +08:00  
> 状态：`FROZEN_BEFORE_IMPLEMENTATION / NOT_RUN`  
> 模式：快速研究实验；单 RTX 5090；OLMoE BF16 eager；不调整 `C=8`

## 1. 唯一问题与 claim ceiling

在完全相同、预先冻结的 128-request × 16-step continuous-decode roster 上，fixed-C8 expert executor 是否同时满足：

1. **C1 — policy 内稳定性**：两次独立 replay 的 expert raw BF16、route membership 与 final logits 对齐结果零不一致；
2. **C2 — 最小成本 Pareto**：expert GPU time 比 serial-M1 低至少 20%，且 token-step p99 相对 native variable-M 增幅不超过 5%。

当前环境无可调用的官方 vLLM Batch Invariance；因此 C1+C2 即使通过，最高结论也只能是：

`PROVISIONAL_SUPPORT_VS_SERIAL / EXTERNAL_BI_OPEN / NOT_A_SERVING_RESULT`

禁止写“优于 vLLM”“完成四臂 Gate”“serving 加速”或“模型质量不变”。

## 2. 冻结 workload 与 replay contract

- workload：`docs/ideas/bcrd/experiments/configs/workloads/olmoe.formal.json`；128 requests、最多 16 decode steps、max batch 8、greedy。
- 先由 unpatched native producer 生成 immutable roster，封存每个 batch 的 `request_ids / decode_steps / input token / position / admission identity`。
- 三臂按同一 roster 与冻结 token 序列 teacher-force replay；不得按各臂实测耗时重新 admission，也不得因 EOS 提前改变 denominator。
- 每臂使用独立 KV state；跨臂 route/logit/token 差异只作 behavior 诊断，不作为 raw equality Gate，也不称 ground truth。
- 两个计量 repeat 使用同一 roster；固定交错 arm order。每臂先做一次不计量 warmup。

## 3. 三个必跑 arms

| Arm | Expert 执行 |
|---|---|
| `native_variable_m` | 对当前 expert 的全部真实 rows 做一次 `expert(rows)` |
| `serial_m1` | 每个真实 row 独立做一次 `expert(row[None])`，再按原 row identity scatter |
| `fixed_c8` | 每个非空 expert 调用补零到 physical M=8，做一次 `expert(padded)[:M]`，再按原 identity scatter |

- top-k、expert identity、routing weight、row identity、combine 次序不变。
- 当前 max batch 8 且同 token 的 top-k expert 唯一，因此每 expert logical `M<=8`；若违反则 fail closed，不隐式 split 或改 C。
- `fixed_c8` 本轮 immediate flush，不跨 token-step 等待；padding 只报告，不设置事后救活阈值。

## 4. Correctness 与行为诊断

每次 live MoE forward 记录 `(repeat,batch,layer,expert)` 的 logical M、physical M、raw BF16 storage hash、row identity 和 route membership；每个 decode batch 记录 final-logits hash 与 greedy token。

机械检查：

- `fixed_c8` repeat0 vs repeat1：raw hash mismatch = 0；route-membership mismatch = 0；final-logits mismatch = 0。
- roster、request-step、row 与 expert call conservation 全闭合；任何缺项、重复或跨 repeat 身份漂移为 `INVALID`。
- native/serial/C8 跨臂差异只报告 route/logit/greedy 与冻结-token NLL proxy；不要求 C8 等于 M1 或 native。已有证据表明 C8 通常是第三种 invariant output。

## 5. 成本测量

- `expert_gpu_ms`：CUDA Event 包围每层 patched MoE 中全部 expert call 与 scatter；模型调用结束后统一 synchronize，再读取 event，不能用整模型 wall time冒充 expert GPU time。
- `token_step_wall_ms`：相同 roster 下，从 decode call ready 到 logits ready 的 CUDA-synchronized wall time；每个 active request-step 继承所在 batch 的该时延。
- 另外报告：kernel calls、real rows、dummy rows、padding fraction、occupied experts、natural M histogram、whole-model wall time。
- 结果是同栈 GPU mechanism cost，不是 vLLM/SGLang serving TPOT；没有真实 scheduler queue wait，因此不得写真实 serving p99。

## 6. 冻结判定

1. 任一 C8 policy 内 raw/route/final mismatch：`NO_GO_D10_C8_CURRENT_STACK`。
2. C8 correctness 通过，但 `expert_gpu_ms_C8 > 0.80 * expert_gpu_ms_serial_M1`：`NO_GO_D10_HEADLINE_COST`。
3. C8 correctness 通过，但 `p99_C8 > 1.05 * p99_native`：`NO_GO_D10_HEADLINE_COST`。
4. 1–3 全通过：`PROVISIONAL_SUPPORT_VS_SERIAL / EXTERNAL_BI_OPEN`。
5. 只有未来在相同模型 revision、GPU、dtype、workload 上运行真实官方 BI，且 `expert_gpu_ms_C8 <= 0.90 * expert_gpu_ms_BI`，才可升级为 `GO_D10_COST_GATE_BOUNDED`。

同一证据上不改 `C`、deadline、workload、repeat 或阈值救结果。成本失败时 D10 不作 headline，仅保留 D01 fixed-M capsule baseline。

## 7. 完整性与预算

- 运行前封存 config、workload、runner、依赖源文件 SHA256 与环境；输出叶目录必须全新。
- completion-last：原始 ledgers、独立 summary、manifest 全部写完且校验后，最后写 `COMPLETE.json`；缺哨兵即无科学结果。
- 运行前单测必须覆盖：三臂 executor、C8 padding/截断、M>8 fail closed、roster conservation、policy 内比较、门限边界、manifest 完整性。
- GPU 预算：预期 20–35 分钟，45 分钟硬停；出现 foreign GPU PID、OOM、NaN/Inf、roster 漂移立即 `INVALID`。

## 8. 当前最多三个 P1

1. **schedule confound**：各臂自行推进 arrival clock 会改变 active set/M。解除：native roster 先冻结，三臂只 replay。
2. **错误的跨臂等价要求**：C8 不等于 M1/native 并不等于 policy 不稳定。解除：correctness Gate 只比较 C8 policy 内 repeats；跨臂只作 behavior 诊断。
3. **成本指标冒名**：整模型 wall time不能替代 expert GPU time。解除：live MoE hook 内 CUDA Event ledger，并同时单独报告 whole-model wall。

本计划只有上述一个 Gate；Oracle action sweep 是互补的 selective-action diagnostic，不改变本协议阈值。
