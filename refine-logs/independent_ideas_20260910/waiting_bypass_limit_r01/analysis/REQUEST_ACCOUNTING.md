# Mixed 请求的互斥时间分解

仅后处理本轮两个 block 的 6 个正式 mixed raw，共 96 次请求执行；没有新增性能实验。每张表只在同一 block 内比较。

请求编号为原到达顺序 1–16，奇数为 128-token 短输入、偶数为 2048-token 长输入；所有请求固定输出 128 tokens。编号与原始 request_id 的映射保存在 JSON。

`到达→提交 + 提交→首次调度 + 首次调度→首token + 首token→完成 = 完成−到达`。时间单位均为毫秒。
“提交”采用 host 调用 add_request 的开始时刻；“首次调度”采用第一次正 scheduled_tokens 所属 scheduler 调用的开始时刻，实际调度位于该次调用起止区间内。这些时间段不是纯 GPU 算子时间。
越过数按真实首次入场的前缀顺序计数，同一步中的顺序不代表请求之间存在额外毫秒等待。

## 直接读数

- 两个 block 的实际排列一致：FCFS 为原顺序；SPT 把尾部短请求 11、13、15 连续提前；bounded 让 10、12、14 各最多被越过一次，尾段交替为 11、10、13、12、15、14、16。
- SPT 中 10、12、14 分别被越过 3、2、1 次；bounded 中均为 1 次。前 9 条和第 16 条的入场名次没有改变，仍可能出现时延差异。
- 下方差值分解展示等待如何在首 token 前后转移；不能仅凭名次变化把全部时延差异归因于排序。

## 仍缺少哪些解释证据

- 第 11、13、15 条提前首次入场并不等于更早完成；其首 token 后跨度同时变化。分解可以定位代价在哪一阶段，却不能证明由某个 kernel、专家路由或单一干扰来源造成。
- 两个 block 的入场排列一致，但同名次请求和整体时延仍不同；现有数据不能把编译状态、热状态、host 调度抖动、不同输出轨迹或排序开销逐一拆成因果贡献。
- 请求重叠执行，不能把 16 条的各段等待相加当成该 episode 的 GPU 时间或额外计算税。
- 最大一次越过是入场次序约束，不是最大等待时间、跨租户服务公平或生产 SLO 保证；当前只测有限 16 请求 episode。
- 首次调度调用边界是 host 观测点，未提供对应请求在 GPU 开始执行的精确时刻；不得将首次调度到首 token 全部解释成纯 prefill 时间。
