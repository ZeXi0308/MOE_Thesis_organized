# 限制等待请求被越过一次后，短请求收益还剩多少？

2026-09-10，GPU 执行前记录。HEAD 为 `2a37765fe522b1d74609a686f1d327ede7619a50`；
工作区含本线程及其他线程的未跟踪实验文件。已读 `docs/current/README.md`、
`docs/ideas/README.md`、20260908 waiting_order 与 waiting_order_repeat 的结论和数据。
封存结论不变，旧 reverse 原件缺口见其 `ADDENDUM_20260910.md`。

已有三个完整 block 显示 SPT 降低短请求 TTFT，但提高长请求 TTFT 和完成延迟尾部。
旧记录中存在同一等待长请求被三条后来短请求实际先入场越过的情况。
本轮只问：限制这种越过之后，能否保留短请求收益并减少长请求代价？
最弱环节是约束是否真正改变首次入场及完整请求结果，不是预测准确率。

## 一次三臂对照

基线为同一 native scheduler 下的 FCFS 和原短 prompt 优先 SPT。
第三臂在 SPT 选择中限制：每个尚未启动的等待请求最多被一个后来到达请求先入场。
计数按原生 scheduler 返回的实际首次调度顺序更新；仅重排而未入场不计数。
在一次调度可能接纳多个请求时，排序需临时推演越过预算，实际账本仍只由真实执行更新。
同长度稳定保留到达顺序；已启动、阻塞或抢占后请求不进入该动作支持域。
三个臂共同承担读取、排序和越过记账开销。

固定 cap8、prefill token budget1024、memutil0.70、BF16、vLLM0.26.0、单 RTX5090；
模型及 tokenizer 为 OLMoE-1B-7B-0924 revision
`6d84c48581ece794365f2b8e9cfb043c68ade9c5`。
逐字节复用旧 mixed `[128,2048]×8` 和 all_short `16×128` 的真实输入 token IDs，
到达间隔 50ms，固定 128 输出 token，seed20260905。
all_short 是队列排序无动作负控，不作为 mixed 指标可扣除的噪声量。
各臂从排空引擎独立推进 KV、batch、生成与完成，不使用另一策略未来轨迹。

两个 fresh engine 各运行 6 个共同 warmup 和 6 个正式 episode；forward 与 reverse
使用相反正式顺序。共 12 正式与 12 预热，不是旧任务的缺失重复。
新主机上的 arm 相互比较；不将新旧主机差异解释成调度收益。
运行前确认依赖/模型就绪和 GPU 隔离；已有安装下载进程不重复启动。

## 计量与判断

完整请求时间 = host submission lag + 入引擎到首次调度 + 首次调度到首 token + 后续生成跨度。
保留全体与短/长请求的 TTFT、平均 TPOT、完成延迟、逐请求最大 ITL、episode wall、
全部失败/未完成和实际越过次数。参考 SLO 固定 TTFT5s 与平均 TPOT0.2s，不换阈值。
越过次数上界不是等待秒数上界，也不意味着每个请求满足 SLO。

若新规则没有实际触发，只能说运行域没有区分度；若违反计数语义，实验无效。
若两个 block 都保留相对 FCFS 的短 TTFT 降低，且相对 SPT 减少长请求尾部代价，
才称此域存在可控制的公平/延迟权衡。全体完成延迟、wall 与最大 ITL 的任何损害同时报告。
接近波动或变号不写稳定收益；不扫描越过阈值、等待年龄、seed 或第三种选择器。
没有强于普通队列策略的稳定 residual，就停止机制扩展。

证据上限为一个模型/运行域的请求级探索测量；不构成新颖性、专家感知、质量保持、
HTTP 生产服务或多卡 EP 结论。Oracle 未测，三个可执行策略不能称精确 Oracle。
