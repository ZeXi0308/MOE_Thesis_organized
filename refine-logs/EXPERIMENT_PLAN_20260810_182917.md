## 1. 唯一问题

在 batch membership、单次 launch、最终 service finish 与 executor busy interval 不变时，把 whole expert batch 内的 row milestone 暴露给原 top-k join，是否产生 atomic whole-batch completion 无法表达的 exact-Oracle flow headroom？

这是 completion-semantics action-space existence 检验，不是 GPU、自然负载、online policy、EP/NCCL/RDMA 或论文收益证明。CriticalSplit 的封存结果与 formal artifacts 保持不变。

## 2. 冻结对照与新动作

- Baseline exact Oracle：`ATOMIC_WHOLE(queue) + bounded HOLD`。同 batch 所有 rows 在 `start + S(M)` 同时完成。
- Expanded exact Oracle：完整包含 baseline actions，另加 `STREAM_WHOLE(queue, frozen_row_order)`。
- `STREAM_WHOLE` 不拆 queue、不改 membership、只 launch 一次；executor 直到最后 milestone 仍 busy。
- row order 固定为运行前声明的唯一 `request_id ascending` canonical physical order；Oracle 既不选 order，也不能修改 milestone 数值。
- 每 row exactly-once completion；top-k join、`combine_us=1`、successor reveal、future visibility 和 replay 守恒与 baseline 相同。

### 2.1 可执行 producer/consumer contract（解除 physical-legality P0）

- 本 CPU Pilot 只建模**同一 device 上的两个 logical expert executors**；不建模跨 GPU 可见性。
- Producer 是一个 device-resident persistent task executor。某 row 只有在 expert MLP 的最终 activation/cast 完成并写入该 row 独立 global-memory output buffer 后，才用 device-scope release store 置位 `row_ready[row]=1`。
- Consumer 是同一 device-resident task graph 中的 join task；它以 device-scope acquire load 读 `row_ready`，只在同 token 的两个 top-k flags 都到齐后读输出、做 combine 并 release 下层任务。
- Producer 发布一个 row 后继续处理同 whole batch 其余 rows；该 logical executor 在最后 row flag 前不变 idle。CPU milestone 表示 release store 的完成，`h` 显式向该发布/通知收费。
- CUDA 官方 memory model 给出 device-scope release/acquire message passing 合同；Event Tensor 证明 tile completion 与 data-dependent task dependency 可在 persistent megakernel 中成为一等 event。因此该 action 不是不可执行的虚构状态，但它的性能、row-order 可控性和与现有 kernel 集成仍是未验证项。

一手合同依据：[CUDA C++ Memory Model 的 release/acquire message passing](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cuda-cpp-memory-model.html)；[Event Tensor / MLSys 2026](https://openreview.net/forum?id=PJqFhAbUHa)。

## 3. 冻结 8 cells

每 cell 用 `M` 个 aligned-arrival requests，2 replicas，top-k=2，2 layers，1 decode step，loose deadline。所有请求在每层各向两个 replica 产生一个 row，因而 whole queue 恰有 `M` rows。

| 因子 | 冻结值 |
|---|---|
| `M` | `2`, `4` |
| milestone curve | `uniform`, `tail` |
| emission tax `h` | `0`, `2 us` |

- Service curve：`S(1)=10 us, S(2)=14 us, S(4)=20 us`。
- uniform：第 `i` 个 milestone 为 `start + h + S(M)*i/M`。
- tail：第 `i` 个 milestone 为 `start + h + S(M)*sqrt(i/M)`。
- stream final finish 为 `start + h + S(M)`；`h` 计入 total service。Atomic baseline 不支付 stream tax。
- 不增加 deadline、arrival、service 或 Critical/Bulk 因子。

## 4. Exact objective 与完整性

两个 Oracle 都使用相同 lexicographic objective：

`flow -> tardiness -> misses -> launches -> total_service -> deterministic_action_tokens`

每个 Oracle `max_states=500,000`；超限为 `UNSOLVED`，不提高 cap 救结果。必须验证 action replay objective 一致、terminal state 闭合、每个 physical node exactly once、每个 request 完成且 executor 不在 final milestone 前释放。

## 5. 机械判读

- `SUPPORT_ACTION_SPACE`：至少 1/8 cell 中 expanded flow 严格小于 baseline，且其最优 replay 实际使用 `STREAM_WHOLE`。
- `COST_TOLERANT_SIGNAL`：上述条件在至少一个 `h=2` cell 中仍成立；它只是更强的 synthetic signal，不是新 gate。
- `NO_FROZEN_CURVE_SIGNAL`：8/8 无严格 flow improvement，或所有最优轨迹均未用 stream。只削弱这两条冻结 milestone curves。
- `INVALID`：expanded 缺少 baseline action、curve/order 未冻结、future leakage、node/replay/objective 不闭合，或任一 Oracle 未在 cap 内解出。

不使用 post-hoc 阈值，不根据结果改 cells、curve、tax、row order 或 objective。
