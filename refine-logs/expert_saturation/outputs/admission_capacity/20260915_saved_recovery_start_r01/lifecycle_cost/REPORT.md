# cooldown 对照：更短间隔与更高恢复频率的代价

本会话沿用保存语义、请求测量与生命周期职责。主会话已经完成[轻量主分析](../execution_weste_26862/analysis.json)和[生命周期汇总](../execution_weste_26862/lifecycle/REPORT.md)，这些结果直接复用。本次新增：将诊断抢占位置标注到可见输出路径完全吻合的轻量运行，分解累计生成间隔；另外定位三个短服务事件的原生容量原因。没有新GPU运行或增加重复数。

证据为既有NATIVE_SERVING进程内请求结果的MEASUREMENT_ONLY补充，不是新方法GO或性能Oracle。

**结论。** 取消cooldown20后单次停顿更短、恢复更频繁，部分请求的累计中断反而更多。当前证据支持评价延迟—效率取舍，没有提供必须延长服务保护的依据。主表的最大间隔降低9.80%/10.41%，平均完成增加2.04%/1.41%，吞吐−0.50%/+0.12%；并非所有维度一起改善，也不据此自动判失败。

**分解依据与局限。** current使用原保存组diag-on，eager使用本组diagnostic-eager作位置标注。每个轻量格的32/32请求，其 `(call index, 累计输出数, new token IDs)` 全序列均与对应诊断完全一致。诊断抢占发生在累计输出k之后，便标注轻量实际k→k+1输出间隔；若一次间隔跨多次抢占，只计一次。本组没有首输出前抢占，44/90个诊断抢占分别对应44/90个不同输出间隔。

轻量计时**没有直接记录抢占事件**。可见输出吻合支持这种条件标注，不证明隐藏调度、KV或抢占事件完全相同。表中的时间来自当组四个轻量运行，抢占位置来自诊断；它不是对每次轻量抢占原因的直接测量，也不代替完整同前态干预。以`recovery`命名的JSON字段均指这些诊断标注的间隔。旧诊断不提供本表毫秒，不计为新性能重复。

| 轻量配对 | current标注间隔总和 | eager标注间隔总和 | 增量 | 其余生成间隔增量 |
|---|---:|---:|---:|---:|
| 0：current→eager | 57.301549 request-s | 65.146933 request-s | +7.845384 request-s | +6.003270 request-s |
| 1：eager→current | 57.527558 request-s | 64.647385 request-s | +7.119827 request-s | +2.613267 request-s |

每个标注间隔的均值从1.302/1.307 s降到0.724/0.718 s，同时段数44→90；均值的分母随策略改变，不能当作匹配单事件的加速比。跨请求总和在墙钟上重叠，单位为request-seconds，不是episode墙钟或可节省时间。

逐请求采用互斥守恒式：

```text
完成延迟 = TTFT + 诊断标注的生成间隔 + 其余生成间隔 + 最后输出到完成的尾部
```

四格共128请求的时间分解残差均为0。两对TTFT总差分别为+0.051669/−0.111852 request-s、尾部差为0；总完成延迟差为+13.900323/+9.621242 request-s。没有将历史重算、加载、同步时间相加或从结果中扣除。标注间隔包含抢占前后的执行，不能将它全部叫排队；其余生成间隔同样包含batch和必要系统成本，不能全部叫正常decode计算。

两对均有17请求标注间隔总量增加；其中同8请求的最大标注间隔反而降低。例子使用全部配对保留结果，不作为独立显著性或只选赢家：

| 请求（ID后四位） | 第0对：current→eager | 第1对：current→eager | 含义 |
|---|---|---|---|
| 1710 | 最大1.530→0.651 s；累计1.530→1.948 s；段数1→3 | 最大1.535→0.648 s；累计1.535→1.933 s；段数1→3 | 更短单次停顿仍可能伴随更多累计中断 |
| 0799 | 最大2.258→1.960 s；累计4.989→3.926 s；段数3→4 | 最大2.270→1.958 s；累计5.018→3.897 s；段数3→4 | 恢复次数增加也不必然使累计中断恶化 |

混合取舍的8请求为0000001、0000051、0000316、0000480、0001157、0001401、0001710、0002733，完整32请求/配对均在JSON。频率、最大间隔、累计间隔需要分开解释；这不是新增事后SLO，而是解释既有平均完成代价。

**短服务来源的限定补充。** 主生命周期汇总已有58个恢复后再抢占段、0个零输出及0个仅1–2输出段；这些计数不算本会话的新独立证据。新定位是在显式3–8输出诊断分组中的三例，均为target保护解除后，peer KV增长触发的原生容量回退：

| 请求 | 返回的新输出调用 | 随后原生抢占 | 抢占调用开始时free / 自身增量 | 需要增块的peer |
|---|---|---:|---|---|
| 1710 | 663—668，共6 token | 669 | 0 / 0 | 2270、0976各1块 |
| 0133 | 818—820，共3 token | 821 | 0 / 0 | 0507、1856各1块 |
| 2733 | 986—989，共4 token | 990 | 0 / 0 | 0133需1块 |

三个事件均没有强制轮转plan或受保护target，发生了peer分配失败；它们不是主动轮转再次选择了刚恢复的请求。主报告已经验证0133/2733的后续load分别复用3776/3920位置，余下仅重算8/6位置，直接引用而不重复计数。3–8只是列举分组，不把原本为空的0/1–2缺口改阈值包装成正结果。三例也不足以解释全部request-s代价，不能因已付恢复成本直接推出延长保护净正。
