# 提前启动后的恢复生命周期

问题：提前臂是否把启动前等待换成更多短服务、再次抢占或 peer 停顿？

**答案：是，但主要体现为更频繁的有效恢复和停顿重新分配；没有增加零输出恢复。** 新诊断的再次抢占段明显增多、典型服务段更短；统一以恢复 host engine-call 起点计，至首个新输出的中位时间仍约 20 ms。当前两对轻量计时均有同一组 9 个请求的最大间隔和完成时间一起恶化。不能把这些 GPU 状态释放写成全部历史 KV 失去 host 复用。

本报告读取已完成的 [当前主分析](../analysis.json)，直接使用其中逐请求 delta，不重算主结果表。生命周期参考为另一个已完成组的 [旧 diag-on](../../../20260915_repeated_kv_service_r01/analysis/analysis.json)；两组诊断的时延只作描述性参考，不能代替当前轻量配对。原始证据保持只读。

| 生命周期观察 | 旧组 diag-on 参考 | 当前 diagnostic-eager |
|---|---:|---:|
| 抢占后恢复段 / 涉及请求 | 44 / 26 | 90 / 32 |
| 恢复后再次抢占段 | 18 | 58 |
| 零输出 / 仅 1–2 输出后再次抢占 | 0 / 0 | 0 / 0 |
| 再次抢占段的输出数中位数 | 219 | 158.5 |
| 最短五个再次抢占段的输出数 | 3、4、9、13、17 | 3、4、6、15、17 |
| L→S_host_engine_call 中位数 | 1.346 s | 0.690 s |
| S_host_engine_call→F 中位数 | 0.0205 s | 0.0204 s |
| 累计各请求恢复间隔 | 61.956 s | 71.148 s |
| 完成的 store / load jobs | 38 / 43 | 84 / 89 |
| 实测累计 load 字节 | 20,984,102,912 | 43,970,985,984 |
| 执行的历史重算位置 | 3,731 | 4,058 |

L 是上一个返回的新输出，F 是该次恢复后的首个返回新输出；表中统一使用首次恢复 host engine-call 起点。load-submit 是另一个更早边界，保留在原件和原 summary 中，不能与 host-call 起点混用；原口径和修正值见 [计时边界补充](TIMING_BOUNDARY_ADDENDUM.md)。累计请求间隔会跨请求重叠，不是 episode wall 的分解，也不是可节省的墙钟时间。诊断显示单段等待缩短，同时段数增加；它不支持“所有用户停顿总量减少”。最短几段的输出数仍相近，且没有零输出或仅 1–2 输出的段，不能把 58 个再次抢占段统一称为无效恢复。

当前轻量配对的逐请求结果更直接地说明了代价分配：两对均为 23 个请求最大间隔改善、同 9 个请求恶化；这 9 个请求的完成时间也全部恶化。第一对整体完成时间为 12 个请求改善、20 个恶化，第二对为 14 个改善、18 个恶化。九个共同受损请求为 `0000133`、`0000628`、`0001107`、`0002932`、`0003128`、`0003299`、`0003345`、`0003475`、`0003571`（均为 `memory-train-article-` 后缀）。

其中后六个在旧诊断中没有抢占，在当前 eager 诊断中出现抢占；两对轻量结果中，这六个请求的最大间隔分别增加 0.604–0.643 s，完成时间增加 0.664–1.384 s。这是与 peer 停顿转移一致的证据。跨组诊断不能逐个证明当前轻量执行中的具体抢占来源，不能将这项对应关系升级为每个事件的因果归因。

两个最短段明确区分了 GPU 释放和 host 复用损失：

| 请求与短服务段 | 再抢占时 GPU 历史 | 下一次真实恢复 |
|---|---|---|
| `0000133`，step 785 抢占后的恢复产生 3 个新输出，step 821 再次抢占 | 3,784 个已计算位置、237 blocks | accepted load job 207；下一次执行从位置 3,776 开始，仅重算 8 个历史位置，随后产生 210 个输出才再抢占 |
| `0002733`，step 953 抢占后的恢复产生 4 个新输出，step 990 再次抢占 | 3,926 个已计算位置、246 blocks | accepted load job 263；下一次执行从位置 3,920 开始，仅重算 6 个历史位置，随后产生 46 个输出才再抢占 |

因此这两个例子付出了再次加载和少量尾部重算，并未丢失全部 host 历史复用。全组累计 load 字节约翻倍，而历史重算位置仅从旧参考的 3,731 增至 4,058，更符合“恢复频率与传输成本增加”的解释。该观察不证明整个运行中从未发生 host eviction，也不把传输字节直接换算成完整服务损失。

新增证据改变的是代价解释：**提前启动减少单段等待，却扩大了轮转范围，并让一部分原本连续执行的请求承担新的停顿；当前短段仍保留有效输出和 host 历史复用。** 它没有提供延长保护窗口或更换 victim 排序的依据。完整服务收益和是否接受这种权衡由当前轻量主分析及主研究会话决定。
