# LTR-style counter/quantum on selected-offload backend

`CPU_INTERFACE_READY / GPU_UNRUN`. Honest arm name: **LTR-style counter/quantum on G selected-offload backend**. It is neither the existing recompute adapter nor full LTR: it omits LTR's predictor and CPU-SWAP path and deliberately keeps G's one-target/one-victim native-save action space.

Executable seam: call `LTRCounters.begin_schedule(live_ids)` before each native scheduling decision; among priority `-1` requests, select the earliest-arriving `PREEMPTED` recovery request, preserving the caller's queue order on equal arrival. If current free blocks suffice, prioritize it without eviction. Otherwise choose the same `most_output` victim from the shared eligible set, again preserving caller order on equal output, and pass the pair through the existing prepare → one victim decode/store → commit/preempt → async load path. Request ID is used only for state lookup and identity tracking. Call `after_schedule(actual num_scheduled_tokens)` after the native result. Pending-load scheduler calls spend no quantum; prefill/recompute/decode calls actually assigned to the boosted request each spend one. Keep the target prioritized for exactly that source-defined quantum, independent of whether a new output has appeared. Current `output_tokens` is a legal past/present victim-ranking input; future output is excluded.

The shared backend must retain: pinned `OffloadingConnector` qualification; one active staged action; `PREEMPTED` target and a distinct, lower-priority running pure-decode victim that will not finish in prepare; the fixed `most_output` mapping among individually full-history-funding victims; unchanged request/block ownership across prepare/commit; registered selected store; next-step commit; no in-flight victim load; exact single forced preemption; required store flush; safe target reservation while the active boost owns it; and actual scheduling/transfer/peer-cost accounting. These constraints define legal execution and a common one-victim action space, rather than the LTR trigger.

The LTR-style arm must not retain G's longest-absence target rank, `min_absence_steps`, global swap cooldown, `min_residency_steps`, progress/near-EOS threshold, `max_absences`, or “free pool can resume” as a no-action rule: each can suppress a counter-triggered action. It also cannot bind exclusivity/peer holding to first new output, whether that output arrives before or after quantum exhaustion. Backend serialization and load-owned block safety remain, while `recovery_guard` may reserve capacity only during the active boost; once load is ready, service duration is controlled by actual selected-call quantum. Mixed-prefill, unrelated blocked-load and concurrent-recovery states may stay fail-closed, but must be logged as `boosted_but_backend_censored` without resetting the counter. The adapter orders the active target ahead of ordinary FCFS work while boosted, then removes that override when its quantum expires.

Semantic checks in `ltr_style_selected.py` fix four boundaries: an async-load step does not consume quantum; two actual selected calls exhaust a two-call quantum even when the first returns output only after the first call; sufficient free capacity removes the eviction but not the waiting-priority action; and adversarial ID renaming leaves tied target/victim queue positions unchanged. Retaining G cooldown/absence/victim gates would turn an eligible LTR step into `noop`; binding tenure to first output would shorten or extend a fixed quantum. Multiple sub-capacity victims are not combined because that would reintroduce the old planner's wider action space.

Already covered: official-source counter transitions and fixed `200/10`, CPU begin/after identity, and the old d6 recompute boost-off/on runs. Uncovered: calibration of `200/10` in G's natural domain, a combined native adapter, OffloadingConnector lifecycle qualification for this arm, and same-budget request-level results. The minimum implementation is one mutually exclusive private adapter that replaces only G's target trigger/service-release logic with this seam; stacking either existing wrapper remains invalid.
