# KV 可行性接纳：长上下文域三臂对照（执行前冻结）

2026-09-08。承接 [`20260908_kv_pressure_probe_r01/REPORT.md`](../20260908_kv_pressure_probe_r01/REPORT.md)
定位的运行域。冻结时本实验 GPU 执行数为 0。本文件在见到任何新 GPU 数据前写定，
不得在结果产出后修改；需修改则另立新日期文件，两者均保留。

## 研究问题

> 在 KV 成为绑定约束的长上下文域，一条**只用 KV 预留算术、不用任何延迟信号**的接纳规则，
> 能否同时避免容量越界并超过最好的已测静态 cap？

最弱环节是：可行性保证要求按**最终**足迹预留，这在请求生命早期必然低用 KV。
该保守性是否吃掉它相对静态 cap 的全部优势，是本轮唯一要测的事。

## 为什么这次值得测（前三轮不值得）

前三轮全部运行在 `max_model_len=256`、54,622 个 step 零抢占、KV 利用率约 12% 的域内：
**没有稀缺资源**，接纳上限只能调 batch 宽度。本轮域已由实测确认存在硬约束，
且在正反序两次重复中一致：

| 域 | cap | repeat0 | repeat1 | goodput (r0 / r1) |
|---|---:|---|---|---:|
| short(128) | 32 | COMPLETE 32/32 | COMPLETE 32/32 | 2.4364 / 2.4234 |
| short(128) | 16 | COMPLETE 32/32 | COMPLETE 32/32 | 0.7663 / 0.8112 |
| long(3072) | 16 | COMPLETE 32/32 | COMPLETE 32/32 | 0.5582 / 0.5634 |
| **long(3072)** | **32** | **CAPACITY_BOUNDARY_STOP 0/32** | **CAPACITY_BOUNDARY_STOP 0/32** | **0 / 0** |

实测 KV 区域 15.00 GiB = 122,848 tokens；32 × 4096 = 131,072 tokens，**超出 6.7%**。
专家权重占参数 93.1%（12.00 GiB），闲置专家常驻 10.50 GiB = KV 的 70.0%。

因此这是本仓库第一次有一个**可行性边界要守**，而不只是一个宽度要调。

## 规则（无训练参数，无延迟信号）

```text
admit next queued request iff
    reserved_tokens(running) + footprint(candidate) <= kv_capacity_tokens * (1 - margin)
footprint(r) = prompt_tokens(r) + output_tokens
```

- `kv_capacity_tokens` 由 `num_gpu_blocks × block_size` 从引擎**读取**，不估算。
- 只用候选自身 prompt 长度（提交时已知）、本次运行固定输出长度、当前 running 集合。
  **不使用**任何 ITL/TPOT/TTFT/未来到达/未来 route/结果信息；测试逐字段断言此点。
- 按最终足迹预留 ⇒ 被接纳的请求**总能跑到完成而无需驱逐**。这是静态 cap 与延迟反馈
  都给不出的保证，也是本规则的全部主张来源。

`margin = 0.05` 在见到结果前固定。该值下规则推出的长域安全 cap 为 **28**：

| n | 预留 tokens | usable = 116,705 | |
|---:|---:|---|---|
| 16 | 65,536 | FITS | 已测可行 |
| **28** | **114,688** | **FITS** | **规则选择** |
| 29 | 118,784 | EXCEEDS | |
| 32 | 131,072 | EXCEEDS | 已测越界 |

短域规则推出 cap 32（与已测最优一致），故短域预期无动作。

## 三臂 + 一个消融

同一引擎配置、同一输入身份、同一到达序列，每臂独立推进自身 KV/route/batch/completion。

| arm | 说明 | 已知/预期 |
|---|---|---|
| `static32` | 已测越界 | 0/32 完成 |
| `static16` | 已测可行，最好已测静态点 | 32/32，goodput ≈0.558–0.563 |
| `static28` | **消融**：规则算出的 cap，静态给定 | 分离"选对数字"与"在线决策" |
| `kvfeas` | 在线 KV 预留规则 | 需自行发现 ≤28 |

`static28` 是本设计的关键：若 `kvfeas` 与 `static28` 无差异，则贡献只是
**一个可从引擎状态算出的容量公式**，不是在线调度机制。二者必须同时报告。

长域为主，短域跑 `static32` 与 `kvfeas` 作为**负控**（预期规则不干预、不损失）。
正反序两个全新引擎重复。长域 4 臂 + 短域 2 臂 = 6 episode/引擎，共 12 个。

## 冻结预测

| # | 预测 | 证伪条件 |
|---|---|---|
| V1 | `kvfeas` 长域完成 32/32，无 `CAPACITY_BOUNDARY_STOP` | 越界 → 预留算术或容量读取有误，先修测量 |
| V2 | `kvfeas` 长域 goodput 高于 `static16`（两次重复一致同向） | 不高或变号 → 保守预留吃掉了并发优势 |
| V3 | `kvfeas` 与 `static28` 差异在噪声内 | 差异显著 → 需解释在线决策的额外来源，不得直接归功 |
| V4 | 短域 `kvfeas` 不劣于 `static32`（负控） | 劣化 → 规则在无约束域产生了净损失 |

**V2 是唯一的收益主张，V3 是它的novelty过滤器。** 若 V1、V2 成立但 V3 显示无差异，
本轮结论只能是"容量公式有效"，不能写成"在线接纳机制成立"。

## 停止与解释规则

- V1 失败：判 `MEASUREMENT_INVALID`，只修容量读取或预留算术，不解释收益。
- V2 失败：KV 可行性接纳在本域 `CONDITIONAL_NO_GO`。**不调 margin、不换文本、
  不加延迟信号抢救。** 记录保守预留的代价量级，转向"预留能否随实际用量收紧"这一
  新问题（需新的存在性证据）。
- V3 显示 `kvfeas` ≈ `static28`：降级为容量公式贡献，明确写"不构成在线机制"。
- 任何指标变号或接近噪声：先做受控重复，不先编机制解释。
- `CAPACITY_BOUNDARY_STOP` 的 episode **绝不可用其截断吞吐与完整运行比较**；
  它按 0 goodput 计入，并单列标注。

## 会计

```text
episode 服务时间 = 同一 host 时钟终点 − 原点
  含排队、prefill、decode、KV 预留计算、接纳决策与循环开销，不重复累加
goodput = 同时满足 TTFT 与平均 TPOT 的已完成请求数 / 服务时间
```

预留计算与决策成本全部落在分母内。`static` 臂不运行决策代码，因此同时充当
决策开销的对照。未完成与失败请求保留，不得成为 SLO pass。

SLO 沿用继承实验的 5 s / 0.2 s 参考值（长输出 1024 tokens 下 TPOT 中位数为
13.57–13.68 ms，远低于阈值，故 goodput 差异主要由完成数与时长驱动）。
**不因结果调整 SLO。**

## 证据上限

单模型、单卡、32 条真实 WikiText 文档、128/3072 prompt × 1024 output、
单一 steady 到达、每格两次重复。不涉及 EP/多卡、第二模型、生产服务、任务质量、
变长输出、自然 EOS。**未测 U/C 专家信号增量**，仍 `UNRUN`；本轮不含专家感知贡献。

专家驻留税是本域约束的**结构性成因**（已实测），但本轮**不实现任何专家 paging**，
也不主张 paging 收益。
