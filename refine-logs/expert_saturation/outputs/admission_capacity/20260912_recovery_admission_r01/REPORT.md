# 同 KV 池恢复准入对照

**结果：直接关闭完整历史可容纳检查没有减少长暂停，反而引发反复重算，并在两次配对中降低完整请求吞吐。** 四项均完成，128/128 请求，按原定顺序保留全部数据。证据为 `NATIVE_SERVING` 的单模型、单 GPU、in-process 请求测量；当前研究问题仍 `OPEN`。

## 同资源对照结果

同一 RTX 5090、OLMoE-1B-7B-0924 固定 revision、BF16、vLLM0.26.0、32 篇 WikiText 输入，各 3072 输入/1024 输出、50ms 到达间隔、cap32、1024 token budget。实际 KV 均为 **16,089,350,144 bytes / 7,671 可用块**。每项新进程、新引擎，统一三项预热并保留 warmup raw。

只改变原生 `scheduler_reserve_full_isl`：`full=True`，`chunk=False`。各策略真实独立推进请求、KV、路由和生成序列。

相对同轮 full，chunk 的吞吐分别 **−6.89% / −4.74%**，墙时 **+7.40% / +4.98%**，平均完成延迟 **+7.83% / +5.68%**，最大 ITL 增加 **1.384 / 1.294 秒**。这是同 cohort 两次反序配对的描述性结果，不是生产尾延迟或总体显著性估计。

## 为什么提前恢复反而更慢

两臂在首次抢占之前有相同的实际调度 token/计算位置路径；首次动作差异在第 **807** 步。

chunk 允许受害请求立即按 993-token chunk 恢复：已重算位置依次达到 993、1986、2979。第 **810** 步，剩余 802 token 需要新增 **50 块**，但其他 decode 已把空闲块消耗到 **41 块**。原生 FCFS 再次抢占同一请求，丢弃刚恢复的 KV。

两轮都发生 **68 次未产生新输出便再次抢占**，加上两次最初抢占共 70 次。两个受害请求被重复丢弃的部分恢复位置分别为 55,608 和 60,634，合计 **116,242**，准确等于两臂额外重算量：

`123,927 − 7,685 = 116,242`。

执行工作守恒也闭合：full 为 `138,725 = 98,304 新 prefill + 32,736 新 decode + 7,685 重算`；chunk 为 `254,967 = 98,304 + 32,736 + 123,927`。上述位置数是实际执行区间计数，不是 GPU 时间。调用跨度、排队与记录开销已包含在请求时钟中，不能再次相加或全部归为纯 GPU 重算成本。

原始事件、首次失败的块数、各受害者重试分布及源码位置见 [recovery_cause.json](analysis/recovery_cause.json)。该文件另记了一项与旧运行的源码定位核查：首轮 full 复现了此前低预算运行的全部 1,348 步实际调度位置/KV 池状态及 32 条输出序列。此项由恢复路径分析单独核验，不属于本轮四臂指标审计的覆盖范围。

## 结论边界与唯一下一步

- **已否定的机制假说：** 在该运行域中，仅关闭完整历史检查就能通过提前恢复降低暂停并保住吞吐。原生 full 是这两个配置中更强的基线。
- **成本模型更新：** 当前 chunk 能放下不等于恢复过程能持续推进。其他请求的后续 KV 增长会使已支付的部分重算成本再次丢失；模型需要表达恢复期间的资源保障。
- **没有否定：** 同预算下改善请求进度的整个问题、保留 KV 的暂缓动作、完成余量保护、其他恢复顺序或新的运行域。当前没有跨策略 Oracle/上界，也没有同预算方法 GO。
- **输出与测量范围：** 两次配对均有 31/32 条完整输出序列一致，同一非受害请求在第 855 个输出 token 首次不同；同策略两轮序列一致。本实验是原生自由生成对照，不声称位级输出一致或质量已验证。四项均逐 token 回传，无插值。时延包含采集，未单独剥离重试增加带来的主机记录成本。
- **运行隔离证据：** 每项有初始化前、测量前和测量后三点 GPU 进程快照，未连续监测全程外部进程。
- **唯一下一步：** 在同一问题内检验“保留已算 KV、在耗尽前保住一个请求完成所需余量”的最小动作，再与原生 full 同池比较。该动作尚未实现/实测；不能把本次反例当作其正结果，也不继续扫描关闭检查后的阈值。
