# Completion transfer and narrow-tail path

这是本次八格 raw 的最小路径补充，复算程序为 `tail_paths.py`，逐请求数据为 `tail_paths.json`。不读取历史实验，不启动新实验。

B 延后了它前四次驱逐、原本在 A 中最早完成的请求。按到达次序 0/1/2/3：cohort0 是 0003733/0003820/0003941/0004015；cohort1 是 0008366/0008446/0008542/0008901（共同 ID 前缀 memory-train-article- 省略）。四配对的完成名次均从 A 的 1/2/3/4 变为 B 的 23/9/25/13；完成 step 从 1025/1029/1032/1035 变为 1102/1062/1108/1069。各位置 B−A 的完成时长差，在四配对内分别落于 1409.649–1491.862、726.071–813.649、1258.272–1347.415、688.374–775.217 ms。区间仅压缩展示四个配对观察值，不是跨 cohort 请求配对或噪声界。

A/B 最后两名请求相同：cohort0 为 0007877/0008125，cohort1 为 0011810/0012079。它们的完成 step 从 1244/1256 前移至 1150/1161；第 31 名请求 host completion 提前 250.546–351.123 ms，第 32 名提前 254.717–355.337 ms。A 的 repeated least-progress 早期交换集中反复驱逐这两个低输出请求，B 把早期轮转分散到高输出请求，最终两个尾请求此前已产生更多输出。

进入 width=2 尾段时，四配对的这两个请求已经产生的输出数都从 A 的 937/925 变为 B 的 1016/1005；这是原生 output_tokens_before，非重算位置。也就是说 79/80 个真实输出被移到了之前较宽的批次中执行，支撑了“尾部工作集中程度改变”的路径解释。

这 87/8 次 width=2 执行确实都属于各 cohort 相同的最后两个请求。A 为 1158–1244，B 为 1143–1150。少 79 次占纯 decode 总少 104 次的 76.0%，是最大的次数缩减桶；width=4 另从 46 降为 7，width=3 则从 3 增为 21，说明也存在其它批宽搬移。该表按完整 engine.step 的 host 时长归类，不等价于纯 GPU 时间，也不能把某桶减少当成可独立相加的因果收益或硬上界；其它阶段与重算增量共同决定最终 wall。它足以解释为何观察到总吞吐稍增、平均完成却变差：最早一批被延后，末尾两个请求更接近其余请求完成，窄批收尾减少。

唯一下一最小可证伪环节建议：用一个完整 in-loop 的“仅首次交换改为 B，其后恢复 A”诊断臂，保留同 KV、到达与恢复规则并让后续状态独立演进，与冻结 A/B 在同 cohort/block 配对；不复用任一臂的未来动作或 route。问题只问“836 的单次 victim 改变是否已足以缩短两个尾请求的 width=2 收尾”。若单次改变已产生相近尾段压缩，则重复 most_output 的额外高输出驱逐可能非必要；若没有，则尾段改善依赖持续排序或后续轨迹，不能归因于第一次交换。仍同时计完整请求均值、wall、最长暂停与全量重算，不把窄批次数下降单独判 GO。本建议未实现、未运行。
