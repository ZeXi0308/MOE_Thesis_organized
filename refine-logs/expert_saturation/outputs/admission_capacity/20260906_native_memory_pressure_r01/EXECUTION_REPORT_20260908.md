# 自然长上下文容量实验：decode 增长可重复耗尽 KV 池

2026-09-08；HEAD `2a37765fe522b1d74609a686f1d327ede7619a50`，分支 `agent/publish-current-moe-code`，继承现有未提交准入实验代码。原 [REPORT.md](REPORT.md) 与 [ADDENDUM.md](ADDENDUM.md) 保留当时 GPU 未运行和连接阻塞的历史。本报告记录本次真实执行，不修改旧报告或原始数据。

**研究问题已回答：在当前全驻留 BF16 OLMoE / RTX 5090 上，合法长上下文会造成真实 KV 容量约束，而且边界出现在全部 prefill 完成后的 decode 增长阶段。** 两次长输入 cap32 都耗尽 KV 块并触发保护终止；两次长输入 cap16 均完成 32 条请求。本轮是容量运行域的测量结果，不是专家感知调度方法收益。

## 问题、设计与证据范围

已读 `docs/current/README.md`、`docs/ideas/README.md`、准入实验 README、[最新短文本配对结论](../20260908_capture_ladder_paired_repeat_r01/REPORT.md) 及本目录 [冻结方案](DECISIONS.md)。继承事实是短文本档位替换没有稳定超过静态基线的收益，专家感知方法尚未成立。本轮唯一最弱链路是自然长上下文能否暴露实际容量约束，不再重跑短文本反馈。

输入为源顺序选择的 32 篇真实 WikiText-103 train 文章，同文短前缀 128 tokens、长前缀 3072 tokens，两臂都固定生成 1024 tokens；长臂总长度 4096 合法。没有重复文本填充、缩小专家缓存、量化、offload 或修改路由。到达为每 50ms 一条的合成 steady 序列。文章身份、输入与准备记录见 [输入说明](inputs_preparation/README.md)。八次重复执行的是这 32 篇文章，不是 256 篇独立文档。

严格执行既有八项顺序：short16 / long16 / short32 / long32，再完整反序。每项使用新进程、共同 engine32、context4096、token budget1024、显存预算0.90、chunked prefill、FCFS、关闭 prefix cache、同步 in-process 捕获；模型 revision `6d84c48581ece794365f2b8e9cfb043c68ade9c5`，vLLM0.26.0 / PyTorch2.11.0+cu130 / CUDA13.0。0.90 是此实验原先冻结的共同配置，不是看本次结果后调整的值。

每进程共同 warmup 为短输入32条 cap16、短输入32条 cap32、长输入2条 cap2，各生成16 tokens。warmup 未消费完整压力 episode。已有 decode 继续推进，cap 只控制接纳；首次原生抢占请求被钩子截住，在释放 KV 前停止整个 episode，随后退出进程。失败调度步没有执行 GPU forward。

完整 episode 分母为同一 host 时钟的终点减到达原点，包含排队、prefill、decode、采集与调度循环成本，不再叠加局部时长。参考 SLO 仍为 TTFT5s / 请求平均 TPOT200ms，仅作辅助；没有套用短文本 9ms 阈值。表中 TPOT 是各请求平均 TPOT 的中位数，不是逐 token 间隔保证。

## 边界定位：已接纳之后的 KV 增长

两次 long32 均在 **attempt809（从零计数）** 发生相同边界。该次调度开始前有32条 running、0条 waiting，32条均已进入 decode，computed tokens 范围为3783–3878。KV 池已有7675个块占用、仅2个空闲；本次调度继续分配2块后，某条 computed3792 的请求再申请下一 token 时分配失败，空闲块归零。

随后原生调度器尝试抢占另一条 computed3783、已有237块的请求。保护钩子记录该事件，未调用原 `_preempt_request`，未释放其 KV，也未执行失败调度步的 GPU forward。原生 caller 在调用钩子之前已经从 running 列表移除了 victim，所以 after 快照中的31条不能解释成一种成功的降并发策略。

两次停止时刻为16.39847 / 16.51773秒；各请求只生成712–807/1024 tokens，没有任何完整请求。捕获 wrapper 因 episode 终止把它们标为 `failed`，应理解为64条受保护中断的轨迹，不是64个独立模型故障。JSON 中保留全部部分指标，但完成数0对应的截断吞吐不能用来计算相对 cap16 的“加速”。

这个定位支持具体因果边界：初始 prefill 能进入池，不代表后续 decode 的 KV 增长仍有容量。它没有测量允许原生抢占/重算继续执行后的完整请求代价，也没有证明专家负载造成了这次耗尽。

## 会计、留存与执行检查

## 最强简单基线与下一实验

当前长输入唯一已测且能完整完成的静态基线是 cap16；cap32提供容量边界证据。KV随生成增长、耗尽后抢占是已有通用问题：[PagedAttention §4.5](https://arxiv.org/html/2309.06180#S4.SS5) 描述了相关机制，[vLLM0.26官方文档](https://docs.vllm.ai/en/v0.26.0/configuration/optimization/#preemption) 也说明重算的端到端成本及降低并发的处理方式。[WiSP §3.3–3.5](https://arxiv.org/html/2606.21868v1#S3.SS3) 已研究专家/KV共享预算与准入边界。这些来源支持先建立普通 KV 基线的判断，本次全驻留容量现象本身不能作为 MoE 新颖性。

**唯一下一最小实验：用实测 KV 池计算保守安全静态 cap，再与 cap16 做两次相反顺序的完整请求对照。** 每个新引擎先核实块大小/布局、可用块和所需最大长度，计算 `safe_cap = min(engine_limit, floor(usable_blocks / 每请求完整长度所需块数))`，冻结计算规则而不是看完成指标选 cap。继续复用同一长输入、1024输出、到达、显存预算和共同预热，四项均独立推进状态并完整回传；只有实际 safe_cap>16 才有该对照空间。

当前所有请求都具有相同的3072输入和已声明1024输出上限，最大长度预留在这个运行域会退化为一个常数cap。先测这项最强简单策略，无需实现动态预算控制器或专家预测器。若安全cap仍触发边界，先定位块会计/动作资格问题；若它覆盖完成收益且无其它已测 residual，就停止此域的复杂准入方法搜索。只在真实异质长度或新的专家侧可执行动作留下普通基线无法解释的净收益时，重新评价方法空间。
