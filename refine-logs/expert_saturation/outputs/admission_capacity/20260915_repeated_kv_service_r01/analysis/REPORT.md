**只改变保存行为。** 两臂共同使用同一两阶段 most_output、相同等待/cooldown/victim 规则和恢复至新输出的保护。准备阶段选中 victim 后它继续解码一次；下一步重新核验并抢占、优先恢复原 target。off 禁止 measurement 期间所有 native store，GPU KV 释放后凭请求输出历史重算。on 只允许该 victim 的准备步骤保存，范围为 `16*floor(computed_at_prepare/16)` 已物化位置对应的实际完整 GPU 块；不保存尚未生成的下一位置或半块尾部。native 增量保存可只补缺块；没有 job 不被当作命中证据。加载/缓存失效/eviction 由原生后端处理，未覆盖部分重算；pending store 必须经原生 flush 才能复用 GPU 块。

**同预算与完整成本。** 固定 GPU KV 13,960,740,864 B、6656 个可用 16-token 块；OLMoE-1B-7B-0924 revision 6d84c48581ece794365f2b8e9cfb043c68ade9c5，vLLM 0.26 及原环境直接复用。两臂 `offload_prompt_only=False`，测量前清除 warmup connector 状态。267 份快照中，实际 CPU KV 始终为一个 16 GiB pinned storage，load/store 的两个引用按同一底层内存计一次。父 cgroup 上限184 GiB、swap为0；不是额外给 on 分配内存。

**四时间点与有效服务。** L 是最后新输出；E 是第一次观测到历史 KV 可获足够块（直接空闲或固定 most_output victim 能提供，另扣其它受保护请求的未分配余量）；它不包含目标优先级、cooldown、准备批增长等全部执行条件，不能叫“此刻应当立即调度”。保留每段实际 load dispatch、首次重执行调用和 F（下一新输出）；内部调度从不重置 L。详细区间与实例见 [TIMING.md](TIMING.md)。统一采用承载首次加载或重执行的 engine-call 入口作 S_call，Σ(S_call−L)/Σ(F−L) 为 off 92.45%、on 94.96%。E→S_call 累计等待为61.829/57.481 request-s；S_call→F为5.157/3.124 request-s。另保留真实load提交时间，不把host入口当GPU开始；on一处E快照落在同一调用内部，产生−1.040ms边界偏移，未解释成负等待。新增字段结果见 [analysis-call-boundary.json](analysis-call-boundary.json)。44段/臂均完成恢复并产生新输出；多个请求区间之和只能叫 request-seconds，不是 episode 墙钟。

off 有一段重执行3888个位置后只输出2 token再丢弃GPU状态，下一恢复重执行3890；on消除了本轨迹中的0/1–2输出段，但仍有一次3-token再抢占。该 on 请求随后真实加载并复用3872位置，余下仅重执行19，最终又输出204 token完成。因此 GPU 释放与内部工作永久丢失分别记账，既不宣称保证足量服务，也不把已保存前缀说成全部浪费。

受损请求的后续定向定位见 [PEER_COST.md](PEER_COST.md)：两对同样8个max-gap受损请求中，6个是连续调用变长、1个为原冷恢复、1个是3输出后的原生容量再抢占。最后一例自身增长0块，但4个peer需要新块、实际空闲仅1块；不将它误归给主动轮转或把全部8例统称恢复饥饿。只读复用原六格，不增加重复数或改变主表结论。

**边界和唯一下一步。** 证据为 NATIVE_SERVING 的同步进程内请求测量，只有单模型、32个封闭同长度请求、强制1024输出、一个KV压力点、两对性能重复；未测自然EOS、持续到达、第二模型、客户端传输或更小host预算。每对完整输出26/32相同，其余6个请求均在动作后首次不同；策略独立演进真实batch/KV/token轨迹，未证明隐藏KV数值一致或回答质量。无新的Oracle/全局上界，也无窗口控制器收益结论。

本轮没有机制执行失败；父cgroup峰值不可读是测量边界。保存作为该运行域的强基线保留。唯一下一GPU实验固定 save=on、most_output/victim/host/GPU 后端，只比较 min_absence_steps=30 与0，保持 min_steps_between_swaps=20、min_residency_steps=30及全部原生可执行性检查。依据是诊断on真实selector有62次因absence门槛停下、592次因cooldown停下；这只是门槛调用数，不是可消除的墙钟，也不推断改门槛后的未来状态。比较将沿各自真实轨迹运行，区分额外absence延迟是否仍有摊销价值；不扫描阈值、不同时改cooldown、不把E直接视作可调度。记录完整输出停顿、其它请求代价与调用/传输/再抢占。若提前启动改善完整请求权衡，推进启动时机；若失败源于恢复期间增长/状态再失效，才返回资源可持续性。本轮不再追加GPU或窗口控制器。
