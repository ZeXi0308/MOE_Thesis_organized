# 保存实验的受损请求：一次定向生命周期定位

新增证据来自已完成六格的只读复用，不是新 GPU 运行或额外重复。保存作为当前运行域强基线的主结论不变。本次只回答：两对性能重复中同样 8 个请求的最大新输出间隔增加，是否都由恢复饥饿造成？答案是否定的。

计时仍为同步引擎返回新 token 的 host 观测时间，不是客户端收到。下表比较各请求**各自的最大间隔**；不同臂的最大值可能来自不同调用，不能把差值当作单次保存的纯传输税。

| 受损请求（ID 后四位） | 观测到的代价 | 第 0 对 gap 增量 | 第 1 对 gap 增量 |
|---|---|---:|---:|
| 2932、3128、3299、3345、3475、3571 | 连续输出调用间隔增加；对应诊断中两臂均无自身抢占 | 每个 +7.005 ms | 每个 +0.571 ms |
| 3640 | 两臂均为 call298→333、输出202→203的原冷恢复 | +7.846 ms | +28.632 ms |
| 0799 | 输出轨迹改变后的再次抢占，on 最大间隔为 call987→1108 | +126.293 ms | +217.662 ms |

六个持续解码请求的 on 最大间隔都在 call329→330，与首次保存后的 commit/flush 阶段重合；off 最大间隔分别在 call663→664、1084→1085。这里只定位共同执行阶段，未隔离 D2H、同步、计算或系统噪声的贡献。这六个请求和 3640 在两对中均完成更早。3640 的首次恢复没有已保存前缀可加载：首次 prepare 保存的是被替换的 0000001 的状态，不能将它视作对 3640 的暖恢复。

0799 的 on 最大间隔为 2.276445 / 2.351724 s，off 为 2.150152 / 2.134063 s。它的完成延迟在第 0 对减少 661.940 ms、第 1 对增加 217.570 ms；不能由 max-gap 单指标推出全部服务量都更差。两臂最大间隔的输出位置也不同：off 是836→837，on 是820→821，属于各策略独立演进的真实结果，不是同一前态的局部因果分叉。

**再次抢占的具体资源原因。** 在 diag-on 中，0799 经 step983 强制切换恢复，在 call985、986、987 返回3个新 token；step986 已观察到首个新输出并解除 target 保护。step988 的轮转 selector 为 cooldown/noop，没有强制 victim/target。此时实际只空闲1块，0799 自身下一次解码不需要新增块，但2932、3475、0480、2038分别需要1块。2932先消耗唯一空闲块，3475申请失败；原生容量抢占选中0799并释放244块。这解释的是首次输出之后的 peer KV 增长与原生 victim 后果，不是目标自身增长或主动轮转再次选中它。

这次 GPU 状态释放并未丢掉全部历史价值：0799 下一恢复实际复用已保存的3872位置，只剩19位置重执行，随后输出204 token完成。保存降低了恢复内部成本，仍可能留下再次进入恢复队列的服务停顿。该实例证明“产生首个 token”不是持续服务的充分条件，**没有证明延长保护一定净正**；保护会转移其他请求的等待，尚无同前态干预数据。

这段诊断的四时间点为 L=19.948349 s、E=19.968877 s、S_call=22.388558 s、F=22.458461 s；真实 load dispatch 为22.395470 s。E 是通过固定 victim 可筹措资源的首次观测，直接空闲足够要到22.242506 s，不能据 E 宣称无需代价即可提前2.42秒。S_call 是承载加载的 host 引擎调用入口，不是 GPU 执行开始。此处诊断区间不与上表性能毫秒合并；完整原字段见 [analysis-call-boundary.json](analysis-call-boundary.json) 的 diag-on、request0799、preempt_step988。

对齐检查覆盖全部请求：每个性能臂的32/32请求与同臂诊断具有完全相同的 `(engine call, 累计输出数, 新 token IDs)` 序列。诊断事件通过与 `engine_steps.returned_s` 完全相等的时间戳连接，并核验该调用实际返回的请求ID；性能事件直接记录调用号。所有事件时间与请求 token 时间逐项一致，输出数1—1024连续。该吻合支持用诊断解释观测路径，不证明隐藏 KV 数值一致，也不将诊断毫秒混入性能表。


[peer_cost.json](peer_cost.json) 保留每对全部32请求的间隔端点、完成差值及诊断对齐结果；[peer_resource_988.json](peer_resource_988.json) 保留988资源事件和来源定位。前者加入逐事件时间/计数核验后复算与原输出逐字一致。所有输入仍是 [原 readback](../execution_weste_26862/readback/results)；无原件修改、无额外计时实验。

本会话交接给主会话的决策增量：当前保存基线的受损代价至少有三类，不能用“8个请求受损”统称恢复饥饿。唯一下一实验仍由 [CURRENT_EXPERIMENT](../../../../CURRENT_EXPERIMENT.json) 的原执行方完成 save-on、cooldown20/0 对照。若提前启动改善完整请求权衡且没有不可接受的 peer 代价，继续收敛启动规则；若恢复等待减少但增加搬运、短服务再抢占或 peer 停顿抵消收益，再由主会话选择资源可持续性问题。此定位不追加保护窗口、victim规则或独立GPU组。
