# 下一动作选择：提前启动的净价值

唯一新增问题：保存已开启后，固定全局交换冷却是否仍有必要，提前启动会增加哪些实际成本？这是科学筛选，不是新GPU结果。

复用已在新diag-off/on验证的结构模型及原共同前态。每个候选独立推进KV、队列、输出计数；只将全局cooldown20改为0，保留absence30、residency30、most_output、原target顺序、首新输出保护和1024计算预算。未注入真实未来完成通知；输入中的1024为本组配置上限，不是预测自然EOS。不使用请求ID或事后step选择干预，ID只沿用基线身份/相同tie规则。

| 结构量 | 当前save-on | 无全局cooldown |
|---|---:|---:|
| 引擎调用数 | 1312 | 1270 |
| 平均完成step | 1167.125 | 1177.15625 |
| 轮转 | 38 | 84 |
| 加载 | 43 | 89 |
| 加载位置 | 160096 | 335472 |
| 重执行位置 | 3731 | 4058 |
| 模型活跃保存状态峰值/B | 12501123072 | 15974006784 |

两个峰值未越16GiB，但模型不表示真实cache淘汰、已完成请求缓存、搬运竞争或物理store等待，因此不能宣称host预算下的真实性能资格。调用减少与平均完成方向冲突，加载流量翻倍，足以否定“少42步即可选择提前”的判断。它没有否定提前恢复家族，也没有给出性能Oracle。

选择依据来自真实[门槛定位](../execution_weste_26862/residual_decision/summary.json)：488个记录条件满足的候选机会被cooldown挡住，覆盖35个轮转间隔；absence门槛显式阻塞仅62次且止于早段421。故主线下一对照选择全局cooldown，而非先前测量方提出的absence30/0。E只是资源观测，GPU资格必须重验native队列接受与联合prepare增长。

下一只做该固定两臂，不扫中间值；完整停顿/吞吐/均完成的实际权衡决定是否继续。新运行域先于第三种启动机制。原件、计算入口和完整候选决策记录见 [screen.py](screen.py) 与 [analysis.json](analysis.json)。
