# 保存、复用与下一次恢复成本

本方继承保存语义/生命周期/成本分工。**新增结论：原生完整保存已把本格恢复的历史重算压到不足一个块的尾部；剩余重复成本主要是重新加载和等待，不能继续以“再次抢占丢失整段历史计算”作为保护理由。** 全量保存又产生大量本episode没有加载过的KV，两种成本应由已安排的selected/full轻量对照裁决。本分析不新增GPU样本、不复算主性能表、不实现窗口或保存预测器。

HEAD为de64dae5；共享工作树有多会话修改，本方源码在独立worktree开发，仅新增本目录。依据主方[已完成结果](../RESULTS.md)、[canonical分析](../execution_weste_26862/analysis.json)、保存注册元数据、实际加载/完成记录。本轮唯一假说是“原生完整保存之后，重复恢复仍主要损失历史计算”；下述逐身份会计否定了它在此格的成立，但没有否定重新加载/等待的优化空间。

## 新增证据：同一份保存可多次加载

| 本格完整episode的块会计 | 16-token块数 | 累计物理字节/GiB |
|---|---:|---:|
| 不同注册逻辑块的已完成保存 | 10,332 | 21,667,774,464 B / 20.179688 GiB |
| 至少一次恢复加载的不同逻辑块 | 3,225 | 6,763,315,200 B / 6.298828 GiB |
| 所有恢复加载，按次数累计 | 5,743 | 12,043,943,936 B / 11.216797 GiB |
| 已加载过同一块后的再次加载 | 2,518 | 5,280,628,736 B / 4.917969 GiB |
| 保存过但本episode未观察到加载 | 7,107 | 14,904,459,264 B / 13.880859 GiB |

同一`request + logical_chunk_index`及其注册key均只保存一次。1/2/3/4次加载的不同块分别为1,758/648/587/232；重复访问占加载块次数43.845%。7,107个未加载块占保存块68.786%，其中6,697块来自44个从未发生实际load的请求，410块来自发生过恢复的请求。3,725/3,866个保存job只含一块；这解释了作业数量为何与字节量不同，但没有测出每job净暴露时间。

这些是**累计传输与事后访问分类**：不是额外host分配，不是同一时刻驻留量，也不是可直接省下的服务时间。已完成主测量的host allocation/末态有效KV都是16GiB。未观察到load不等于这个块在保存当时可判无用；后续新请求的前缀复用也未观察。没有逐次host驱逐记录，不能给这些块补造驱逐时间或声称从未干扰有用缓存。

## 再抢占到底丢失了什么

16个服务后再抢占的状态转移共释放41,386个GPU已计算位置；其中41,248个位置在随后的真实恢复中从host重新加载，138个位置重算。按这些相关事件累计，99.667%的历史位置得到复用；它不是独立样本置信度，也不是请求时间节省率。全部36次恢复的266个重算位置都恰好等于`抢占前computed − 恢复首计算前loaded_prefix`，范围0—15，未出现完整历史块缺失后重算。

一个支持成本修正的实例：0748在首次恢复后生成4个新输出，再于step1021被抢占。该时刻GPU历史为3,712位置；下一次实际恢复加载3,712位置（232块，464MiB），历史重算为0。因此这次再抢占没有丢失历史计算，但确实产生了后续加载与等待。继续保留若有价值，应来自能避免这次**未来**加载和停顿，而不是已经付出的首次保存/恢复成本。不能仅凭464MiB就判定保护优于其他请求执行。

一个反例限制“每次多保存都有服务价值”：44个请求累计保存6,697块，却在本episode没有一次load。它们的保存未通过恢复路径贡献新输出；但这个标签需要看完轨迹，不能用来构造在线理想跳存器。相反，5679在尚无新输出时被抢占，后续实际加载432个历史位置、只重复计算2个位置，另执行此前尚未计算的990个prompt位置，再输出1,024个token完成。其首两次计算调用是759位置（2重算＋757新prefill）和233新prefill，不能写成“恢复只需2位置/1调用”。这展示了完整保存可以覆盖selected-victim之外的恢复需求。二者共同说明保存价值依赖未来是否需要恢复，而不能由“保存已完成”判定。

## 最小成本模型及决策影响

请求状态只需保留当前GPU有效位置/实际块、host已完成且仍有效的连续前缀、pending store/load、尚未完成的尾部、最后新输出时刻，以及队列和当前batch。设抢占时GPU已计算历史为C，下次可实际加载前缀为H，则当前后端在该次恢复需要：

```
H2D = ceil(H / 16) × 每块物理字节
需重新执行的历史位置 = max(0, C − H)
```

本格H均为16的整数倍，故ceil等于除法。尚未计算的prefill与首次新输出工作另记，不能包括在历史重算里。H在在线决策中必须来自当时有效KV和已完成通知；本报告用后续真实加载的H做诊断，**不能将它回填为抢占前已知状态**。已发出的D2H和上次恢复成本为沉没成本；可避免的未来加载、尾部重算和重新排队才进入继续保留的收益侧。

同版本原生源码还限定了最小状态接口：`next_stored_chunk_idx`表示保存范围处理进度，创建store时就可推进，不等于ready/驻留前缀；普通抢占清GPU映射但不回退此游标，实际BLOCK_LEVEL加载可把它改为命中的chunk数。相关scheduler源码已保存于[原始来源](../../20260914_kv_roundtrip_feasibility_r01/native_offload_source.json)，其hash与本组记录一致。不能拿游标或累计保存量代替当前有效H，也不能假定host驱逐自动触发完整重存。具体CPU manager逐次驱逐/请求结束清理未在本分析核验。已结束请求的store元数据只证明注册/传输范围，未做逐字节KV正确性验证。

保存选择的成本先用向量表达：新增store作业数、D2H、host占用/替换、后续H2D、历史重算、目标输出等待及其他请求等待。不能用任意权重先合成有利分数。真实时间应沿实际依赖路径计价：load完成才允许目标计算，其他请求计算可能与传输重叠；因此传输计时和含混合decode的调用计时不直接相加。

停顿边界沿用L（最后新输出）、E_direct/E_fixed_most_funded（首次采样到必要资金条件）、S_host_engine_call（统一恢复调用入口）、S_load_submit和F（下一新输出引擎返回），36段均保留在本目录JSON。E不是充分就绪保证，F不是客户端收到；少重算和更早启动仍是不同结论。

**改变的决策：** 不再为此格的短服务段设计“防整段重算丢失”的窗口。本轮最有区分力的实验仍是主方已选的同卡selected/full/full/selected四格，预算、输入、current调度、轻量测量及EOS语义一致。该实验只改变保存范围：若full的完整服务权衡更好，吸收为强基线，再研究剩余等待；若selected更好，保留它并把未兑现保存、作业数和host压力作为成本解释候选，不能直接宣布13.88GiB都能在线免除；若各有取舍，则按共同延迟—效率目标保留边界，不挑单个最优数字。此处没有额外实验组或GPU启动。

```bash
  --analysis refine-logs/expert_saturation/outputs/admission_capacity/20260915_natural_native_full_gate_r01/execution_weste_26862/analysis.json \
  --output /tmp/native-full-saving-cost-recheck.json
```

脚本已实际运行。它核对每段恰好一次accepted且completed load、恢复前缀对齐、无computed调整、每个对应store在load提交前已完成、全部store/load字节与实测传输守恒、唯一逻辑key及重算尾部关系。加载块身份由实际完整前缀与唯一注册store重建：本包没有单独导出load的逐块src/key数组，所以不冒称直接观测逐key load；这一方法限定于本格no-APC、单group、单load的已核路径，遇到不符状态立即报错。

证据层级是NATIVE_INPROCESS_DIAGNOSTIC上的派生会计，状态MEASUREMENT_ONLY。强基线是已资格化的原生完整保存与selected保存，性能排名未定；没有秒级Oracle、客户端测量、质量判断或新增性能重复。所否定的是本格的历史重算损失解释，不是全部恢复/保存问题。若轻量完整服务及新的有效负载呈现完整块丢失或暴露加载成本，再按实际证据决定下一最小改动。
