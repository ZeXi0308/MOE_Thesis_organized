# 动作前的四步专家统计混合了扩批历史

2026-09-06。仅分析已经保留的 GPU raw；不修改原始数据，不新增 GPU 运行。

**Verdict：`MEASUREMENT_ONLY / SIGNAL_SURVIVAL_UNRESOLVED`。**
本轮发现，已有升档试验的四步 U/C 窗口全部混合 batch 宽度，不能将它当作
当前 shape 的专家结构。此结果定位了信号解释的混杂来源，没有测出信息衰减率，
也没有证明专家信号在动作生效时必然失效。

## 实际分析与时间边界

读取首次 `actions` 与受控复测 `actions-repeat` 的八个 telemetry-ON pulse episodes，
以及八个实际执行的 hold6 episodes；仍只复用同一组 16 条文本。
分析八个升档和八个降档事件，事件、step 和 layer 均不作为独立 workload 样本。

动作在循环首、prefill 前记录此前已完成的四步统计。`token_emission_s` 位于
pressure 计算之前，不能作遥测可用时刻。本分析用
`start_s + iteration_s - prefill_s` 还原 pressure 完成后构造记录时的 host 时间，
它忽略极小的字典构造/append 开销，所有年龄只是该记录边界的近似。
重建的各次 U/C 窗口与 action 内保存的统计一致。

`effective_s` 表示 runtime 首次观察到 active 达到目标不等式；升档可能在 prefill
后被观察到，降档可能在 decode 完成并移除请求后被观察到。本分析只取其后的首个
decode，读取真实宽度，并且不跨下一动作，避免把已完成的旧 batch 算作新 shape。

## 结果

| 量 | 升档 6→8，8 个事件 | 降档 8→6，8 个事件 |
|---|---:|---:|
| 动作前窗口混合宽度 | 8/8 | 0/8 |
| 四步宽度序列 | `[3,4,5,6]` 或 `[2,3,4,5]` | `[8,8,8,8]` |
| 应用至观察到生效 | 0.433–0.872 秒 | 0.271–0.741 秒 |
| 生效时窗口样本的平均年龄 | 0.841–1.372 秒 | 0.476–1.012 秒 |
| 四步平均 U − 最近一步 U | −0.128 至 −0.114 | −0.012 至 +0.024 |
| 四步平均 C − 最近一步 C | +0.875 至 +1.250 | +0.125 至 +0.563 |

这里 U 的差是比例差；升档窗口与最近一步相差约 11.4–12.8 个百分点。
这不是统计实现错误：该字段本来就是历史四步均值。错误会发生在后续把它解释成
“同一当前 batch/KV 下的专家压力”，或者把它与生效后的 U/C 差值解释为信号衰减。
U 和 C 的定义均受实际 width 影响，窗口还混合不同请求成员与 KV/生成进度。

作为有限诊断，分析真实 hold6 轨迹中从自身 sham 时刻起、经历对应 pulse 生效延迟后
的首个 decode。八个升档对应区间中，六个 hold6 区间保持同一请求成员；这些区间的
最近一步至未来一步 U 差均为 −0.0273，C 差为 0–0.9167。八个降档对应区间没有保持
相同成员的样本。此处借用事后测得的 pulse 延迟仅用于回顾时间对齐，不是在线策略，
也不是把 hold 的未来当作 pulse 的反事实；相同成员仍不代表 KV、token 或时延相同。
重复的 U 差来自复用的轨迹，不能解释为六份独立的稳定性证据。

## 研究判断

- **支持：** 必须把遥测窗口本身的 batch 历史与动作延迟纳入信号定义；仅记录当前
  active 再附加混合宽度的 rolling U/C，会留下未解释的历史 shape 差异。
- **尚未回答：** 在普通状态可比时 U/C 的额外预测或动作选择价值、信息是否持续到
  生效、完整成本后的请求收益。年龄不是有效期，数值相近也不是预测能力。
- **基线与上界：** 使用实际 hold6/sham 作为描述性参照；没有训练普通状态或 U/C
  predictor，没有动态 Oracle，也不从这组数据构造动态收益上界。
- **精确失败范围：** 现有固定墙钟 pulse 缺少可识别的同状态专家信号变化；这不是
  非抢占并发控制家族 NO-GO，也不撤销原请求测量及固定 pulse 未复现的结论。

后续记录信号时，应保留窗口中每步 width、成员、KV 和样本年龄；最新单步与四步
均值代表不同统计对象。先解释这些对象，不增加 predictor 或通过换窗口挑选收益。

**唯一下一实验仍是已准备的原生 vLLM cap 6/8 对照**，先解决代表性 runtime 中
实际并发、排队与 SLO 区间是否可辨认。本轮不因为传输审批等待而改造第二个控制器。

重算：[analyze_signal_windows.py](analyze_signal_windows.py)；
逐事件记录：[signal_windows.json](signal_windows.json)。分析输出使用新文件，拒绝覆盖。

直接回答：现有 raw 足以证明四步窗口混合了扩批历史，但不足以判断专家信息是否
能在非抢占延迟后继续改善动作选择；这一必要链路仍未验证。
