# 单次恢复排序：先恢复谁

Verdict: SINGLE_EVENT_ORDER_DIAGNOSTIC。既有实测核对+CPU条件分支；新排序GPU_UNRUN，不支持方法收益。

两次实测均相同：原资格实现329抢占3571后，native把它放到waiting首位。无保存3571在333产出新token，原缺席3640直到1047才恢复；保存后分别332和1045。由此确认保存主要缩短了刚抢占请求自身恢复，原缺席请求只提前两步。

同329前态、同victim/抢占，只把原waiting首请求提到前面的CPU无保存分支：3640在333恢复、3571在1047恢复，首服务顺序交换714步。总调用1869→1836，但平均完成步号1156.9375→1156.90625；仅两个请求完成步改变，3571晚75、3640早76，其余30个不变。它主要交换等待和末尾完成者，不是稳定均完成改善证据。步号不能转换为秒或论文吞吐收益。

| 条件分支 | 总调用 | 平均完成步号 |
|---|---:|---:|
| victim优先、不保存 | 1869 | 1156.93750 |
| 原缺席优先、不保存 | 1836 | 1156.90625 |
| 原缺席优先、load等1步 | 1834 | 1156.84375 |
| 原缺席优先、load等2步 | 1835 | 1156.87500 |
| 原缺席优先、load等4步 | 1837 | 1156.93750 |

同排序关保存是必要强简单基线。其上保存仅−2/−1/+1调用，且随假设完成延迟改变方向；不能把33步排序差全部归给保存。1/2/4步只是灵敏度情景，不是实测延迟包络或物理上界。已知固定两步不能匹配原保存完整轨迹，因此本表不能作为反事实实证或可靠动作排序器。没有输入其他策略的实际未来load完成序列。

本轮不为该单事件排序分支追加GPU矩阵，不把它包装成方法。单事件已完成接口、首次前缀保真及性能混淆定位；剩余研究应针对重复恢复的累计代价，而非继续改善这一个局部gap。

唯一下一CPU分析：复用既有least/most完整轮转轨迹，盘点多次恢复时实际重算工作、可保存完整前缀、累计搬运字节及混合decode服务，判断多次保存是否还有值得实现的累计成本空间。固定轨迹盘点仅为诊断，不能删除重算区间后声称新策略性能；若缺口主要仍是容量等待，就不继续扩大保存机制。

实现与验证：compare_saved_recovery_order.py独立推进各分支状态；recovery_progress_model.py新增默认关闭的native_resume_first，仅接受当时waiting请求，不设置保护期或未来通知。原least/most/defer完整预测回归一致。analysis.json同时保存4格实测恢复步和全部8个条件场景；model_source.py保留本次模型。无GPU执行、无fresh独立审阅。
