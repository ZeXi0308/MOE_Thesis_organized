# 容量合格 victim 基线：首组减少停顿，代价是更多抢占

## 结果与决定

同一 RTX5090、OLMoE/vLLM0.26、H128 已见输入，固定 off/on 探索配对全部 256/256 请求完成。开启容量筛选后发生 78 次实际替换提交，全部有目标后续新输出。实际输出率提高 5.17%，平均到达至完成降低 10.34%，全请求最大生成间隔降低 39.63%。首组通过预定效率与停顿方向，但它只有一个执行顺序，不作统计确认或新算法声明。

反序块已完成且未复现共同服务判据：on/off输出率99.96%、mean flow105.09%、最大gap3.690/3.468s。首组结果保留，最新结论见 [两块完整报告](A_CAPACITY_VICTIM_TWO_PAIRS_RESULT_R01_20261001.md)。没有追加参数或seed扫描。反序换用独立目录避免一次性启动标记，实验包字节未变。

## 唯一变化

保持原最长缺席恢复目标、年龄/进展/驻留资格和 most-output victim 排序。开启时先排除 `free_blocks + held_blocks < target_need` 的 victim，再从合格集合按原排序选一个；无可行者 noop。H1 与 fit-first 均关闭。实际准备、提交时重检、原生抢占与目标首输出保护沿用原实现。

旧诊断中 511/511 次准备资金不足状态均有另一个合格且可提供足够块的 victim，这只是实施此基线修正的依据。当前首组在独立演化的轨迹中测量它的服务结果，不把修正本身包装成算法新意。

## 动作与成本

79 次容量改选准备中，78 次在下一步通过 READY 检查并实际原生抢占新 victim，随后目标都有新输出。剩余 1 次因提交时目标资源不足取消，未计成功；说明准备时可行不保证下一步仍可行。提交到首个后续 host 返回 token 的间隔中位 47.608 ms，范围 43.126–94.397 ms，包含排队、加载和执行，不能解释成纯传输时延。

两臂初始化为 137.293/29.272 s，应用预热为 43.029/0.903 s，正式 host 调用为 87.145/82.866 s；后续 drain 均 0 次，7.77/8.11 微秒。正式区间没有编译或 WARNING/ERROR 日志，不等于没有顺序效应或运行波动。保存、加载、重算与在线调度已包含在完整服务时间中，尚未隔离纯决策开销。

## 等待路径与剩余代价

[成本和尾部分析](A_CAPACITY_VICTIM_COSTS_R01_20261001.json)显示，每次抢占到该请求下一次输出的等待中位数由 0.978 降至 0.574 s，p95 由 3.002 降至 1.713 s。这些区间可能互相重叠，不能相加当总耗时。全 token 的 ≥2 s 生成间隔计数由 39 降至 10，≥3 s 由 12 降至 0；这是间隔计数，与上表请求等权分布不同。

78 次容量替换涉及 46 个目标、47 个新 victim、34 个原 victim。去重的 47 个新 victim 中，flow 46 个改善、1 个恶化，最大 gap 30 个改善、17 个恶化，37 个请求抢占次数增加。唯一 flow 恶化的新 victim `0014802` 增加 8.062 s，抢占从 1 次增至 5 次。这个由 on 动作定义的子集不能作单动作因果对照。

两臂均未出现两次抢占之间零新输出；只有 1–2 个新 token 的连续抢占对由 2 增至 23。这是新出现的代价线索，尚未证明扩大保护量会带来完整请求收益。两臂前三大 gap 的主要时间都在自身抢占后到恢复提交之前，原始链条保存在成本 JSON 中。

[短服务定位](A_CAPACITY_SHORT_SERVICE_LOCATION_R01_20261001.json)进一步显示，23 对覆盖 21 个请求，后一次全部是原生抢占；此前 11 次经容量替换恢复、12 次经普通轮转恢复。20 对在首输出保护释放的同一步再次抢占，只产 1 token；3 对下一步再次抢占，产 2 token。随后 gap 中位 0.645 s、最大 2.225 s，仅与前三大 gap 中第二名重叠。它提供了保护量实验的具体动作依据，但当前主步骤仍是原候选反序对照；有限覆盖不支持预先宣称整体收益。
