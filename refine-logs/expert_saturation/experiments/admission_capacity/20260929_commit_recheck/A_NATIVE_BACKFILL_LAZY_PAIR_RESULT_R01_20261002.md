# Native full-save ordinary：同机 original/lazy 计时配对

本次固定顺序为原 `begin` 构造方式，再到按需构造 running view；两臂保持 native full-save、ordinary backfill、Q1 首输出保护、强制旋转关闭和相同主机计时器。[权威配对分析](A_NATIVE_BACKFILL_LAZY_PAIR_RESULT_R01_20261002.json)核对了同一 128 请求输入、两格完整归档与计划哈希。两格各 128/128 完成；原版 19/19、lazy 27/27 次选择均有原生异步准入、后续新输出与完成链，主动 forced rotation 均为 0，动作步均无实际新增抢占。选择次数不同是两格自然状态轨迹不同，不能当作同状态的策略变更。

主 CPU 判据按每次 `begin` 的 **thread CPU** 检验：736,983→113,571 ns，lazy 为原版 **15.410%**，低于冻结的 50% 上限。服务护栏分别为输出率 **103.225%**（至少 97%）和 mean flow **100.519%**（至多 105%）。加上两格完整请求、真实动作链和强制旋转为零，预设六项判据全部通过。该实验没有设最大 gap 必须下降的 CPU 成本假说；实际全体最大 gap 略升 0.040 s，因此不能写成尾部改善。

合计 wall 分别占各自正式测量 91.297/89.035 s 的 **4.738%/1.122%**。表中总 calls 是四段调用数之和，不是调度步数。两格测量结束快照至卸载的四段 calls/wall/CPU 增量均为 0，请求后 drain 均为 0 次；每次调用的最大值不可作快照差。原生调度主体、GPU 和异步传输不在这四段内，计时器自身有开销。`begin` 下降支持本次按需构造减少适配器主机 CPU 的预设代码成本假说，不能直接折算成因果 episode 加速。

全部请求等权比较中，lazy 相对 original 的 flow 为 53 改善/75 恶化，TTFT 为 26/102，单请求最大 gap 为 77/51；固定 20 点 goodput 为 7 提高/13 降低。**68/128** 条输出序列和 **1/128** 条 stop 原因不同。这是一个同机固定顺序的开发配对，服务变化受自然生成与不同调度轨迹影响，不给方差或同状态因果估计。此前另一物理 GPU 上 native full-save 原生参照对 ordinary 的 97%/105% 性能预算失败仍成立；本次两个臂都安装 ordinary 适配器，不能用它们宣称该旧预算已修复。[原始配对会话](moe-a-native-backfill-lazy-session-r01-20261002/)保留完整请求和计时原件。
