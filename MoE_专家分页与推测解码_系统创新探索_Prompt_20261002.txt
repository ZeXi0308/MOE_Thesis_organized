二、研究问题与自由度

围绕以下问题形成统一系统方法：

有限 GPU 内存和专家搬运带宽下，如何协调验证规模、执行粒度与资源使用，以更低的完整服务成本交付真正有效的输出？

系统应明确考虑：专家权重与 KV 争用显存；多个 token 共享专家加载；更大验证批次可能提高复用，也可能扩大冷专家并集；prefill、decode 和恢复阶段的计算/传输特征不同。

不要预先锁定“层内草稿裁剪”为唯一方案，也不要把三个子系统简单拼接成一个大控制器。允许重新定义控制动作和执行接口，但应最后收敛为一个中心机制。

三、用模型寻找可执行的创新

先从已有反常现象中选择最有信息量的一个，建立能改变决策的成本模型。

模型至少应能区分：
- 调度/验证了多少 token，以及最终提交了多少有效输出；
- 每个 token 选择的专家，以及整个批次实际需要的专家并集；
- 驻留与非驻留专家、实际搬运字节、重复加载和缓存替换；
- 计算与传输中真正暴露在关键路径上的部分；
- 已经发生且不可追回的工作，与当前动作仍能改变的剩余工作；
- 额外决策、重排、kernel、KV 回退和未来补算成本。

例如，固定当前层缓存、且每个冷专家只需加载一次时，搬运量可先用“保留行与必须执行行的专家并集，减去驻留集合，再累加专家字节”描述。它是简化成本项，不能自动当作真实请求时间或容量不足时的完整加载量。

模型需要解释为什么删除一些 token 完全省不了专家搬运，为什么较大 batch 有时更好、有时更差，以及何时额外计算能够摊薄传输。后续层的路由和状态随动作变化，应由各策略执行产生，不能固定一条未来轨迹来评估所有动作。

无需先证明复杂最优化定理。先用小规模枚举、分段成本模型或简单贪心判断可利用的空间，再实现低开销策略。建模的价值在于发现状态、约束或动作，而不是给已有启发式补公式。

四、候选机制：先提出 2–3 个，再择一深入

以下是启发，不是指定答案；欢迎基于数据提出更强的切口。

A. 专家成本驱动的验证规模与执行粒度。
结合当前驻留状态、可用草稿信号和真实执行成本，协调验证长度及批次组织。潜在动作可以发生在验证前，也可以发生在已观察到真实路由的层内。必须解释它相对简单固定短草稿和已有自适应验证的额外价值。

B. 阶段相关的专家加载摊销。
研究 prefill、decode、混合批次下，何种可执行粒度能提高有效专家复用而不制造严重等待。可以改变组织方式或资源预算，但要超越“把 token budget 调大”或普通 chunked-prefill 参数调节。

C. 专家驻留与 KV 进展的联合资源分配。
研究增加专家驻留空间与保留 KV/活跃请求之间的真实取舍，寻找能够低成本执行的容量调整或阶段切换。如果当前内存池无法动态调整，先检验最小可实现动作，不要先开发整套新内存管理器。相关信号应在线可见，不能依赖未来输出长度。

对每个候选，简洁写出：问题、状态、动作、收益来源、主要代价、相对最近邻的差别、最小实验。根据可实现性和潜在完整请求收益，选一条主攻和一条条件备线。允许廉价原型比较，不同时铺开多个复杂系统。

五、特别说明：如果选择层内后缀撤销

需要把它看作改变执行与提交过程的系统动作，而不只是删几行 tensor：
- 明确草稿行属于哪个请求和位置，保留合法前缀。
- 保留幸存 token 的原始 top-k 专家贡献，区分它与专家剪枝/重路由。
- 正确处理采样位置、bonus token、KV 提交和回退，保证后续请求状态可继续执行。
- 实际减少专家加载或执行工作；只改变掩码而未减少完整成本没有价值。
- 将少提交 token 带来的后续轮次和补算计入结果。

初期可限定 greedy。基于 token 内容的截断不能自动沿用随机采样分布保持结论；greedy 也需要检查计算形状变化导致的输出差异。把这些检查融入最小原型，不要求先完成通用采样理论和所有后端支持。

如果固定 N1/N2 已提供很好的收益，需要明确层内动作还能多解决什么；如果合法截断通常省不掉冷专家，或者完整代价抵消收益，就切换其他机制，而不是继续扩大离线任意删行 oracle。

七、实验与论文结果

先用现有环境尽快完成一个小而完整的原型比较。无需先取得第二模型、大模型或完整相关系统，才允许开始探索。关注实际有效输出和完整请求结果，局部字节/步骤只能用来解释机制。

原型出现正信号后，集中完成：
- 强基线：相同资源与计时口径的原生系统、调优后的静态预算/并发配置，以及与所选动作相关的已有方法。推测解码方向包括 AR、固定 N1/N2/N4 和适配的自适应验证参照。
- 主结果：完整请求完成时间、实际有效输出率、TTFT、可测的输出间隔以及并发请求的公平性。多 token 同次返回时，区分 host chunk gap 与不可观测的 token ITL。
- 机制证据：专家并集、驻留命中、实际搬运、GPU 执行、有效提交量和额外开销如何共同解释收益。
- 消融：保持相同执行底座，只移除中心机制的关键部分，不用改变资源预算来制造优势。
- 泛化：未见输入、不同生成长度和到达形态；争取第二 MoE 模型或有实质差异的模型配置。
- 部署真实性：验证实际受限的专家内存/传输环境，并加入专家全驻留或低压力情形，说明收益何时消失。
- 质量：在真实任务上报告正确性或质量；输出长度和内容不同就明确报告，不能仅凭相同准确率宣称完全等价，也不能把少输出当等工作量加速。
- 稳定性：保留全部运行，做运行级重复和独立输入确认；不把同一轨迹的 token 或专家调用数当独立重复。

改进幅度应超过实际波动，并体现相对强基线的实用价值，不预先承诺某个百分比。若只能得到稳定的系统规律，也可以评估 measurement 论文路径，但需要可推广解释和充分实证，不能用若干失败实验拼凑贡献。
