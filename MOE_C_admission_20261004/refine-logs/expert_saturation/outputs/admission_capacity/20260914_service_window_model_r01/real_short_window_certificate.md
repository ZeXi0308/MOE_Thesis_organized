# 真实短服务窗口证书：首个一输出后再抢占事件

Verdict：`STRUCTURAL_ALL31_INFEASIBLE_FCFS_SUBSET_FITS`。两个 guard_residual repeat 的最早事件相同：请求 3640 在 step 405 开始恢复，408 返回恢复后的首个新 token（累计输出 203），409 即再次抢占。选定此事件后没有换事件或改规则。

计算状态严格是首个新输出之后的下一次 schedule-before409：target history=3275、computed=3274、held=205；实际 free=0，整个 pool 为 6656 可用块。31 个 running 请求均为 resident pending=1，包括 target 和 30 个 peers。

候选是继续保留这些请求，每步共同获得一个新输出机会，让 target 再获得 3 个、即本次恢复合计 4 个输出机会。保持已有资源与固定 victim 约束，不新增 victim，不信用未来释放。每步 31 个 token，低于 1024 预算；请求数也低于 32。

| target 额外输出机会 | 所有当前 resident 的累计新增块 | target 自身新增块 | free | 缺块 | token 预算 |
|---:|---:|---:|---:|---:|---|
| 1 | 3 | 0 | 0 | 3 | 31/1024，足够 |
| 2 | 5 | 0 | 0 | 5 | 31/1024，足够 |
| 3 | 6 | 0 | 0 | 6 | 31/1024，足够 |

因此第一步共同输出机会就不可行，阻塞来自 peers 的增量 KV，既不是 target 自己增长也不是 token 预算。第一步跨 block 边界的是 799、2820、3345，各需 1 块；第三步累计另有 133、1401、2038 跨边界。

算式为 `Σ max(0, ceil((H_i+n−1)/16)−held_i)`，只使用该 before 状态，`n=1,2,3`。首输出已实际返回，引擎返回时间分别为 8.44759576022625 / 8.583219146355987 秒；这是 runner 记录的引擎返回边界，不是客户端收到。

真实 409 的 victim 正是 target 3640，随后调度 30 个 peer token。若保留该 victim，就不能同时信用它释放的 205 块。固定实际 victim 列表和“保护 target 继续执行”本身相冲突；上述资格计算没有将这 205 块虚构为空闲。

这说明仅增加固定 4-token 保护、同时维持当前所有 pending1 请求继续 co-batch，并不能在该真实状态兑现。target 独自再输出 3 个机会的存量 KV 是足够的，但那会改变 peer 服务安排，不是这里冻结的候选，不据此报告成功。调整 peer 服务安排、选其它 victim、后端变化、输出年龄代价、到达/EOS及完整请求收益均未测；本证书不是整个负载无解。

当前唯一下一 GPU 复用共享会话已经选定的新 cohort3（排除前 128 文档）native/most/fit/residual 反序八格。先判断强简单 most/fit 是否已覆盖问题；本证书不新增延长窗口 GPU 组，窗口动作保持有残差之后的条件接续。

完整 cohort 的 history/computed/held、每步需求、两个原件 SHA 和实际事件选择记录保存在同名 JSON。未修改已有模型报告或 examples，未调用 GPU，未读取未来 EOS 来决定窗口。


## 同一个 409 状态的 FCFS fit 子集

前面的不可行结论严格针对 all31 连续共同输出，不是所有窗口无解。固定 FCFS 顺序，用每个请求当前持有块内的槽位 `s_i=16*held_i−(H_i−1)` 判断：机会步 n 只调度 `s_i>=n` 的 resident pending1，请求需要新块时跳过，不新增 victim，不从未来释放借块。此处仅做当前状态的三步代数，不运行另一个生成轨迹。

| 额外机会步 | 可选请求数（包含 target） | 累计暂停 peers | 新增块 | 每步 token |
|---:|---:|---|---:|---:|
| 1 | 28 | 799、2820、3345 | 0 | 28/1024 |
| 2 | 26 | 再加 133、2038 | 0 | 26/1024 |
| 3 | 25 | 再加 1401 | 0 | 25/1024 |

target 在每步均被包含；其当前块内可提供 6 个新输出机会，因此再提供 3 个不需要新块。选择顺序保持当前 FCFS，没有 victim 搜索。六个将暂停的 peer 在原 step408 都刚获得输出；在 schedule-wrapper409 入口的真实 output age 全部分别为 block0 **0.286592 ms**、block1 **0.280820 ms**，这是同一 capture clock 的两事件之差，不是对未来 batch 时间的预测。

| 需暂停 peer | 当前块内还可输出 | 第几个机会起暂停 | 三步窗口内新增无服务等待 |
|---|---:|---:|---|
| 799、2820、3345 | 0 | 1 | ≤3·t_batch |
| 133、2038 | 1 | 2 | ≤2·t_batch |
| 1401 | 2 | 3 | ≤1·t_batch |

`t_batch` 仅表示这三个候选 mixed batch 各自耗时的符号上界，未填入未测毫秒；没有统一上界时应写对应 batch duration 之和。表中约束只描述该有限窗口内新增的无服务等待，不保证窗口结束后的下一输出会立刻发生。窗口结束还必须确定如何释放/交还资源，并计入 target 再次丢弃状态与未来恢复的成本。原来已排队的 3571 也继续等待，不能漏掉：两次当前 output age 为 112.408075 / 112.891495 ms，还会增加最多 3·t_batch 的窗口内等待。JSON 单列了该请求。

因此这里保留的是一个有明确代价的局部动作空间：继续输出 target 和当前可 fit 的 resident，逐步暂停六个跨块 peer。它是否优于提前保留增长块、是否满足等待约束、是否比 most/fit 更好，都没有由 CPU 证书回答。唯一下一 GPU 仍是共享的新 cohort3 强基线八格；本证书只为残差存在时的条件动作提供输入。
