# 共同 KV 增长能解释短段，但当前强底座没有新增动作需求

**结论：这个信号没有普遍报警，但尚不足以支持在 E 上启动新的分配动作。** D/E 共 50 个首输出保护释放边界全部符合预先声明的可观察条件；共同增长公式只在 D 的两个已知短段附近报警，E 的 25 个边界均不报警。两步风险的动作集合与简单的 `free_blocks==0` 完全相同，没有新的动作排序价值。保留公式解释资源边界；停止把当前数据中的这项信号继续扩展成 predictor 或 controller。

本结果为 `MEASUREMENT_ONLY`：对两组不同诊断运行的结构核验，不是轻量性能比较，也不是 action-conditioned 反事实。D 的两个短段先前已知，因此不能把这里的分类结果包装为独立 holdout 准确率。

模型只使用释放边界的 current running 请求已计算位置 `c_i`、持有块数 `b_i`、pool 空闲块 `F`，以及当前保护和 plan 状态。block_size=16，固定公式为 `G(h)=sum(max(0,ceil((c_i+h)/16)-b_i))`；`G(h)>F` 报警。身份只作事件对齐，不进入公式。主检验 `h=1` 指紧接着一次调度；`h=2` 是相同 running 集合继续执行两个 token 的结构包络，不猜未来 EOS 或释放。完整约定见 [MODEL.md](MODEL.md)。

|---|---:|---:|
| 一步 G1：TP / FP / FN / TN | 1 / 0 / 0 / 24 | 0 / 0 / 0 / 25 |
| 一步 free==0 基线 | 1 / 1 / 0 / 23 | 0 / 0 / 0 / 25 |

| 两步 free==0 基线 | 2 / 0 / 0 / 23 | 0 / 0 / 0 / 25 |

没有边界被过滤，也没有两步标签受另一个 forced rotation 干扰。标签来自原始 `_preempt` 事件，已剔除同 step/victim 的 READY staged commit；没有用公式生成真假标签。

决定边界的实例和反例：

- D step 902：`F=0, G1=0, G2=6`。该步没有 native 抢占，下一步抢占恢复 target `0000406`。这是“只要 free=0，下一次 decode 就必然抢占”的反例；block 内位置能够解释发生时刻。如果把一步预测错误解释成覆盖两个输出的持续执行保证，此例也会成为漏报。
- D step 1161：`F=0, G1=5, G2=6`，native 当步抢占恢复 target `0000748`。两步共同增长信号识别了它，但相对于 free==0 并未多出一个值得行动的上下文。
- E 全部 25 边界的 `F−G2` 最低仍为 4 blocks；最近的 step 1018 是 `F=7, G1=1, G2=3`。没有观察到可通过该信号触发的强底座分配动作，也没有正例可用于验证其在 E 上的正例识别能力。

因此应修正研究优先级：此前对 D 两例的“共同增长导致恢复后立即 native 再抢占”解释仍成立；但它在当前 E 的释放边界上没有形成剩余动作需求。现有证据既没有优于 free-only 的两步选择增量，也没有证明调缓 peer 增长能带来完整服务收益。一次分配动作仍必须付出 peer 延迟/吞吐代价，不能从两个正确风险标签推导净收益。

适用范围仅限这两个单卡、block=16、decode-ready 的首输出保护释放边界。它不说明 E 全程没有 native 抢占，不覆盖更晚的生命周期、其他并行运行状态、未来 admission、EOS/完成释放、异步可用块变化或不同模型。两步公式假定当前集合继续执行；这些假设变化时即使本次没有 FP/FN，也可能失效。

**唯一继续条件：在正常后续运行中，E 或更强底座实际出现该释放边界的负增长余量，再以当时可见状态检验一个最小分配动作的请求级收益与 peer 成本。** 当前不增加人工压力、不扩展第三个 predictor，也不启动一个预期零动作的 GPU 对照。
