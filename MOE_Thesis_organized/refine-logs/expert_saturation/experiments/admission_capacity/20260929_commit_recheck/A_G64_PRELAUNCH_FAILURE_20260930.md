# A G64 单格预启动失败（2026-09-30）

本次使用固定 [1860 秒单格计划](G64_LTR_NATIVE_PLAN_PRIVATE_MODEL_20260930.json)和 [控制器](serial_group_model_guard.py)。远端上传哈希与本地固定 SHA-256 一致，`--validate-only` 返回 `VALID_CPU_ONLY`。控制器以 `flock(..., LOCK_NB)` 取得共同 GPU 锁，持锁重新核验 C 缓存的固定 OLMoE revision、六个元数据和三个权重分片，随后尝试 `cp -a --reflink=always` 复制整个模型仓库到 A 私有 `HF_HOME`。远端 [原始会话收据](moe-a-ltr-g64-session-private-model-20260930/receipt.json)及状态文件已读回本地。

控制器在复制后的逐分片检查中发现第二个权重分片短于共享源，以 `ABORTED`、退出码 75 停止；`cells=[]`，未启动模型、warmup 或请求测量。`model-private-copy.stderr/stdout` 均为空，复制子进程返回 0，但这不能推翻独立尺寸检查。现场 `stat` 显示共享源三个分片分别为 `4,997,744,872 / 4,997,235,176 / 3,843,741,912` 字节；A 副本分别为 `4,997,744,872 / 4,305,453,056 / 536,870,912` 字节。没有 A 性能或生命周期结果，科学状态仍是 `GPU_UNRUN / METHOD_UNPROVEN`。这是环境/复制资格失败，不能作为策略负结果。

启动前数据盘约剩 9.3 GiB，失败后约剩 58 MiB。`du` 对 A 副本给出约 9.2 GiB，但 reflink 共享区块会被重复计数。A 只读回收据后，仅删除自己不完整的 `/root/autodl-tmp/moe-a-model-cache-20260930`；删除后 `df` 仍约剩 55 MiB，因此**不能断定 A 副本独占消耗了 9.2 GiB**。一次共同锁的非阻塞清理尝试返回 75（锁忙）；为避免共享盘持续满额，随后只清理了上述 A 专属未完成缓存。未删除或改动 C 缓存和其他会话进程。共享盘占用变化和复制短文件的因果原因尚未定位。

追加只读现场检查：C 三个源分片的 `ctime` 均为本次 A 复制之前的 04:17，本次 A 复制约在 04:31，检查时尺寸仍与固定值一致；没有观察到复制期间源文件元数据变化。这缩小了原因范围，但尚不能证明存储层或复制工具的具体缺陷。删除 A 私有副本后稍晚数据盘回升至约 6.8 GiB 空闲，期间也有其他会话活动，不能把变化单独归因于删除。系统盘 `/` 为独立的约 30 GiB overlay 文件系统，现场几乎空闲；可以另冻新身份，考虑在系统盘做明确的非 reflink 完整副本，再复核每个文件哈希。

后续只在共同锁可非阻塞取得时执行新的有界资格单元，核对复制子进程退出、源/目标尺寸与哈希、文件系统空间和私有缓存离线解析。原固定单格计划与失败收据保留，不在已消耗的 session/output 身份上重试。若仍不能可靠生成 A 私有模型缓存，先解决隔离和空间问题；不可用本次失败判定 LTR 机制。
