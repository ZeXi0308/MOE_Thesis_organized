# 容量筛选两块结果：动作复现，服务收益未稳定复现

## 结论

固定原候选、输入、资源和阈值，off/on 与 on/off 两块共 512/512 请求完成。两块分别发生 78、83 次真实容量替换，全部产生目标后续输出；但反序块的平均完成时间和最坏停顿恶化，**两块共同判据失败**。首组正结果保持原样，不能据此宣称容量筛选稳定改善完整请求服务，也不能将可行性筛选单独称为新算法。

|---|---:|---:|
| 实际输出率比 | 105.17% | 99.96% |
| 平均到达→完成比 | 89.66% | 105.09% |

| off / on prepare 资金不足拒绝 | 703 / 0 | 440 / 0 |
| off / on 1–2 token 连续抢占对 | 2 / 23 | 5 / 19 |
| 预定效率与最坏停顿方向 | 通过 | 未通过 |

B2 的 flow 比 105.09% 略高于预定 105% 上限，同时最坏 gap 更长。这里没有把阈值改成足以接纳结果的新数值。两块独立展示，未按 token 池化或把 161 次动作当独立重复。

逐请求 flow 改善 21/恶化 107，TTFT 改善 12/恶化 116，最大 gap 改善 69/恶化 59。固定 goodput 前沿 15 点提高、5 点降低。64 个输出序列和 1 个终止原因不同；on 少 616 个 token，时长较短不构成等工作量加速。两块完整尾部见[双块 ECDF](A_CAPACITY_VICTIM_TWO_BLOCKS_FIGURE_R01_20261001/capacity_victim_two_blocks_ecdf.png)。

B2 的 85 个容量替换准备中，83 个实际提交并有新输出，2 个未提交。全部准备 328 次，其中 324 READY、3 次目标资源不足取消、1 次因 pending 队列取消。容量选择与真正执行分别计数。

两块 on 的 prepare 资金不足事件均为零，但新筛选会在 prepare 之前处理不可行候选。性能日志未记录“全部 victim 都不足”时的 selector noop，因此零 prepare 拒绝不证明全部容量等待已消除。实际动作和完整请求后果才是本实验的依据。

## 下一步与备选边界

最近 H1 两块、fit-first 一块和本实验两块，均观察到第二格 mean flow 更低；这些格间改变了策略，且共享已见 H128，不能证明执行顺序造成差异。具体数值保存在 `A_RECENT_PAIR_ORDER_DESCRIPTION_R01_20261001.json`。下一步只执行一组**完全相同 capacity=true、首输出保护 q1 策略**的 first/second 对照，沿用现有运行流程。若同策略也出现相近量级的差异，就需要先处理测量与运行变化；若没有，也不能用单个对照证明此前差异全是策略收益。

短服务对在两块 on 中均增加，是单独的成本线索。B2的19对覆盖15请求，其中18对在首输出保护释放后再次native抢占，另1对无adapter恢复提交；B2前三大gap均不与这些短对重叠，短对后续gap最大1.965s。见 `A_CAPACITY_SHORT_SERVICE_LOCATION_B2_R01_20261001.json`。直接把保护延长至 q10 的 CPU 反例显示，跨 KV 块增长可能令当前保护失效。一个默认 q1、仅在首输出时剩余输出块预算足够且原生 R=0 才延长的备选已有 3 个 CPU 检查，尚未运行 GPU；它不是本次反序结果，也没有收益结论。
