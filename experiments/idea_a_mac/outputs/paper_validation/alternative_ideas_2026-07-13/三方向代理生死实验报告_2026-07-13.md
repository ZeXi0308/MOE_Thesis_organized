# 三个替代 MoE 系统 Idea 的代理生死实验（2026-07-13）

## 最终判定

| 方向 | 代理实验判定 | 文献撞车 | GPU/工程门槛 | 当前建议 |
|---|---|---|---|---|
| DeadlineEP | 仅 balanced + 极低调度开销成立；hot receiver 反转 | 高：FAST、UBEP、AMoE、QLLM、Gimbal 已覆盖相邻问题 | 很高：至少 2 nodes × 4 GPUs，需修改 EP runtime/异步执行 | **有条件保留，但必须极度收缩** |
| HedgeEP | 20% 额外执行只换 5%～7% P99；receiver tail 为 0 收益 | 中高：PROBE、动态副本、EEP/elastic EP 已接近 | 高：需要拓扑分散副本、额外 HBM、straggler 注入 | **原样停止** |
| Complementary Batching | predicted 收益约 0%；oracle 也只有 2.6%～7.8% mean headroom | 高：Sem-MoE、Gimbal 已做相邻 model-data/request co-scheduling | 中：4～8 GPUs 即可，但上限太低 | **停止** |

最重要的结论不是“DeadlineEP 有 53% 收益”，而是：**其收益只存在于能够打破跨请求 layer barrier、且每 request-layer 额外开销不超过约 1 us 的理想条件。** 这已经接近重新设计执行引擎，而不是给 DeepEP 加一个简单优先级队列。

## 最新相关工作撞车审计

- [FAST（NSDI 2026）](https://www.usenix.org/conference/nsdi26/presentation/lei-yiran) 已处理 All-to-All(v) skew、两级异构 fabric、incast 与动态 traffic；所以“拓扑感知 incast 调度”不能作为 DeadlineEP 新意。
- [UBEP](https://arxiv.org/abs/2607.06202) 已把 coarse BSP serialization、同步开销和 distance-agnostic scheduling 作为核心问题；DeadlineEP 不能只讲“打破 BSP”。
- [AMoE](https://arxiv.org/abs/2505.08944) 已做 per-layer token queue、异步 expert execution 和 adaptive re-batching；DeadlineEP 的剩余缝隙只可能是 **request deadline/SLO 进入 EP data plane，并提供隔离/公平保证**。
- [QLLM](https://euromlsys.eu/pdf/euromlsys25-32.pdf) 已研究 mixed-priority MoE 的 layer-level preemption；若 DeadlineEP 只做 decode priority，创新不足。
- [Gimbal](https://arxiv.org/abs/2606.15177) 已联合 DP engine pressure、MoE pressure、prefill-aware ordering 与 expert placement；DeadlineEP 必须证明 collective 内部调度是不可由前端 request ordering 替代的。
- [PROBE](https://arxiv.org/abs/2602.00509) 已联合预测、dynamic expert replication 和 token assignment；HedgeEP 不能声称“首次动态复制 expert”。
- [EEP](https://arxiv.org/abs/2605.10670) 已处理 wide EP rank failure 与 expert coverage repair；HedgeEP 只能聚焦未触发 failure detector 的 transient sender/expert straggler。
- [Sem-MoE](https://iclr.cc/virtual/2026/poster/10009943) 已做 model-data collaborative scheduling；Complementary Batching 即使改成“互补而非 affinity”，也必须先跨过本实验显示的极低 oracle ceiling。

## 资源门槛与真实论文上限

### DeadlineEP

- 最低可信平台：2 nodes × 4 GPUs，必须有真实 inter-node EP；单机 8 卡不能证明 topology/incast。
- 需要修改：DeepEP/NCCL-EP/NVSHMEM 数据面、request tile metadata、GPU-resident priority queue、跨层异步执行、CUDA Graph 或替代 replay 机制。
- 必须测：GroupGEMM batch fragmentation、SM occupancy、message aggregation、scheduler overhead、decode P99、prefill starvation、SLO attainment、goodput。
- 论文上限：若能相对 FAST/UBEP/AMoE/QLLM 展示 request isolation，且 throughput 损失很小，有 B 潜力；只有 trace simulator 或 Python queueing model，不足以形成 C 保底。

### HedgeEP

- 最低可信平台：至少 8 GPUs、最好两节点；必须把相同 expert replica 放在不同 sender/故障域，并注入 compute/network straggler。
- 显存风险：大模型 expert replica 会直接占用 HBM，可能迫使降低 EP size 或增加 GPU，成本很高。
- 必须测：真实 tail 来源中 sender/expert、receiver、network path 各自占比；cancel latency；重复 dispatch/combine 对原 traffic 的反压。
- 论文上限：只有在 ≤10% extra work 下稳定降低 ≥15% P99，且使用真实 transient-straggler trace，才值得继续。当前代理结果未达到。

### Complementary Batching

- 最低可信平台：4～8 GPUs 和 SGLang/vLLM scheduler 修改即可，三者中资源最低。
- 但当前 oracle mean headroom 随 batch 4/8/16 从约 7.8% 降到 5.1%/2.6%，predicted policy 接近 0；即使工程完全成功，也很可能被 scheduler overhead 吃掉。
- 论文上限：当前更像 negative characterization，不值得作为独立系统论文。

## 共同边界

- 输入：`experiments/idea_a_mac/outputs/paper_validation/olmoe_signal_mxfp4_n32/test_routes.csv`，OLMoE held-out routing trace；
- EP=8，按 expert id 映射 owner；
- 这些是 trace replay / analytical service models，不是 GPU、DeepEP、RDMA 或真实 P99；
- 目的只是在投入多 GPU 工程前发现机制雷点，正结果不能作为论文性能 claim。
