# LongBench 150：经典 Horn 树调度的 CPU 参照

在[固定的150条 LongBench 输入](20261001_c_long_document_qa_full_inputs_v1/workload.json)上，把每个唯一的可复用16-token前缀块建成处理时间 `p=16`、权重 `w=0` 的作业；每条请求另有一个 `p=1..16, w=1` 的私有终端作业。父块先于子块，得到一棵 outtree；处理一次的块永久可用。模型目标是单处理机上150个终端作业的完成工作量之和 `ΣC_leaf`，不含解码、EOS或真实时间。

[实现](C_LONG_DOCUMENT_QA_HORN_ORDER_V1.py)的精确密度计算如下：对节点 `v` 和终端数 `k`，`D_v(k)` 是包含 `v`、满足祖先闭包、恰含 `k` 个终端的连通子树所需的最少处理工作。子树之间用按 `k` 的最小加法卷积合并，`ρ_v = max_{k≥1} k/D_v(k)`；然后按 `ρ_v` 从高到低执行当前可用作业，并以最小源序作确定性并列消歧。这是 [Horn 原问题](https://epubs.siam.org/doi/10.1137/0123021)的经典单机加权完成时间参照；[Galil 1980 原文 §§1、3](https://www.cs.toronto.edu/~anikolov/CSC265F18/Galil80.pdf)直接给出变长处理工作的最大 `W/P` 根子树及可用作业顺序。[2024 年论文 §§3.2、4.1](https://arxiv.org/html/2404.17544#S4.SS1)明确展示零权重内部节点、叶节点权重与单机 Horn 最优性，但其正文证明表述为单位处理时间。

这里所有 `p` 都是正整数，因而还可把各作业展开成 `p` 个单位作业链，仅在链末保留原权重，并把原后继接到链末。所得仍是零权重内部节点的 outtree。在链中，下一单位作业的可选根子树少了一个零权重单位而拥有同样的后继，故其最大密度严格高于当前单位作业的正密度；已选择的链不会在中途被另一条链打断。于是单位时间的 Horn 顺序也对应原作业的完整执行。终端出现顺序可投影成请求顺序：任何提前计算却未服务当前终端的独立内部块，都可移至首个依赖它的终端之前，不会推迟终端完成。

[CPU 结果](long_document_qa_horn_order_v1.json)：Horn 与此前 whole 顺序的唯一 prompt 工作同为 **386,498 token**；150条请求的累计完成工作为 **23,086,503 对 23,101,594**，平均 **153,910.0200 对 154,010.6267**，减少 **0.0653245%**。请求序34个位置改变，首32-token组连续段为101；五个小树的所有请求排列穷举均与 Horn 目标一致。实际150的作业目标与投影后请求顺序目标完全相等。脚本在本地 CPU 上求序约 **0.308 s**，仅描述这次计算成本。

这项最优性限于**全请求同时可知、串行 prompt 工作、无限缓存且每块只算一次**的模型。386,498 token 是该模型的固定最终工作量；0.0653% 是该模型的完成工作改善，不是有限 KV、连续批处理、decode 与真实 TTFT/flow 的收益上界，也未观察 GPU 输出。如此微小的代理差距只用于把 whole 顺序与强经典参照定位清楚，不能据此声称新调度方法或新的 GPU 收益。
