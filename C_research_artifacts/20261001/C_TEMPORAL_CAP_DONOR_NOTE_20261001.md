# Cap-only 单 donor 规则：CPU 数学定义

状态：**CPU_MATHEMATICAL_ONLY / NATIVE_ADAPTER_UNRUN**。

本文件与 [CPU 规则](C_TEMPORAL_CAP_DONOR_RULE_V1.py)只定义一个部分机制消融：受 [CacheOPT §3.3.2](https://arxiv.org/html/2503.13773v1#S3.SS3.SSS2) 的未来释放 donor 匹配启发，用已知 cap 替代完成长度预测。不包含其长度预测器、置信 padding、SLO 加权分配、空间 embedding、全局 reserve 和抢占选择，不是完整 CacheOPT 复现，也未证明已经补足最近方法基线。本次没有 GPU 执行、测量收益或主策略/新输入变更。

## 定义与返回值

冻结常数：16 token/块，容量 4,096 块，最多 32 个请求，`guard=1` token。居民为 `(P_i,O_i,M_i)`：prompt 长度、当时已输出长度、已知最大输出 cap。每个居民均已有完整逻辑预留：

\[
Q_i=\lceil(P_i+M_i)/16\rceil,\qquad F=4096-\sum_i Q_i.
\]

`F` 是逻辑未承诺容量，不能替换成现场物理空闲块。函数不读未来 EOS。调用方必须确认所有居民处于同步、无 speculative 的纯 decode 状态，并构成每次调用推进一个 token、直到 cap 或真实 EOS 的受保护前缀。尚有部分预留 receiver 或未完成 promise 时返回 HOLD，避免用完整预留求和误计现有承诺。

对尚未运行的 FIFO 队头 `(P_h,M_h)`，`Q_h=ceil((P_h+M_h)/16)`：

1. 若无序列槽则 HOLD。
2. 若 `F>=Q_h`，按 ordinary full-bound 分配 `Q_h`，无 donor。
3. 否则先要求 `16F>=P_h`，即完整 prompt 能放入初始配额。
4. 按居民输入顺序选择第一个未承诺、完整预留的 donor `j`，要求：

\[
H_j=M_j-O_j,\qquad H_j+1\le16F-P_h,\qquad Q_j\ge Q_h-F.
\]

成功时返回 donor ID、`receiver_initial_blocks=F`、完整目标 `Q_h`、待转移 `Q_h-F`、donor 的 `H_j/Q_j`；否则 HOLD。函数不修改请求或分配器。

原建议不等式无需修正。这里保守地把 receiver 的全 prompt 立即计入，并在第 `t` 次推进计入最多 `P_h+t+1` token（上限为 `P_h+M_h`）。额外的一个 token 保留调用/输出记账余量；这是占用上界，不是对真实 prefill 时序的等式。即使 donor 在最终 cap 步的块释放之前仍全部计费，receiver 在该步也不会超过 `F` 块。donor 释放后，剩余居民完整预留加 receiver 完整预留最多为：

\[
\sum_{i\ne j}Q_i+Q_h=4096-F-Q_j+Q_h\le4096.
\]

较早的真实 EOS 只会提前释放；较慢的 receiver prefill/解码只会减少该上界。donor 的单 token 推进条件失效则保证失效，未来原生适配器必须检测并停止该实验，不能继续假设释放时刻。

在当前所有 `M_i=M_h=1024` 且 `P_i>0` 的域内，只要 prompt 能放进 `F`，短缺 `Q_h-F<=64`，而 donor 的 `Q_i>=65`，所以 donor 大小条件自动满足。仍保留它以明确守恒关系，并支持 CPU 层面的一般 cap 输入；这没有改变实际实验的固定 cap。

## CPU 检查

运行 `python3 C_TEMPORAL_CAP_DONOR_RULE_V1.py`，仅向标准输出打印结果。脚本逐一枚举每个整数 token 步，分别计算释放前与释放后的保守占用，不复用准入不等式来计算峰值。

边界接受例：16 个居民均 `P=2976,M=1024,O=989`，因此每个 `Q=250,H=35`，`F=96`。队头 `P_h=1500,M_h=1024,Q_h=158`，runway 为 36 token；`H+1=36` 恰好成立。选择首个 donor，先分 96 块、后转移 62 块。枚举 1,025 个 token 步得到保守峰值 4,096 块，释放前 receiver 峰值 96 块。

另枚举 donor 在第 1–35 步提前 EOS、receiver 在第 `{1,2,16,512,1024}` 步 EOS 的 175 个组合，所有步骤均满足配额和容量条件。其他更早 EOS 只从同一步占用和中移除非负项，因此无需将所有请求 EOS 的笛卡尔积作为测试。还检查 ordinary full-bound、一个 token 的拒绝边界、纯 decode 条件缺失、已有 promise，以及首位 donor 已承诺时按输入顺序选择下一位。

这些检查只支持所述数学账本，不验证 native 事件顺序、实际 KV 分配、吞吐、输出质量或额外开销。

## 两个方向的合成接受集合差异

以下每例均有 16 个居民：8 个 `P=2976,M=1024,H=H_early`，另 8 个 `P=2976,M=1024,H=960`，其中 `O=M-H`。所有 `Q=250`，总完整预留 4,000 块，`F=96`；队头 cap 均为 1,024。这些是人工整数状态，不是实测 trace 或反事实收益。

全局规则的比较量为 `max_t sum_i ceil((P_i+O_i+t)/16) 1[t<=H_i] + Q_h`，通过所有整数步枚举计算。

| 合成例 | `H_early` | 队头 P | 队头 Q | runway | 全局居民包络 | 全局包络+队头 | 单 donor 拒绝原因 |
|---|---:|---:|---:|---:|---:|---:|---|
| Prompt 未放下 | 64 | 1,600 | 164 | −64 | 3,552 | 3,716 ≤ 4,096 | 96 块仅含 1,536 token，prompt 已超出 |
| donor 退休过晚 | 64 | 1,500 | 158 | 36 | 3,552 | 3,710 ≤ 4,096 | 最早 donor 也需 64+1 > 36 |
| 一个 token 余量边界 | 36 | 1,500 | 158 | 36 | 3,544 | 3,702 ≤ 4,096 | 36+1 > 36 |

反方向由上面的边界接受例给出：16 个居民均在 H=35 退休，居民全局包络峰值为 4,000 块。当前全局规则还会给新队头立即计入完整 158 块，因此 4,000+158=4,158>4,096，拒绝；单 donor 规则按 receiver 在 donor 退休前的增长只需 96 块，接受，逐步保守占用峰值为 4,096。`self_check()` 显式核对并输出该反方向结果。

因此在这些共同适用的合成状态上，两种接受集合互不包含：当前全局规则利用居民之间不同的退休时间，但为新队头保留完整上界；单 donor 规则限制 donor 匹配，却对新 receiver 在承诺转移前的增长做时间计账。这是有意义的机制比较差异，不能宣称某一规则支配另一规则，也不能从接受集合推断完整请求性能收益。

## 尚需实现的最小原生状态

未来适配器必须只允许一个未完成 promise，不允许 receiver 成为 donor，不允许 donor 重复承诺或形成链。需要在同一逻辑账本原子记录初始配额/承诺，在 donor **真实释放**时把短缺额度先转给 receiver，在 receiver 提前 EOS 时取消 promise。等待转移期间不再准入新请求；转移完成后 receiver 才成为完整预留居民。原生块所有权与释放仍由 native allocator 维护。

当前下一步只是将这个精确定义交给主实验结果之后的实施选择；本 CPU 文件本身没有启动新调度实验。
