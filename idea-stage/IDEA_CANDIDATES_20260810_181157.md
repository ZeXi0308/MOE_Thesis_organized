## 负结果的结构解释

1. 当前 `RunningBatch` 只有一个 `finish_us`，一个 batch 的所有 rows 同时完成；Oracle 看不见 row/token milestone。
2. successor group 只有在 top-k 全部完成后才进入固定 `combine_us`，所以提前完成一个非 join-closing contribution 不产生下游价值。
3. 当前 M=1/2/4 service 为 10/14/20 us。典型两行 split 把一个请求从 14 提前到 10，却让剩余行再付 10；它转移尾延迟并把总 service 从 14 增到 20，没有创造并行容量。
4. Oracle 已枚举所有 idle replicas 的完整 ready queues 与 bounded HOLD；普通 queue priority 不是缺失动作。

## Candidate cards

### C01 — JoinStream / Whole-batch Prefix-Ready Emission

- **Hypothesis**：保持一次 whole launch、同样成员与最终 batch finish，但让 canonical row prefixes 在执行中产生真实 completion event，可提前关闭部分 token join。
- **New action/state**：`LAUNCH_WHOLE_STREAM(queue, row_order, milestone_curve)`；executor 仍 busy 到最终 finish，rows 在冻结 milestone 上逐个完成。
- **Why it may work**：不增加 launch 或总 service；某请求的两条 top-k row 可在两个 replica 上被共同前置；其下层可与 batch 尾部重叠。
- **Minimum Oracle**：8 cells = rows {2,4} × milestone {uniform, tail-heavy} × overhead {0, nontrivial}；atomic whole 为 `all milestones = finish` comparator。
- **Positive / negative**：正结果只证明 atomic completion 隐藏 headroom；负结果只削弱所测 milestone/overhead，不否定 transport 或 consumer streaming。
- **Cost**：中；约 3–5 天的完整实现，但可用二行固定 milestone 做 1 天 existence Pilot。
- **dedup_key**：`whole-batch-prefix-ready-emission`。

### C02 — AccuJoin / Order-Preserving Incremental Top-k Accumulation

- **Hypothesis**：严格按 top-k slot 顺序，把已完成 contribution 的加权归约提前到 reducer，可将大部分 combine work 与 expert skew 重叠。
- **New action/state**：per-group arrived mask/cursor；`ACCUMULATE_NEXT_SLOT`、`FINALIZE`；后继仍等所有 slot 和 finalize。
- **Why it may work**：不改 expert launch；只把固定算术工作移出最后 join tail；共享 reducer 还能形成真实跨请求调度。
- **Minimum Oracle**：8 cells = top-k {2,4} × skew {low,high} × movable combine fraction {small,large}；原子 reducer 保持完全相同总工作。
- **Positive / negative**：正结果定位 consumer barrier；负结果不否定 producer row milestone。
- **Cost**：中，3–6 天。
- **dedup_key**：`order-preserving-incremental-topk-accumulation`。

### C03 — SegmentReturn / Segmented Cut-through Expert Return

- **Hypothesis**：expert vector 的 segment production、link transfer 与 receiver reduction 可流水，缩短最后 required bytes 的尾部。
- **New action/state**：segment bitmap、link/receiver resource；`SEND_SEGMENT`、`RECEIVE_REDUCE`。
- **Why it may work**：即使最终 token 仍等全向量，前段网络/归约可以被晚段 compute 覆盖；link contention 产生 join-aware ordering。
- **Minimum Oracle**：8 cells = segments {2,4} × bottleneck {compute,link} × skew {low,high}；atomic return 同 bytes/work。
- **Positive / negative**：仅为 CPU pipeline existence；不支持 NCCL/RDMA claim。
- **Cost**：中高，5–8 天。
- **dedup_key**：`segmented-cut-through-expert-return`。

### C04 — TileConsume / Exact Post-MoE Consumer Wavefront

- **Hypothesis**：所有 top-k 对某 hidden tile 齐备后，tile-separable suffix 可先执行，直到第一个非 separable operator 才保留 hard barrier。
- **New action/state**：tile-ready/suffix-done bitmap、consumer resource；`CONSUME_READY_TILE`。
- **Why it may work**：把 residual/combine 等 exact-safe tile work 与晚 tile 重叠；不允许提前进入全局 nonlinear operator。
- **Minimum Oracle**：8 cells = tiles {2,4} × readiness {aligned,staggered} × suffix cost {light,heavy}。
- **Positive / negative**：负结果只否定声明的 tile-safe suffix。
- **Cost**：中高，5–8 天。
- **dedup_key**：`tilewise-exact-post-moe-consumer-wavefront`。

### C05 — RouterWave / Incremental Exact Router Accumulation

- **Hypothesis**：按固定 hidden-dimension 顺序提前累加 next-layer router logits，最终 tile 到达后只做 exact top-k finalize。
- **New action/state**：router tile cursor、partial logits、router resource；`ROUTER_ACCUMULATE`、`FINALIZE_ROUTE`。
- **Why it may work**：不预测 route、不提前 reveal expert node，却把 router matvec 大部分移出 layer-boundary tail。
- **Minimum Oracle**：8 cells = tiles {2,4} × arrival {uniform,tail-heavy} × router work {small,large}；atomic comparator 同算术顺序/工作。
- **Positive / negative**：负结果不否定其他 consumer；正结果仍需 GPU kernel 可实现性。
- **Cost**：高，6–10 天。
- **dedup_key**：`incremental-exact-router-accumulation`。

### C06 — ReplicaSteal / Residency-Constrained Whole-Queue Mobility

- **Hypothesis**：当 target replica 忙而 compatible resident replica 空闲时，迁移整条 queue 能创造固定 QueueKey ordering 无法表达的并行。
- **New action/state**：residency mask、execution replica、migration cost；`MIGRATE_WHOLE`。
- **Why it may work**：改变执行资源，不改 route/node/join；拥塞 executor 的等待转成并行执行。
- **Minimum Oracle**：8 cells = skew {hot,balanced} × migration cost {0,4} × deadline {loose,tight}。
- **Positive / negative**：负结果只削弱 resident whole migration；不否定长期 placement。
- **Cost**：中，3–5 天。
- **dedup_key**：`residency-constrained-whole-queue-replica-migration`。

### C07 — QuantumYield / Cooperative Expert-Batch Preemption

- **Hypothesis**：固定 service quantum 上挂起 running batch、先服务随后 reveal 的 urgent join sibling，再恢复 remainder，可解除 non-preemptive blocking。
- **New action/state**：suspended batch、remaining service、penalty；`PREEMPT`、`RESUME`。
- **Why it may work**：旧 Oracle 无法触碰 RunningBatch；抢占直接改变 running state，并显式向被抢占请求收费。
- **Minimum Oracle**：8 cells = incumbent rows {2,4} × urgent offset {1,3} × deadline {loose,tight}；quantum=2、penalty=1、最多一次抢占。
- **Positive / negative**：只回答 cooperative preemption existence，不证明 CUDA preemption。
- **Cost**：中高，4–7 天。
- **dedup_key**：`quantized-running-batch-preempt-resume`。

### C08 — OpenBatch / Append-before-Compute Dynamic Batch

- **Hypothesis**：将 launch 分为 setup/open 与 compute/closed，在 open window 内追加随后 reveal 的同 queue rows，可同时隐藏 setup 并保留 batching economy。
- **New action/state**：open membership/deadline；`OPEN`、`APPEND`、`CLOSE`。
- **Why it may work**：旧 HOLD 只能等后再启动，不能让 setup 与未来 arrival 重叠。
- **Minimum Oracle**：8 cells = arrival gap {1,3} × open window {2,4} × deadline {loose,tight}；冻结 setup=2。
- **Positive / negative**：若旧 HOLD 等价则该 formulation 失败，不外推其他 in-flight batching。
- **Cost**：中高，4–6 天。
- **dedup_key**：`open-append-close-inflight-dynamic-batch`。

### C09 — MultiExpertFuse / Cross-Expert Whole-Queue Launch

- **Hypothesis**：同 layer/replica 上多个 singleton expert queues 可共享 setup/kernel 并共同关闭 joins，优于至少两次串行 single-queue launch。
- **New action/state**：multi-QueueKey RunningBatch、mixed-expert curve；`FUSE_WHOLE`。
- **Why it may work**：不切单 queue；新原子动作改变物理 launch composition。
- **Minimum Oracle**：12 cells = queues {2,3} × reveal {aligned,staggered} × deadline {loose,medium,tight}；预先冻结 mixed curve。
- **Positive / negative**：负结果只覆盖该 synthetic fusion curve，不证明 grouped-GEMM 无用。
- **Cost**：高，5–8 天。
- **dedup_key**：`multi-expert-multi-queue-fused-whole-launch`。

### C10 — DuplexWave / Explicit Link–Compute Co-scheduling

- **Hypothesis**：把 dispatch/return 变成独立 link/DMA tasks，并允许与 compute 同时启动，可缩短 join-closing path。
- **New action/state**：dispatch-ready/compute-ready/return-ready stages、link occupancy；`START_DISPATCH/COMPUTE/RETURN` 与 joint start。
- **Why it may work**：新增不同资源与 pipeline stage；不是 ready compute queue 重排。
- **Minimum Oracle**：8 cells = transfer/compute ratio {light,heavy} × contention {aligned,staggered} × deadline {loose,tight}；serialized stage Oracle 为 comparator。
- **Positive / negative**：CPU-only；不支持真实 EP interconnect claim。
- **Cost**：中，约 300–500 LOC。
- **dedup_key**：`explicit-link-compute-joint-actions`。

### C11 — HedgeJoin / First-Completion Duplicate Execution

- **Hypothesis**：对 late join-closing contribution 启动一个 compatible duplicate，first exact completion commit，可用有限冗余换 tail latency。
- **New action/state**：logical-to-physical copies、first commit、loser service；`HEDGE`、`COMMIT_FIRST`、`CANCEL_COPY`。
- **Why it may work**：创建冗余物理路径，无法由 queue ordering 表达；所有 loser work 被收费。
- **Minimum Oracle**：8 cells = straggler location {local,remote} × hedge cost {low,high} × deadline {loose,tight}；每 node 最多一个 hedge。
- **Positive / negative**：依赖 replica exact equivalence 与可取消/丢弃合同；负结果只覆盖冻结 straggler traces。
- **Cost**：中高。
- **dedup_key**：`first-completion-duplicate-copy`。

### C12 — ShapeLease / Execution-Tactic and Residency Scheduler

- **Hypothesis**：保持 logical whole queue 不变，在 native/padded/persistent tactics 中选择并付 reconfiguration cost，可胜过任何固定 tactic。
- **New action/state**：resident tactic/bucket、mode service table；`LAUNCH_SHAPE`、`RECONFIGURE`。
- **Why it may work**：物理执行形状与连续 reuse 改变 finish time；CriticalSplit 不含 tactic 状态。
- **Minimum Oracle**：16 cells = shape {sparse,dense} × residency {warm,cold} × reuse {low,high} × deadline {loose,tight}。
- **Positive / negative**：必须击败每个 fixed-tactic exact Oracle；synthetic curve 不是 GPU 结果。
- **Cost**：中。
- **dedup_key**：`physical-tactic-residency-selection`。

### C13 — CutThroughEP / Chunk-Pipelined Dispatch–Compute–Return

- **Hypothesis**：将每个 contribution 的 mandatory dispatch/compute/return 拆成有序 chunks，可把 phase latency 从相加变成 pipeline tail。
- **New action/state**：per-stage chunk counters、window、link/compute occupancy；`SEND/COMPUTE/RETURN_CHUNK`。
- **Why it may work**：保持 logical contribution 完整且所有 chunks 必做；只改变内部 pipeline granularity。
- **Minimum Oracle**：16 cells = ratio {light,heavy} × chunks {2,4} × contention {low,high} × deadline {loose,tight}；one-chunk atomic comparator 同总 work。
- **Positive / negative**：FinDEP 是强近邻；只有 join-specific finding 才可能保留。
- **Cost**：高。
- **dedup_key**：`mandatory-stage-chunk-pipeline`。

### C14 — RouteAhead / Causal Setup Prefetch

- **Hypothesis**：只用当前可见 predictor signal 提前搬运下一层 expert setup，native router 最终决定执行，可隐藏 cold delay。
- **New action/state**：setup cache/prefetch/eviction；`PREFETCH_SETUP`、`EVICT`、`CANCEL`。
- **Why it may work**：动作发生在 route reveal 前、只影响物理 setup；miss 明确占 link/cache。
- **Minimum Oracle**：12 cells = trace {all-hit,mixed,all-miss} × pressure {low,high} × deadline {loose,tight}。
- **Positive / negative**：SpecPrefetch/MoE-Infinity 是直接近邻；主要作为低 novelty control。
- **Cost**：中。
- **dedup_key**：`causal-prefetch-setup-cache`。
