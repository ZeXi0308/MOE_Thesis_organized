## C01 — Full-DAG Oracle Distortion Audit

- **问题**：single-layer / local-window Oracle 没有传播 assignment、hold、release 或 reconfiguration 对后续 layer、decode step、batch composition 和 admission 的影响，局部动作排序可能在完整请求中反转。
- **假设**：自然 continuous-decode 下，局部 Oracle 对 full-DAG SLO-goodput 上界存在跨模型、可复现的偏差；否则它只是基础设施补齐，不构成独立贡献。
- **最小证伪 pilot**：冻结同一 identity-complete trace、route、service surface 与 action set，对比 single-window、truncated-horizon、full request-DAG exact replay；若两模型共同自然 cell 中净收益差异均 <5%、动作一致率 >95%、符号几乎不反转，则停止独立 idea。
- **最近邻**：AMoE、Gimbal、UltraEP；当前工作区 BCRD/DEPA 的 full request-DAG 缺口。
- **so what**：直接决定过去和未来局部 Oracle 结论是否可信；负结果也能封住错误上界。
- **机械合并来源**：`full_request_dag_oracle_distortion` + `full-request-dag-reconfiguration-spillover-versus-local-placement-oracle`。

## C02 — Exact Action-Surface Existence Certificate

- **问题**：现有系统把 admission、batch composition、assignment、seal/release、placement 等动作混合报告收益，却很少证明每个动作在决策时刻可见、删除了哪条依赖、跨层传播后是否仍非等价。
- **假设**：把动作编译为“可见状态、可改对象、被删除依赖、传播、成本”五元组后，大量策略会坍缩为少数等价类；只有至少一个等价类 full-DAG exact Oracle 净空间 ≥10%，action space 才存在。
- **最小证伪 pilot**：在小规模完整 DAG 上枚举 assignment、bounded seal、admission、release；输出依赖删除证书、等价类和成本。所有类 <10%、依赖 future leakage/zero cost 或改变语义时返回 `ACTION_SPACE_ABSENT`。
- **最近邻**：Mixture-of-Experts Serving、AMoE、UltraEP、METRO、Gimbal；一般 scheduling DSL / causal simulator。
- **so what**：能在写 controller 前机械判定“根本没有可用动作空间”。
- **机械合并来源**：`action_space_existence_certificate` + `exact-action-surface-equivalence-compiler`。

## C03 — Route-Conditioned Barrier Amplification Boundary

- **问题**：平均 token/expert imbalance 不等于 barrier 的端到端暴露贡献；max-rank、跨请求排队、可重叠 slack 和后续 decode 传播可能放大或吞掉局部 skew。
- **假设**：route concentration、expert service CV、rank correlation、barrier fan-in 和 downstream slack 构成一个可迁移边界，预测局部 imbalance 何时形成 ≥10% full-request Oracle 空间。
- **最小证伪 pilot**：固定总 work，对自然 route 做 real-barrier、no-barrier 与去相关 matched replay；若共同自然 cell exposed share 均 <5%，或简单 max-load/CV 已达到同等跨模型预测能力，则停止。
- **最近邻**：AMoE、UltraEP、Gimbal、METRO、Scaling Multi-Node Activation Patterns。
- **so what**：回答负载均衡何时有必要、何时任何精细策略都不值得做。
- **机械合并来源**：`route_conditioned_barrier_amplification` + `barrier-amplification-critical-path-boundary`。

## C04 — Joint-Intervention Deduplicated Exposure Ledger

- **问题**：fragmentation、straggler、HoL 可能落在同一关键路径；分别删除后相加会双计，简单时间切片又遗漏交互。
- **假设**：八个干预子集的 exact counterfactual 会显示单项收益之和系统性高估 union gain，并给出一个稳定的最小主导依赖集合，或把总空间压回 Gate 以下。
- **最小证伪 pilot**：对三类现象运行空集、三个单项、三个两两组合、全集共八种 replay，报告 union、overlap、interaction 和顺序敏感性；主导因素随合法归因顺序频繁翻转时不得选 controller。
- **最近邻**：通用 critical-path attribution、Shapley-style profiling；当前共同 Gate 1 accounting。
- **so what**：避免用重复计算的“总瓶颈”把不存在的机制空间做大。

## C05 — Route-Conditioned Censored-Tail Ledger

- **问题**：只统计完成请求会丢掉 timeout、cancel、window-end unfinished 或长期 admission delay；若删失与 route 相关，completion-only P99 会偏置 Gate。
- **假设**：接近饱和时删失不是随机的，会集中于特定 route / working-set / queue structure，并改变 all-arrival SLO-goodput 与现象 verdict。
- **最小证伪 pilot**：记录所有 arrival 到 terminal state，比较 completion-only、all-arrival deadline metric，并做延长 drain window 与低负载负控；删失率 <0.1% 且所有 cell verdict 一致时停止。
- **最近邻**：一般 serving benchmark、排队论、生存分析；AMoE、ExpertPlex、Gimbal 可能已有完整 request accounting。
- **so what**：防止 P99 因最差请求从分母消失而看起来变好。

## C06 — Expert-Pressure Negative-Result Boundary Map

- **问题**：单模型/单负载 NO-GO 难以区分“机制无效”与“落在无 actionability 区域”；synthetic skew 的正结果也不能外推自然流量。
- **假设**：arrival slack、service CV、active-expert working-set ratio、route overlap、parallel slack 等少量量可以在 holdout 上预测 Gate 区间。
- **最小证伪 pilot**：两模型 calibration/evaluation split，预测 exposed share 属于 <5%、5–10%、>10% 三段；若不优于只用 offered load 的简单基线，或跨模型失效，则停止。
- **最近邻**：METRO、UltraEP、Gimbal、Scaling Multi-Node Activation Patterns。
- **so what**：将窄负结果变成可迁移的适用域，而不是为失败机制调 workload。
- **特殊风险**：名称和“相图”表达容易与已停止 PhaseMap 混淆；必须证明研究对象是 verdict boundary，而不是 closed-pair actuator。

## C07 — Causal Work-Metric Validity Map

- **问题**：METRO 证明 memory-bound decode 下 activated-expert count 可能优于 token count，但这一 proxy 未必跨 batch、dtype、expert shape、cache residency、prefill/decode 和网络区间成立。
- **假设**：可迁移成本应分解为 weight working-set bytes、routed rows、launch/dispatch 固定税和 exposed communication bytes，并在 compute/HBM/launch/network-bound 区间分段。
- **最小证伪 pilot**：正交改变 activated experts、rows、dtype、cache warmness，在留一模型/留一区间上验证；若 token count 或 expert count 单独达到相同误差，复合指标无贡献。
- **最近邻**：METRO；HOBBIT、FloE 和一般 roofline/modeling 工作。
- **so what**：决定调度器应优化哪个 workload proxy，并明确 proxy 失效边界。

## C08 — Route-Induced Cross-Tenant Queue Coupling Audit

- **问题**：request/token/GPU-time quota 可能看不见 expert-set overlap；相同 token 数的租户仍可能通过热门 expert 队列产生非对称干扰或 timing channel。
- **假设**：匹配 token、长度、到达率与优先级后，victim P99 和 attacker observation 仍随 route overlap 变化。
- **最小证伪 pilot**：双租户 matched natural episodes，比较高/低 overlap 与标签置乱负控；full-path victim 差异 <5%、不跨模型或盲测 AUC 接近 0.5 时停止。
- **最近邻**：RepetitionCurse、FaaSMoE、通用多租户公平调度/side-channel；现有 RouteShield 开发态 scaffold。
- **so what**：若成立，说明 route-blind quota 不是充分隔离边界；碰撞和硬件风险都高。

## C09 — Route-Conditioned Silent-Degradation Identifiability

- **问题**：expert worker 慢化、降频、重试或局部通信退化可能没有显式错误，只影响路由到相关 expert 的请求；全局 GPU 指标难定位。
- **假设**：request latency residual 与完整 route identity 的覆盖矩阵能给出 degraded expert 的可辨识边界，并优于 GPU-wide baseline。
- **最小证伪 pilot**：注入冻结的单 expert 5/10/20% slowdown，比较 route-aware 稀疏定位与全局基线，做随机 slowdown 和 route-label permutation 负控；自然覆盖矩阵不可唯一定位或 slowdown 不进入 full path 时停止。
- **最近邻**：fault localization、straggler detection、observability、EEP。
- **so what**：可能形成可靠性/可观测性论文；也可能被审稿人视为普通异常检测。

## C10 — Scheduler-Induced Popularity Drift Identifiability

- **问题**：wall-clock expert popularity 会被 admission、batching、排队和 completion speed 改变；同一批请求、同一 exact routes 在不同调度下也可能出现不同热点与 change point。
- **假设**：一部分“workload drift”其实是 scheduler-induced active-set shift，会触发假阳性迁移并损害 P99。
- **最小证伪 pilot**：同一 identity-complete trace 回放多种不改语义的调度时序，对比 wall-clock、request-index、token-index popularity 与冻结 detector；假阳性迁移 full-path 影响 <5% 或三种索引基本一致时停止。
- **最近邻**：Scaling Multi-Node Activation Patterns、Gimbal、Mixture-of-Experts Serving。
- **so what**：挑战动态 placement 的输入是否外生这一共同假设；候选不提出新 placement。

## C11 — Placement Calibration Half-Life vs Reconfiguration Break-Even

- **问题**：已有工作知道 popularity 会变，也研究重配置成本，但自然流量中一次 calibration 的收益能维持多久、是否长于迁移回本期仍需直接测量。
- **假设**：只有可预测 half-life 显著长于 copy、barrier 和 queue spillover 的 break-even horizon，动态 placement 才有正净收益。
- **最小证伪 pilot**：按真实时序做 past-window calibration/future-window evaluation，比较 stay-put、周期重配、检测后重配和带实测迁移税的 offline oracle；稳定窗口短于 break-even 或 Oracle <10% 时停止。
- **最近邻**：Mixture-of-Experts Serving、Scaling Multi-Node Activation Patterns、Gimbal。
- **so what**：给出动态 placement 是否值得存在的时间尺度 Gate；方法新颖性碰撞风险高。

## C12 — Layer-Sparse Persistent Drift on the Critical Path

- **问题**：模型级 popularity shift 可能由少数层驱动；若漂移层不在暴露关键路径，全模型或逐层迁移都浪费成本。
- **假设**：自然 shift 具有 layer sparsity，且只有同时满足高 drift、长 persistence、高 exposed share 的少数层值得迁移。
- **最小证伪 pilot**：全层 route + service trace，比较 no migration、all-layer、oracle layer subset；漂移均匀、漂移层不在 critical path，或简单 top-critical-layer 捕获 ≥90% Oracle 时停止。
- **最近邻**：UltraEP、Scaling Multi-Node Activation Patterns、Gimbal。
- **so what**：可能得到很干净的 no-go boundary，但与逐层实时平衡工作碰撞较高。

## C13 — Prefill-to-Decode Forecast Horizon vs Migration Lag

- **问题**：prefill/decode activation correlation 不等于 proactive placement 可执行；早期 route 信号可能在观测、求解、copy 完成前已过期。
- **假设**：只有跨模型存在 forecast horizon 大于真实 reconfiguration lag 的自然 cell，预测式 placement 才有 action space。
- **最小证伪 pilot**：冻结 prefill-only、prefill+first-h-step、persistence predictors，按 document-disjoint split 测未来 demand；扣除完整迁移时延。优势不跨模型、horizon 短于迁移或 persistence 捕获 ≥90% Oracle 时停止。
- **最近邻**：Scaling Multi-Node Activation Patterns、Gimbal、UltraEP。
- **so what**：把“相关性”转化为可执行时间预算；碰撞风险高，且不得退化为已停止 Prefetch。

## C14 — Robust Static Placement as a Dynamic-Oracle Baseline

- **问题**：动态 placement 可能只击败按单一历史分布优化的脆弱 static baseline；自然 domain mixture 改变时，该比较不够强。
- **假设**：calibration split 上的 min-max robust static placement 能捕获带迁移税 dynamic offline Oracle 的 ≥90%，从而取消复杂在线重配置；若失败，才构成动态 action space 的可信证据。
- **最小证伪 pilot**：document-disjoint calibration/evaluation，比 current/default、single-domain static、pooled static、robust min-max static、dynamic exact oracle；冻结相同副本容量和显存。
- **最近邻**：Mixture-of-Experts Serving、Scaling Multi-Node Activation Patterns、Gimbal；robust optimization。
- **so what**：这是强 baseline 研究，正负结果都能直接改变是否值得做动态 controller。
