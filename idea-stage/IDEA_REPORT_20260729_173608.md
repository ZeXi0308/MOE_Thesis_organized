## 结论

本轮真正找到的最好新问题不是“再做一个专家调度器”，而是：

> **调度器会不会反过来污染它用来判断 expert popularity drift 的观测量？**

这对应 C10。现有工作已经大量覆盖负载均衡、异步执行、逐层复制、预测式 placement 与迁移成本，但通常把观测到的 expert demand 当作外生输入。自然 continuous serving 中，admission、batching、排队和请求完成速度会改变 wall-clock active set；因此同一批请求、同一 exact routes，可能仅因 schedule 不同就出现不同 hotspot/change point。若这些假漂移会触发错误迁移并造成 full-path SLO 损失，这既是新的测量问题，也可能改变一批现有动态 placement 的评价方式。

独立 jury 的科学潜力排序是 **C10 > C09 > C14**；考虑 2–4 周可证伪性后的执行顺序是 **C10 → C14 → C09**。评审为 `same-family / provisional`；辅助二审在收口时中断，不能写成 fully independent acceptance。

## Landscape Summary

MoE serving 的显式调度/均衡空间已经非常拥挤。[AMoE](https://arxiv.org/abs/2505.08944) 做异步 expert parallelism 与动态 re-batching，[UltraEP](https://arxiv.org/abs/2606.04101) 做逐 microbatch/逐层 exact-load balance，[METRO](https://arxiv.org/abs/2512.09277) 证明 memory-bound decode 应关注 activated experts 而非 token count，[Gimbal](https://arxiv.org/abs/2606.15177) 已联合 frontend/backend pressure、queue ordering 与 placement，[ExpertPlex](https://arxiv.org/abs/2607.18002) 又做到 tile-level adaptive scheduling。一般性的“expert-aware scheduler”已经不能构成新意。

动态 placement 也有更直接的近邻。[Activation Patterns](https://arxiv.org/abs/2604.23150) 用超过 100k 条真实 route trace 报告 domain-specific popularity 与 prefill/decode correlation；[Mixture-of-Experts Serving](https://arxiv.org/abs/2607.17880) 形式化随时间变化的需求、GPU assignment 与 reconfiguration cost；[Director](https://arxiv.org/abs/2607.08782) 已做预测驱动的在线 proactive placement；[CRAFT](https://arxiv.org/abs/2603.28768) 已做逐层、成本感知的 expert replication。因此 prefill 预测、逐层 drift、一般 half-life 不能单独立项。

另一方面，[DODOCO](https://arxiv.org/abs/2605.20982) 已直接审计“路由不均是否能由系统层纠正”和 mock-token benchmark 是否可信，显著压低一般 barrier/regime-map idea。可靠性方面，[EEP](https://arxiv.org/abs/2605.10670) 与 [Tarragon](https://arxiv.org/abs/2601.01310) 聚焦显式 worker/rank failure 和恢复，尚未直接覆盖 silent slowdown 的 route-based identifiability，这为 C09 留下窄缺口。

## Recommended Ideas（按科学潜力排序）

### Idea 1 — C10：Scheduler-Induced Popularity Endogeneity

- **Method（实际做什么）**：
  1. 在两个 MoE 模型上冻结自然、document-disjoint 的 arrival、request ID、完整 route、输出长度和 output hash。
  2. 对同一批请求重放 FCFS continuous batching、一个简单 pressure-aware schedule 和一个 schedule-invariant negative control；不改变 top-k、expert identity 或输出。
  3. 用同一冻结 detector 分别读取 wall-clock、request-index、token-index 三种 expert-popularity 序列。
  4. 把仅在 wall-clock 序列出现的 hotspot/change point 转成迁移动作，在 full request-DAG 中计入 copy、barrier、queue spillover 后测 P99 与 SLO-goodput。
- **Hypothesis**：一部分被解释为 workload drift 的 hotspot 实际由 scheduler 改变 active set 造成，并会触发净负的迁移。
- **Minimum experiment / Kill**：若两模型自然 workload 的 hotspot Jaccard 均 ≥0.90 且 false change point <5%，或错误迁移的 full-path 影响 <5%，立即停止；identity、ledger、denominator 不闭合则 `INVALID`。
- **Expected outcome**：正结果是跨模型的 false-migration 与 ≥5% full-path 损失；负结果同样有价值，说明现有 wall-clock popularity 足够稳健。
- **Novelty**：**8.5/10（provisional）**。最近邻是 Gimbal、Activation Patterns、MoE Serving、CRAFT；它们没有显式识别 scheduler-induced measurement endogeneity。
- **Feasibility**：**8/10**；CPU exact replay + 1×RTX 5090 可做资格性 pilot，2–4 周可得到 GO/NO-GO。正式 migration/TPOT/P99 仍需真实多 GPU optimized EP。
- **Risk**：MEDIUM。
- **Contribution type**：diagnostic + empirical finding；若能提出无偏/可辨识 estimator，才上升为 method。
- **Pilot result**：`SKIPPED — 当前执行环境未检测到 NVIDIA GPU；无 native continuous-decode formal producer`。
- **Reviewer objection**：可能只是“换索引后显然出现的统计伪影”。必须证明它会跨模型触发错误决策和真实 full-path 损失，不能只画三条 popularity 曲线。
- **Why do it**：这是本轮唯一没有被 2026 placement/scheduling 工作直接覆盖、且两周内可被杀死的核心问题。

### Idea 2 — C09：Silent Expert Slowdown Identifiability

- **Method（实际做什么）**：
  1. 冻结两模型的自然 request-to-expert incidence matrix。
  2. 在 exact replay 中向单个 expert 注入 5%/10%/20% slowdown，并用隔离 kernel 测量校准。
  3. 用 route-aware NNLS/sparse/change-point 方法从 request latency residual 定位故障 expert，与 GPU-wide telemetry baseline 比较。
  4. 用 label permutation、random slowdown、correlated slowdown 做负控，再到多 GPU EP 复核真实 worker/network slowdown。
- **Hypothesis**：route coverage matrix 的秩与条件数决定 silent degradation 能否定位，并存在清晰的不可辨识边界。
- **Minimum experiment / Kill**：20% slowdown 时跨模型 top-1 localization <0.8、AUC 优势 <0.1、matrix 不可辨识，或 full-path P99 变化 <5%，停止。
- **Expected outcome**：正结果需要 identifiability theorem/coverage boundary；仅“稀疏回归能定位”不够新。
- **Novelty**：**7.5/10（provisional）**。EEP、Tarragon 处理显式 failure，不是 silent slowdown 定位。
- **Feasibility**：**6.5/10**；CPU+5090 可做资格，正式可靠性主张必须有多 GPU EP fault injection。
- **Risk**：HIGH。
- **Contribution type**：reliability method/diagnostic。
- **Pilot result**：`SKIPPED — 无可用 GPU/正式 EP 环境`。
- **Reviewer objection**：在已知 incidence matrix 上做 sparse regression 本身不新，且真实 slowdown 会与网络、batch、route drift 混杂。
- **Why do it**：学术新颖性高于 C14，但与当前 thesis 主线距离更远，应作为可靠性 pivot，而非并入当前 Gate。

### Idea 3 — C14：Robust Static Placement as the Mandatory Dynamic Baseline

- **Method（实际做什么）**：
  1. 对两个模型和至少三类自然任务做 document-disjoint calibration/evaluation。
  2. 在相同 replica、HBM 与 capacity 下，构造 default static、per-domain static、pooled static 和 min-max robust static placement。
  3. 与扣除迁移税和 full-DAG spillover 的 dynamic offline Oracle 比较。
  4. 计算 worst-cell SLO-goodput、P99、dynamic Oracle capture ratio，并据此决定是否取消动态 controller。
- **Hypothesis**：强 robust static 会捕获带迁移税 dynamic Oracle 的 ≥90%，说明很多动态收益来自弱 baseline。
- **Minimum experiment / Kill**：robust static 相对 simple static 的 worst-cell 改进 <5%，且不改变 dynamic net Oracle 是否 >10% 的结论时，C14 不独立成立；只在单模型或 synthetic mixture 成立也停止。
- **Expected outcome**：捕获 ≥90% Oracle 是有价值的 NO-GO；若 dynamic 相对 robust static 的 95% LCB 仍 ≥10%，C14 降为强制 baseline 而非论文主方法。
- **Novelty**：**5.5/10（结果型）**。MoE Serving、CRAFT、Activation Patterns、Gimbal 已覆盖相邻算法，min-max optimization 本身不新。
- **Feasibility**：**8/10**；2–4 周最稳，但正式结论仍受 full-DAG 与多 GPU 阻塞。
- **Risk**：MEDIUM。
- **Contribution type**：strong baseline + negative empirical result。
- **Pilot result**：`SKIPPED — 无 native GPU producer`。
- **Reviewer objection**：这只是审稿规范中的强 baseline，不是新方法。
- **Why do it**：它是最快阻止“动态方法只赢弱 baseline”的办法，适合紧跟 C10 执行。
