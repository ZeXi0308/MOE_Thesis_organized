## Negative-result insight

CriticalSplit 封存负结果只削弱了：

> 在冻结 full-DAG、服务曲线和 atomic batch completion 下，向 `WHOLE + HOLD` 增加 join-closing `CRITICAL/BULK` proper-subset launch 并未产生新 headroom。

它没有否定 row/token milestone、partial consumption、running-state transition、多资源 overlap 或 execution tactic state。不再修复、变更或调参 Critical/Bulk。

### 为什么 split Oracle 完全不用 split

1. `RunningBatch` 只有一个 `finish_us`，batch 内所有 rows 同时完成，Oracle 看不到 prefix completion。
2. successor 只在 top-k 全部完成并付出 `combine_us` 后 reveal；提前完成非 join-closing row 没有下游价值。
3. `S(1/2/4)=10/14/20 us`：把 M=2 拆为两个 singleton 使总 service 从 14 变为 20 us，只转移尾延迟，不创造并行容量。
4. whole-ready exact Oracle 已枚举所有 idle executors 上的 eligible queues 与 bounded HOLD；普通 EDF、queue score 或 cross-request priority 不是缺失 action。

## Top 3 最小 Oracle 设计

### C01 JoinStream（已运行）

- 8 cells：`M={2,4} × curve={uniform,tail} × emission_tax={0,2 us}`。
- Baseline：`ATOMIC_WHOLE + HOLD`；Expanded：完整包含 baseline，加 `STREAM_WHOLE`。
- 同 membership、一次 launch，executor busy 到 final；唯一 canonical request-id order 与 curve 均在运行前冻结。
- 2 logical executors、top-k=2、2 layers、1 decode、M 个 aligned requests、loose deadlines。
- 正结果：expanded flow 严格更小且 replay 实际用 stream；负结果只削弱两条冻结 curves。

### C07 QuantumYield（查新后停止）

- 8 cells：incumbent `M={2,4} × urgent_offset={3,7} us × resume_penalty={0,2} us`。
- Baseline 可预知 urgent arrival 并提前 HOLD；Expanded 加固定 quantum 的一次 `PREEMPT/RESUME`，完整收费已执行与 remaining work。
- 只有严格击败 future-known baseline 才是 running-state signal。
- 未运行：ExpertPlex 的 tile-boundary preemption 与 QLLM 的 MoE expert-level preemption 已直接削弱方法 novelty。

### C12 ShapeLease（查新后停止）

- 16 cells：mixture × reuse order × initial residency × reconfiguration cost。
- Baseline 必须取 native/padded/persistent 三个 fixed-tactic exact Oracles 的最佳者；Expanded 切换 tactic 且付全部 cost。
- 必须击败最佳 fixed 且实际用至少两种 tactics。
- 未运行：EPS-MoE、RaMP、DA-MoE 已覆盖 runtime tactic selection；没有真实 GPU table 时 synthetic crossing 容易机械制造收益。

## New hypothesis

> 保持 whole expert batch 的 membership 和 launch 不变，仅把真实 row completion 暴露为 top-k token-join event，可以创造 atomic whole-batch finish 隐藏的 request-flow headroom。

## New action space

Baseline 只能在整个 ready expert queue 的全部 rows 一起 finish 时观察 completion。JoinStream 允许：

> 对同一 whole queue 只 launch 一次，但在冻结 physical order 的 row 数值完整后立即发布 milestone，使 top-k join 可在 batch final 之前关闭；executor 仍 busy 到最后 row。

这改变 completion visibility，不是 input split、re-batching 或 Critical/Bulk 变体。

## Why it may work

1. 不增加 launch，`tax=0` 时总 service 不变。
2. 两个 logical expert executors 的 canonical row order 对齐，同 token 的 top-k rows 可一起提前到齐。
3. join 关闭后可立即做 combine 和 downstream release，不必等 batch 尾 rows。
4. expanded Oracle 严格包含 atomic baseline，不会因强制 stream 而制造收益。
5. `tax=2 us` 显式向发布/通知收费，可区分零成本 existence 与成本容忍 signal。

## Minimal oracle experiment

### 完整性

- 新 JoinStream tests：10/10 PASS。
- FrontierCredit + CriticalSplit + JoinStream 兼容 Python 下完整回归：38/38 PASS。
- Baseline actions 是 expanded actions 子集；M=1 不制造伪 stream；replay objective 一致；每 node exactly once；executor 不在 final milestone 前释放。
- max state cap 保持 500,000，实际最大仅 3,872。

机械判定：

- 8/8 cells 严格 flow improvement 且最优 replay 实际使用 stream：`SUPPORT_ACTION_SPACE`。
- 4/4 `h=2 us` cells 仍严格改善：`COST_TOLERANT_SIGNAL`。
- launch 数均为 baseline 4 / expanded 4；`h=0` 总 service 相同，`h=2` 的 expanded 总 service 多 4 us（两个 stream launches 各 2 us）。
- deadline miss delta 全部为 0。

### 机制定位

8/8 最优轨迹都在 layer 0 使用 atomic，只在最后建模层 layer 1 的两个 queues 使用 stream。所以当前正信号精确定位为：

> **最后建模层的 token/request 可在 whole batch 尾部之前完成。**

它尚未证明：

- next-layer compute 真正与上一层 tail rows overlap；
- 真实 GPU kernel 能以该 curve/order 发布 row；
- 自然 MoE route 中存在相同 headroom；
- 优于 FlashMoE/Event Tensor 的 generic tile/task scheduling；
- EP/NCCL/RDMA、serving 或论文收益。

## Outcome interpretation

### 如果成功（本轮）

说明 atomic batch completion 的确隐藏了一个 exact request-flow action freedom；CriticalSplit 失败的一个关键原因是它改了 input membership，却没改 completion visibility。但本轮只是 synthetic CPU action-space signal，且收益局限在最后建模层。

### 如果失败

原定义只会削弱 uniform/tail curves、canonical order 和 `h={0,2}` 的同 device completion contract，不否定 transport streaming、consumer streaming 或其他 physical milestone。本轮未触发该负判定。

## 查新边界

- C01 的核心构件已有强近邻：[FlashMoE](https://arxiv.org/abs/2506.04667) 的 persistent tile tasks、[Event Tensor](https://openreview.net/forum?id=PJqFhAbUHa) 的 first-class completion dependencies、[AMoE/AEP](https://arxiv.org/abs/2505.08944) 的 token-level top-k dependency。
- 暂未发现直接覆盖完整组合：固定 whole membership / one launch / total service，row completion 成为跨 expert token-join event，再释放 downstream。这只是 provisional 窄缺口，不是绝对 novelty。
- C07 被 [QLLM](https://arxiv.org/abs/2503.09304) 和 [ExpertPlex](https://arxiv.org/abs/2607.18002) 直接削弱。
- C12 被 [EPS-MoE](https://arxiv.org/abs/2410.12247)、[RaMP](https://arxiv.org/abs/2604.26039)、[DA-MoE](https://arxiv.org/abs/2607.23099) 和 Moebius 的相邻动态/有状态选择覆盖。

## P0/P1 状态

1. **P0 physical legality：已在 CPU abstraction 级解除，GPU 性能未验证。** Producer 只在完整 row output 写 global memory 后做 device-scope release store；join consumer 用 acquire load 后读数据。[CUDA C++ memory model](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cuda-cpp-memory-model.html) 支持该 message-passing 合同，Event Tensor 支持 persistent task completion 事件。
2. **P1 curve/order freeze：已解除。** curve、tax 和唯一 canonical order 均在输出前冻结，Oracle 不能塑造 milestone。
3. **P1 strongest-prior-art comparator：不阻塞当前 action-space Pilot，但阻塞 method claim。** 若 JoinStream 只是 Event Tensor/FlashMoE 的 ready-task priority，则只保留 join-aware characterization，不作新方法。

## Next action

不扩大 CPU cells。下一个最小实验是**单 GPU completion-legality + measured-curve probe**：

1. 只实现 M={2,4} 的 persistent producer，每 row 完成后 release-store flag，consumer acquire-load 并记录时间戳。
2. 同时测量 per-row notification tax、最终 finish 和总 service，不使用 CPU synthetic curve 代替 GPU 数据。
3. 将实测 curve/tax 回灌同一 exact Oracle；若 signal 消失，接受 GPU-level 负结果。
4. 若仍为正，再增加 generic Event Tensor/FlashMoE-style task-ready comparator，判断剩余 delta 是新 runtime contract 还是 join-aware priority finding。

在这个 probe 前不实现 vLLM controller、不跑多模型、不做 EP/NCCL/RDMA 或大规模 benchmark。
